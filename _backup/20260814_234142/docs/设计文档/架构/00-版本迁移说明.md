# v2.0 → v3.0 版本迁移说明

## 1. 迁移原则

v3.0 对原有内容做全局重构，不要求项目一次性重命名所有代码目录。现有实现可以渐进迁移，但新增功能必须遵守 v3.0；旧规则只能作为历史参考，不再作为新的冲突裁决来源。

## 2. 原文件映射

| 原文件/主题 | v3.0 归属 |
|---|---|
| 规范体系索引与总则 | `00-规范体系总纲.md`、关系矩阵、术语、生命周期、Gate、例外、规则索引 |
| 01-基础层规范 | `01-基础层规范.md`，规则重编号为 `BASE-*` / `TEST-*` |
| 02-核心架构 | `02-架构层-核心架构规范.md`，规则重编号为 `ARC-*` |
| 03-数据与扩展 | `03-架构层-数据与扩展规范.md`，规则重编号为 `DATA-*` / `SAVE-*` |
| 04-兼容与接入 | `04-架构层-兼容与接入规范.md`，规则重编号为 `COMP-*` |
| 05-表现层 | `05-表现层规范.md`，拆分为 `UI-*` / `LOC-*` / `ASSET-*` / `PERF-*` |
| CHANGELOG_SPEC | `06-变更日志与发布规范.md`，并纳入生命周期和 Release Gate |
| AI 开发/标准化开发规范 | `07-AI开发规范.md`，改为可执行 AI 协议 |
| 高拓展高接入架构方案 | `附录-项目架构实施映射.md`，保留 Provider、Read Model、Compatibility 和 PersonalChronicle 具体落地映射 |

## 3. 规则 ID 迁移

v2.0 旧 ID 可能出现 `BAS-*`、`ARC-CORE-*`、`ARC-DATA-*`、`ARC-COMP-*`、`PRE-*` 等格式。v3.0 不再混用这些前缀；代码注释和旧文档可暂时保留旧 ID，但新文档、Review、Change Summary 和 Exception 必须使用 [00-规则编号索引.md](00-规则编号索引.md) 的新 ID。

## 4. 渐进采用顺序

```text
1. 把总纲、关系矩阵和术语加入项目 docs
2. 对 Core/UI/Compatibility 画依赖图并消除循环
3. 给 Def、Key、Asset、Save schema 建清单
4. 将第三方接入移到 Compatibility/Adapter
5. 将 UI 改为 Read Model 消费者
6. 补 Migration、Localization、Performance、Testing Gate
7. 用 Change Summary + Changelog 记录每次迁移
```

## 5. 迁移完成条件

```text
[ ] 新需求不再引用 v2 旧 ID 作为唯一规则来源
[ ] Core/UI/Compatibility 依赖符合矩阵
[ ] 已发布 DefName/API/Save 字段有身份清单
[ ] 旧 Save 和旧接入具备迁移/别名策略
[ ] 现有兼容方案有独立 Adapter/Exception 记录
[ ] Release Gate 可重复执行
```
