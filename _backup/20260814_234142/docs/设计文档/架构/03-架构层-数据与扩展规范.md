# 03 架构层：数据与扩展规范

**版本：** v3.0  
**定位：** 统一 Def、Runtime State、Save Data、UI Read Model、扩展点和 Migration  ̵  
**关联：** [00-统一术语与定义.md](00-统一术语与定义.md)、[00-统一验收标准.md](00-统一验收标准.md)

## 1. DATA-001 四类数据边界

```text
Def                 静态配置与内容定义
Runtime State       当前游戏会话中的可变状态
Save Data           跨会话恢复所需的稳定状态
UI State/Read Model 界面临时状态和只读投影
```

强制边界：

```text
Def          ✕→ Pawn 实时状态 / UI 滚动位置 / Texture 实例
UI State     ✕→ Save schema / 领域权威状态
Save Data    ✕→ Window / GUIStyle / Translation 结果
Runtime      → Read Model → Presentation
```

## 2. DATA-002 Def 建模与 DefOf

Def 适合表达：数值、标签配置、分类、规则参数、资源路径、静态能力声明。需要频繁引用的固定 Def 使用 DefOf 或等价类型安全引用；动态、可选或外部配置查询才使用受控的 `GetNamed`/查找。

```xml
<ThingDef>
  <defName>MyMod_AdvancedRifle</defName>
  <label>advanced rifle</label>
  <modExtensions>
    <li Class="MyMod.ArchiveExtension">
      <category>Weapon</category>
      <tier>3</tier>
    </li>
  </modExtensions>
</ThingDef>
```

DefName 是机器身份，label/description 由 [LOC-002](05-表现层规范.md#loc-002-definjected-与-keyed-分工) 管理。

## 3. DATA-003 DefModExtension 选择

当需求是“给现有 Def 附加一组属于本 Mod 的静态数据”，优先使用 `DefModExtension`。扩展类应只保存配置，不在其中持有 Pawn、World、UI 或可变全局状态。

## 4. DATA-004 Comp/ThingComp 选择

当需求是“给具体实例增加运行时行为或状态”，使用 `Comp`/`ThingComp` 及其 `CompProperties`。Comp 必须说明：宿主对象、生命周期、Tick 频率、Save 字段、缺失宿主时行为。禁止为了少量字段直接修改大型 Vanilla 基类。

## 5. DATA-005 Patch 最小化与 XPath 精确性

修改已有 Def 时：

```text
目标 Mod/Def 检测
→ 精确 XPath（类型 + defName + 必要条件）
→ 只改必要字段
→ 条件执行与日志
```

禁止完整复制第三方 Def 只修改一个字段。任何第三方 Patch 进入 Compatibility 层并遵守 [COMP-003](04-架构层-兼容与接入规范.md#3-comp-003-条件-patch-与最小范围)。

## 6. DATA-006 稳定引用与动态查找边界

优先使用：

```text
DefOf / 类型安全引用 / Contract / 稳定对象 ID
```

限制使用：

```text
全库扫描、反射、显示文本匹配、每 Tick GetNamed、未经缓存的字符串查找
```

查询失败必须有明确结果（`null`、Unavailable 或错误状态）和诊断，不得静默创建伪数据。

## 7. DATA-007 配置、缓存与权威数据源

每个缓存必须声明：来源、Key、有效期/失效条件、重建方式、容量和 Save 关系。缓存必须可从权威 Runtime/Save 数据重建；不能把缓存作为唯一真相。

```text
权威数据 → DataRevision 变化 → 失效缓存 → 按需重建 Read Model
```

## 8. DATA-008 事件输入与数据校验

跨模块写入通过事件 Contract 或 Service，输入必须校验：稳定 ID、事件类型、Tick、对象生命周期、参数范围、去重键和最大集合容量。写入失败必须返回结构化结果，不得依赖 UI 是否打开。

## 9. DATA-009 数据生命周期与重建

明确以下状态：

```text
未初始化 / 可用 / 部分可用 / 已归档 / 迁移中 / 失败降级
```

运行时聚合、统计和 UI Read Model 应优先在需要时重建，不把临时结果写入 Save。加载完成后重新建立 Provider、缓存和索引。

## 10. DATA-010 数据契约版本

公共 DTO、事件、Provider 能力和 UI Read Model 必须有版本语义，例如 `archive.events.v1`。新增字段优先向后兼容；改变含义、删除字段或改变身份时必须进入 Release/Save Review。

## 11. DATA-011 数据与本地化隔离

Save、Runtime 和 Def 只保存稳定 ID、数值、枚举和可迁移数据，不保存翻译后的显示文本。UI 读取 Translation Key 和参数，语言切换时重新解析，不改变权威数据。

## 12. SAVE-001 存档身份与版本

Save 数据必须有稳定宿主 ID、schema 版本和字段语义。DefName、事件类型、对象 ID 和枚举值一旦写入存档，就视为兼容契约的一部分。

## 13. SAVE-002 可持久化字段边界

可持久化：稳定 ID、基础值、有限集合、必要的时间/版本信息。不可持久化：Window、Rect、GUIStyle、Texture、Provider 实例、缓存、翻译结果、第三方对象直接引用。

## 14. SAVE-003 默认值与向后兼容

新增字段必须有合理默认值；未知枚举、缺失 Def、缺失目标 Mod 和损坏单条记录必须降级为可诊断的空/Unavailable，而不是阻止整个存档加载。

## 15. SAVE-004 迁移流程

```text
读取旧 schema
→ 识别版本
→ 顺序执行幂等 Migration
→ 校验目标 schema
→ 记录摘要与失败项
→ 写入当前格式
```

Migration 不得依赖 UI、当前语言或第三方 Mod 是否安装。迁移失败必须保留可诊断信息，并尽可能隔离到单条记录。

## 16. SAVE-005 重命名、删除与别名

DefName、事件 ID、Key 或枚举值重命名时，保留旧值别名/映射，并在至少一个兼容周期内支持读取。删除前必须有 Deprecated 说明、Migration 和 Changelog `Breaking`/`Removed`。

## 17. SAVE-006 Migration 幂等和失败隔离

同一 Save 重复读取不应重复追加记录或改变结果。Migration 必须能单独测试；单条异常不能阻止其他记录恢复。日志包含旧版本、新版本、对象 ID 和失败原因。

## 18. SAVE-007 Save 测试矩阵

```text
当前版本新建 Save
上一发布版本 Save
更早版本 Save（如有承诺）
缺失字段 / 未知字段 / 未知枚举
目标 Mod 存在 / 缺失
语言切换后读取
重复读取同一 Save
```

## 19. DATA-012 / SAVE-008 数据与 Save 验收

```text
[ ] DATA-001–DATA-011 适用项通过
[ ] Def/Runtime/Save/UI 边界清晰
[ ] Patch 最小且可定位
[ ] 缓存可重建
[ ] Save schema、默认值、Migration、别名明确
[ ] 不保存显示文本/UI/资源实例
[ ] 通过 GATE-DATA 与 GATE-SAVE
```
