# 07 AI 开发规范

**版本：** v3.0  
**定位：** 将本体系转化为 AI 可执行、可审查、可回滚的开发协议  
**最高约束：** AI 不得绕过总纲、依赖矩阵、例外登记和统一 Gate

## 1. AI-001 任务入口协议

AI 收到需求后，必须先输出或记录：

```text
需求目标与非目标
涉及文件/模块
任务层级
适用规则 ID
新增/修改的 Def、Runtime、Save、UI、Key、Asset
第三方 Mod/DLC/语言影响
是否触发 Architecture Review
计划使用的扩展点
验证和 Gate 计划
```

信息不足时，AI 必须采用最小安全假设，并标记假设；不得凭方便扩大范围。

## 2. AI-002 先架构后编码

AI 在写代码或大幅修改 XML 前，必须完成：

1. 读取总纲、关系矩阵、术语和对应专项规范。
2. 标出依赖方向和数据边界。
3. 说明为何选择 Def、DefModExtension、Comp、Service、Provider、Patch 或 Harmony。
4. 判断是否需要 Exception Record。

出现 `Harmony = Yes`、`Hardcoding = Yes`、`Cross-Mod Direct Reference = Yes`、`Static Mutable State = Yes` 任一项，必须进入 Architecture Review。

## 3. AI-003 扩展点选择协议

默认优先级：

```text
原生 Def / XML
→ DefModExtension
→ Comp / GameComponent
→ Service / Contract / Provider
→ PatchOperations
→ Harmony Postfix
→ Harmony Prefix
→ Harmony Transpiler
```

这不是“越后越强”，而是风险升级顺序。AI 必须记录被跳过方案及原因；不得因实现简单直接选 Harmony。

## 4. AI-004 依赖与硬编码禁止清单

AI 默认不得生成：

```text
Core 中的第三方 Mod 条件分支
显示文本/label 逻辑判断
完整覆写第三方 Def
裸 Translation Key / DefName / Asset Path
无界静态可变单例
Tick 中的全库扫描、反射和无界分配
空 catch、静默失败、无界重试
未登记的 Harmony
将 UI/翻译/Texture 写入 Save
```

如确实必要，必须使用 [00-规范例外与变更管理.md](00-规范例外与变更管理.md) 登记。

## 5. AI-005 实现协议

实现顺序：

```text
确认 Contract / 数据 schema
→ 写 Domain/Core
→ 写 Data / Def / Comp
→ 写 Read Model / Provider
→ 写 UI / Theme / Asset / Localization
→ 写 Compatibility Adapter / Patch
→ 补测试和诊断
```

AI 不得在同一类中混合“采集、聚合、存档、UI 绘制、兼容 Patch”。

## 6. AI-006 Localization 协议

新增任何用户可见文本时，AI 必须同时处理：

```text
Key 命名空间
默认语言
目标语言/fallback
参数一致性
长文本布局
Translation 扫描
```

AI 不得把中文默认值、英文覆盖值或某一语言的缺失状态当作业务条件。翻译结果永远不是稳定 ID。

## 7. AI-007 Save/Migration 协议

凡是改变持久化字段、DefName、事件 ID、枚举值、Provider schema 或缓存重建逻辑，AI 必须先写出：

```text
旧 schema → 当前 schema
缺失字段默认值
未知值降级
重命名映射
Migration 幂等性
失败隔离
旧 Save 测试
```

无法证明旧 Save 行为时，AI 必须暂停实现并报告风险，不得假定“字段会自动兼容”。

## 8. AI-008 Compatibility 协议

第三方 Mod 接入必须生成独立 Compatibility 文件/模块：

```text
检测 → 能力判断 → Adapter → 项目 Contract → 可选 UI/数据消费
```

目标 Mod 缺失时基础功能必须继续工作；目标 Mod 失败时必须降级并记录一次结构化诊断。AI 不得引用第三方内部类型扩散到 Core/API/Save。

## 9. AI-009 Testing 与 Gate 协议

AI 完成实现后必须执行适用 Gate，至少包括：

```text
Architecture / Data / Localization / Compatibility
Save / UI / Performance / Testing / Release
```

每项给出 PASS、BLOCKED 或 NOT APPLICABLE，并附 Evidence。没有可执行环境时，AI 必须诚实标记“未执行”，不得伪造通过。

## 10. AI-010 Change Summary 协议

每次交付必须生成 Change Summary，包含：变更范围、规则 ID、行为影响、兼容、本地化、Save/Migration、性能、测试、例外和剩余风险，并按 [REL-002](06-变更日志与发布规范.md#rel-002-change-summary) 更新 Changelog。

## 11. AI-011 审查优先级

违规等级：

| 等级 | 示例 | AI 行为 |
|---|---|---|
| P0 | 循环依赖、破坏存档、污染全局/第三方、绕过安全边界 | 禁止生成/必须立即修复 |
| P1 | 未登记 Harmony、完整覆盖 Def、第三方硬引用、UI 改领域状态 | 阻止交付，要求重构或 Exception |
| P2 | Service 依赖 UI、缓存无失效、性能证据缺失 | 必须修复或明确风险 |
| P3 | 命名、注释、文档互链不完整 | 交付前修正 |
| P4 | 纯风格问题 | 可后续优化 |

AI 不能用“代码能编译”覆盖 P0/P1 架构问题。

## 13. AI-013 变更标注协议

AI 在 Gate 定稿前必须生成**变更标注**（开发者向精确改动清单），解决“验收时无法精准定位已修改内容”。

> 规范性定义、Change ID 贯穿链路、改动类型与符号要求、范围约束、删除/重命名处置、GATE-DELTA 衔接，**全部以 [GOV-013](00-规范体系总纲.md#4-全局不可违反规则) 为唯一权威源**；本条目仅声明 AI 侧的强制动作。

**AI 侧强制动作：**
1. 交付前必生成变更标注（YAML front matter + 表格），覆盖全部 git 改动。
2. 用 `scripts/gate-runner.ps1 -Annotation <标注.md>` 自动校验：标注⊆diff、无超范围、无调试残留。
3. 缺失或不一致时 `GATE-DELTA = BLOCKED`，阻止 Release，不得绕过。

## 14. AI-014 交付粒度协议（禁止碎片化交付）

**目标**：防止 AI 将本属「一个可交付单元」的产品（如一个完整页面、一个端到端功能、一组强耦合模块）人为切分为无数小模块、逐一多轮交付，迫使使用者反复往返才能获得可用整体。

**定义——可交付单元**：在 AI-001 任务入口规划时，凡满足以下条件的集合视为一个可交付单元：
- 共享同一业务目标与同一组调用方；
- 内部模块间存在强依赖（后片依赖前片产物，且无独立验证价值）；
- 合并后单轮输出规模在模型可靠范围内（见下「允许拆分」第 3 条）。

**强制动作**：
1. **先整体规划，再整体产出**：AI 在 AI-001 必须一次性列出该单元的全部目标文件/模块与改动，并在同一轮回复中产出完整实现；不得自创「先给 A、下一轮给 B」的节奏。
2. **变更标注一次性覆盖单元全量**（承接 AI-013）：单元内所有文件写入同一份变更标注，禁止把单元切成多份标注、多轮 Gate。

**允许的拆分（不视为违规）**：
1. 跨 Gate 层级隔离所需（先架构后编码：先定 Contract/Def，但实现仍应在确认后一轮内完成）；
2. 存在**方向性阻塞**：架构选型 / 第三方 API 事实 / 预览目标形态未定，需用户拍板后才能继续；
3. 单元规模超过单轮可靠输出上限（经验阈值：单文件 > ~600 行或单元总量 > ~1500 行）——此时可物理分批，但**不得每片都等用户确认才继续**，应连续产出直到单元完成；
4. 用户在提示中**显式要求**分阶段 / 分批交付（用户意图优先于本规则）。

**禁止的「假拆分」**：
- 把可一次完成的单元按“我会分几步”表述为 N 轮，且每轮强制要求用户确认后才继续；
- 把同一页面的视觉 / 逻辑 / 数据层分别作为“独立交付”反复交回，无视它们构成一个整体；
- 以“先搭骨架”为名只给空壳 / 占位，把真实实现推到后续多轮。

**判定标准**：若拆分后任一片都**无法独立运行或被独立验证**，且整体合并后单轮可完成，则该拆分属过度拆分，AI 必须合并为单轮交付。

**Gate 关联**：用户主张“被碎片化交付”且违反本规则时，GATE-DELTA 视为交付粒度不达标，`BLOCKED` 直至单元合并交付。
