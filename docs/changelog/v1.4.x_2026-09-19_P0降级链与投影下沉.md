## [开发线] 2026-09-19

### 一、P0-A：三个 `AppendKpis` 无保护 ⇒ 一张卡出错整页空白

**证据链**：`SystemCenterReadModelProvider.cs:230-233` 在**整体 try** 内调用
`provider.AppendKpis(snapshot.Kpis, map)`，唯一的 catch 在 `:404-408` 且置 `snapshot.IsEmpty = true`
⇒ 任一 Provider 的 `AppendKpis` 抛异常，**整个中心详情页变空白**。

而本工程的硬要求写在自己的代码里（`BuiltinEconomyProvider.MarketPanel.cs` 的自述）：
「**硬要求：吞掉自己的异常，返回安全空快照（一块坏不得拖垮整页）**」。
`BuiltinManufacturingProvider` / `BuiltinLogisticsProvider` / `BuiltinMedicalProvider` 三家**从未实现**它。

**修法**（三家同形）：

```csharp
int start = buffer.Count;          // ⚠ 只清自己追加的那一段（buffer 是全中心共用收集器）
try { AppendKpisCore(buffer, map); }
catch (System.Exception ex)
{
    ChronicleLog.Error(ChronicleLog.Category.Ui, "... kpis failed: " + ex);
    if (buffer.Count > start) buffer.RemoveRange(start, buffer.Count - start);
    AppendPendingKpis(buffer);     // 全部转「未接入」——如实告知，不画半截、不画 0
}
```

**顺带修掉两处「0 冒充空态」**（审计 §3 登记）：
- `BuiltinLogisticsProvider`：`wealthWatcher == null` 时此前画 **0 银** ⇒ 改发 `Pending`
  （仓储建筑数**保持画 0** —— 那是真计数，数出来 0 就是真的一栋都没有）
- `BuiltinMedicalProvider`：`resourceCounter == null` 时此前画 **0** ⇒ 两张药品卡改发 `Pending`
  （卧床人数是**独立真实读数**，照常出）

### 二、P0-B：`WorkshopFloorViewProvider` catch 只写 Hint ⇒ 半截快照进屏

**问题**：catch 只 `snapshot.Hint = ...`，但失败前已 `Add` 的 `Bays / Devices` **原样留在快照里**
⇒ 会画出「有设备、但没有轨道/链路」的残缺视图。

**修法**：清干净（Bays/Devices/Workers/RawItems/Routes/Depot + 计数 + Caption）+ `IsEmpty = true`
+ 新增诚实的 `PersonalChronicle.UI.Floor.ReadFailed` 提示。

⚠ **有意不置 `NoMap`**：UI 的门控是 `!workshop.NoMap`（`MasterControlTabWindow.Detail.cs:149 / :303 / :381`），
置 true 会让整块车间视图**无声消失**，玩家只看到制造中心少了一块、不知道为什么。
清空 + Hint 则画出框架与失败提示，符合 **LAND-009**「框架与数据无关，没数据也照画框架 + 一行提示」。

### 三、P0-C：归档 Provider 四个构建方法无 try/catch ⇒ 异常直抛进原版绘制循环

`ArchiveUiDataProvider` 的**类注释早就承诺**：
「Failure isolation: a null service or a throwing query yields an empty snapshot rather than
propagating into the UI draw loop.」—— **四个方法一个都没实现**。

后果比"整页空白"更重：调用链 `ArchiveMainTabWindow.DoWindowContents → RefreshCacheIfNeeded
→ RefreshNow` **全程没有 catch** ⇒ 异常直接抛进原版绘制循环。

**修法**：四个方法各补 try/catch，降级返回**干净的新空快照**（新建对象而非清字段 ——
清字段要穷举，漏一个就把半截数据交给 UI）：
- `BuildHome` / `BuildOverview`（`ArchiveUiDataProvider.cs`）
- `BuildEvent`（保留 `Event` 入参，只丢派生出的后续事件）/ `BuildTimelineEvents`（返回**空数组**而非 null —— 调用方按 `IReadOnlyList` 迭代）

### 四、P1：链路投影下沉（`EconomyInventoryChainPanel` 的派生逻辑 → Provider）

**问题**：绘制路径里做了三件**数据**事 —— 参与边的节点集、上下游分类、下游排序 + 截 TOP3 ——
且每帧 `new List` ×2 + 一个排序委托分配。这是 `Economy/UI` 目录的**唯一黑点**
（其余 5 个文件 `Translate(` = 0、`new Color(` = 0、中英文字面量 = 0）。

**修法**：产物进快照（3 个新字段），Provider 在**同一次构建**里算好：

| 新字段 | 含义 |
|---|---|
| `ChainNodeIndices` | 参与至少一条边的节点下标（顺序 = 节点声明顺序） |
| `UpstreamEdgeIndices` | 指向选中节点的边（**在 `Edges` 里的下标**，顺序 = Edges 顺序） |
| `DownstreamEdgeIndices` | 自选中节点出发的边，**已按权重降序 + 已截 TOP3**（同权重用 `ToIndex` 兜底保证确定性） |

三条设计要点：
1. **产出「`Edges` 里的下标」而不是边对象** —— 下标与 `Edges` 同批生成 ⇒ 结构上不存在
   "UI 自己筛一遍、下标对不上"的可能（这一条直接呼应本轮修掉的 `Weight01` 错位事故）。
2. **必须放在 `SelectedNodeIndex` 定案之后** —— 三组投影都依赖 Provider 解析出的**有效值**
   （`effective` 会回落首个参与边的节点），UI 不需要也不得自行推算。
3. **UI 侧仍留一次边界守卫** —— 绘制路径上的越界异常会让 GUIClip 出入栈失衡 ⇒ 整局 GUI 卡死
   （铁律 3）；一次 int 比较换这个保险不亏。

**净值**：`EconomyInventoryChainPanel` 每帧 **0 分配**，删掉 3 个方法 + 1 个重复常量（共 −70 行）。
⇒ 该目录**可以宣布 100% 合规**。

## 残余风险 / 已知降级

1. **⚠ 四组修复全部无法离线单测**：它们都是"异常路径"与"Provider 投影"，依赖游戏运行时
   （`Map` / `ArchiveService` / `MarketContracts`）。单测 400 通过**只证明没破坏既有契约**，
   **不证明异常路径正确**。⇒ 实机验证方式见下。
2. **`AppendPendingKpis` 的降级文案是"未接入"**：它复用既有的 `SystemCenterKpiFactory.Pending`
   ⇒ 屏幕上的表现与"该中心本来就没接这块数据"相同，玩家无法区分"没接"与"读取失败"。
   **已知取舍**：日志里有 `ChronicleLog.Error`，且两者的**玩家侧行动**相同（都是"暂时看不到"），
   故不新增一套"失败"文案（那会让 KPI 卡出现第三种状态，收益不抵复杂度）。
3. **`BuildChainProjection` 每次构建都会分配**（`bool[]` + 一个临时 `List<int>`）：
   构建期、且面板刷新受节流门控（`BuiltinEconomyProvider` 的既有节流）⇒ 可接受，
   不在绘制热路径上。**不引入静态 scratch 缓冲**（那会在 Def 访问层引入可变静态状态，项目明确反对）。
4. **本批未实机验证**（与 004~007 同批待验），见下。
