## [开发线] 2026-09-19

### 一、必须讲清楚的一件事：物品级的"生产/消费/净值"不存在

这不是本次偷懒，而是 **MVS 的建模决策**：`MVSCommodityDef` 的供需基线、`MarketFactor`、
`shockOffsets` **全部以「品种」为单元**。系统里根本没有按 `ThingDef` 粒度的供需读数。

把品种的 `supplyBaseline = 150` 摊给它的 38 个成员物品，摊法（均分？按 MarketValue 加权？）
**没有任何依据可循** —— 那是编造数据，直撞工程红线（「⛔ 禁止假演示」「缺失显示 `—` + 原因」）。

⇒ **处方**：
- 三列如实画 `—`（不是留空）。**留空会被读成"渲染坏了/数据没加载"，`—` 才读作"此列对当前行不适用"**
  —— 用户上一轮看到的正是留空，所以判定「没有细分数据」。
- 把**真正在物品级存在**的那一列填上（下一节）。

### 二、物品级真实存在的数据：单价

原版每个 `ThingDef` 都有自己的 `statBases/MarketValue`（①原版锚），乘上**本品种的市场因子**
即得该物品的**实际市场单价**。这与本面板既有的价格口径是**同一个公式** ——
`EconomyMarketRow` 的类注释早就写着「价格是推导量（原版 MarketValue × 因子）」。

- 因子缺省（未建模 / 未就绪）⇒ 退化为原版基价，**不是填 0、也不是编造** ✓
- 基价为 `0`（未在 `statBases` 声明 MarketValue 的 Def）⇒ 显示 `—`
  —— `0` 的语义是「**未声明**」而不是「不值钱」，必须可辨识。

### 三、值源必须单一：与排序键同函数

`CommodityMemberPicker.PickTop` 按 `MarketValue` 基值**降序**取成员（所以截图里黄金排第一，
因为它是"基础原料"里最贵的）。若单价另找价格源，一旦两者对不上，就会出现
**「黄金排第一但数字比玻璃钢小」**这种自相矛盾、且极难察觉的显示。

⇒ 单价用 `CommodityMemberPicker.MarketValueBaseOf(thing)`，**与排序键是同一个函数** ✓

### 四、⚠ 一处平台事实补正（附 IL 证据）

`CommodityMemberPicker` 原注释写：「`ThingDef.BaseMarketValue` 在 1.6 **已不存在**
（`fieldsearch` 零命中）」。

我在本次核实中**部分证伪**了它 —— 同类型上确实有 `BaseMarketValue`，但它是**属性**不是字段：

```
get_BaseMarketValue()  =>  this.GetStatValueAbstract(StatDefOf.MarketValue, null)
set_BaseMarketValue(v) =>  this.SetStatBaseValue(StatDefOf.MarketValue, v)
```

⇒ 原注释是**检索方法用错导致的误判**（`fieldsearch` 找字段，自然找不到属性）。
**落点仍然正确**（唯一静态价格源就是 `statBases` 里的 `MarketValue`），只是理由写错了。
补充证据：XML 侧的 `<BaseMarketValue>` 元素在游戏 `Data` 全库 **0 命中**（该写法确已废弃）。

⇒ 已就地补正注释，并**明确禁止消费方另走那条属性路径**（两条路径虽同源，多一条就多一处漂移）。

### 五、实现要点

1. **契约换成对象列表**：`EconomyMarketRow.MemberNames: List<string>` →
   `Members: List<EconomyMarketMember>`（`Name` + `ValueText`）。
   **不用"名字列表 + 数值列表"两个平行 List** —— 平行数组是本工程明确反模式
   （一处增删、另一处忘改 ⇒ 越界，而越界发生在绘制路径上会导致**整局 GUI 卡死**）。
2. **`AppendMembers` 调用位置后移到价格块之后**：单价要用本品种的因子，而因子到价格块才确定。
   若按直觉放前面，拿到的是 `float` 的**类型默认值 0** ⇒ 每个物品单价都变成 0，
   而且**编译期完全看不出来**（`float` 无未初始化告警）。这一点已在代码里写死注释。
3. **货币格式走游戏自身的 `GenText.ToStringMoney(value, format)`**：读 `MoneyFormat` Keyed
   ⇒ 跟随语言与货币符号，**不硬编码 `$` / `¤` /「银」**（那是文案硬编码，且中文语言包里
   `MoneyFormat` 与英文未必同形）。⚠ 该 API **没有单参重载**，必须传 format
   （Mono.Cecil 已证：`ToStringMoney(Single f, String format)`）。
4. **精度按量级分档**：`≥ 100` 用 `F0`（`$1235`），否则 `F1`（`$10.5`）。
   单价列只有约 50px，`F2` 会把 `$1,234.00` 顶出列宽被硬切。
5. **带色列两条路径都要覆盖**：RUIF 走 `TableFmt.BandTextOf(bandValues, bandTexts, r)`
   ——**不读 `rows[r][c]`** ⇒ 必须把单价文本同时交给 `bandTexts`；D2 自绘路径读 `line[4]`。
   子行的带色真值沿用**父品种的因子**（单价 = 基价 × 因子 ⇒ 颜色与数值自洽，
   且同品种所有行同色，读起来是一组）。

## 残余风险 / 已知降级

1. **⚠ `FormatMemberValue` 无单测覆盖**：它依赖游戏内货币格式器（`GenText.ToStringMoney`
   → `Translate`），在 net48 离线测试宿主里不可用。本次已把**判定分支**（`≤0` / NaN / Infinity
   ⇒ `—`）写在函数首，逻辑面很小；但**首次实机必须目视确认单价文本正常**
   （尤其中文语言包下 `MoneyFormat` 的形态）。
2. **子行三列的 `—` 是终态而非临时占位**：除非将来真的建立物品级供需统计，
   否则这三列对子行永远是 `—`。若日后要为子行加需求侧数据，需要新的数据源（例如
   `map.resourceCounter` 这类真实计数），**不能摊品种的基线**。
3. **子行仍不可点**（004 已登记）；**RUIF 路径仍无 tooltip**（004 已登记）。
4. 单价含因子 ⇒ 因子变化时子行数字会一起变。当前因子表为空（MVS 结算器尚无写入侧），
   故实际显示 = 原版基价。
