## [开发线] 2026-09-19

### 一、要求二（质询）的结论：**上一版不符合，已修正**

用户问「成员结构是否符合游戏原版数据」—— **查了，答案是：上一版有实质偏差。**

我用 Mono.Cecil 把原版挑选成员的**完整链路**取了出来：

```
TryGetRandomPawnGroupMaker
  faction.def.pawnGroupMakers
    → Where(gm => gm.CanGenerateFrom(parms.groupKind))          // 先过滤场景（战斗/贸易/定居…）
    → ignoreCommonality ? TryRandomElement : TryRandomElementByWeight(<>c.<…>b__4_1)
                                    ↑ 该 lambda 的 IL 只有一条：ldfld PawnGroupMaker::commonality ✅

ChoosePawnGenOptionsByPoints
  → GetOptions(...)  // 先按点数预算/有效性筛出候选
  → TryRandomElementByWeight(<>c__DisplayClass9_0.<…>b__0)
        ↑ 该 lambda 的 IL：
            gr.SelectionWeight
          × PawnWeightFactorByMostExpensivePawnCostFractionCurve.Evaluate(gr.Cost / highestCost)
                                                                    ↑ Cost = kind.combatPower（get_Cost IL 直读）
  → chosenOptions.Add(...)  // **反复抽取**，每抽一个扣掉它的 Cost，直到点数耗尽
```

⇒ **我上一版只用了 `commonality × selectionWeight`，漏掉了那条成本曲线乘子。**

而那条曲线**不是温和修正** —— 它是原版静态构造里硬编码的三点（Cecil 已核实）：

| `Cost / 最高Cost` | 权重因子 |
|---|---|
| **0.2** | **0.01** |
| 0.3 | 0.30 |
| 0.5 | 1 |

⇒ 语义：**成本不到该组最高值 1/5 的兵种，权重被压到 1%**（原版防止"廉价兵种灌满编队"）。
漏掉它 ⇒ 我会把一个原版只给 1% 权重的兵种按**满权重**计入 ⇒ **占比可差几十倍**。

**已修正**：现为三因子 `commonality × selectionWeight × CostWeightFactor(Cost / 最高Cost)`，与原版公式一致。
曲线以 `const` **镜像**（原版是源码常量、不是 Def 数据 ⇒ 只能镜像），并在代码里写明 **Cecil 依据与复核命令**，
另加单测**逐点钉死**（镜像漂移必须变红）。

### 二、仍然**不完全等同**原版的部分（如实登记）

| 项 | 为什么 |
|---|---|
| **点数预算过滤**（`PawnGenOptionValid`：`Cost ≤ 剩余点数`、已选约束） | 需要"这次出兵有多少点数"这个运行时输入 ⇒ 属**实际出兵规模**的口径。本段口径是"**权重构成**"，不引入该输入 |
| **反复抽取的循环尾部效应** | 同上。点数快耗尽时昂贵兵种会失去资格，廉价兵种尾部略占优 |
| **`highestCost` 的取法** | 原版取"**当前有效候选**里最高成本"（随点数变化）；本段取"**该集团全部选项**的最高成本"作**稳定近似** |
| **跨 `groupKind` 汇总** | 原版按"这次要生成哪种集团"（战斗/贸易/定居…）过滤 `CanGenerateFrom`；本段**汇总所有场景** ⇒ 是"该派系的**总体**成员构成"，不是某一次出兵的构成 |

⇒ **结论**：**权重公式已与原版一致**（这是"数据是否原版"的实质），
**边界条件仍是近似**（因为我们刻意不引入"本次点数预算"这一运行时输入）。
段标题「成员构成」+ 口径注「按出兵权重」如实反映了这一点，**未声称是实测人数**。

### 三、要求一（干净化）的执行：三处**减法**

| # | 动作 | 理由 |
|---|---|---|
| ① | **砍「无爵位 ②」** | 它是"**某东西不存在**"，属**零信息量** —— 玩家不会因此做出任何判断，只增加噪声 |
| ② | **「爵位层级」+「领导头衔」合并为一条治理 chip** | 两者同在讲治理，原实现占两个位置 = 同一件事占两次 |
| ③ | **砍「服装材料 ②」** | 信息量最低（"不限"/"限 N 种"几乎不影响判断）；且 §4.2 的材料**分类**本就未做（原版无稳定结构化依据，只能裸字符串比对）⇒ 只报**半个维度**不值得占位 |

⇒ chips 上限 **9 → 7 枚**，且**没有一枚是零信息量的**；构成行 **7 → 5 行**（`DefaultTopN` 6→4 + 聚合行）。
⚠ 三个被砍的键（`Trait.NoTitles` / `ApparelLimited` / `ApparelOpen`）**保留在语言包**以便一行恢复。

> 📌 **判据（可复用）**：面板上每一条都必须能回答"**玩家会因此改变什么判断？**"
> —— 答不上来的，无论是"数据为零信息"还是"某东西不存在"，都该砍。

### 四、一条我没有采用的做法（说明取舍）

那条成本曲线是 `PawnGroupMakerUtility` 的 **`private static` 字段** ⇒ 运行时**读不到**（除非反射）。
可选的三条路：

| 方案 | 评价 |
|---|---|
| 反射读原版私有字段 | **未采用**：私有字段是原版内部实现，改名即断；一次读虽可缓存，但引入反射与降级分支的复杂度不划算 |
| 挪进 Def 当"可调参数" | **未采用**：它不是我们的设计参数，而是**原版的行为** —— 一旦可调就不再"符合原版数据"，恰恰违背本次修正的目的 |
| **镜像为常量 + Cecil 依据 + 单测钉死** ✅ | **采用**：零反射、零新 Def，且漂移会被测试抓住；升版本时按注释里的 Cecil 命令复核 |

## 实机验证建议（重启后）

| 项 | 怎么看 |
|---|---|
| **头号：廉价兵种被压低** | 某派系若有"低成本杂兵"，其占比应**远低于**其 `selectionWeight` 给人的直觉（原版曲线把它压到 1%） |
| **治理 chip 只有一条** | 应看到形如「爵位 3 级 · 领导 伯爵 ②」**一条**，而不是两条；**无爵位派系不应出现"无爵位"** |
| **chips 更少** | 上限 7 枚（科技 / 治理 / 贸易接口 + 4 系数），不应再有「服装材料」 |
| **构成行更少** | 最多 5 行（4 明细 + 「其余 N 项」），合计仍为 100% |
| **回归** | 市场面板可见品种与供需数值应与本批之前**一致**（本批不动四系数） |
