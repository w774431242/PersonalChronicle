## [开发线] 2026-09-19

### 一、修复的是**根因**，不是症状

用户报告「画像太少 ⇒ 社会背景同质化」。诊断结论：**不是画像少，是上游 §4 设计的 9 类输入只落地了 1 个**（`techLevel`）：

```23:63:Source/PersonalChronicle/MVS/Application/Adapters/FactionProfileAdapter.cs
// 层 1 之前，TryGetProfile 真正参与画像的输入只有：
//   def.techLevel   ← ★ 唯一
// （IsEconomicallyModeled 的 6 字段门禁**只产出布尔**，不产出维度）
```

⇒ 画像空间 = **7 档**（Animal..Archotech），面板模板 **2 套** ⇒ **同 techLevel 派系完全一样**。

### 二、🔴 实现期**推翻了自己草稿里的一处设计**（本批最重要的判断）

草稿（SDD v0.1 §3 层 2）原写：「既有 4 系数**改为"由多维输入合成"**」。

**实现时我把它推翻了。** 理由：

| | 若按草稿"合成" | 本批实际做法 |
|---|---|---|
| 四个系数的性质 | 被 **② 真读数**混合 ⇒ **不再纯粹的 ③ 假设** | 保持 **③ 假设**不变 |
| 圈码 | **无法分标**（混血值该标 ② 还是 ③？） | ② / ③ **各自标对** |
| T1a（品种过滤）/ T1b（供需偏置） | 输入被改 ⇒ **行为静默变化** | **零回归**（逐档穷举单测钉死） |
| 与 §4「分界线」原则 | 跨过了线（把假设与读数搅在一起） | 严格守线 |

⇒ 改为**并列**：新增 `FactionTraitsData` 独立子结构，与四个系数**同挂一份画像、类型上分开**。
**这不是妥协，是比草稿更严的做法** —— 草稿那版会让 ② 与 ③ 无法分别标注，而**分别标注正是裁决 C 的要求**。

### 三、新增维度（**全部 ② 真读数，零编造**）

| 维度 | 来源字段 | 读法 |
|---|---|---|
| 爵位层级 | `royalTitleTags` | `Count`（**0 = 无爵位，是真读数不是缺数据**） |
| 领导头衔 | `leaderTitle` | 原值（游戏加载期已按 DefInjected 本地化） |
| 固定领导种数 | `fixedLeaderKinds` | `Count` |
| **贸易接口** | 四条 `*TraderKinds` | **四类计数之和** |
| 服装材料 | `apparelStuffFilter` | 是否受限 + 允许种类数 |
| 据点密度 | `settlementGenerationWeight` | 原值（**相对量**，非有限/负值净化成 0） |

🔑 **「贸易接口」这一维尤其关键**：这四个字段此前**只被门禁当布尔用**（"四条里有没有一条非空"）
⇒ 「商队 3 条 + 轨道 1 条」与「只有访客 1 条」被判成**同一种派系**。
现在把计数读出来 —— 这是去同质化**最有效的一维**（第三方派系几乎各不相同）。

### 四、⚠ 三类输入**没做**（如实登记，不假装覆盖 §4 全部）

| §4 输入 | 为什么不做 |
|---|---|
| `apparelStuffFilter` → Metallic/Fabric/Woody **分类** | 原版没有结构化的"金属/织物/木质"轴；分类只能按 `StuffCategoryDef` 的 **defName 比对** —— 那正是本工程 P1 红线所禁的**裸字符串匹配**模式 |
| `backstoryFilters` → 人口构成（worker/noble/slave） | 同上，需要把 filter 分类成人格类别，无稳定结构化依据 |
| `pawnGroupMakers` → 集团类型（raider/trader/settler） | 「战斗/贸易」语义只能从 `PawnGroupKindDef` 的 `workerClass`（类型比对）或 `defName`（字符串匹配）推断，两条都缺官方结构化依据。（该字段目前**只**用于人数模型的权重和） |

⇒ 已逐条写在 `FactionTraitsReader` 类尾的「未做项」，**不是漏写**。

### 五、② / ③ 圈码（裁决 C 的执行）

- 圈码**写进 Keyed 模板**（`科技档位 {0} ②` / `产能系数 ×{0} ③`）⇒ **只要该 chip 被画出来，标记就在**，调用点无法遗漏。
- chips **按圈码分组排列**：② 组在前、③ 组在后 ⇒ 读者一眼看出"哪条是读数、哪条是假设"，不必逐枚认圈码。
- ⚠ **不可用就不画**（延续 T2 纪律）：`leaderTitle` 为空 ⇒ 不画该 chip（不是画空值）。

### 六、🔴 一个我自己造成的事故（已修复，如实登记）

同步前的单测跑出 **1 失败**：`Measure_Content_vs_Viewport`，而它此前一直是「已跳过: 1」。

根因**不在本批代码**：该测试是**既有取证工具** `Tests/TempR8Measure.cs`（`[Ignore]` 标注），
但它的 **`[OneTimeSetUp]` 会往 `_verify_tmp\` 写诊断文件** —— 而**我在早先几轮里把这个目录当"临时目录"清理掉了**，
还当作"清理完成"上报。

⇒ `OneTimeSetUp` 抛 `DirectoryNotFoundException` ⇒ 整个 fixture 报错 ⇒ 那个被 `[Ignore]` 的测试被记为失败。
**已重建 `_verify_tmp\`，跑回 443 通过 / 1 已跳过 / 0 失败。**

📌 **教训**：「看着像临时目录」的目录可能是**既有工具的运行前提**。删之前应当先检索谁在用。
（`_verify_tmp` 是 `TempR8Measure` 的写入目标，名字里没有"被依赖"的线索。）

### 七、另一处编译期发现（值得记的设计代价）

`FactionArchetypeData` 加了**结构体类型字段** `Traits` 后，`Make()` / `Neutral()` 逐字段赋值的写法
会触发 **CS0165（使用了未赋值的局部变量）** —— C# 要求结构体的**全部字段**赋值后才能用。

⇒ 这是**编译器会提醒的那一类**（安全的设计代价），但也意味着：
**将来给该结构再加字段，所有逐字段构造点都要补一行**。
本批已同步修好 `Source/MVS/Domain/FactionArchetype.cs` 与 `Tests/TradeBiasTests.cs` 的构造点。

## 实机验证建议（重启后）

| 项 | 怎么看 |
|---|---|
| **头号：同档位不再同质** | 选一个**工业档**的第三方派系，再选另一个工业档派系 —— chips 里「贸易接口 N 条」「服装材料 限/不限」「领导 · X」应**不同** |
| **圈码可见** | 每枚 chip 末尾应有 **②**（科技档位/爵位/领导/贸易接口/材料）或 **③**（四系数） |
| **圈码分组** | ② 组应在左/上，③ 组在其后 —— 不应混排 |
| **不可用不画** | 没有 `leaderTitle` 的派系，「领导」chip **不应出现**（不是空值） |
| **回归：市场面板未变** | 市场面板的可见品种与供需数值应与本批之前**一致**（层 1 明确不改四系数） |
