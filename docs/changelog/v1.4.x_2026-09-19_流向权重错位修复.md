## [开发线] 2026-09-19

### 一、修复：`Weight01` 用「子集下标」取「全表」

`BuiltinEconomyProvider.FlowGraph.cs` 的边构建分两遍：第一遍把合格边追加进 `snapshot.Edges`，
第二遍按 `maxFlow` 归一化权重。旧代码：

```csharp
for (int i = 0; i < snapshot.Edges.Count; i++)
{
    EconomyFlowEdge e = snapshot.Edges[i];
    float baseline = edges[i] != null ? edges[i].Baseline : 0f;   // 🔴 跨表取下标
    e.Weight01 = baseline / maxFlow;
}
```

**为什么必然错**：`snapshot.Edges` 是**过滤后的子集** ——
- `:145-149` 对"一端被封顶截掉"的边 `continue`（不画悬空线）
- `:136` 对超过 `MaxFlowEdges` 的边不纳入

⇒ `snapshot.Edges[k]` 与 `edges[k]` **不对应**。只要有一条边被跳过，**其后所有边的权重整体错位**。

**影响链**：`Weight01` → `EconomyInventoryChainPanel.cs:358-362`（下游 TOP3 排序）+ `:253`（链路条宽）
⇒ 呈现为「**看起来完全正常，但顺序和长度是错的**」——无报错、无日志、无异常，属最难察觉的一类缺陷。

**修法**（零分配 + 结构上不可能再错位）：第一遍把 `e.Baseline` 存进 `Weight01` 作占位，
第二遍**只遍历 `snapshot.Edges` 自身**就地 `/= maxFlow`。同时把负值夹到 0，避免 `maxFlow == 0` 时残留负权重。

> ⚠ 这条是**本轮审计的产物**：审计本来是查"前端有没有正确消费后端数据"，
> 结果发现后端给前端的那个数字本身就是错的 —— 它属于"对齐"问题的最坏形态。

### 二、审计报告（本轮主交付物）

见 `docs/设计文档/架构/审计-前后端数据对齐-2026-09-19.md`。核心结论：

| 维度 | 对齐度 | 判断 |
|---|---|---|
| Read Model 三向对齐 | ≈80~93% | **0 个「无理由的未填字段」**；问题全在"填了没人读"（18 个孤儿） |
| UI 是否只画不派生 | 92% ~ 50%（分区差异极大） | `Economy/UI` 是成品；`MasterControl` / `Manufacturing/UI` 是**半迁移态** |
| 可见数据真实性 | 高 | **未发现伪造的数值型假数据**（除 DevMode 假数据工厂） |
| 数值正确性 | 🔴 1 处真错 | 本轮已修（见上） |
| 降级健壮性 | 🟠 3 处缺口 | 3 个 `AppendKpis` 无 try/catch ⇒ 抛异常会**整页空白** |

**三条最值得说的**：

1. 🟢 **没有"假数据"**：8 个从不填充的字段**全部**带"有意不再填充 + Keyed 键保留"注释，
   理由可回溯到瘦身批次的 changelog ⇒ **不存在"UI 拿到永远为空的数据却没人知道为什么"**。
2. 🟠 **"填了没人读"共 18 处**，其中 `SystemCenterDetailSnapshot.KpiSectionTitle` 最典型：
   5 个 Provider 实现 `KpiSectionTitleKey`、翻译后写入，**全仓 0 读取**；且接口注释
   `ISystemCenterDataProvider.cs:26` 承诺"UI 回落默认标题"——**该回落逻辑从未实现**。
3. 🟠 **降级链有缺口**：`BuiltinLogisticsProvider.cs:41-70` / `BuiltinMedicalProvider.cs:40-81` /
   `BuiltinManufacturingProvider.cs:81-148` 的 `AppendKpis` **无 try/catch**，一旦抛异常会落到
   组合层整体 catch（`SystemCenterReadModelProvider.cs:404-408` 置 `IsEmpty=true`）
   ⇒ **一张卡出错 → 整个中心详情页空白**，恰是本工程硬要求禁止的
   （对照 `BuiltinEconomyProvider.MarketPanel.cs:163` 的自述：「一块坏不得拖垮整页」）。

1. **审计报告中的计数为粗估**：`Read Model 三向对齐` 的比例来自"关键词命中数 + 逐文件审阅"，
   不是精确行占比；但所有 `文件:行号` 均为实测。报告中已明文标注。
2. **未修复项按优先级列在报告 §5**（P0 三项：3 个 `AppendKpis` + `WorkshopFloorViewProvider.BuildWorkshopView`
   的 catch 不置 `IsEmpty` + 归档 Provider 四个构建方法无 try/catch）。
3. **`Weight01` 修复无单测**：该逻辑在 Provider 内且依赖 `MarketContracts` 运行时数据，
   离线宿主不可复现（与既有 `MVS` 系列同理）⇒ **需实机确认**：打开库存链路面板，
   检查下游 TOP3 的顺序是否与「生产/消费」列的数值方向一致。
4. 本轮**未实机验证**（与 004~006 同批待验）。
