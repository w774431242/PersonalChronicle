## [开发线] 2026-09-19 · 审计结论（逐条带证据）

### 🔴 A1（P0）内容溢出 ⇒ **静默丢行**

| 项 | 内容 |
|---|---|
| **表征** | 截图里「市场特征」只有**两条**（方向 / 需求）。而 Keyed 明确有第三条 `Q3 门槛 · 敏感度` / `A3 Silver ＋ Favor；无爵位不交易…`，Provider 也确实 `Add` 了三条 ⇒ **数据在、没画出来** |
| **根因** | `Draw` 自上而下推进，循环里 `if (… y + RowHeight > body.yMax) break;` —— 满了就**丢**。实测内容总高约 420px、面板身体约 380px，正好把最后一行挤出去 |
| **违反** | 绘制规范铁律 4「**禁止静默截断**（不给完整文本）」· LAND「截断必须配补偿」· 反劣质清单 |
| **修复** | 改为**内层滚动**（与 `EconomyMarketPanel` 同规），内容一行不丢 |

### 🔴 A2（P1）三档档位色**撞色**（A 类缺陷，非引擎限制）

旧映射 `t1→UITheme.Info / t2→UITheme.Accent / t3→UITheme.Alive`。查主题令牌实际取值：

```
Epic  theme:  accent = (0.831, 0.686, 0.216)   ← 金 #D4AF37
              info   = (0.855, 0.706, 0.341)   ← 琥珀金 #DAB457   ⇐ 与 accent 距离仅 0.13
              alive  = (0.459, 0.773, 0.498)   ← 翡翠绿
```

⇒「上层·贵族」与「中层·军人」两条的色条/占比**几乎同色**，而档位色存在的**唯一目的就是区分档位**。
旧注释自称「全组仍保持三档可辨」，**与主题令牌的实际取值矛盾** —— 按定责法属 **A 类（我做错了）**，
旧注释把它登记成 B 类（引擎做不到）是**误判**：预览的紫在工程里是拿得到的。

**修复依据（强证据）**：预览 `--t-floor:#967EBC = (0.588, 0.494, 0.737)`，
与 Epic 主题的 `UITheme.TimelineSocial` **逐字节相同**（该字段源码注释即写着 *amethyst*）。新映射：

| 档 | 新色 | 依据 |
|---|---|---|
| t1 上层 | `UITheme.TimelineSocial`（紫） | 与预览 `--t-floor` 逐字节相同；三主题下都是紫族 |
| t2 中层 | `UITheme.Accent`（Epic 金） | 预览 `--info` 是金，语义对齐 |
| t3 底层 | `UITheme.Alive`（绿） | 预览 `--gain` 绿（这一档本来就对） |

三主题下**最小欧氏距离由 0.13 提升到 0.29** ⇒ 全主题可辨。

⚠ **已登记**：`TimelineSocial` 是**语义借用**（Timeline 色本是「时间轴事件类别色」）。真正的解法是给
`UITheme` 补一组**语义中性的分类色令牌**（跨全局 UI，需全 UI 回归，另案评估）。

### 🟠 A3（P1）长文本截断且**无悬停补偿**

「需求」行中文文本约 344px、答列宽约 276px ⇒ 必然截断。而 `.qa` / `.tier` 的描述**都不挂任何补偿**
⇒ 玩家永远看不到被截掉的那一半（LAND 明确禁止）。**修复**：两处均挂完整文本悬停。

### 🟡 A4（P2）玩家可见文本混入**英文 defName**

`A2` 原文：`奢侈与象征性建造为主；材质仅 Metallic ＋ Fabric（对 Woody 无偏好）` ——
`Metallic` / `Fabric` / `Woody` 是 `StuffCategoryDef` 的 **defName** 直接漏进了中文玩家文本（GOV-009/010）。
**修复**：中文 Keyed 改为「材质限金属 ＋ 织物（不偏好木质）」。英文 Keyed 本来就是英文，未动。

### 🟡 A5 / A6 / A7（P3）

- **A5** `.tier` 缺预览的 `border:1px solid var(--hair)` ⇒ 层次比预览少一层。**已补**。
- **A6** `EconomyPanelChrome.DataRow` 注释称「虚线分隔退化为细横线」，实现里**一条线都没画** ⇒
  注释承诺了实现没做的事。**已按预览补 1px 实线**（引擎无虚线，B 类降级）并更正注释。

## 实现要点：为什么引入「布局计划」

内容要滚动，就必须在**绘制之前**知道内容高（`BeginScrollView(rect, ref scroll, content)` 的
`content` 是入参）。若另写一个测量函数，它与绘制函数就是**同功能两处实现** —— 反模式清单明确禁止，
且症状极隐蔽：滚动量差一点 ⇒ 底部被切、或永远留一块空白。

故引入**布局计划**：一次算出 `(块类型, 下标, 高度)` 序列，**测量与绘制共用同一份**。
配套两条防漂移约束：

1. **chip 换行判定抽成单点** `ChipNeedsWrap`，测量与绘制都调它 —— 差一个换行就是 24px 偏差。
2. **滚动分支必须用滚动时的实际宽度重建计划**：内容窄一个滚动条宽之后 chips 的换行点可能前移，
   否则预算高 < 实际画高 ⇒ 最后一行 chip 被 content 底边裁掉。（这一条是本轮自查抓到并修掉的。）

## 残余风险 / 已知降级（诚实登记）

1. **⚠ 「需求」行中文下仍会截断**：现由悬停兜底（合规），但**没有折行**。根治需要
   `EconomyPanelChrome.DrawWrapped` 提供**可测量的折行 API**（返回行数），否则测量与绘制又会分叉。
   属共享 chrome 改动，**另案**。
2. **`TimelineSocial` 语义借用**（见 A2）——需补分类色令牌才能正名。
3. **未做游戏内实测**：编译 / 单测 / 两区一致已验证；但「三档色实际观感」「悬停是否覆盖到值得悬停的列」
   **需实机确认**（尤其 Steampunk 主题下 accent 与 alive 同绿族、靠明度区分）。
4. **滚动可用性未验证**：社会背景面板此前**从未滚动过**，其滚动条出现是否会挤压 chips 换行
   （已按上面第 2 条处理）需实机确认。
