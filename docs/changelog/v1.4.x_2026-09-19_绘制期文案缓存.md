## [开发线] 2026-09-19

### 一、问题：绘制期 `Translate()` 的真正代价不是"慢"，是**每帧分配**

`"Key".Translate()` 单次只是一次字典查询（约百纳秒级），**不是帧时间问题**。
真正的代价是 `.ToString()` **每帧分配一个新字符串** ⇒ 稳态 GC 压力，
且与 GOV-010「绘制期零翻译、零拼接」的既定约定直接冲突。

**本次先精确统计了实际分布**，而不是照着审计的清单盲改：

| 位置 | 数量 | 处置 |
|---|---|---|
| `MasterControlTabWindow.Translate(string)` 助手 | 1 处，**背后 ~50+ 调用点** | ✅ 改助手实现体 |
| `WorkshopLayoutCanvas.Translate(string)` 助手 | 1 处，背后 13 处 `Draw*` | ✅ 改助手实现体 |
| `FloorDeviceDetailWindow.Translate(string)` 助手 | 1 处，背后 9 处 `OnGUI` | ✅ 改助手实现体 |
| `Archive/UI` 下的直接 `.Translate()` | 6 处 | ✅ 5 处改缓存，1 处**有意保留** |
| `PopulationViews` / `Roster` 的直接调用 | 6 处 | ✅ 全改 |
| `SystemCenterKpiFactory` / `SystemCenterReadModelProvider` 的 `Translate` 助手 | 2 处 | ⛔ **有意不动**（见下） |

> **关键判断**：那 3 个 UI 助手是**同一段代码的 3 份拷贝**（`private static string Translate(string key) =>
key.Translate().ToString();`）。**改助手的实现体一处，就覆盖了它背后全部无参调用点** ——
这是本次投入产出比最高的一步。而 `Application/` 层的那 2 个同形助手**必须不动**：
它们在**构建期**运行（Provider 建快照），不在绘制路径上，给它们加缓存只会引入无谓的静态状态。

### 二、实现：`UIComponents.Loc`（新增 partial 切片 `UIComponents.Loc.cs`）

```csharp
internal static string Loc(string key)   // 只服务**无参**键
```

四条设计约束，每条都有理由：

| 约束 | 理由 |
|---|---|
| **⛔ 只服务无参键** | 带参翻译（`Translate(arg)`）参数逐次不同，缓存会把**上一次的结果**返回给下一次调用 —— **错值远比慢严重** |
| **按语言失效**（`LanguageDatabase.activeLanguage.folderName`） | 无参 Keyed 键的值**只随语言变化**，与 `BuiltFromRevision` 无关（那是快照缓存的事）。用 `folderName` 与工程既有两处先例同源（`UIComponents.ThemeSwitch.EnsureThemeTexts` / `MasterControlTabWindow.Population` 的绘制缓存） |
| **有界**（容量 512，超出即清表） | 键来自代码字面量 ⇒ 正常路径不增长；但仍设上限兜底 —— 万一有人传了动态键（DefName / 拼接串）也不会无界增长，代价只是重新翻译一轮 |
| **单线程假设**（无锁） | 调用者全在 `OnGUI` 路径上；将来若有后台线程要读，必须先加同步（已写进文档注释） |

### 三、⚠ 迁移时踩到并规避的一个**静默错值陷阱**

`PopulationViews` 的「未落地项」行原本是：

```csharp
("PersonalChronicle.UI.MasterControl.Contract.Gap" + i).Translate().ToString()   // 键 = "…Gap1" / "…Gap2" / "…Gap3"
```

按"最小改动"的直觉很容易写成：

```csharp
UIComponents.Loc("PersonalChronicle.UI.MasterControl.Contract.Gap") + i          // 🔴 错！
```

—— 那样缓存里塞的是**不含数字的键**（`…Gap`），它**不存在** ⇒ `Translate()` 回退返回**键名本身**
⇒ 屏幕上会显示 `PersonalChronicle.UI.MasterControl.Contract.Gap1` 之类的**英文键名**，
而且**因为缓存了，切语言也不会恢复**。

**正确写法**（先拼键、再交给缓存）：

```csharp
Translate("PersonalChronicle.UI.MasterControl.Contract.Gap" + i)
```

⇒ 已在代码里就地写下这条警告（含反例），避免下一个"顺手简化"的人重蹈。

| `Archive/ArchiveMainTabWindow.*`（`PawnWork` / `Metrics` / `Labels` 等） | **另一个窗口**，是独立的更大迁移面（见下节残余项） |

### 五、切语言正确性（本批最需要验证的点）

缓存**只按语言失效**。若失效写错，症状是「切语言后界面仍是旧语言」——而快照缓存（300 tick）
最长 5 秒才自愈，这个缓存**永不**自愈 ⇒ 一旦漏判就是**永久性混语言**。

⇒ 故失效判据用**字符串比较**（`StringComparison.Ordinal`）而不是引用比较，
且在任何 `TryGetValue` **之前**执行；语言标识取 `folderName`（`LoadedLanguage` 的稳定字段）。

## 残余风险 / 已知降级

1. **⚠ 未实机验证**（与 004~010 同批待验）。**本批的头号验证点就是切语言**：
   打开总控制台 → 界面上应全部变成新语言（页头 / 面包屑 / 各面板标题 / 空态 / 表头排序提示），
   **不能有任何一处残留旧语言**。若有残留 ⇒ `Loc` 的失效判据被绕过了。
2. **`Archive/ArchiveMainTabWindow.*` 仍未迁移**：该窗口（人物档案主界面）有 `PawnWork.cs` 43 处 /
   `PawnCombat.cs` 52 处 / `Dialog_QualificationFlow.cs` 41 处等大量绘制期翻译。
   它**有自己的缓存范式**（`ArchiveMainTabWindow.Cache.cs` 的"never recompute in the draw path"），
   但只有部分文件用上了。**属独立的更大迁移面**，本批有意不碰（一次改 100+ 处无法有效复核）。
3. **`Loc` 不解决"每帧拼接"**：例如 `Shell.cs` 的 `JoinTags` 仍每帧 `new StringBuilder()`。
   那类问题要用调用方的 revision+语言缓存（范式见 `Population.cs:618-624`），属另一类改造。
4. **缓存命中的键不感知运行期注入**：若某键在运行期才被别的 Mod 注入，本缓存不会察觉。
   本缓存只服务本工程自己的 `PersonalChronicle.*` 键（不在运行期变化）⇒ 可接受。
