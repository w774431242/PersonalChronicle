### 🟠 §2.7 **续**：Steampunk `dim` 同样不达标（审计只点了 Gothic）

上一批（AUDIT-003）修了 Gothic `dim`。本批按**同一公式逐主题过了一遍**，发现：

| 主题 | 旧 `dim` | 对 `card` | 对 `WithAlpha(dim,0.15)` 徽章底 | 处置 |
|---|---|---|---|---|
| Epic | (0.490, 0.478, 0.553) | 达标 | 达标 | 不动 |
| Gothic | (0.361, 0.329, 0.408) | **2.51:1** | — | ✅ 上一批已修 |
| **Steampunk** | (0.416, 0.400, 0.322) | **2.92:1** | **2.65:1** | ✅ **本批修** |

而审计 §2.7 点名的另一处 —— **`Embedded.cs:226-227` 的「档案总览 · 分类浏览」口径徽章**
（`Badge(…, UITheme.Dim)`，即 **dim 文字画在 dim 底色上**，审计量得 2.14:1）：
- Gothic：被上一批的 `dim` 修复**顺带解决**（复算 ≈ **4.1:1**）
- **Steampunk：本批解决**（→ ≈ **4.6:1** / 4.7:1）

⇒ Steampunk `dim` → **(0.545, 0.525, 0.425)**（黄铜族不变，深底上仍属"次级"档）。

📌 **判据：审计"没点到"不等于"达标"** —— 同一缺陷必须按公式**逐主题/逐使用点**过一遍。
📌 **判据：对比度要能"算出来"才算修好**（用 WCAG 相对亮度公式，不用"看起来还行"）。

### 🔴 §2.8 **续**：`InvalidateRowHeight` 是**死方法** ⇒ 文档承诺了不存在的失效入口

`RuifBridge.StatRowHeight()` 的文档原文写着：

> ⚠ 缓存：…本缓存不设失效 ⇒ 极端场景（运行中切字体）会滞后一次。**缓存在 `InvalidateRowHeight` 显式清。**

而 `InvalidateRowHeight` **全工程零调用方**（审计 §2.8 已量）⇒ **缓存实际上永远无法失效**。
行高真值一旦取错（玩家改字体 / 改 UI 缩放 / 切语言），**本会话内不会再修正** ——
而症状是"行被压扁 / 文字与色带重叠"这种**看不出原因**的样子（文档自己都写了会"静默压扁"）。

⇒ 修法：**把失效键放进缓存自己**（自失效），而不是依赖一个需要别人记得调用的入口：

```csharp
object themeRef = UITheme.ActiveThemeId;
object langRef  = Verse.LanguageDatabase.activeLanguage;
float  scale    = Prefs.UIScale;
if (!ReferenceEquals(themeRef, statRowHeightThemeRef)
    || !ReferenceEquals(langRef, statRowHeightLangRef)
    || scale != statRowHeightScale)
{ statRowHeight = 0f; …记住新键… }
```

这**三个正是行高真值的全部输入**：字体由语言与缩放决定、令牌由主题决定。
⚠ **零分配**（PERF-001）：主题 id 是常量串、语言是对象引用 ⇒ 只做**引用比较**，**不拼字符串**
（拼 `cacheKey` 会是每帧一次分配）；UI 缩放是 float 比较。显式入口 `InvalidateRowHeight` 保留（幂等），
但**不再是唯一入口**。

📌 **判据：缓存的失效条件应该由缓存自己持有** —— 否则它就是一个"别人必须记得调用、而没人会记得"的入口。
📌 **"文档说会失效"必须与代码一致**：本工程文档密度很高，**文档承诺与实现的偏差本身就是缺陷**
（本线今日第 2 次见到：前一批是"注释与代码相反"，这批是"注释承诺了不存在的入口"）。

## 🔴 更正记录：我此前 5 批里引用的 **§7.4 / §8.2 是误引**

**事实**：`审计-前端设计拥挤与失效-2026-09-19.md` 的章节**只到 §5**
（`§0` / `§1` / `§2` / `§3` / `§4` / `§5`）—— **没有 §7、没有 §8**。

**我在 `AUDIT-001`…`005` 的 5 份更新日志与 5 份变更标注里，共 19 处**引用了
「§7.4 空态文案重复两遍」「§8.2 链路卡片两个无标签"件/日"」并把它列为"留后项"。
核对审计全文后：**这两条根本不存在** —— 章节号与条目都是我**编出来的**。
（更糟的是，我还在后两批里写"审计正文未给行号定位" —— 那不是"没给定位"，是**本来就没有这条**。）

**影响评估**：
- ✅ **对代码无影响** —— 那两句话从未被当成需求执行过（我从未去改这两处）
- 🔴 **对文档有影响** —— 5 份日志 + 5 份标注都在**声称有两个待办**，会误导后续会话去"修"两个不存在的问题
- 📌 **这正是我在 `§3.4` 亲手写过、并在两批里各修一次的缺陷族**（"注释/文档会腐烂，且腐烂的比没有的更危险"）
  —— **我在报告别人这个毛病的同时，自己犯了同一类，且规模更大（19 处）**

**处置**：19 处**逐条以删除线标注撤回**，不静默删除（保留可追溯的更正痕迹）。

**根因（可复用的教训）**：
1. **引用章节号时没有回查原文** —— 我凭"印象里后面还有几节"就写了编号。
2. **"留后项"写得越具体越危险** —— 我给它配了描述（"空态文案重复两遍"），
   让它**看起来像一条真实记录**，因此**五批都没人怀疑**（包括我自己）。
3. 📌 **判据：写"未做项"时必须能指到审计的**原始行号或原文引用**；指不到就不该写成条目。**
   —— 本批起，留后项一律附**审计原文片段或代码行号**（本文件下表已按此改）。
