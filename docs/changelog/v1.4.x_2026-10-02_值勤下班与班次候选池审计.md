# v1.4.x · 2026-10-02 · 值勤下班机制审计 + 班次候选池回落收窄

- Change ID：`CHG-SHOP-DUTYAUDIT-001`
- 类型：**审计 + 缺陷修复**（P1 行为错误）
- 用户问题：① 车间为什么必须存在「值勤」工作类型？② 为什么没有工作交接，导致 pawn 下班后无法离开车间？
- 影响范围：车间排班 → 值勤 Job 的收工判定链

---

## 一、审计结论：为什么存在「值勤」工作类型

**唯一硬性理由：原版只认 `WorkTypeDef` 作为 `WorkGiver` 的宿主。**

原版派工系统（`JobGiver_Work`）只会遍历「已启用的工作类型 → 该类型下的 WorkGiver」。
要让「去车间站岗」成为一个能被原版调度的行为，就必须：

```
WorkTypeDef PC_WorkshopOperation        (Defs/Automation_WorkType.xml:22-37)
   └── WorkGiverDef PC_WorkshopDutyGiver (Defs/Automation_Jobs.xml:37-48)   ← 唯一的接线点
          └── WorkGiver_Workshop.NonScanJob → TryGetDutyJob → JobDriver_WorkshopDuty
```

其余用途（在岗缓存、加成、工时分类）**都能用别的手段承载**：

| 用途 | 是否必须依赖该工作类型 | 替代方案（工程内已存在） |
|---|---|---|
| 开工速度 / 生产加成 | ✕ | `WorkingBonusOf` 已是「在岗 ∪ 物理位于车间内」 |
| 工时会计分类 | ✕ | 键字符串即可（4 个隐藏 WorkTypeDef 只是标签） |
| 派发「去车间站岗」 | **✓** | 无 —— 原版只认 WorkTypeDef |

⇒ **结论**：它是实现载体，不是设计目标。**可以保留，但它的触发条件必须严格收紧** —— 这正好是下面要修的东西。

## 二、审计结论：为什么下班后离不开车间

### 因果链（逐环有代码证据）

1. 值勤 Job 是 **`ToilCompleteMode.Never`** 的无限等待 toil（`JobDriver_WorkshopDuty.cs:75-83`），
   **系统里没有任何"班次结束"事件**（全 Source 对 `EndJob` / `ShiftEnd` / `handover` 零调用）。
   唯一的收工路径是 `FailOn(() => !manager.IsScheduledForDuty(pawn))`（`:64`，每 tick 求值）。
2. 于是"下班"= **派工计划不再包含本 pawn**。而计划由当前小时重建（`RebuildDutyPlan(hour)`）。
3. 计划里每个活跃班次的**人员来源**是 `ResolveShiftPool`；当班次未启用班组轮转 / 未指定序位 / 未编组时，
   它回落到 `EffectivePool`（`Schedule.cs:273-279`）。
4. **`EffectivePool` 在候选池为空时回落「整份车间名单」**（`WorkshopShift.cs:77-87`）。
5. 而**名额默认 `0` = 不限人数**（`WorkshopShift.cs:35-43`）。

⇒ **两个班次（早班 08–20 / 夜班 20–08）× 各自候选池 = 全体员工 ⇒ 任何小时都有人命中排班
⇒ `IsScheduledForDuty` 恒真 ⇒ `FailOn` 永不命中 ⇒ 24 小时连续值勤，班次之间不可能交接。**

**这不是"缺失交接功能"，而是"候选池回落语义把交接架空了"** —— 系统按"谁该在岗"判定，
但当每个班次都覆盖所有人时，"下班"这个概念在数据上不存在。

### 为什么之前没暴露

单班次车间下该回落是**正确**的（"这个班全员上"），所以老档与直觉都对；
一旦建了第二个班次，回落就变成"每个班都全员上" —— 静默、无告警、UI 无提示。

## 三、修复

### 3.1 候选池回落收窄（根因）

新增 `CollectZoneShiftCounts()`（统计每个车间的班次总数），并把它作为
`ResolveShiftPool(..., bool allowZoneWideFallback)` 的参数：

```diff
-            basePool = shift.EffectivePool;                    // 池空 → 整份车间名单（任何班次数都生效）
+            basePool = FallbackPool(shift, zone, allowZoneWideFallback);
```

`FallbackPool` 规则：

| 情形 | 结果 |
|---|---|
| 班次有自定义候选池（旧档遗留） | 用自定义池（行为不变） |
| 候选池空 + 该车间**只有这一个班次** | 回落整份车间名单（行为不变） |
| 候选池空 + 该车间**有多个班次** | **不再回落** ⇒ 由「班组设置里勾选本班次的班组」供给人员；都没有 ⇒ 该班次空岗 |

⇒ 多班次车间从「全员 24 小时值勤」变为「按班组指派分班上岗」，**下班时 Job 会在小时边界立即收工**
（`FailOn` 每 tick 求值，`RebuildDutyPlan` 在跨小时时必然重建）。

### 3.2 空岗可见（可发现性）

`HasResolvablePool(shift)` 公开查询 + 排班页班次 chip 的悬停提示新增一行
（Key `ShiftNoPool`，中英各一条）：

> ⚠ 本班次没有可用人员 —— 请在「班组」设置里把某个班组指派给该班次

否则玩家只会看到"排了班却没人去"，无从排查。

### 3.3 审计附带修复

`PurgeDeadReferences` 清理死亡/离图成员时，原先只清 `activeWorkers` / `bonusCache`，
**不清 `dutyStartTicks`**（它只在 `NotifyDutyEnded` 里删）⇒ 字典条目随 Pawn 引用永久滞留。已补清。

## 四、本次审计发现、但**未修**的问题（如实登记）

| 编号 | 问题 | 证据 | 等级 | 说明 |
|---|---|---|---|---|
| A-1 | 无显式「班次交接」事件/记录 | 全 Source 无 `ShiftEnd` / `handover` / 交接日志 | P2 | 交接由计划重建隐式完成；交接板 `WorkshopHandoverBoard` 只读。**本次修复后功能上已可用**，是否需要显式记录待定 |
| A-2 | 跨班次重叠无告警 | `RebuildDutyPlan` 只做同小时互斥，不做跨时段冲突校验 | P2 | 同一人被多班覆盖时不报错（修复后可表现为该人全天在岗） |
| A-3 | `start == end` 静默视为全天 | `WorkshopHours.InRange:58-61` | P2 | 编辑器仅显示一句「全天」提示，不拒绝 |
| A-4 | 跨天班次加班基准错 | `ShiftTicksFor` 用"收工那一刻的小时"反查班次，查不到即按 8h 兜底 | P2 | 18:00–06:00 的班在 06:00 收工 ⇒ 加班被系统性高估 |
| A-5 | 死亡/离图成员工时不计入账 | `PurgeDeadReferences` 直接 Remove，不走 `NotifyDutyEnded` | P2 | 本次只补清了起点字典，未做结算 |
| A-6 | 值勤进出无任何日志 | `NotifyDutyStarted/Ended` 无 Log；Automation 目录无 Alert | P2 | 实机无法区分"Job 未结束"与"Job 结束后被立即重派" |

## 五、回滚

撤销代码即止；无 Save schema 变更。收窄是**行为变更**：多班次车间若未在班组设置里指派班次，
修复后会出现空岗（悬停提示会指引修法）。

## 六、待实机验证

1. 多班次车间在班组设置里把早班组指派给早班、夜班组指派给夜班 → 到点后应看到早班组离开车间、夜班组到岗。
2. 未指派班次的班次 → chip 悬停出现「无可用人员」提示，且该时段无人值勤。
3. 单班次车间行为不变（仍全员上岗）。
4. 值勤成员在班次结束后的**下一个游戏小时**内离开车间（`FailOn` 每 tick 检查）。
