# v1.4.x · 2026-10-02 · 修复「有人一直值勤、不去干活」

- Change ID：`CHG-SHOP-DUTYFIX-001`（Bug 修复）
- 影响范围：车间排班 → 原版「工作」面板联动的**档位写入**
- 引入来源：`CHG-SHOP-WORKPRIO-001`（同日）
- 依据：用户实机反馈「为什么有一些 pawn 值勤而不工作？有些是正常工作」

## 现象

同一个车间里，部分成员正常干活（做饭等），另一部分人**整天站在车间里值勤**、什么活都不干；原版「工作」面板里所有人的「车间」列都被标成最高档 **1**。

## 根因

`MapComponent_WorkshopManager.WorkEnable.cs` 里，**值勤类型被误加进了「该提升到最高档」的列表**：

```csharp
workSyncTypes.Add(duty);              // ⚠ 值勤类型被塞进待提升列表
...
settings.SetPriority(type, TopWorkPriority);   // → 值勤也被设成了 1
```

这与设计直接冲突 —— 值勤本应**只勾选、不改档**。设计意图（`Defs/Automation_WorkType.xml` 注释）是：值勤是「没有本职工作时才回车间看护产线」的**兜底**。

**为什么有人正常、有人一直站岗**：原版派工按 `naturalPriority + (4 − 档位) × 100000` 排序，第一个能出结果的胜出。同档位内再比 naturalPriority：

| 类型 | naturalPriority | 会不会干活 |
|---|---|---|
| 烹饪（映射工作，1 档） | 1000 | 排在值勤（350）**之前** ⇒ 优先做饭 |
| 锻造 / 制作等（映射工作，1 档） | 470 / 400 | 同上，仍排在值勤之前 |
| **车间值勤**（被误设成 1 档） | 350 | 排在搬运 / 清洁 / 研究之前 |

所以：**映射工作正常被提升的人**会先去做那些活，只有没活时才值勤（表现正常）；
而**映射工作被背景或技能禁用的人**（例如驾驶员背景禁用烹饪），提升被原版守卫跳过、该类型保持关闭 —— 他面板里就**只剩「车间」一项高优先级**，于是一有空就去站岗，永远不干活。

## 修复

1. 值勤类型**不再**进入「提升到最高档」的列表（`CollectWorkSyncTypes`）。
2. 值勤档位改为**主动收敛**到原版默认档（`DutyWorkPriority = 3`）：关闭 → 勾选；被错误提升或手改的 1 / 2 / 4 → 拉回 3。
3. 修正「映射为空就整体跳过」的提前返回：未指定车间类型的车间现在仍会勾选值勤（否则会漏掉值勤链）。
4. **自愈**：以上收敛在排班变更与打开车间管理面板时都会执行 —— 重启游戏后打开一次管理面板，已被设成 1 的「车间」会自动回到 3。

## 修复后的预期行为

- 「车间」列回到默认档 **3**，与其它默认档工作按 naturalPriority 排队：值勤排在建造 / 采矿 / 种植 / 砍伐 / 锻造之后，排在搬运 / 清洁 / 研究之前 —— 即「有正经活就干活，没有才去看产线」。
- 车间类型映射的工作（烹饪 / 锻造 / 制作…）仍保持最高档 **1**，被排班的人优先做车间里的活。

## 附注：如果某人始终不做车间里的话

那说明他的**映射工作被背景或技能禁用**了（原版禁止给这类工作设档位）。处理方式：
- 把他排到别的岗位（例如「维护」岗位映射到建造），或
- 接受他去做自己擅长的工作 —— 车间加成判定已包含「物理位于车间内」，只要人在车间里干活同样能吃到加成。

## 回滚

撤销代码即止；无存档格式变更。
