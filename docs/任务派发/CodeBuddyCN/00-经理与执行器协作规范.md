# 经理与 CodeBuddy CN 执行器协作规范

用户在本聊天直接授权：Codex 仅承担设计方案、标准规范等经理职能，其余任务分发给 CodeBuddy CN；随后要求继续实装。

## 分工和真实状态

经理负责需求、架构、任务书、依赖及范围、验收标准、读取证据与审查。执行器 CodeBuddy CN 负责源码、资源、测试、构建、部署、实装文档及证据。经理不代替执行器写运行代码、执行测试或构建部署。

状态必须区分 Prepared（任务书已准备）、DispatchAttempted（命令已发出）、Accepted（执行器已回执）、Running（有进度回报）、ReadyForReview（成果等待经理审查）、Reviewed（经理已审查）、Deployed（部署校验完成）、GameVerified（实机验收完成）。CLI 退出码 0 只能证明命令入口返回，不能证明模型收到提示词、开始工作或交付完成。

每项任务独占明确文件范围，保留其他工作区变更。不撤销、不提交、不覆盖其他任务的修改，不重复派发同一写任务来测试连接。若发现同文件同期变更，记录文件哈希和冲突范围，停写冲突文件，其余独立部分继续。

## 回执和回报协议

执行器读取任务书后，先创建本任务指定的 ACK JSON：taskId、executor="CodeBuddy CN"、status="Accepted"、workspace、acceptedAt（带时区）、taskFile、taskSha256。尚未读取任务或仅由经理写入的文件，不算执行器回执。

随后持续更新 PROGRESS JSON：taskId、status="Running"、updatedAt（带时区）、currentStep、completedSteps、remainingSteps、blockingReason（无则 null）。只报告实际发生的进度。

完成后写 RESULT JSON 及可读回报 Markdown：taskId、status="ReadyForReview"、changedFiles（路径/符号/行号/哈希）、build（命令/退出码/日志）、tests（命令/通过/失败/跳过/TRX及哈希）、schemaMigration、gates、notExecuted、remainingGaps、deployReady、deployment（未执行为 null）、rollback。未运行的实机/UI/性能不得标通过；缺口不通过总测试数抵扣。

本轮部署采用经理审查后的第二阶段执行指令。执行器先交付可审查代码、验证证据和待部署清单；经理审查通过后直接派发已获用户授权的部署任务，不再次要求用户逐批批准。游戏运行中不得关闭游戏、强行覆盖 DLL 或修改玩家存档，应保留待部署结果并报告。

协议只规定本地工作交接，不授权给第三方发邮件、工坊上传或与无关账户/服务通信。不输出登录凭据或用户秘密；使用已有正常登录环境。

## 工程纪律

读取仓库适用 AGENTS.md 和工程规范，服从任务书明确边界。Domain 不引用 Verse/RimWorld/Unity/RUIF；原版/第三方访问在适配器，前端硬依赖 RUIF；无必要不增 Harmony。金额、资源、权属和存档证据不得靠 UI 或学习模块改写。

使用实际游戏 DLL/公开 modding 支持验证 API。完成必要行为测试并绑定测试前后的 DLL、源文件和 TRX 哈希；共享工作区构建刷新后不能沿用旧测试报告。每次交付生成变更标注和用户向 Changelog，设计文档不当实现证据。
