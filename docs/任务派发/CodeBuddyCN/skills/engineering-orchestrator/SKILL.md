# 工程总控

把用户要求推进为可运行、可解释、可验证的结果；不要把代码文件齐全、调用过方法、提交了收据或测试数量当作功能完成。此技能是可执行工作方法，不是模型推理能力或隐含思维过程的复制。

## 先确定真正要交付的行为

从当前请求与已接受的决定确定范围和权限。审计只读；实装才修改；部署遵守既有授权。沿用用户指定的框架、数据来源、单一资金来源和玩家保护边界。例行实现选择自行解决，只有阻断正确性的信息缺失才提问。

先读取当前工程规范、入口与关键事实源。旧审计和注释是线索，不是当前证据；工作目录持续变化时记录取样哈希与时间，交付前重新查关键分支，不宣称原子快照。

用一句可复现场景定义完成，例如“新 Pawn 零余额、工作全零，在合法机构有岗位时自主签约、劳动、收薪、到店、使用商品，需求改善”。在改代码前走通入口→调度→判决→提交→实际执行→完成事件→权威状态→存档→UI；至少追出关键消费者和失败恢复入口。详细方法见 [闭环与不变量](references/closed-loop.md)。

## 先归并根因，再排依赖

不要按审计编号逐条改文件。把同根因和同权利边界的问题合为修复单元；用最小复现证据分开“断链、规则错误、假事实、恢复缺陷、容量生命周期、表现错误”。例如界面读旧状态与设置无法启用需要追共同读写源，不能只改标签。

先定契约与不变量，再切任务依赖图。每个任务明确依赖、单一负责人、可写文件、禁止写入边界、输入契约、交付契约、验收场景。使用 [任务图与派发](references/dispatch.md) 和 [任务模板](assets/task-contract.md)。任务图可用 `scripts/check_plan.py` 检查依赖环与同时写入冲突；检查通过只代表结构合法。

## 实际并行，不假并行

发现、调用图、兼容、测试设计等独立只读工作可以并行。实现只有在契约已稳定、文件/状态所有权不冲突时并行。共享运行时、序列化器、公共 DTO、项目文件和最终集成由一个写者负责；多个修复同改一个方法时合并派发。

使用当前 harness 实际提供的子代理或任务工具，不臆造工具名，不假设团队功能已开启。可用并发数是预算：派发已就绪独立任务后，同时处理主线工作；等待必要依赖，避免逐个派发后逐个阻塞等待。只有真实派发/返回记录才能声称多代理运行。子代理不可用时继续执行依赖图，批量独立搜索与检查，并说明串行降级。

适配 CodeBuddy 与既有工程集群见 [CodeBuddy 接入](references/codebuddy.md)。不要重复启动两个总控，或为并行而越过现有门禁。

## 实装必须修完整状态转换

修改前列出成功、失败、重复、取消、中断、读档、离图、容量满、版本改变的行为。检查判断和执行是否复用同一规则；检查失败提交的所有权/租约/余额/实物是否都可恢复。新的“预留”若只存在于签约比较，而其他提款路径不读它，不算真正预留。

完成一批后立刻追最终接线：新 DTO 的消费者、状态的唯一来源、回调的授权检查、原版/玩家保护、终态与重放、UI 解释。不要每写一行都跑全量，也不要未经关键链验证就攒到最后。测试规模随改动风险决定，修错真实边界而不是照抄实现断言。

## 用结果证据收口

详细规则见 [验证与裁决](references/verification.md)。按任务验收场景检查，并明确区分 Implemented、CodeVerified、GameVerified/RuntimeVerified、Released。证据绑定当前源码/构建版本、场景、命令或真实事件、结果与限制。

子代理的“PASS”不能直接升级为主线 PASS；总控读回改动和证据，检查契约是否破坏、共享文件是否冲突、是否复现原问题。未执行写 NOT RUN，缺信息写 UNKNOWN；一个失败场景不能靠其他1195项成功覆盖。

交付简要给出：实际改变的行为、关键缺陷/剩余缺口、验证范围、版本/部署状态、下一步具体修复单元。用户只要求设计/审计时不顺手改业务代码。优先复用已有文档，不为每个动作强制造报告。
