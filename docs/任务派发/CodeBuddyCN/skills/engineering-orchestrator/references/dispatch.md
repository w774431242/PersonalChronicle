# 依赖图、文件所有权与派发

先用契约稳定共享边界，再启动实现。需要改同一关键方法的六条审计项通常是一项状态机修复，不应拆六个并发写者。

## 可调度条件

任务依赖全部完成至其要求的证据等级、输入版本仍有效、可写资源没有其他活跃写者，才能开工。路径冲突采用保守粒度：同一文件串行或一个集成写者；函数不同不自动代表无冲突。共享保存schema/资金协议需要显式契约交付。

例：C=确定合同/预留契约；J=岗位执行；T=交易恢复；U=只读UI；V=验收场景设计；I=集成。

- 第一波：调用图调查与V可独立并行；C接收调查结论。
- 第二波：C稳定后，J、T仅在不同文件且边界已定时并行；U按同一只读契约工作。
- 第三波：I等待所有必要任务，集中接线和交叉验证。
- 若J/T都改EconomyRuntime.cs，声明该文件归I；子任务提交接口实现/补丁建议，不抢写。

不必凑固定人数；小改动一个写者即可。只读工作也给明确产物，避免多个审计者全仓重复扫描。

## 派发必须给具体上下文

至少提供目标、源版本、依赖契约、允许写入文件、不可改动行为、关键验收场景、返回格式。不要只说“修R01”。子代理发现需要改非所属文件时报告总控，由总控调整所有权与依赖，不自行扩写。

父任务没有人的消息授权时不能通过外部聊天或第三方服务联系他人；harness内部子代理按当前授权使用。主代理保留集成、证据裁决和最终交付责任。

## 进行中任务

已派发才是running，模型想象中的团队不是运行事实。收到失败/新发现后更新依赖图和剩余工作；不因一个子任务卡住停掉独立任务。用户 steering 变更及时同步相关契约，过期产物标记stale并复核。

`assets/plan-example.json` 是可直接校验的合成示例，不是实际任务状态。
