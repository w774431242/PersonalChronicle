## 可复用的现有模式

IdeologyAdapter 把理念类型细节隔离在适配器方法内，入口检查启用与 null。返回 null、空字符串和空计数是不同查询语义，未来统一查询不要把它们全部解释为“没有 DLC”。NoInlining 是当前适配器的设计选择，不能代替启用门控和 Def/Tracker 判空。

Biotech 适配器实现 `IVanillaLifeExtension`。VanillaPawnFactCapture 构造时以已加载 `NeedDef.needClass` 验证注册映射，再要求实际 Need 类型精确匹配；在主线程捕获事实。可见怀孕结果区分 Known、NotApplicable、Unknown，不把未启用当成“没有怀孕”。需求未知类型已有 unadapted 路径，未来能力扩展应保留该语义。

3 个直接门控/适配器的原文件副本放在 `snapshot/project-source/`。复制目的是阅读，不建议把这些类直接移入新包编译；其中 Biotech 还依赖当前项目的 Fact/Need 注册类型。

## 未来统一入口需要解决的空缺

1. 门控分散在 Domain、Application、Capture、Compatibility；当前没有统一的 DLC 目录/能力注册表。
2. DlcStatus 只缓存 Anomaly 的单个 bool。新接口若需要随配置/加载快照更新，应绑定本次运行会话/修订；不要追加永久静态缓存。
3. IVanillaLifeExtension 只承载需求与怀孕，不能代表全部 DLC。保持该窄接口，新的基因、理念、异象等能力分别设计读取协议。
4. 项目里还存在 Application 直接读取 IdeologyActive。未来统一门控时先替换读入口并做行为回归，再考虑重构适配器；本次未修改这些代码。
5. `_scripts/_mod_audit/build_report.ps1` 的官方 packageId 名称映射只服务分类报告，输入是 TSV；它不是 DLC 发现器、XML 解析器或运行时加载证据。

建议最先验证三个实际场景：DLC 未启用时无异常；启用后 Play/Learning 等已加载 Def 正确识别；第三方修改 DLC Def 后读取最终对象仍正确且来源语义没有误报。此前后端构建通过不能替代这三个游戏场景。
