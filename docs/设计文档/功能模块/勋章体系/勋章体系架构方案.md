## 1. 需求拆解（分层）

### 1.1 勋章定义（Def 数据驱动，AI-003 最高优先级）
- **阈值类勋章**（劳动奖章/战斗奖章）：达到累计阈值自动授予。
  - 数据源已存在：`PawnObject` 的 `WorkTime`(工时累计)、`Production`(产出件/银)、`MeleeKills/RangedKills`(击杀)、`DamageDealtTotal`(伤害)、`ParticipatedBattles`(参战)、`Consumption`(损耗)。
  - 判定无需新增捕获，纯读已有累计字段。
- **排名类勋章**（荣耀勋章）：连续 N 期登榜前三授予。
  - 数据源：需**期结算历史**（见 §2 数据层）。当前 C# 只有累计，无按期排名 → 必须新建期结算。
- **载体**：
  - 个人（殖民者）→ `PawnObject` 挂勋章授予记录。
  - 团体（工坊）→ 复用 `BuildingStableId` 稳定键 + `BuildingAliases` 识别；累计聚合需新建（见 §2.3）。
  - 装备（武器）→ 复用 `ThingObject.HolderRecords`/`Decommission` 传承链载体（已存在）。

### 1.2 Buff 双通道
- **通道 A · 原生 Stat 注入**（真正影响游戏平衡）：勋章提供 RimWorld 原生 `StatDef`（如 WorkSpeed / MeleeDPS 等），经 Harmony Postfix 注入 `StatWorker.GetValue`。**全仓零先例 → 高风险，需 PowerShell 反射核验注入点（铁律）+ Architecture Review**。
- **通道 B · mod 内展示增益**：仅在 ITab/装备卡显示「+X% 工效」等，不改原版数值，零平衡风险。
- 设计原则：先实现通道 B（零风险跑通链路），通道 A 作为独立阶段（阶段三）开启，预留扩展点（`MedalBuffDef` 同时含 `statDefName` 与 `displayBonus` 两字段，stat 字段为空即只走展示）。

## 2. 实现逻辑梳理（数据层 → 判定 → 注入 → UI）

### 2.1 勋章 Def 模型（Domain，对标 WorkIntensityDef 模式）
新增 `Source/PersonalChronicle/Domain/MedalDef.cs`：
```csharp
public sealed class MedalDef : Def {
    public MedalKind kind;            // Threshold / Rank
    public string ownerType;          // Pawn / Workplace / Thing
    public string metricKey;          // 绑定 PawnObject 字段或聚合键（workTime/production/silver/kills/...）
    public float threshold;           // 阈值类：达标值
    public int rankTopN = 3;          // 排名类：前三
    public int streakPeriods = 3;     // 排名类：连续登榜期数
    public string buffDefName;        // → MedalBuffDef（可为空=纯展示勋章）
    public int order;
}
public sealed class MedalBuffDef : Def {
    public string statDefName;        // 原生 StatDef（通道 A，空=不注入）
    public float statOffset;          // 注入偏移量
    public string displayBonus;       // 通道 B 展示文案键（UI.Medal.Buff.*）
}
```
XML 实例：`Defs/MedalDefs.xml`（标签 `<PersonalChronicle.Domain.MedalDef>`），中英翻译键同步。
> 复用现有 7 个自定义 Def 的成熟模式（DefDatabase 消费 + XML 完整类名标签），工作量低。

### 2.2 期结算数据层（排名类前置，新建）
- 触发点：挂载 `ChronicleGameComponent.GameComponentTick()` 的 reconcile 窗口（每 `ReconcileIntervalTicks=600` tick，与 LocationAtlas 同节奏）。新增 `EvaluateRankPeriods()`。
- 结算内容：按 `metricKey`（工时/产出/击杀等）对全殖民地殖民者 + 工坊实例排名，生成一期 `RankPeriodSnapshot`（periodId=游戏年季或 tick 区间 + 各 owner 排名）。
- 持久化：`ChronicleGameComponent` 增 `Dictionary<string, List<RankPeriodSnapshot>>` 或按 owner 的 `List<PeriodRank>`，Scribe_Collections（append-only，不 bump schema）。
- 连续登榜判定：从最近期往前数，owner 在 labour+relic 合并前三集合连续命中 `streakPeriods` 期 → 授予荣耀勋章（逻辑移植自 `docs/UI预览/档案馆主界面功能/档案馆主界面.html` 的 `computeStreaks`，已是验证过的 JS 范式）。

### 2.3 团体工坊聚合（新建只读聚合，复用稳定键）
- 识别/显示：`BuildingStableId` + `BuildingAliases` 可直接复用（零成本）。
- 累计聚合：当前仅 per-pawn `Workplace.UseCount`，无跨 pawn 全员聚合。需在 `ArchiveService`/`ArchiveUiDataProvider` 新增只读方法 `AggregateWorkplaceUsage()`：扫描所有 `PawnObject.Workplace.BuildingStableId` 累加 UseCount/产量 → 支撑团体工坊勋章（如「某工坊累计被使用 N 次」）。**只读聚合，不改现有写入路径**。

### 2.4 勋章判定引擎（ReadModel，对标 BuildHealthVerdict 范式）
- 新增 `ArchiveUiDataProvider.BuildMedals(pawn/thing/workplace)`：
  - 阈值类：读 `DetailSnapshot`/`PawnObject` 累计字段 ≥ `MedalDef.threshold` → 授予。
  - 排名类：读期结算历史 `computeStreaks` → 授予。
  - 输出 `MedalView`（defName/labelKey/iconColor/isGranted/buffText）。
- 授予记录持久化：阈值类勋章**判定结果可运行时派生**（不强制持久化，除非需记忆"首次授予时刻"）；排名类必须持久化（因依赖历史）。建议：`PawnObject` 增 `GrantedMedals`（List<string> defName，Scribe_Values 集合，append-only），供展示与 Stat 注入查询。

### 2.5 Stat 注入链（阶段三，高风险）
- 目标方法（待 PowerShell 反射核验签名）：`RimWorld.StatWorker.GetValue(StatRequest)` 或 `Pawn.GetStatValue(StatDef, bool)` 的 Postfix。
- 注入逻辑：Postfix 读取 `pawn` 的 `GrantedMedals` → 匹配 `MedalBuffDef.statDefName` → 对返回值加 `statOffset`。
- 隔离：仅当 `statDefName` 非空时生效；注入前 `Traverse` 核验原版签名；签名漂移则静默禁用 + `ChronicleLog.Warning`（沿用 Patch_BillProduction 探针模式）。
- **AI-004 合规**：Stat 注入属 Harmony，必须在 ChronicleMod 注册并登记；不触碰 UI 写 Save 禁止项。

### 2.6 UI 展示（Design System 合规）
- 复用 `UITheme` 令牌 + `UIComponents` 组件；`ArchiveUiStyle` 转发。禁止窗口内 `new Color`；Font/Anchor/color 配对恢复。
- ITab 人物档案：新增「勋章墙」区块（`MedalView` 列表，色块/文字徽章，复用 `DrawTierMedalInline` 范式）。
- 团体工坊：在 `DrawResidenceBar` 工坊卡旁扩展或新增聚合卡。
- 装备传承：在 `LegacyView` 卡叠加装备勋章。
- Buff 展示：通道 B 文案（`+X% 工效`）就近展示于勋章或对应 KPI。

## 3. 分阶段落地计划（AI-005 顺序）

### 阶段一 · 阈值类 + Def 链路跑通（低风险）
1. Contract：`MedalDef`/`MedalBuffDef` 模型 + `Defs/MedalDefs.xml` + 翻译键 `UI.Medal.*`。
2. Domain：`MedalDef.cs`（Def 子类，复用 WorkIntensityDef 模式）。

5. UI：ITab 勋章墙（通道 B 展示增益，不注入 Stat）。
6. Compat/测试：NUnit 覆盖阈值判定纯逻辑（Domain 级）。

### 阶段二 · 期结算 + 排名类（中风险）
1. Data：`ChronicleGameComponent` 期结算钩子 + 排名历史持久化（append-only）。
2. ReadModel：`computeStreaks` 移植（C# 化，复用 JS 范式）+ 荣耀勋章判定。
3. UI：榜单/荣耀勋章高亮（与 `docs/UI预览` 对齐）。
4. 团体工坊聚合：`AggregateWorkplaceUsage` 只读方法 + 工坊勋章。

### 阶段三 · 原生 Stat 注入（高风险，需 Architecture Review + 反射核验）
1. 反射核验 `StatWorker.GetValue` / `Pawn.GetStatValue` 签名（铁律）。
2. Harmony Postfix 注入（登记 + 探针 + 静默降级）。
3. 兼容性声明（与其他 Stat 修改 mod）。

## 6. 勋章内容设定方案（建议值，待用户确认平衡）

> 命名风格：**现实表彰口径**（劳动模范/先进工作者/战斗英雄/一等功/先进集体等）。数值为基于 RimWorld 常识的**推断建议值**，落地前须用户确认平衡。
> **等级模型（用户决策）**：**称号 + 材质独立**。勋章 = 成就称号（如劳动模范），材质 = 铜/银/金三档强度叠加在称号上。`MedalDef` 含 `tier` 字段（Bronze/Silver/Gold），defName 形如 `Medal.<系>.<称号>.Bronze/Silver/Gold`。
> 增益阶梯：铜 +3% / 银 +5% / 金 +10%（通道 A）；通道 B 展示同档。**金牌额外权益**：殖民地公告（Letter）+ 专属称号后缀「·金质」。
> 数据源映射：工时→`PawnObject.WorkTime`（tick 累计，1 殖民者日≈60000 tick）；产出→`Production.TotalQuantity/TotalMarketValue`；击杀→`MeleeKills/RangedKills`；伤害→`DamageDealtTotal`；参战→`ParticipatedBattles`；损耗→`Consumption.TotalSilver`；传承→`ThingObject.HolderRecords`/`Legacy`。
> Buff 双通道：**通道 A** = 原生 Stat 注入（阶段三）；**通道 B** = mod 内展示增益（阶段一/二先行）。`★` 标注依赖期结算/排名的勋章。

### 6.8 平衡备注（推断，需你确认）
- 阈值量级对齐 RimWorld 常规：殖民者日 = 60000 tick；一场袭击战约 1~3 击杀 → 120 击杀≈金质战斗英雄（数值偏高可下调）。
