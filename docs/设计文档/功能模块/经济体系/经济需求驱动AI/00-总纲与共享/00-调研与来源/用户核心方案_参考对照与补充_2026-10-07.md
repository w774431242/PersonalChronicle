## 1. 参考结论

**这份方案适合作为经济 AI 的概念主线。** 它把经济行为建立在生活状态与期望之间的缺口上，并允许购买、公用、自制、出售、等待等替代方案，方向与本轮调研相容。

建议保留以下主线：

```text
状态输入 → 多维 UtilityGap → 持久目标 → 候选方案
       → 合法性筛选 → 效用比较 → 原版 Job 执行
       → 交付与账务结算 → 需求反馈 → 下一次决策
```

主要补充集中在三个地方：**目标必须跨 Job 保留；产权、挂牌和预约要分开；收入与消费必须有真实且可审计的结算。** 这份概念稿没有这些细节不构成方向错误，但不能仅按所列七个模块名称就认定闭环已成立。

用户本次要求将文档作为参考。文档中的“新增”“第一阶段”“完成后再扩展”等内容在本轮仅作为方案建议评估，不据此修改代码、Def、存档或自动推进开发。原参考文件保持原样。

## 3. UtilityGap 如何变成可执行模型

### 3.1 保留多维缺口

不要一开始就把所有状态压成一个无法解释的总分。对可表达为“满足程度越高越好”的维度，可以采用如下概念形式：

```text
Gap_i = clamp((ExpectedLevel_i - CurrentLevel_i) / Scale_i, 0, 1)
```

`ExpectedLevel` 表示这个人的期望；`CurrentLevel` 是当前满足程度；`Scale` 为正值，统一该维度的变化范围。实际食物、温度、债务等输入需先转成各自的满足指标，不能直接把原始数值代入同一公式。

例如现金安全可定义为“可用余额能覆盖多少天必要支出”，地位可以是有限的生活目标或阶层预期。首次原型可以只启用两三个维度，暂不承诺六维都有充分且可靠的输入。

**财富不宜定义为永远想要更多钱。** 应先表示应急金、已选目标的资金缺口和可选的有界资产追求。若资产积累本身也是人格目标，要给它明确的满足曲线和行动预算。

### 3.2 最高缺口不是每轮强制换目标

推荐按以下顺序处理：

1. 原版紧急状态与玩家命令先处理。
2. 更新当前目标的进度、可行性和失效原因。
3. 保留仍有意义的目标；发现更重要目标时，在允许的中断点切换。
4. 从有合法机会的缺口生成有限候选。
5. 若最高缺口短期无解，进入暂停/缺货/无法负担状态，同时允许处理其他需求。

需要持久保存的是目标类型、目标对象或类别、预算、阶段、已完成里程碑及重试条件。评分与临时候选可以重建；已入账余额和已履约事实不能重建成新的收入。

### 3.3 评分公式需做量纲处理

原式“效用收益 × 紧迫度 × 个体偏好 − 价格 − 时间 − 风险”可作为概念表达，但不能直接把银币、ticks 和风险概率相减。

建议将预计收益、预算压力、耗时、风险、切换成本转换成有界的评分输入，并记录权重含义。比较不同动作时使用一致计划窗口，或明确采用完成目标的预计总成本。

此外：

- 偏好为零不能阻止必要进食或医疗；这些应由保护层处理。
- 已由缺口体现的紧迫性不要再无界乘一次，避免临界状态把所有分数拉爆。
- 购买本身应有满足需求的收益；不能因余额减少就永远败给“继续工作”。
- 负分不意味着必须选择最不坏的动作，允许返回“暂无合适经济行动”。
- 不可达、无资格、未经允许动用公款等属于拒绝条件，不能仅扣几分。

## 4. 个人经济与产权的最小修正

### 4.1 Tracker 是入口，不包揽全部业务

```text
PawnEconomyTracker
├─ AccountId / 个人状态
├─ 活跃目标与经济偏好
└─ 已承诺预算与合同关联

LedgerService：唯一写入余额、交易流水、预留和退款
LaborSettlementService：将有效劳动/验收产出结算为收入
OwnershipService：归属、转移及权限
Market/ServiceProvider：提供报价、库存、营业和可用服务
```

以上为概念职责，不是已存在 API。每人入口不能自行派生第二套钱包；UI 中的 Income、Expense、NetWorth 应由同一账本和估值规则生成。

```text
可用余额 = 已入账余额 - 活跃付款预留
区间收入/支出 = 指定区间内对应已提交交易的合计
净资产 = 余额 + 私有资产估值 - 负债
```

净资产中的衣物、饰品等估值不是保证可立即变现的金额，需另有买家与成交事件。默认不修改原版财富统计，也不因为私人买卖就把原本存在的物品价值再次计入殖民地财富。

### 4.2 所有权、挂牌、预约分成三个轴

建议替代原四选一结构：

```text
Ownership：Public / Personal / 后续家庭或企业
Listing：未挂牌 / 待售，关联卖方、数量和报价
Reservation：未预约 / 已预约，关联预约者、数量和过期条件
```

一件个人衣物可以同时由 A 所有、由 A 挂牌、被 B 预约；成交后才转归 B。预约不会提前转移产权，挂牌也不会把资产变成无主物。

堆叠物品还需要按数量表达权利。拆分、合并、搬运、消耗和掉落不能让私有权消失或复制。首版可优先选择不堆叠的单件衣物验证产权转移，减少这部分复杂度。

原材料公有的首版边界有价值，但“自己制作”必须有材料使用政策。否则殖民者可免费拿公共材料制造私人物品再出售，形成对公共资产的无授权转移。

军用武器、公共药物和岗位工具可以被列为不可私售资产。个人获取行为仍需满足玩家的装备、医疗与库存保留策略。

## 5. JobGiver 的职责与反馈边界

`JobGiver_EconomicAction` 应读取当前允许执行的短期意图，并返回有限 Job。它不负责每次查询都重新生成长期目标，也不直接增减钱包或授予产权。

| 原动作 | 建议处理 |
|---|---|
| Buy | 预留预算/货物 → 到达 → 再核验 → 交付并提交交易；失败释放预留 |
| Sell | 自有且可售 → 真实买家/回收方接受报价 → 交付 → 到账；不能按估值直接凭空加钱 |
| Save | 记录目标预算、保留余额及降低非必要消费；有实际存款设施时才需要相应行动 |
| Consume | 使用原版进食/穿戴/娱乐等链；必要时通过适配器收费；以真实使用结果反馈 |
| Acquire | 具体化为领取、购买、制作、交换等；每种方式独立核验权限、库存和交付 |
| Work | 向现有车间/工作机会查询合法工作，由劳动结算系统处理报酬 |

现有 `MapComponent_WorkshopManager.Runtime.cs` 已有征召、倒地、精神状态、岗位与作息门控，应通过契约复用。不能只把经济行动加入行为树，就绕过这些已有规则。

原稿的电视示例要补上使用阶段：

```text
娱乐缺口 → 比较公共娱乐/付费服务/购买设备
       → 有必要时储蓄与工作 → 合法购买及交付
       → 设备可用、可达、有使用权且获得娱乐时间
       → 实际娱乐 → 需求改善
```

**买到电视并不立即降低娱乐缺口。** 该例还涉及建筑类产权、电力、摆放和娱乐 Job，已超出原稿首版列出的可移动私人物品范围，建议作为后续示例。

## 6. 首阶段应保留哪些经济基础

原稿将商品价格、商店、工资制度全部放在七个核心模块完成之后。作为复杂系统的扩展顺序可以理解，但要验证“工作 → 收入 → 消费”的最小闭环，以下最简机制必须提前存在：

| 必需基础 | 可以先简化为 | 后续再扩展 |
|---|---|---|
| 收入来源 | 一种合同、一个支付方、一种劳动结算规则 | 职业工资曲线、谈薪、企业雇佣 |
| 报价 | 挂牌的固定价格 | 动态市场、税费、供需报价 |
| 供给与对手方 | 有限公共售卖点/服务点，真实库存或容量 | 多商店、私人经营、跨图贸易 |
| 货币规则 | 有限初始内部资金，工资与消费为账户转移 | 实体白银托管、兑换、金融 |
| 失败恢复 | 交易 ID、付款预留、提交/取消、读档对账 | 更复杂的合同争议与清算 |

不需要先开发完整商店和工资行业体系，但不能缺少“谁付钱、谁收钱、按什么价、交付什么”这四项。

## 7. 整合后的首版建议

**推荐先做成年自由殖民者的一种衣物改善目标：** 有限公共挂牌供给、一种现有岗位收入、个人钱包、预算与应急金、购买交付、实际穿戴后的状态反馈。衣物更换必须受原版装备策略与玩家设置约束。

原型需要观察的完整链：

```text
衣物状态不足 → 比较公用领取/合法购买/可授权制作
           → 选定合法目标与报价
           → 余额不足：保留应急金、执行允许的有薪工作
           → 有效劳动结算到账
           → 余额足够：合法购买、交付、产权变更
           → 在装备策略允许时穿戴
           → 重新测量衣物状态和对应生活缺口
```

若原版换装或免费公共领取已经满足需求，应降低购买必要性；没有购买不等于 AI 失败。若衣物不足由缺货造成，不能只通过提高工资或增加焦虑解决。

先验证余额变化会影响决策、目标跨 Job 保留、实际使用才缓解需求、交易和工时不重复结算；再增加娱乐服务、租房、择业和更丰富的人格。工资、价格等参数全部视为待验证项，不给未经实机验证的平衡结论。
