## 1. 调研结论

**可行，但需要建设“个人经济制度 + 长期目标 + 行为仲裁 + 交易执行”的闭环。仅增加工资、扣费或缺钱心情，不能实现经济需求驱动的殖民者 AI。**

公开发行先例已经覆盖相当多的功能。最直接的对标是 [Colony Coupons 2](https://steamcommunity.com/sharedfiles/filedetails/?id=3657676020) 和 [Smart Pawns](https://steamcommunity.com/sharedfiles/filedetails/?id=3738853303)：作者分别描述了个人财务制度与基于经济人格、余额、债务的自主经济行动。因此，不能将本项目定位为“工坊首个个人经济 AI”。这些是作者的发行功能声明，本轮没有安装运行它们，也没有证明其完整闭环、性能或兼容性。

**建议立项方向：围绕现有车间系统，先完成“真实劳动取得收入 → 个人预算 → 消费或储蓄 → 需求缓解 → 改变下一次选择”的小规模闭环。** 核心使用本地规则、效用评分与目标状态机。允许后续接入对话模型作建议，但账户、权限、预约和 Job 执行仍由本地规则裁定。

| 目标 | 可行性 | 主要条件 |
|---|---|---|
| 个人账户、工资、消费、现金缓冲 | 高 | 新建受控账本、劳动结算与交易幂等机制 |
| 缺钱时倾向有薪工作；有余钱时消费或储蓄 | 中高 | 必须存在合法岗位、可支出的商品和足够的决策机会 |
| 租房、改善居住条件、攒钱买房 | 中高 | 新建租约/产权；原版床位指派只能辅助识别居住关系 |
| 个性化消费、就业和有限加班 | 中 | 明确玩家授权、作息、岗位资格、收入预期与身体负担 |
| 同时兼容各种工作管理、餐厅、个人货币 Mod | 中低 | 分别开发适配器，建立单一账户与调度权威，逐组合实测 |
| 一步实现完全自主的企业、金融、私有制社会 | 低，首版不建议 | 范围过大，产权、生产资料、物流、公共服务和破产形成耦合 |

## 2. 问题定义与研究方法

### 2.1 本报告采用的需求解释

把“经济需求”理解为对可获得生活条件的追求，而不是单纯追求余额最大化。殖民者应在规则允许的范围内回答：

1. 我缺什么？当前缺衣物、住房、现金缓冲，还是想改善生活？
2. 我有什么选择？哪里有可执行的工作、能买的商品或可租的住房？
3. 哪个选择值得做？考虑收入、成本、时间、风险、个人偏好及现有承诺。
4. 我是否真的获得结果？工作不一定完成订单，到账不等于买到了房，付款也不等于吃到了饭。
5. 环境变化后怎么办？店铺关门、材料不足、被征召、失业或房屋被毁，需要暂停、换方案或求助。

典型行为是：某人想改善住房，保留应急金后储蓄不足，于是选择有资格且可履约的薪资合同；工作和结算使目标资金逐步增加；攒够后在允许时段签订租约或购置资产；目标完成后降低额外赚钱的吸引力。不同殖民者可在住房、娱乐、装备和储蓄之间作不同取舍。

这是本次调研的工作假设，**用户尚未决定是否启用全面收费、私有生产资料、债务或自由择业**。

### 4.2 本机静态核对：不能照搬旧方案的四点

本地反编译文件属于研究副本；本轮读取了它们，并核对了实际安装目录的 XML 与版本文件，**没有重新反编译当前 DLL**。因此下面 C# 结构结论有本地副本证据，落地前仍须针对目标 DLL 重新确认签名/IL。

**一、`NeedDef.fallPerDay` 不会自动让任意自定义 Need 衰减。**

本地 `Need.cs:145` 的 `NeedInterval()` 是 `public abstract`；`NeedDef.cs:111` 虽有 `fallPerDay` 字段，但基础 Need 不提供通用自动扣减。`Pawn_NeedsTracker.cs:83–92` 按 150 ticks 调用具体 Need 的结算方法；具体类需处理冻结、增加、减少和状态持久化。旧经济驱动配置中的 `protected override void NeedInterval()` 也与此签名不符。

若日衰减率为 `r`，常规 150-tick 结算的一次减少量应按时间单位换算：

```text
Δlevel = r × 150 / 60000
r = 0.12 时，Δlevel = 0.0003
从 1 降到 0 约需 8.3333 个游戏日（忽略冻结、补充和离散误差）。
```

旧稿例子每次扣 `0.12 × 0.5 = 0.06`，日扣减为 24，相当于约一个游戏小时见底；**比期望速率快 200 倍**。经济压力不宜照该例子实现。若有加速曲线，其倍率和累计时长也必须单独受控。

**二、床位/房间归属不等于可交易产权。**

`Pawn_Ownership.cs` 确有 `OwnedBed`、`OwnedRoom` 等；`OwnedRoom` 从床及房间 Owners 关系推导。它们能辅助判断住在哪里，不能完整表达房价、卖方、租期、共同产权、家具归属、驱逐、损毁与继承。应自建稳定的 `DwellingId + Lease/Title`；房间重算后通过床/建筑锚点重新解析，不能把临时 Room 对象编号当永久产权 ID。

**三、`Humanlike_PostMain` 是闲置机会，无法保证经济决策及时执行。**

实际安装版 `Humanlike.xml:361–383` 先执行 `MainColonistBehaviorCore`，再到 `Humanlike_PostMain`；`SubTrees_Misc.xml:11–36` 的主行为包含吃饭、睡觉、娱乐和普通工作。只要前面产出有效 Job，PostMain 就没有执行机会。`ThinkNode_SubtreesByTag.cs:36–44` 也显示插入子树按优先级降序、第一个有效结果胜出。

因此，“经济意图只挂 PostMain”适合作为空闲时试验，**不能承诺繁忙殖民者会准时购物或主动选择更合适工作**。反过来把它挂到 PreMain，又可能抢走尚未处理的食物、睡眠与娱乐需求。接入点必须和需求/作息门控一起验证。

**四、Need 的 `major` 不是一套完整的行为仲裁。**

声明经济 Need 或把它标为 major，不会自动生成找工作、储蓄和交易 Job。应明确区分生理状态、经济目标、可执行意图和原版 Job；“住房压力高”也不能取得高于吃饭/医疗的抢占权限。

新增核心至少包括：个人/公共账户、岗位报酬合同、可购买服务或商品、目标状态、交易记录、租约/产权，以及统一决策入口。适配器通过契约接入，经济 UI 保持只读；不应把全部业务塞进现有 MapComponent。

当前经济账本仍遵守只读 `MarketValue` / `wealthWatcher` 的定位。本原型通过内部工资和挂牌服务价表达激励，**没有必要恢复已删除的动态 MarketValue 系统**。

## 6. 建议的 AI 模型

### 6.1 五层结构

```text
原版状态 + 个人账户 + 家庭/居住 + 公开岗位/商品/服务
                         ↓
需求层：生存约束、现金安全、居住、衣物、娱乐、成长
                         ↓
目标层：选择目标、预算、里程碑、暂停/替代/完成
                         ↓
决策层：资格过滤 → 分层仲裁 → 效用比较 → 承诺/冷却
                         ↓
执行层：既有 WorkGiver/JobDriver + 新增有限交易 Job
                         ↓
结算层：真实劳动/交付 → 幂等流水 → 更新状态 → 反馈目标
```

这是本报告建议的模型，不是第三方 Mod 已证实采用的内部架构。

### 6.2 需求模型：钱是实现目标的手段

| 需求 | 观测输入 | 可产生的目标 | 首版建议 |
|---|---|---|---|
| 生理生存 | 饥饿、疲劳、健康、安全 | 原版吃饭、睡眠、医疗、避险 | 作为受保护约束；紧急情况下提供基本保障 |
| 现金安全 | 可用余额、日必要支出、已承诺付款 | 建立若干日应急金 | 首版经济需求之一 |
| 居住稳定与改善 | 合法住处、租约剩余期限、居住品质 | 租住、续租、储蓄改善住所 | 先租约/居住使用权，再做房产交易 |
| 衣物与装备 | 温度、防护、耐久、允许的装备策略 | 购买或领取合适物品 | 先做单类商品；作战配装仍受玩家策略约束 |
| 娱乐和舒适 | 原版娱乐状态、余钱、偏好 | 使用付费服务或储蓄 | 原型中选一种可验证服务 |
| 职业与成长 | 资格、技能、岗位偏好、预期收入 | 培训、择业或申请调岗 | 后续；先保证岗位与合同可履约 |

住房焦虑可以来自当前缺口、租期与负担率，并采用有上限的变化；不必做成永不缓解的时间惩罚。拥有基本住所后目标应可完成，升级追求应有满足期。避免“买完一套又永久焦虑”的无限劳动循环。

原型可先把经济需求作为 Goal 的可解释指标，未必立即新增一排 Need。需要 Need 面板展示、持续压力和心情反馈时再增加自定义 Need；持久化同一个权威状态，避免 Goal 与 Need 各自计算出矛盾结果。

### 6.3 仲裁：先判断能否做，再比较值不值得

推荐顺序：

1. **强制门控**：是否启用自主模式、适用人群、地图、征召、玩家命令、身体状态、危险区域及第三方控制权。
2. **保护原版与公共关键服务**：进食、睡眠、医疗、灭火、救援等；不得因低报酬或付不起钱就关闭。
3. **遵守已有承诺**：班次、已接受合同、排队服务；只在允许的中断点转换。
4. **在可执行的经济候选中评分**：工作、购买、续租、储蓄、休闲、等待机会。
5. **执行前复核**：预算、库存、营业、资格、目标有效性、预约与付款对象仍然成立。

第三步的承诺不凌驾于前两步。轮候老化只能改善同一权限/需求层内部的公平性，不能把奢侈消费老化成医疗或饥饿优先级。

### 6.4 可以验证的简化评分

候选动作 `a` 对殖民者 `p` 的评分可从以下有界模型开始：

```text
Score(p,a) = Σ wi(p) × ExpectedNeedReduction(i,a)
           + wcash × FinancialProgress(p,a)
           + wgoal × GoalProgress(p,a)
           + wfit  × PreferenceFit(p,a)
           - wtime × TimeCost(p,a)
           - wrisk × RiskCost(p,a)
           - wswitch × SwitchingCost(p,a)
```

输入均先归一到约定范围，权重按需求层和人格配置。**先过滤非法/不可执行动作；不能把“不可达”“不符合技能”“侵占公款”仅作为一个小额扣分。** 食物、休息等高优先状态不参与这一池子的任意权重竞争。

`FinancialProgress` 区分动作类别：工作看可信预期净收入，消费看预算许可和目标收益；不能因为所有购物都花钱，就把它们永久评分为负。收入高但耗时长的工作，比较相同计划时间窗口的净收益，而不是只比较合同总金额。

现金目标可用：

```text
AvailableBalance = PostedBalance - ActivePaymentHolds
ReserveTarget = NecessaryDailyExpense × ReserveDays
SavingsGap = max(0, PlannedPurchasePrice + ReserveTarget - AvailableBalance)
DailySurplus = ExpectedDailyIncome - NecessaryDailyExpense
ExpectedSavingDays = SavingsGap / DailySurplus，前提 DailySurplus > 0
```

若 `DailySurplus <= 0`，目标应标为“当前收入下不可负担”，评估降低目标、换合同、申请补助或延后。不能以更高焦虑反复派发同一个不足以解决问题的任务。余额、每日支出和目标报价需标注来源与更新时间。

### 6.5 跨 Job 的目标状态

```text
提出目标 → 估算预算 → 选择收入机会 → 累积收入
                                    ↓
                       资金足够且保留应急金
                                    ↓
                       选择供给 → 预约/付款 → 获得交付 → 满足期

各阶段均可转入：暂停 / 无供给 / 无合法机会 / 无法负担 / 已失效
```

换工作或读档不能清空储蓄进度；征召中断购物不能丢失钱款。经济行为失败必须带原因和退避，出现新供给或条件变化后才重新考虑。

### 6.6 机会来源与集体协调

经济 AI 不能凭空制造岗位。建议由车间/公共机构发布机会：岗位、工种资格、允许时段、可执行任务、支付方、工资规则、剩余人数、合同有效期。

同一个工作台、最后一件衣物或唯一房屋不能无限复制给所有人。地图侧维护有限候选、名额与预约；多人竞争时先按公共最低覆盖和岗位规则过滤，再按个体匹配与等待时间分配。为清洁、搬运、医疗等服务设置公共职责或有资金的公共合同，避免人人追逐高薪制造导致殖民地停摆。

首版以“已编入车间者的经济反馈 + 有限范围内的选择”验证闭环；自由换岗和自愿加班分阶段开放。加班应有显式允许时段和身体预算，不能绕过现有饭点、睡眠、休闲设置。

## 7. 经济制度与账实一致

### 7.1 首版采用什么钱

建议先使用殖民地内部记账单位，公共账户与个人账户在同一账本转移。它们不自动等于原版实体白银，也不自动增加殖民地财富。

| 方案 | 特点 | 首版取舍 |
|---|---|---|
| 每人搬运实体白银 | 支付可见，但库存、掉落、堆叠、搬运和交易 Mod 交互复杂 | 暂缓 |
| 实体白银完全托管的个人余额 | 可兑付，但需专用托管、防止公共交易花掉储备和财富重复计算 | 后续适配，兑入/兑出均需原子兑换 |
| 内部账户/生活信用 | 支付高效、易审计，需定义发行和兑换边界 | **原型推荐：有限初始资金，关闭随意印钞与兑换** |

初始资金属于一次明确的发行/配置事件；后续工资、消费、租金与补助都必须有支付方。禁用贷款时，公共账户不足应暂停新承诺或明确登记欠薪，不能静默从零制造工资。

关闭发行、销毁与外部兑换的封闭原型，应满足：

```text
Σ 所有公共、企业与个人已入账余额 = 初始总发行额
ActivePaymentHolds 只减少可用余额，不额外从总余额中扣除。
```

自动化设备创造产品，不必给不存在的劳动者发工资；产品销售收入归实际定义的公共/企业账户。原版自动生产不应同时生成“个人计件收入”与重复公共收入。

### 7.2 劳动与收入

建议首版只选一种工资口径：按有效劳动时间支付，或按验收后的产出支付。两者可扩展，但不能同时默认对同一份劳动重复奖励。

- 时间工资区分有效加工、允许的服务劳动、移动、待命、休息和中断；哪些属于带薪时间由合同明确，不能由 UI 工时推断。
- 计件工资使用实际完成/验收事件，不把开始 Job、尝试配方或得到失败产物当完成。
- 收入结算由合同服务写入，JobDriver/评分器不得直接修改余额。
- 使用稳定的合同 ID、劳动事件/区间 ID、结算游标和交易 ID 防止重复结算；读档应续算未结部分。
- 殖民者因救援离岗不应被经济调度立即拉回；公共工资或补偿规则单独表达。

现有 120-tick 档案采样可以做统计对照；**本轮不将它升级为货币结算权威**。已有 StartJob/EndCurrentJob 采集应复用事实出口，具体有效劳动区间仍需原型取证。

### 7.3 消费与住房

消费采用有限订单：报价、预算预留、目标预约、实际交付、提交支付。到店时再次核验，失败释放预留。若支付已提交但交付失败，要有唯一对应的补偿交易；同一物品、同一顿饭只能由一个模块负责扣款。

第一种住房商品建议是**租住使用权**：稳定的住宅锚点、租户/家庭、租期、价格、可入住条件。公有宿舍提供基本保障，私人房间构成升级目标。后续买房再增加产权份额、共同所有、家具和拆迁规则。

不能允许殖民者“自动购买”玩家没有挂牌的房间、关键工作台、公共药物或作战装备。购买范围和权限应由玩家政策与挂牌状态决定。

### 7.4 一个仅用于检查量纲的例子

设每天有效劳动 8 小时，时薪 3 内部单位，必要日支出 10；改善居住目标需 100，应急金目标 30，起始可用余额 30：

```text
日收入 = 8 × 3 = 24
日结余 = 24 - 10 = 14
储蓄缺口 = 100 + 30 - 30 = 100
预计需要 100 / 14 ≈ 7.14 个游戏日
```

若疾病使日收入降到 6，日结余变为 -4，应报告无法按当前合同完成目标。**这只是算术示例，不是仿真结果，也不是建议平衡数值。** 模型应在缺少岗位、收入波动和供给短缺时仍能解释自己的状态。

## 8. 技术接入建议

### 8.1 与现有车间分工

经济决策层决定“想做什么、愿意为此保留多少预算、倾向哪种合法机会”；现有车间执行层继续决定“这个人此刻能否在这个岗位执行这张工单”。两者通过机会和劳动事实契约联动，不能各自重写同一个人的工作优先级。

推荐概念契约：`IEconomicOpportunityProvider`、`IPersonalLedger`、`ILaborSettlementService`、`IConsumptionProvider`、`IDwellingProvider`。这些名字为草案，不表示代码已经存在。第三方 Mod 放在 Compatibility 层；UI 只读快照。

### 8.2 行为树/工作链路线比较

| 接入方式 | 优点 | 关键限制 | 使用建议 |
|---|---|---|---|
| 自定义 WorkType / WorkGiver，复用原版工作链 | 原生工作与资格检查，可配玩家优先级 | 时段、普通工作机会和 PC 现有门控可能使消费饥饿；不能把休息娱乐全部改成普通上班 | **先用于有薪任务原型**；消费需另定义允许窗口并实测 |
| PostMain 插入单一经济 JobGiver | 改动小，适合空闲时消费试验 | 忙碌时可能一直没有机会 | 仅作为早期机制实验，不承诺主动经济 AI 完整性 |
| 在主行为仲裁中加入经济节点 | 可以获得合适的决策机会 | 涉及排序和原版生理需求，需窄范围 XML Patch、资格门控与兼容验证 | 经济消费需要及时性时再选择；首版不冻结优先级常数 |
| 改写所有工作优先级 | 路线有 Free Will 先例 | 会和 PC、Work Manager、Work Tab 等争夺控制；难保玩家安排 | 不作为当前默认路线 |
| 高频 CheckForJobOverride / StartJob 抢占 | 响应快 | 重启 Job、预约泄漏、工单损失和兼容风险 | 首版不引入新的通用抢占；使用已有边界通知与自然决策点 |

不能用“之前某点没人 patch”作为当前兼容证明，也不能宣称单个框架能独占整个生态的插入槽。应读取本次启动后的 Harmony patch owners 和最终 Def 树，再决定适配规则。

### 8.3 存档与生命周期

全局账本与合同保存在 GameComponent 等明确的单一所有者；地图机会缓存只重建。保存个人 ID、目标阶段、余额、预留/订单状态、合同与结算游标。持久化字段只存稳定业务数据，不能存 UI 对象、评分器委托或遍历中的 Job 引用。

需定义死亡、离开殖民地、远征、跨图、建筑毁坏、关系改变、加入/移除 Mod 时的处理。首版可将对象限定为当前地图成年自由殖民者；儿童、囚犯、奴隶、访客和临时任务成员默认不自动纳入，后续各自制定规则。

租约与账务数据允许历史追溯；损毁建筑引用失效不能删除已经发生的交易。安全卸载不能仅承诺“删除 DLL 即可”，需要先停用新行动、结清预留并导出数据的迁移设计。

### 8.4 性能和可观测性

- 普通经济候选可从每人 600–2500 ticks 的 hash 错峰开始试验；这是 H 级参数。需求或余额变化可标脏，按预算重算。生存保障和征召取消不能等待该低频周期。
- 地图维护按工种/服务类型的机会索引；每人只评估有限候选，廉价过滤后再做少量寻路/预约检查。
- 目标是避免 `人数 × 全图物品 × 每 tick` 的扫描。候选上限、服务队列长度、每 tick 预算都配置化。
- 同分采用稳定 ID 排序或可保存随机源；若将来支持 Multiplayer，需单独验证同步，不能凭确定性设计就宣称兼容。
- 显示“为什么现在工作/储蓄/消费”：目标、缺口、前三个候选、资格拒绝原因、已承诺时段、下一次重试条件。

100 名殖民者、每 1500 ticks 评估 16 个缓存候选，在实际 60 TPS 下平均约 64 次候选评分/现实秒；**这只是吞吐量估算，不包含寻路、Job 构造和第三方开销，更不是性能基准**。

> 上述参数与门槛的**绝对值刹车线**、原版侧成本主项与「填充空闲 pawn 可能反而更省」的可证伪假设，见 §12.3(3)(4)。

## 9. 兼容性风险与处理

| 风险 | 失败表现 | 建议控制 | 必须验证 |
|---|---|---|---|
| 工作控制权冲突 | 优先级反复变动，岗位与 UI 不一致 | 每人明确手动/车间/经济/第三方控制模式；适配器协商，缺省退出竞争 | PC + Free Will / Work Manager / Work Tab 分别组合 |
| 重复钱包/重复扣费 | 一顿饭扣两次，银币与账面不一致 | 一个账户权威、一个消费结算者，第三方调用经过适配 | CC2、Colonist Wages、Gastronomy 等开关组合 |
| 经济行为压住生理行为 | 为攒钱饿死、失眠、服务等待不退出 | 受保护状态门控、有限等待、无支付能力时基本保障 | 高饥饿/低休息/病倒/征召时中断各阶段 |
| 公共劳动无人承担 | 人人挑高薪，清洁医疗搬运停摆 | 公共最低服务覆盖、带预算的服务合同 | 缺粮、瘟疫、火灾和物流紧张 |

## 10. 推荐原型范围和推进路线

### 10.1 首个闭环原型

建议限定为：单地图、成年自由殖民者、现有车间岗位、公共账户与个人账户、单一工资口径、一个生活升级商品或付费服务、一个跨日储蓄目标，以及基本救济。

**第一阶段可选“改善衣物/固定服务”，再加“租住较好房间”。** 这样先验证支付和交付，再处理房间重算与家庭归属。暂不做股票、私人借贷、自动企业治理、土地交易和全面收费；这些不影响验证经济需求是否真的改变劳动与消费。

| 阶段 | 产物 | 验收条件 | 停止扩展的条件 |
|---|---|---|---|
| R0：细化需求与机制试验 | 人群/权限、资金来源、工资口径、消费时段；最小 Job/结算探针 | 能确认工资事实来源和消费决策机会；不破坏现有排班 | 仍依赖“PostMain 一定会运行”或估计工时直接支付 |
| R1：账本与劳动 | 内部资金、合同、劳动区间/产出、幂等结算 | 收入真实到账；失败、中断、重复事件不重复支付 | 账不平、短工单无法计量、公共支付方不存在 |
| R2：消费与长期目标 | 一种商品/服务、预算预留、储蓄、解释面板 | 资金不足时工作/储蓄；足够时合法消费；交付后目标缓解 | 只会扣费，行为不变化；或只能通过无限加班完成目标 |
| R3：租住和个体差异 | 稳定住房锚点、租约、不同偏好 | 可租/续租/失效；不同人对相同机会作可解释选择 | 全体同一选择、关键公共服务下降、房间变动破坏产权 |
| R4：长期与兼容 | 30–60 游戏日样本、压力测试、第三方组合矩阵 | 无账务复制、无经济原因阻断生存；性能与行为达标 | TPS 超预算、存档持续膨胀、不可解释行为反复出现 |

阶段是研究后的建议，不是已经批准的开发里程碑，也没有给出未经试验的工期承诺。

### 10.2 如何证明“经济驱动”确实存在

使用同一初始存档、相同世界随机条件和多组重复实验，保留三个对照：A 为现有排班；B 加入工资/消费但关闭经济决策；C 开启完整经济目标。外部事件可能使轨迹分叉，应比较多个样本而非单次截图。

至少做以下干预：

| 干预 | 预期可观察行为 | 不能接受的替代现象 |
|---|---|---|
| 有资金缺口且提高合法岗位净报酬 | 同类合法候选中该岗位吸引力增加 | 绕过资格/班次，或所有人无条件改岗 |
| 目标资金已经足够 | 转向购买/保留应急金；额外赚钱吸引力降低 | 永远继续加班，目标没有完成条件 |
| 同样财务状态，改变消费/储蓄偏好 | 合法的购买与储蓄分布产生差异 | 只换说明文字，决策完全相同 |
| 删去目标商品或关闭服务 | 进入缺货/暂停/替代目标 | 不断重启购物 Job 或原地等待 |
| 日结余降为非正 | 解释无法负担，触发降级/救济候选 | 用更大压力不停重复低收入动作 |
| 征召、饥饿或急救 | 立即让出权限并释放/保留正确交易状态 | 坚持购物、扣款后卡死或抢回岗位 |

建议记录：有效劳动时长、收入/必要支出、储蓄目标完成率、合法机会选择比例、消费/服务成功率、失败原因分布、需求满足程度、公共服务覆盖、Job 切换次数、账本不平差、原型 CPU/GC 与存档体积。

性能的初始 H 级门槛可设为：在固定机器、固定 Mod 列表、固定速度及 30/100/200 人场景下，相对同场景基线的模拟 CPU 均值增加不超过 5%、P95 不超过 10%；受硬件与场景影响，基线记录后再冻结。NPC 数量只对不同负载场景分组，不混成一个平均值。

资金守恒、同一劳动不重复结算、同一物品不重复交付、征召/玩家命令不被自动夺权属于硬判据；行为多样性、满意度与吞吐量需看分布和对照，不能用一个总分掩盖生存失败。

#### (3) 性能预算与判据（工程既有实测，可直接引用）

来源：`docs/设计文档/性能/原版工作系统性能成本分析_2026-09-10.md`（C1–C7 + §6 量级模型 + §8 W1–W10 硬约束）与 `docs/设计文档/性能/数百Pawn规模压力测试方案.md`。

- **绝对刹车线**：单帧累计 **45.454544 ms**（= 1000/22，`WorstAllowedFPS = 22`）即停止追加 tick，且 `realTimeToTickThrough` **清零（丢弃不补）** ⇒ 玩家看到的是**游戏变慢**而非掉帧，因此不能用 FPS 判断性能。
- **无错峰（分桶退化的后果）**：全部 pawn 每 tick 被 tick（`TickerType.Normal` 单桶）。
- **成本主项 = 「无工作时重新决策」**：`curJob == null` → `TryFindAndStartJob` → `JobGiver_Work.TryIssueJobPackage` 全表遍历；区域 BFS 无果后**退化为全图扫描**（`MaxRegionsToScanBeforeGlobalSearch` 默认 `-1`）。
- **最坏量级**：`O(N_p² × N_w × N_t)` —— 争抢使**决策频率** `f ∝ N_p`，兜底使**单次扫描** `∝ N_t`，故对人数呈超线性。
- **验收判据**（§1.2）：`T_tick` **≤8 ms 通过 / 8–15 ms 边缘 / >15 ms 失败**；唯一权威口径是 `TickManager.MeanTickTime`，**禁用 FPS**。

与本文的接口：

- §8.4 给出的是**相对参数**（每人 600–2500 ticks 错峰、候选上限、每 tick 预算）与**相对增量门槛**（§10.2：模拟 CPU 均值 +≤5%、P95 +≤10%）。
- 本节给出的是**绝对值刹车线**与**唯一量测口径**。两者互补，**不可互相替代**：原型期用 §10.2 判「有没有变糟」，压力测试用 §12.3 判「有没有撞上 8 ms / 15 ms」。
