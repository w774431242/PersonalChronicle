# 原版需求缺口驱动经济 AI 设计方案 v0.3

状态：设计草案，尚未接入运行代码。日期：2026-10-08。游戏核验基线：本机 RimWorld 1.6.4871 rev590，当前程序集指纹与接口清单见[原版机制证据](../04-实装指导手册/evidence/原版需求与家庭机制_证据.json)。前端继续强制使用 RUIF。

多需求同时出现时的顺序、同级竞争、中断恢复、家庭分工和长期公平性，见[多需求并发仲裁补充 v0.4](多需求并发仲裁_设计补充_v0.4.md)。该补充细化本册 P0–P3，生活类别不固定对应某一等级。

本方案将下一阶段的决策入口改为“先发现原版生活需求缺口，再寻找满足方式”。当前已实现的衣物交易、计件工资、体检、账本与机构作为执行工具复用；不将当前实现描述为已经具备本方案的多需求模型。本方案细化并更新手册 M01–M04 的后续设计，不自动改变现有发布行为。

## 1. 核心行为与边界

```text
原版状态变化
→ 读取本人及被照护者的真实需求
→ 计算缺口、紧迫度和完成条件
→ 生成生活目标
→ 比较公共供给 / 自己完成 / 购买物品 / 购买服务
→ 需要资金且来得及时，才派生有限收入目标
→ 原版调度与 Job 实际执行
→ 观察需求是否改善、资产是否使用、服务是否交付
→ 回写目标、预算与账目 → 重新评估
```

经济动机来自“满足尚未被覆盖的生活需求所需的资源”。饥饿不是劳动指令，疲劳不是租床指令；钱、岗位、机构和订单都是满足需求的手段。缺货时仍保留生活目标并寻找其他路径，不能因没有商品而停止评估需求。

原版继续负责需求自然变化、吃饭睡觉、恋爱求婚、婚礼、育儿和学习的实际机制。Mod 负责读取事实、计算缺口、长期规划和可选经济服务。不为原版 Food/Rest 再建第二套随时间衰减的数值；也不通过付款直接提高 Need。

## 2. 三种事实来源

| 来源 | 示例 | 缺口的表达 | 约束 |
|---|---|---|---|
| A 原版 Need | Food、Rest、Joy、Comfort、Beauty、RoomSize、Outdoors、Indoors；Biotech 的 Play、Learning | 当前满足度相对于配置目标的不足 | 只读 Pawn 实际存在的 Need；缺失为 Unavailable，不当作 0 |
| B 原版状态、关系与事件 | 衣物、床位、伤病、Lover/Fiance/Spouse、怀孕、孩子关系 | 合法生活目标所需条件尚未具备 | 不是假装原版存在“结婚需求条”或“住房需求条” |
| C 本 Mod 制度资源 | 余额、合同、监护安排、服务容量、家庭分担、应付工资 | 完成已存在生活目标的资源差额 | 不凭空产生永不满足的赚钱需求 |

首批映射 **12 个生活观测域**，其中涉及 **10 种原版 Need 类型**。这是首批范围，不是游戏所有 Need 的穷举，也不是每个 Pawn 必有 12 项缺口。Mood 为结果和风险观察量，不重复生成“购买心情”目标。DrugDesire、成瘾、基因需求、王室身份及其他 DLC 特殊需求后续通过独立适配器接入。

结婚、生育、育儿是不同目标：单身不自动产生缺口；已订婚可以产生婚礼筹备目标；明确的原版生育规划或怀孕可产生准备目标，已有孩子产生照护责任。原版恋爱和求婚机制决定关系进展，经济系统不能购买关系或保证成功。

| ID / 生活观测域 | 原版事实 | 缺口如何形成 | 满足方式与经济机会 | 真正完成的依据 |

| D10 伴侣关系与婚礼 | DirectRelations、Lover/Fiance/Spouse、原版婚礼可执行条件 | 已有关系/事件下的相处机会、婚礼筹备或共同生活条件不足 | 原版社交、求婚和婚礼；可选场地、共同床具、婚礼服务 | 关系由原版推进；婚礼以原版事件及 Spouse 关系确认 |
| D11 婴幼儿照护 | 孩子的 Food/Rest/Need_Play、ChildcareUtility、安全环境及照护者可用时间 | 需要喂养/保护/陪伴，但合法照护机会不足 | 亲自照护、公共育儿；可选托育、婴儿食品和婴儿床 | 孩子真实状态改善或安全任务完成；照护者领工资不是完成依据 |
| D12 儿童学习 | Need_Learning、ActiveLearningDesires、原版活动与教学机会 | 学习满足度不足、可参与活动不足 | 原版自主学习、自然活动、公共授课；可选教学服务/设施 | Learning 实际改善；不直接写成长点数或保证成长结果 |

D01/D02 可以作用于孩子，D11 对其已有缺口建立照护任务，不能再创建一份相同的食物/睡眠缺口或重复计算预算。D02 的恢复需求与 D07 的长期空间改善也分别记录，不能把同一次睡眠的收益计两遍。

关系目标不预设一夫一妻家庭结构，不按“配偶数不足”强行建目标；资格、理念、年龄、既有关系和对方的原版回应均由当前机制校验。无伴侣时默认不生成经济性“必须结婚”目标；未来若增加自主择偶意图，必须明确这是扩展策略，并继续由原版互动决定结果。

## 4. 缺口计算、紧迫度与分级

### 4.1 连续需求

对已存在且可用的原版 Need，先读实际满足比例 `x∈[0,1]`。配置有限目标 `t∈(0,1]`：

```text
gap = clamp01((t - x) / t)
```

例：设计目标 t=0.80，观测值 x=0.40，则缺口为 0.50；该目标是 Mod 参数，不冒称原版进食/睡眠阈值。不同需求分别配置目标，不能全用同一个 80%，也不能因需求条尚未满就不断购物。

当前缺口、迫近风险和资金不足分开保存。紧迫度优先读取原版类别和急救条件；对消耗速度可验证的需求，才估计“距危险阈值的时间”。预测读取原版变化机制，不额外扣需求值。暂停、睡眠冻结和不存在该需求的情况由适配器处理。

### 4.2 状态与事件缺口

衣物、居住、婚礼准备和照护容量各自有具名完成条件。对多个必要条件，可以取 `max(各项不足)` 表达最严重短板，并保留明细；条件不合法或事实不足时为 Unavailable，而不是制造一个最高缺口。

婚礼目标只在已有有效 Fiance 等原版条件或明确允许的扩展规划下产生：可用场地/可出席时段等准备条件不足构成缺口，奢华装饰只是可选子目标。预算不足不改变双方关系，更不能拦截合法的原版婚礼。

准备目标完成后关闭；关系变化、流产/分娩、孩子成长、死亡、离图等事件使关联目标重评或终止，不让已经不存在的事件继续积累压力。

### 4.3 优先级与强度分别表示

| 等级 | 含义 | 例子 | 调度规则 |
|---|---|---|---|
| P0 即时保护 | 原版紧急生命、安全与强制行为 | 严重饥饿、急救、婴儿危险、疲劳失能、征召命令 | 立即让出经济 Job；不能要求先付费或先工作 |
| P1 基本保障 | 有明确近期时限的生活与照护 | 即将进食/睡眠、当班喂养、必要防寒 | 优先保障现有合法供给和照护；只接受来得及完成的资源方案 |
| P2 生活改善 | 非紧急、可延后的改善 | 舒适、娱乐、衣物升级、清洁、学习支持 | 同级比较收益与成本，允许工作筹资 |
| P3 事件与长期准备 | 有事实依据的未来计划 | 已订婚婚礼、家庭居住准备、孕期物资安排 | 在 P0–P2 的实际保障之后使用剩余资源；期限迫近的安全子目标独立升为 P1/P0 |

等级决定先后，`gap` 表示不足多少，`urgency` 表示多快要做，`preference` 表示同类合法方案偏好。既有安全门槛继续作为保护起点，但须改为适配当前需求/服务的策略：不能把现有“Food≥50%、Rest≥40% 才介入”的衣物门槛，机械套在原版进食、睡眠或婴儿紧急照护上。

MVP 可从启动 gap≥0.25、完成 gap≤0.10 的滞回试调；这是实验参数，P0 原版保护不受其限制。执行中保持目标稳定，只有目标失效、更高等级出现或明确收益差超过切换阈值才重排。没有适用于所有 Pawn 的“婚龄压力”或“必须生育”计时器。

## 5. 从缺口到经济动机

每个生活目标先枚举满足方式：公共/免费使用、自己完成、亲自照护、购买实物、购买服务。只有能真实改善该目标的合法方案才能进入比较；不能为了制造市场而隐藏公共供给。

```text
uncoveredCost = max(0, 选定方案尚未支付金额 - 本目标已冻结覆盖 - 第三方已落实的直接代付)
fundingGap = max(0, uncoveredCost - 本目标可用预算)
```

预算由唯一账本分配：余额扣除已冻结款、其他已承诺付款和政策保护储备后，才能分给新目标。本目标已冻结资金已在 uncoveredCost 中作为覆盖处理，不能再制造一次筹资缺口。补贴若已到账个人钱包，只计入预算，不再从成本中扣除；只有已落实的直接代付才作为第三方覆盖。未落实承诺、欠薪及预测工资不算已到账可花的钱。储备是软预算边界，不能与订单冻结重复扣除；用于对应紧急保障时按政策释放。

`fundingGap>0` 且资金路径有望在时限前完成，才创建 `EarnForGoal(goalId, remainingAmount)`。工资到账后重新计算差额，达到目标或目标取消就停止新增筹资承诺。已有劳动合同按自身期限/退出规则处理，不能简单因一次消费完成而中断正在履行的合同。

即刻饥饿时比较的是“现在如何获得食物”，不会因为收入目标得分高就继续工作。长期可以根据实际耗用和家庭人数形成下一规划周期的食品/照护预算；已有公共供给计入覆盖，不凭空要求每个人支付一份生活费。

服务提供方的劳动也要对应可验证需求：存在孩子照护目标才能形成有效托育服务单；不能反复给同一个已满足的孩子喂养/陪伴刷工资。提供者自身 P0/P1 需求同样受保护。

## 6. 合法候选选择与效用核算

先硬过滤：原版许可、危险、当前关系/发展阶段、允许区域、工作能力、服务对象、日程、可达预约、实际供给、预算和时限。再按“优先级 → 时限 → 同级方案得分”选择。高收入不能跨越原版保护等级。

同一生活目标、同一有限规划时域内：

```text
benefit = clamp01(方案预计减少的缺口)
score = benefit * urgency * preference
      - wMoney * moneyCost01 - wTime * timeCost01 - wRisk * risk01
```

归一化参考量由版本化政策指定；权重非负，禁止 NaN、无穷和除零。步行、排队、劳动和服务新增时间都纳入有限时域；不假称已经求得跨日全局最优。无法可靠预测的收益使用保守估计并显示理由。

赚钱是消费/服务的前置步骤，不把最终生活改善收益再次记在每个工作 Job 上。首版以阶段规则推进筹资：保持 parentGoalId、有限差额、预计到账时间和可承受劳动时间，不用“工资越高就永远工作”的单步奖励。

同一行动改善多个维度时按唯一 GapKey 分配收益；RoomSize、Comfort、Rest、Mood 不能对同一收益无条件累加。Mood 只用于风险与事后解释；金融余额、持有资产和生活满足度分别展示。

## 7. 四个重点闭环

### 吃饭

Food 下降 → 识别当前/近期营养缺口 → 原版可食物与公共供给优先参与比较 → 必要时订餐/采购 → 实物到手 → 原版进食 → Food 改善 → 关闭即时目标。下一周期实际供给不足时，才产生备餐/采购预算与有限收入目标。没有钱也保留原版合法觅食、公共救济路径；没有任何食物时显示真实供给失败，不能虚构食物。

### 睡觉

Rest 下降 → 识别恢复时限 → 原版合法床位/地点 → 原版睡眠 → Rest 改善。若持续缺乏合适床位，另开 D07 空间目标 → 公共分配/建造/可选床位服务 → 确认可用。支付床位费用与 Rest 恢复是两个结果；睡眠不中断去挣钱。

### 结婚与共同生活

原版恋爱/求婚形成 Fiance → 观察婚礼与共同生活准备条件 → 使用原版场地/日程，或选择可选筹备服务 → 原版婚礼真正发生、关系变为 Spouse → 关闭婚礼目标。筹备中原版紧急需求优先；分手/死亡则取消关联订单并释放未提交款。共同床具等长期子目标独立确认，不能通过付款调用 Married 来冒充婚礼。

### 育儿

孩子产生 Food/Rest/Play/Learning 等实际缺口 → 明确被照护者与责任人 → 先保障即时安全，再比较亲自照护、公共照护、可选付费服务 → 原版合法喂养/陪伴/教学行为 → 观察孩子状态或服务交付事实 → 合同结算 → 重新安排家庭时间与资源。

买下教学或托育时段只代表取得服务资格；排队、教师站岗或孩子尚未参加时不算完成。学习活动保留原版主动性和发展阶段限制，不是任何 Learning 不足都只能付费上课。

## 8. 家庭与照护责任

新增 `CareResponsibility`：孩子、负责成人、有效期、角色、优先级和政策来源。原版亲子关系是候选依据；非父母监护者由玩家安排/明确制度确定，不从同姓或同一地图臆造监护关系。

家庭协作采用 `HouseholdPlan`：成员、允许分担范围、目标、资源承诺、可用照护时段。组成家庭不自动合并钱包或转移产权；婚姻不自动赋予花费对方全部余额的权力。付款方与受益者分开，例如公共账户购买孩子照护服务。

监护者不能把孩子的需求复制成自己的另一条生理 Need。以 `(subjectPawnKey, domainId, facet)` 唯一标识缺口；多个成人共享同一照护目标，由责任分配决定执行者，避免多人同时预约或重复付费。一个成人的同一时段不能同时承诺工作、睡眠和照护。

宝宝/儿童先作为需求主体和服务受益者；自主签约、就业、消费资格独立配置，首版由成人决策和付款，不沿用“只有成年人才读取需求”的现有过滤。

| N02 缺口评估 | 事实 + 配置 → `DemandAssessment[]` | 纯 Domain；不扣钱、不派 Job、不写 Need |
| N03 生活目标 | 缺口 → `LifeGoal` 与有限子目标 | 跨 Job/存档追踪，避免单枚 Goal 状态覆盖不同需求 |
| N04 供给与服务 | 公共资源/机构 → `SatisfactionOption[]` | 真实供给、排队容量、合法性；没有服务也能读取缺口 |
| N05 家庭规划 | 目标/关系/责任 → `HouseholdPlan` | 受益者、执行者、付款方、时间预算分开 |
| N06 行为选择 | 目标/候选 → `DecisionExplanation` | 先等级后得分；保留拒绝理由、无行动原因 |
| N07 执行与账本桥 | 选择结果 → 现有订单或原版行为机会 | Job/预约/交易继续使用原版与现有事务机制 |
| N08 结果观察 | 原版行为、状态变化、交付事实 → `GoalEvidence` | 付款/取得/使用/满足分离；不按任务开始发完成工资 |
| N09 RUIF 投影 | 有界只读快照 → 个人/家庭/机构页面 | UI 不扫地图、不创建需求、不直接改余额 |

核心记录至少包括：

- `DemandAssessment`：GapKey、subjectPawnKey、sourceKind、sourceDefKey、currentValue、targetValue、gap01、tier、urgency01、deadline、available、reason、modelRevision。
- `LifeGoal`：goalId、parentGoalId、GapKey、类型、阶段、受益者/执行者/付款方、完成条件、预算、期限、失败原因、证据版本。
- `ResourceCommitment`：关联目标、账户、金额/物品/时间、有效期；预算承诺与真实冻结分开。
- `ServiceAgreement`：服务对象、提供方、付款方、服务类型、容量/时段、交付标准、收费规则、取消规则、结果证据。

状态建议：`Observed → Planned → WaitingResource / WaitingSupply / WaitingTime → Executing → AwaitingEffect → Satisfied`；任意阶段可按原因 `Paused/Cancelled/Failed`。食物/休息等周期性需求完成后，下一次达到启动条件生成新的有限周期目标，不让旧目标永久挂着。

## 10. 机构如何承接需求

| 工具/机构 | 服务的生活目标 | 实装阶段 |
|---|---|---|
| 原版公共食物、床、娱乐设施 | 直接满足对应原版需求 | 必须首先纳入候选，不等新建筑 |
| 现有生活用品商店 | D03 衣物及后续合法生活用品 | 复用真实库存/产权/事务，扩展前分别适配 |
| 现有劳务站、工坊管理、结算处 | 有限生活目标派生的筹资 | 替换“先见商品再找工作”的唯一触发条件 |
| 现有体检中心 | 岗位资格、可选健康观察 | 继续作为工具；不能承接其未实现的治疗 |
| 食堂/餐饮柜台 | D01 可选订餐与食品准备 | 新增食品合法性、营养、交付与实际进食证据 |
| 居住服务台 | D02/D07 床位和空间安排 | 新增使用权与服务协议，不把 Pawn_Ownership 当房产证 |
| 家庭服务/托育点 | D11/D12 照护、教学时间 | Biotech 可选模块，真实成人/孩子双边行为 |
| 婚礼与家庭筹备服务 | D10/D09 已存在的事件准备 | 后续模块，不能接管原版关系形成 |

## 11. RUIF 前端

个人页主列表：需求域、当前值/目标值、缺口、紧迫等级、当前行动、阻塞原因。详情显示“为什么做、免费替代是什么、为何需要钱、还差多少、如何判定完成”。分类为基本生理、生活环境、关系家庭、照护成长；优先级是另一列，避免混用。

家庭页：被照护者的缺口、责任人、可用照护时段、实际服务、付款方与预算。缺失 DLC 或不适用 Need 显示“不适用”，不画空缺口条；关系目标显示阶段与条件，不给单身者显示“婚姻满足度 0%”。

组件使用已核验的 RUIF `PanelAtoms.StatRow`、`DataAtoms.StatTable`、`FeedbackAtoms.EmptyState/AlertBanner` 和现有按钮/导航原子。汇总读取 Application 快照，禁止 UI 每帧计算家庭关系、寻路和地图供给。代码名与内部版本留在调试详情。

## 12. 分期、迁移与验收

| 阶段 | 交付范围 | 阶段出口 |
|---|---|---|
| A 原版事实与缺口 | 首批 10 类 Need 适配、12 个域注册、只读 RUIF 解释、P0 保护 | 无需商店也能显示真实缺口；缺失 Need 不报错 |
| B 个体生活驱动 | Food/Rest 原版行动桥、衣物目标、公共替代、有限收入目标 | 需求先于商品，钱够后不继续新增无目的筹资 |
| C 家庭照护 | 责任关系、婴幼儿照护、儿童学习、时间预算 | 同一孩子缺口唯一，紧急照护不被工资压制 |
| D 生活服务 | 餐饮、床位、托育/教学合同与实际交付 | 购买不等于满足，服务未交付不重复结算 |
| E 关系与事件 | 已订婚婚礼、共同生活、孕期准备 | 原版关系结果保持权威，事件取消可恢复 |

保存升级新增版本化的缺口策略、生活目标、责任与资源承诺；原版 Need 不重复保存。保留当前账户、产权、已结算工资和报告，不按历史补造生活费或收入。旧衣物订单继续按原事务恢复；旧单枚 Goal 字段仅作迁移线索，不能虚构多维历史缺口。更新当前 CurrentSchema 前必须先实现旧档迁移与未知 schema 保留策略。

验收场景至少包括：

1. **有免费食物**：Food 下降仍参与原版进食，不能先去挣钱或强制买餐。
2. **缺钱且严重饥饿**：P0 先保障原版合法行动；没有供给则明确失败，不生成食物。
3. **疲劳但已有床**：睡眠优先；高工资不能覆盖休息保护。
4. **无商店**：缺口仍可观测，公共/自制候选仍存在，不将需求清零。
5. **衣物到手未穿**：采购完成，生活目标仍等待效果；不再次购买同一待用资产。
6. **有限筹资**：目标资金到位后不再新增筹资；取消目标同步释放软承诺。
7. **单身/已订婚/已婚**：不统一赋“婚姻不足”；只有有效事件生成对应准备目标。
8. **原版婚礼没有高级场地**：经济可选服务不阻止合法原版婚礼；未发生不能按付款结案。
9. **两个监护人一个孩子**：相同 GapKey 不重复生成任务或付款。
10. **婴儿饥饿而成人有班**：紧急照护先于赚钱，且遵守原版合法喂养条件。
11. **儿童 Learning 低**：既可自主学习也可公共授课；不强迫付费，不承诺必获特定成长选项。
12. **DLC/特质差异**：无 Biotech 不启用相关服务；实际没有的 Need 为不适用。
13. **读档与中断**：不重复扣款、照护计费、发工资；重新核验关系与责任。
14. **效用与预算**：无双重计算、无负预算/NaN；Mood 不复制生活收益，欠薪不能消费。

本次只完成方案和证据检查；以上场景是未来实现的验收要求，尚未运行，不能据此声称游戏行为已通过。
