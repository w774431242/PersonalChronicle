# 01 数据模型与源码依据

适用范围、版本与设计状态见[总册](00-总册与实施路线.md)。本册的经济字段和协议是自研设计；原版类型名称只在“依据/适配”部分使用。

## 1. 数据真值分层

| 数据 | 真值来源 | 采集方式 | 不应采用的替代 |
|---|---|---|---|
| 饥饿、休息、娱乐、舒适及心情 | `pawn.needs` 下实际存在的 Need | 游戏线程适配器读取，缺失则标明不可用 | 假设每种 Pawn 都有全部 Need |
| 健康、倒地、征召、强制工作 | 原版 Pawn/Health/Job 状态 | 执行前重读硬保护信息 | 用几秒前的评分快照作执行许可 |
| 当前穿戴/装备、物品质量与耐久 | apparel/equipment trackers 与具体 Thing | 将所需字段投影为值对象 | 从商品名推断已穿戴或已使用 |
| 房屋占用 | `Pawn_Ownership` 的床、房间关联 | 仅作为居住占用事实 | 当作可交易房产证、合同或自动收费依据 |
| 市场价值/殖民地财富 | 原版 stat/wealthWatcher | 只读展示，与内部定价分栏 | 将钱包总额加回原版财富、直接改写 MarketValue |
| 钱包、工资应付、合同、成交价 | 本 Mod 账本和制度记录 | Application 命令统一写入 | 将履历工时、原版银币数量当钱包余额 |
| 私人产权、挂牌、经济预订 | 本 Mod 产权和订单记录 | 分开建模，以实际 Thing 引用核对 | 用 `Faction == OfPlayer` 判断个人主人 |
| 缺口、偏好、目标、评分 | 本 Mod 纯领域规则 | 版本化输入、可解释输出 | 声称原版已有完整 UtilityGap 经济模型 |

公开 Wiki 教程是社区资料，不是 Ludeon 官方 SDK；GameComponent 页面明确存在过时内容。每个新调用都须在目标 DLL 中复核并编译。G05/G07/G09/G10/G11 的细节来自游戏源码取证，不冒称教程给出了经济实现。

特别注意三个已经核实的细节：

* 目标 `GameComponent` 基类构造为无参数；`Game.FillComponents` 用 `Game` 参数构造子类。所以子类可写 `GameComponent_PawnEconomy(Game game) { }`，不能照抄 `: base(game)`。[保存示例](examples/EconomySaveExample.cs)已编译验证。
* 实际继承基类是 `Verse.AI.ThinkNode_JobGiver`；不是不存在的 `Verse.AI.JobGiver`。`TryGiveJob(Pawn)` 是 protected；`JobDriver.MakeNewToils()` 也是 protected。`ReservationManager` 位于 `Verse.AI`。
* 当前 `Bill_Production.Notify_IterationCompleted(Pawn, List<Thing>)` 是 virtual override；列表参数是 ingredients。现有捕获文件注释中有“non-virtual”描述，不能据注释编写适配器。以当前元数据和 Toils 调用点为准。

## 3. 持久化实体草案

以下是逻辑 schema；正式实装先评审保存键和兼容策略。金额统一 `long` 最小单位，例如 UI 1.00 对应 100；使用 checked 加减。游戏刻保留 `int` 原始刻值，作差转 `long` 并处理异常回退；业务 ID 用持久递增 `long` 序号或稳定字符串，不以 ticks 作为唯一 ID。

| 实体 | 主键/核心字段 | 真值责任与约束 |
|---|---|---|
| `EconomySaveRoot` | `schemaVersion`、`lastSequence`、`policyRevision`、各记录集合 | GameComponent 唯一拥有；不能同时由现有 ChronicleGameComponent 再 Deep 保存一份 |
| `EconomyPolicy` | `enabled`、`eligibleGroup`、工资/消费白名单、预算上限、允许时段、修订号 | Application 写；UI 只是发命令；默认 disabled |
| `PawnEconomyRecord` | `pawn` 引用、`pawnKey`、`accountId`、偏好参数、目标 ID、下次决策刻 | `pawnKey` 用稳定加载 ID 作索引；显示姓名不作主键 |
| `AccountRecord` | `accountId`、`ownerKind`、`ownerKey`、`balanceMinor`、`reservedMinor`、`revision` | `0 ≤ reserved ≤ balance`；可用余额是派生值 |
| `LedgerTransaction` | `txId`、`idempotencyKey`、`kind`、借贷账户、`amountMinor`、`status`、原因/业务引用、刻值 | 余额唯一写入口；转账双方总和守恒；不把净资产字段作为真值 |
| `LaborContract` | `contractId`、雇员、雇主账户、地图 ID、工坊 ID、配方白名单、每次工资、预算/修订、状态 | 首版固定计件，工资不随外部 MarketValue 波动 |
| `ProductionCompletion` | `completionId`、合同/雇员/工单身份、捕获序列、观察刻、结算状态 | 一次完成一个结算资格；工单持续循环不能复用同一个完成 ID |
| `OwnershipRecord` | `assetId`、`thing` 引用、`ownerKind=Public/Personal`、`ownerKey`、修订 | 不支持的物品永远不因扫描自动私有化 |
| `ListingRecord` | `listingId`、`assetId`、卖方账户、服务点、`fixedPriceMinor`、可售/暂停/售出、修订 | 一个实体同一时间最多一个活跃挂牌 |
| `PurchaseOrder` | `orderId`、买方/卖方、挂牌与报价修订、金额、目标、预订到期刻、状态、资金/资产确认位 | 同时关联经济预订、原版预约、交付结果；不能仅保存 bool purchased |
| `EconomicGoal` | `goalId`、Pawn、类型/需求、目标规格、状态、优先级、预算/储蓄额、创建/更新/到期刻、失败码 | 跨 Job 保存；不存 Job 实例或 Window |
| `ActionReceipt` | 业务结果 ID、订单/目标 ID、`Acquired/Equipped/Used/Failed`、原因、实际观察状态 | 取得物品不等于使用；一次结果不会被反馈服务重复消耗 |

`Income/Expense/NetWorth/DesiredGoods` 的落地：Income/Expense 由账目滚动汇总；NetWorth 使用“钱包余额 + 合法个人资产的只读估值”，预留仍属于余额不能重复相加；DesiredGoods 投影自活跃目标。若缓存这些字段，必须带版本并可由真值重建。

## 4. 保存方式与生命周期 F01

| 阶段 | 操作 | 必须避免 |
|---|---|---|
| 构造 | 建立空集合，保存自身对游戏的必要上下文 | 扫地图、发工资、查询完整殖民者集合 |
| `ExposeData` | `Scribe_Values` 保存标量；`Collections`+Deep 保存自己拥有的记录；References 保存 Pawn/Thing | 把游戏对象 Deep 复制；在保存函数中创建交易 |
| `PostLoadInit` | 补空集合、补旧字段默认；标记待恢复 | 仍未校验就启动购物 Job |
| `FinalizeInit` | 按 schema 迁移、验证引用与守恒、恢复未完成订单、重建索引；完成后 Ready | 迁移重复发启动金；用缺失引用自动销毁余额 |
| `StartedNewGame`/`LoadedGame` | 幂等初始化辅助入口与状态切换 | 各入口分别创建不同账本真值 |
| Map 生成/移除 | MapComponent 建立/释放机会索引 | 地图卸载后缓存继续提供交易机会 |
| Pawn 失踪/死亡/离队 | 暂停执行；释放短期预订；账户保留并标记待政策处置 | 首版自动继承、退款并发薪三件事混在一起 |

保存键建议统一 `peaSchemaVersion/peaAccounts/peaGoals/peaOrders/peaContracts/peaAssets/peaListings/peaLedger/peaSequence/peaPolicy`；正式发布后改键必须有迁移。集合先使用 `List<Record>`+Deep，运行时重建 `Dictionary<Id,Record>`；避免一开始引入引用字典的复杂跨引用保存。

迁移约束：旧存档没有根键，视为未启用的新 schema；不得无提示按“当前全部资产”追溯产权或补发历史工资。新 schema 高于代码支持值时，经济模块进入只读 Error，保留原始数据；不得把它当空账本覆盖。无法解析 Def/Thing 的目标标记 `Unavailable`，对应订单走恢复协议。

## 5. 账本和商品事务协议

本协议在游戏主线程同步执行，不假设 RimWorld 提供数据库 ACID。目标是正常存读档、Job 中断和可预期异常下的可重入恢复；进程被强杀后只能恢复到最近一次成功保存，不声称额外磁盘持久性。

### 5.1 首版购买状态机

`Created → Prepared → InTransit → AtCounter → Committed → Closed`

任意提交前阶段可转 `Cancelled/Expired`。`Committed` 后不能再走取消退款；真实退款是另一个引用原成交 ID 的逆向业务，不靠重复执行 Cancel。

1. **报价**：读活跃挂牌，校验买方、物品、地图、固定价和 `listingRevision`；生成全局唯一 `orderId`。
2. **准备**：同一次服务调用检查可用余额和资产未被其他订单预订；写入订单、资金冻结、经济预订。失败时全部不改或立即撤销已改字段。
3. **派 Job**：Job 仅带 orderId 和游戏 target；`TryMakePreToilReservations` 取得原版预约。首版货物在售货点真实容器中，物理预约对象是柜台/交互位置；货物靠订单经济锁互斥，不对未 Spawn 的柜内衣物错误地发起地图预约。失败则 Cancel，资金与经济预订同时释放。两类预约必须分别成功，不能互相替代。
4. **到店复核**：重新检查 Pawn 状态、报价版本、物品仍存在/可达/合法、预订归属、实际数量和穿戴适用性。地图缓存不能替代这一步。
5. **交付/提交**：单件衣物先确定合法交付路径与回滚位置；在一个不 yield 的服务调用内执行实际转移、余额借贷、产权改写、挂牌售出和订单 Committed。将每步确认位记在订单中；服务不得在中间向其他订阅者发成功事件。
6. **补偿**：如果物理转移失败，撤销准备；若发生部分修改异常，则按确认位还原实际 Thing 位置/持有者、产权、双方余额与冻结额。无法完整复原时标记 RecoveryRequired，冻结该订单关联资产及金额并上屏，不再自动重试扣款。
7. **公布**：全部确认后发布不可重复的成交 Receipt，刷新读模型。若后续穿戴失败，只改变使用结果，不重新收费。

正式实装须把物理交付作为独立适配器，覆盖地面、背包和装备的实际容器行为；本手册没有把“调用 Wear”当成上述事务的替代。首版只实现已验证的单件衣物路径，其他类型返回 UnsupportedAsset。

### 5.2 恢复和去重

* 命令幂等：`idempotencyKey` 相同且负载一致，返回原结果；相同 key 不同负载拒绝。工资使用 `completionId`，成交使用 `orderId`，退款使用独立退款序号并引用原成交。
* 保存中断：Prepared/InTransit 且引用有效、未超期，可恢复或按明确政策取消；AtCounter 未提交先核对确认位；Committed 只有通知未完成时重发带相同 ID 的通知，不再次转账。
* 原版预约不作为长期账本真值：读档重建/核对，缺失时释放经济预订并重新规划；不无限保留资金。
* 循环完成 ID：不能用 `pawnId + tick + recipe` 去重，同一刻可能多次事件。适配器将一次真实捕获转成持久序列 ID；同一个事件的消费者重试才复用此 ID。重复补丁调用问题要在采集层用活动 Job/工单迭代令牌识别，不把新 ID 生成当万能去重。
* 有界日志：活跃订单、未结工资和未消费结果不裁剪。已关闭明细按保留策略归档为日汇总；过旧命令必须携带有效 epoch/revision，裁掉去重明细后拒绝旧 epoch 重放，不能让它重新付款。

### 5.3 必须始终成立的不变量

| 编号 | 不变量 |
|---|---|
| INV-01 | 所有普通账户余额、冻结额非负；冻结不大于余额；checked 运算溢出即拒绝 |
| INV-02 | 在没有显式发行/回收业务时，所有内部账户余额之和严格不变；首版不提供发行/贷款 |
| INV-03 | 同一完成事件至多一笔有效工资；同一订单至多一笔有效成交 |
| INV-04 | 同一单件资产最多一个当前所有者、一个活跃挂牌、一个经济预订 |
| INV-05 | 取消会释放资金和资产；提交后的取消不会再次退款 |
| INV-06 | 消费改善必须来自实际使用观察；钱包扣款不是 Need 增量 |
| INV-07 | UI、评分器、JobDriver 都不能直接写账户余额 |

## 6. 动态缓存与扫描预算

真值记录→索引→只读快照三层分开。账本索引按 accountId，产权按 Thing load ID/assetId，机会按 mapId+商品种类，活跃目标按 pawnKey。记录修订变动才刷新对应投影。

首版可配置初值：每 Pawn 常规决策间隔 1,500 ticks，按 ID 分桶；事件置 dirty 后最早 60 ticks 再评估；每次最多 16 个候选；商品索引低频一致性校验间隔 2,500 ticks，且分批而非每次全图重建。这些是工程预算草案，必须用实机性能验证。执行前的硬保护/资产检查不等待缓存刷新。

地图缓存只允许主线程访问游戏对象。以后若做后台评分，只发送纯值 DTO；后台线程不能遍历 map.listerThings、pawn.needs、DefDatabase 或写回游戏对象。

## 7. 配置和兼容边界

静态配置拟分 `EconomicPolicyDef`、`EconomicCommodityExtension`、`EconomicRecipeWageExtension`；类型名和 XML 不在本次注册。配置只描述白名单、用途、消费规格和工资档，实际价格政策/账户余额保存到经济根。扩展不存在则拒绝交易或走显式公共服务默认，不能推断为可售私产。

第一阶段不向所有 ThingDef 广泛注入产权 Comp。产权单一真值先集中于根记录，单件衣物以游戏引用关联；若以后加 ThingComp，它只保留索引/展示或明确迁移后的单一真值，不能再复制一份主人字段导致争用。堆叠物上线前必须完成拆分、合并、销毁、搬运、装入容器及地图迁移协议。

首版售货点另需一个保存真实物品的 `ThingOwner<Thing>` 容器（G13）。现有 `Automation/CompItemStorage.cs` 使用 ThingDef+count 平行表，不能保留单件衣物的耐久、品质、风格及产权，**不可直接用它承载个人商品**。柜台容器负责 Deep 保存真实物品；经济根只保存其引用。柜台销毁、拆除或卸载必须先撤销挂牌/预订，再按游戏容器规则释放物品，不能照搬现有抽象缓冲的销毁兜底。
