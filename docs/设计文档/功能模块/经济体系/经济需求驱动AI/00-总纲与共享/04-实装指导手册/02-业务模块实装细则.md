# 02 业务模块实装细则

以下契约均为拟议接口。代码中的英文类型、状态和错误码供拆分任务使用，正式登记前仍可调整；原版扩展依据 G01–G13 见[数据册](01-数据模型与源码依据.md)。金额、存档、不变量和 UI 命令规则必须继承公共契约。

## M01 Pawn 状态与机会采集

**责任**：将游戏对象转成有限、可复用、带版本的经济事实。只读采集，不产生目标、不扣款、不启动 Job。依赖 F01 和游戏适配器；依据 G03/G05/G10/G11/G13。

输入：候选 Pawn、当前地图、个人账户投影、合法商品索引、政策修订。输出拟为 `PawnEconomicSnapshot`：

| 字段组 | 必要字段 | 缺失策略 |
|---|---|---|
| 身份/版本 | pawnKey、mapKey、observedTick、snapshotRevision、policyRevision | 身份失效则 Unavailable |
| 执行保护 | drafted、downed、mentalState、playerForced、紧急需求/服务状态、scheduleAllows | 任一硬阻止标志阻止自主经济执行 |
| 实际需求 | food/rest/joy/comfort 的值和各自 Available 标志 | 缺失不填 0；评分禁用对应维度 |
| 衣物 | 已穿戴 itemId、部位/层、耐久比、质量、允许衣物政策、可替换状态 | 不理解的第三方衣物规格不参与首版 |
| 经济 | availableMinor、reservedMinor、收入汇总、应付收入、当前合同 ID | 应付工资不计入可花余额 |
| 机会 | 前 N 个 listingId、价格、资产规格、卖方、距离粗估、revision | 索引过期只标 dirty，不在 UI 全图重扫 |

实装顺序：建纯 DTO → 游戏线程适配器 → 账户/市场索引 → dirty 分桶刷新 → 调试投影。生理值只反映原版实际状态；距离初筛可用格距，执行前再做原版可达性/预约核验，不对每个候选完整寻路。

前端：个人页通过 RUIF `StatRow` 展示余额/需求，`StatTable` 展示有限商品，缺失原因用 `EmptyState`。完成标准：暂停游戏时 UI 重绘不采集地图；不存在 Need 不抛异常；跨图后旧机会不能执行；快照版本可追溯到观测刻。

## M02 需求缺口与偏好

**责任**：计算“为什么想改善”，输出缺口向量、紧迫度和保护标志。依赖 M01；纯 Domain，无 Pawn/RUIF/Harmony。原版需求事实依据 G05，经济效用公式自研。

拟议契约：`UtilityAssessment Evaluate(PawnEconomicSnapshot state, PreferenceProfile preferences, UtilityPolicy policy)`。

### 首版衣物效用

先以配置指定的一个必要衣物槽位为实验目标，统一固定规格、温度场景及合法政策。以耐久和合身/覆盖规则评估已有衣物的满意度，不能将所有衣物简单按市场价排序：

```text
condition = clamp01(hitPoints / maxHitPoints)
conditionUtility = clamp01((condition - unusableCondition) /
                           (satisfactoryCondition - unusableCondition))
currentUtility = 若无合法衣物则 0，否则按目标槽位规则求 [0,1] 满意度
gap = max(0, targetUtility - currentUtility)
```

`unusableCondition/satisfactoryCondition` 必须来自配置并校验后者大于前者。它们是模型阈值，不冒称原版自动购买阈值。温度防护、覆盖与衣物冲突先作为合法性限制；后续才加入多属性效用。

紧迫度 `urgency` 和偏好 `preference` 各为有限区间参数，例如 0–1、0.5–1.5；偏好影响合法候选排序，不能解除医疗/睡眠等硬保护。财富偏好使用“达到有限安全储蓄额的缺口”，达到目标后归零，禁止每次按财富总额线性奖励继续工作。

前端：目标详情用 RUIF `CapacityBar` 表达 gap，用 `StatTable` 展示需求维度及模型版本；食物/休息显示为“原版保护需求”，不产生私人购买必需品的强制要求。

完成标准：相同输入得相同输出；归一化没有 NaN/无穷/除零；衣物耐久改善时 gap 不增加；买到但未穿上时当前衣物效用不变；钱包增长至储蓄目标后财富缺口不再增长。

## M03 持久目标管理

**责任**：把一次缺口判断转成跨 Job、跨存档的有限目标；管理阶段、预算、超时和替代。依赖 M02/F01；依据 G01/G02，状态机自研。

首版目标类型 `AcquireApparel`、`ReserveSavings`。继续工作通常是实现衣物目标的方式，不再额外生成一个永远冲突的“赚钱”目标。每 Pawn 最多一个主消费目标和一个储蓄约束（可调范围限制）。

| 状态 | 进入条件 | 下一步 |
|---|---|---|
| Proposed | 有效 gap 超过启动阈值 | 绑定规格/预算并激活 |
| Active | 目标仍有效，有合法候选 | 交 M04 评估 |
| WaitingFunds | 可用余额不足 | 保留目标，继续原排班；工资事件置 dirty |
| WaitingSupply | 合法商品缺货 | 等库存事件/低频刷新；到期再替代 |
| Executing | 已有有效订单/Job | 不重复生成第二单 |
| AcquiredPendingUse | 买到但尚未穿戴 | 有限次请求原版使用，给出阻止原因 |
| Satisfied | 实际观察 gap 低于完成阈值 | 关闭目标，保留有界摘要 |
| Paused | 玩家/政策/健康/离图暂不允许 | 释放短期预订，保留意图 |
| Abandoned/Failed | 不支持、超时、明确拒绝或反复失败 | 冷却后才允许同规格重建 |

初值建议：启动 gap 0.25、完成 gap 0.10（滞回）；目标切换需要候选收益超过当前目标至少 0.15，或原目标失效；失败冷却 600 ticks。均为调参起点。原目标的已购资产、有效预订和已执行动作优先处理，不能因评分小波动丢弃。

拟议方法：`UpsertGoal`、`PauseGoal`、`OnIncomeSettled`、`OnListingChanged`、`OnReceipt`；禁止 UI 任意直接改状态。暂停是单独命令，取消执行中的订单须走 M05/M07 清理后再变状态。

储蓄约束先做“可消费预算”的规则，不自动等同于账本冻结：`spendableForGoal = max(0, availableMinor - protectedSavingsMinor)`。如果当前目标就是该储蓄的用途，按政策允许释放相应预算；不能让“攒钱买衣物”因为永久扣除全部目标储蓄而永远买不了。真正的订单冻结仍只由 M05 管理，避免同一金额扣两次。

前端：目标页 RUIF `StatTable` 显示阶段/预算/原因，详情 `StatRow`，暂停与重评估 `PrimaryButton`。完成标准：存读档保留 WaitingFunds；买到不立即 Satisfied；频繁小扰动不反复切换；不存在多个未关闭订单指向同一消费目标。

## M04 候选行为与评分

**责任**：在合法候选中选择下一步，输出可解释意图；不取得游戏预约、不写钱。依赖 M01–M03、M05/M06/M07 的只读接口。评分是自研规则，原版 Job 机制依据 G08/G10。

拟议契约：`DecisionResult Evaluate(GoalView goal, DecisionContext context, CandidateBuffer candidates)`。先硬过滤，再打分；每候选保留 `actionId/type/revision/expectedBenefit/cost/time/risk/rejectCode`。

### 首版候选和前置条件

| 行为 | 合法条件 | 意图结果 |
|---|---|---|
| Buy | 合法卖方、可穿戴商品、价/预算/可用余额足够、允许购物窗口 | 请求创建订单；不是直接成功 |
| ContinueScheduledWork | 有有效有偿合同、既有排班允许、预计未来有收入 | 保留目标并尊重现有劳动调度；不额外强制 StartJob |
| Save | 未来收入有望覆盖差额，等待仍有意义 | 进入 WaitingFunds；无阻塞 Job |
| Defer/Abandon | 缺货、收益不足、规格不支持或到期 | 暂缓/关闭并记录原因 |

PublicUse、SelfCraft、Sell 自第二期加入。若公共衣物政策明确提供同等免费装备，必须作为合法替代；不能为了制造消费而隐藏公共供给。SelfCraft 需说明原料付款和产物归属，避免使用公共材料制成私产再卖回公共账户。

### 同尺度评分草案

```text
benefit01 = clamp01(行动预测可降低的目标缺口)
price01 = min(1, priceMinor / max(budgetReferenceMinor, 1))
time01 = min(1, estimatedActionTicks / max(timeReferenceTicks, 1))
risk01 = clamp01(失败概率或风险的配置估计)
score = benefit01 * urgency * preference
      - wPrice * price01 - wTime * time01 - wRisk * risk01
```

`budgetReferenceMinor/timeReferenceTicks` 来自稳定政策和收入窗口，不随每个候选任意变化。权重非负；硬禁用候选不允许靠高收益抵消风险。时间只计本动作新增成本；在原排班内“继续工作”与“等收入”必须比较同一规划时域，不将整件未来衣物收益同时重复记在每个中间动作上。

第一版对 Wait/Continue 使用明确阶段规则：余额不足且收入路径有效→WaitingFunds；够钱才比较合法购买与继续持有资金。尚未实现多步预测前，不声称已求得跨日最优计划。并列得分用稳定 actionId 排序，避免随机抖动。

前端：目标详情 RUIF `StatTable` 分列收益、价格成本、时间成本、风险、总分与拒绝理由；不要只显示“AI 认为最好”。完成标准：非法动作永远不被选；同输入与版本下决策稳定；所有候选被拒绝时返回 NoLegalAction；钱包再多也不能覆盖硬保护条件。

## M05 钱包与事务账本

**责任**：内部金额唯一真值与转账入口。依赖 F01；G01/G02 支持存储方式，货币制度和事务协议自研。

拟议服务：`GetAccountView`、`PrepareTransfer`、`CommitTransfer`、`CancelTransfer`、`RefundPurchase`。写操作统一接收 `commandId/expectedRevision/reason/businessId`；返回 `Success/AlreadyApplied/Rejected/RecoveryRequired` 以及稳定错误码。

实现步骤：

1. 用 `long` 建 Money 值对象及 checked 运算；禁止把 float UI 价格直接乘减余额。
2. 建公共账户和个人账户；初始化资金只能由明确的新开局设置或玩家确认的政策操作产生，并记录来源；旧档默认不发行。
3. 实现双向转账与经济冻结，贯彻 INV-01..07。退款是逆向新账目，不能删原账。
4. 实现命令去重、业务去重、负载冲突拒绝、单调序列。
5. 实现保存迁移、未完成事务恢复、断言和有界日汇总。
6. 最后开放 M06 工资和 M07 成交，不允许各模块保留第二套可写 Wallet。

错误码至少：InsufficientFunds、RevisionConflict、DuplicatePayloadConflict、InvalidAmount、Overflow、AccountUnavailable、RecoveryRequired。可用余额、冻结、工资应收分栏，欠薪不能花。

前端：个人页 RUIF `StatRow` 与分页 `StatTable`；总览显示账户合计和异常单数；Error 用 `AlertBanner`。默认不提供“随意设置余额”按钮；调试注资必须独立开发工具并有来源记录。

完成标准：所有转账严格守恒；同一命令重复 100 次只生效一次；取消与成交竞争只有一个终态；读档重放不重复扣款；极大金额溢出有拒绝结果；账本明细裁剪后旧 epoch 不能再次支付。

## M06 劳动合同与收入结算

**责任**：把已发生、符合合同的劳动事实转成工资应付和有限资金转账。依赖 M05、既有车间服务；依据 G09/G10/G12。

**首版采用固定计件工资。** 原因是本项目已有 `Capture/Patch_BillProduction.cs` 完成迭代捕获，可以在其 Application 调用链扩展事实出口。`ChronicleGameComponent` 的 120 tick 工作样本用于统计；站岗、去工作台、等原料和 StartJob 都不代表完整计件，不作为发薪权威。

| 事实/政策 | 首版规则 |
|---|---|
| 合同资格 | 玩家自由成年殖民者，绑定有效工坊/地图、雇主账户、白名单配方；不能对全地图所有制造回调发钱 |
| 发薪单位 | 一次真实配方完成迭代；一次迭代产出多件仍只发合同规定的一次工资 |
| 产品获取 | `GenRecipe.PostProcessProduct` 为每个产品观察；完成回调的第二参数是原材料，不能当商品入库 |
| 完成定义 | 合同明确“完成加工”即有工资资格；不把随后搬运失败当作未工作，也不凭空保证产品已入售货点 |
| 异常配方 | 可能生成失败产品、派生 Bill 覆写或绕开基础捕获的配方，首版不纳入白名单 |
| 预算 | 合同设置有限计件承诺上限；已付、应付及已接受的在途迭代共同占用合同额度。该额度不是现金余额，也不自动等于账户冻结；首版不承诺全额预存工资 |
| 余额不足 | 已被有效合同接受并完成的迭代记录一次 Payable，禁止重复追加；暂停新增有偿承诺；注入合法预算后按规则补付。合同额度不足时不再接受下一迭代，不把无合同完成事后追认为欠薪 |
| 停用模块 | 停止新合同/新结算资格；已经确认的应付保留并明确展示，不凭空抹除 |

适配步骤：①在 Capture 层保留轻量守卫；②由 Application 接收 `ObservedCompletion`；③核验有效合同与实际工坊；④绑定一次迭代令牌并分配 completionId；⑤创建应付并交 M05；⑥向 M03/M09 发布已支付或欠薪结果。补丁入口不直接减余额，不复制既有 Prefix/Postfix。

事件 ID 的验证是 R0 必做项：重复观察同一次完成应归一为同一 token；持续工单下一次迭代必须是新 token；不能只用 recipeDefName 或游戏刻去重。对派生 Bill 的覆盖需逐个证明，不能因为基类方法存在就宣称兼容所有 Mod。

劳动开始/接受时登记合同修订及在途迭代额度，取消未完成则释放这部分额度；完成后额度归入 Paid 或 Payable。停止新承诺不撤销已接受迭代的合法收入资格。现金发放时仍以 M05 可用余额为准，欠薪是负债记录，不可当成买方钱包余额。若后续改为预存工资制度，应新增账本预算预留类型并迁移，不把合同额度再叠加到已冻结金额上。

后续时薪必须增加“实际有效劳动区间”适配，识别加工 toil、暂停、搬运及失败，并规定计薪口径；不把固定抽样统计事后乘工资率当可靠结算。

前端：政策页 RUIF `Checkbox` 开关，`StatTable` 展示合同/预算/应付，`PrimaryButton` 提交修订；个人页显示已付/待付。完成标准：无合同不发薪；取消未完成配方不发计件工资；多产物不多发；预算耗尽不印钱；同回调重试不重发；工资失败不破坏原版配方完成。

## M07 产权、商品与固定价市场

**责任**：合法卖方、真实商品、挂牌、预订和交付。依赖 M05/F01；依据 G03/G04/G06/G13。个人产权不是原版 Faction 的别名。

### 三个正交维度

```text
Ownership: Public | Personal(ownerPawnKey)
Listing: NotListed | ForSale | Suspended | Sold
Reservation: None | Reserved(orderId, expiresTick)
```

私人资产可以 ForSale，同时被预订；公共资产也可挂牌。不能继续使用 Public/Personal/Reserved/ForSale 四选一枚举。首版公共原料和常用生产资料保持公共，不让制造者自动占有产品。

### 售货点与真实物品

首版增加一个受控售货点，容器保存真实单件衣物；柜台 Def 和美术复用/新增须正式登记后实装。拟用 `ThingOwner<Thing>` 与 `IThingHolder`；**现有 `CompItemStorage` 只存 Def+count，不能拿来装具有品质/耐久的衣物**。

上架流程：玩家选择公共衣物→合法搬入售货点容器→保留原 Thing 身份→生成公共所有权记录和挂牌→低频/事件刷新索引。未实际入柜的物品不能处于 ActiveListing。普通装备 AI 不会在地图衣物列表中取得柜内商品；柜台锁只防止本模块订单竞争，不宣称防住任意第三方强制取物。

实际入柜/出柜须区分 Spawned 地面物和已有 ThingOwner 持有物：原版 `TryAddOrTransfer` 不是任意 Map↔容器转移的万能入口。上架搬运适配器负责预约、实际取物/Despawn、容器接收、失败复原；交付则选择合法的持有容器或放置位置并保留回滚条件。对应源码见 `ThingOwner.2.cs`，R0/R2 用真实物品验证，不能只测试记录字段变更。

`IEconomicStockAccess` 草案职责：检索持有物、验证资产身份、原子取出/回滚、保存、销毁释放。柜台毁坏/卸载、玩家取货、第三方移动物品都必须使相关挂牌失效并取消提交前预订。取出商品要验证余额/订单，由服务统一执行；不能用“解除原版禁止标记”代替成交。

固定价来自内部配置与当前政策修订，读取 MarketValue 只作对照；两列明确标注货币/口径。`listingRevision` 变化时旧报价重新校验，不能暗中扣新价。首版买方购买后获得单件产权；衣物保持真实品质、材料、风格、耐久和标识。

首版**不提供全面禁止其他 Pawn 使用私物的产权执法**。交易库存采用受控容器避免免费取货；已交付物品继续尊重原版 outfit/forced 状态。若要实现全殖民地私物禁止拿取，单列权限适配工作包并验证原版与第三方装备/搬运入口。

前端：市场页 `SearchField`、分页 `StatTable`、详情 `StatRow`、挂牌/暂停/撤回 `PrimaryButton`。完成标准：两个 Pawn 竞争只有一个订单预订成功；柜内衣物不被普通自动换装免费取得；移除柜台取消订单；读档保留真实物件属性；买到但穿戴失败不二次扣款。

## M08 Job 执行与行为仲裁

**责任**：将已批准经济意图转成短时、可中断的游戏行为；执行前复核保护和事务状态。依赖 M03/M04/M05/M07，依据 G07/G08/G10/G12。

拟议类：`JobGiver_EconomicAction : ThinkNode_JobGiver`、`JobDriver_EconomicPurchase : JobDriver`。JobDriver 保存 orderId，目标为售货点/交互位置；长期目标仍在 M03。

购物 Job 分段：验证订单→预约柜台→走到合法交互位置→有限交互→调用 PurchaseService 提交交付→发布 Acquired→结束；穿戴走独立原版动作/适配。每段失败释放原版预约；未提交的订单释放经济锁和冻结。`Cleanup(JobCondition)`、失败条件和读档恢复都走同一个幂等取消入口。

硬保护检查至少覆盖：征召、倒地、精神状态、玩家强制 Job、紧急食物/休息、医疗/救援/灭火等既有保护服务、不可用地图、政策禁用、正在执行另一订单。阈值尽量复用项目已有语义，不另造能覆盖所有原版紧急性的一个布尔推测。

### 调度策略必须分阶段验证

* R0 可用 PostMain 做“空闲时购物”机制探针；只能证明空闲消费。
* R3 若要覆盖正常忙碌生活，需证明许可窗口中的经济行为能够被自然决策点选择。原版主行为内有 priority sorter；应针对确切 XML 节点添加有限经济分支，设计其 `GetPriority` 与硬保护/排班策略，并保存实际 XPath 命中证据。
* 不直接将经济 JobGiver 塞进 PreMain 宣称完成；不使用新的高频 `CheckForJobOverride/StartJob` 全局抢占；不复制完整 Humanlike 树。
* 若 R0 无法证明安全且可达的入口，R3 必须标记“调度入口未通过”，不能用更高收入/更高 UtilityGap 掩盖。

首版继续工作由现有车间调度控制，储蓄无 Job，换岗默认无权。玩家强制指令和既有重要服务保留。经济分支只决定允许窗口中的购物，不修改全部 workSettings。

前端：个人/目标详情 RUIF `StatRow` 显示 Executing 或 Blocked 原因，`AlertBanner` 提示恢复所需操作。完成标准：突发征召立即停止新经济执行且正确清理；中途吃饭/救援仍正常；忙碌 Pawn 在允许窗口能实际购买；无无限等待/反复重启；取消再读档不重复收费。

## M09 结果反馈与可解释记录

**责任**：区分经济结果和实际生活结果，驱动重新采集与目标收敛。依赖 M01/M03/M05/M06/M07/M08/F01；原版使用/Need 机制依据 G05/G10。

事件分层：

| 事件 | 可确认的事实 | 不能推导 |
|---|---|---|
| WagePaid | 账户完成工资转账 | Pawn 当前需求已改善 |
| PurchaseCommitted | 钱、产权、交付结果已确认 | 已穿戴/娱乐提高 |
| ApparelEquipped | 原版 tracker 确认实际穿戴 | 所有维度都已满足 |
| ConsumptionObserved | 真值重采样发现实际使用/需求变化 | 单凭时间先后证明全部因果 |
| ActionFailed | 阶段/错误码明确 | 无条件把目标归零或退款 |

反馈记录绑定 goalId/orderId/resultId 和前后 snapshotRevision。衣物目标先验证指定槽位/规格被新衣物满足，再重新计算 gap；娱乐/服务后续使用消费开始/结束证据与实际 joy 值，不能把购买电视直接映射为 joy 加满。

执行顺序：去重 Receipt→标记相关事实 dirty→M01 重采样→M02 重算→M03 更新阶段→生成解释投影。失败次数用于冷却/替代，不用于永久剥夺经济行为。只保留有界近期轨迹与汇总，不逐 tick 记所有 Pawn 状态。

前端：总览近期结果表，个人目标下显示“缺口→候选→选择原因→付款→获得→使用”的单行阶段卡/统计行；使用 RUIF 组件组合，不自制状态机控件。完成标准：每次有效反馈只消费一次；付款失败不生成成功消费；买到未穿戴清晰可见；原版其他行为改善了需求也能使目标结束，无须归功于本模块。

## 模块间最小事件契约

| 事件草案 | 发布方 | 订阅方 | 幂等/失效要求 |
|---|---|---|---|
| PolicyChanged | Application 政策服务 | M01/M03/M04/M06/M07 | policyRevision；停用立即阻止新意图 |
| ProductionCompleted | Capture→Application | M06，必要的产品关联器 | completionId；工单迭代令牌 |
| WageSettled | M06/M05 | M01/M03/M09 | transactionId；欠薪与已付分开 |
| ListingChanged | M07 | M01/M03/M04 | listingId+revision；旧报价失效 |
| PurchaseCommitted | M07/M05 | M03/M09 | orderId；提交后通知可重发 |
| UsageObserved | 游戏使用适配器 | M01/M09 | resultId；实际 tracker 证据 |
| ExecutionCancelled | M08 | M03/M05/M07/M09 | orderId+阶段；Cancel 可重复调用 |

生产事件可以在主线程同步服务调用中传递，不必先造全局事件总线。事件发出前先提交真值；订阅者异常不能回滚已完成的原版生产，也不能使钱部分转账。
