## 3. R0：必须先做的两项机制探针

### 3.1 真实工资事实探针

在本地开发存档放置一个有效车间、一个操作者、一条白名单工单。观察以下输入：配方开始、加工中断、一次完成、多产物、连续两次迭代、读档继续。记录活动 Job/工单身份、捕获顺序、是否到达基础完成回调、product 事件数量。

退出标准：明确一次迭代令牌如何建立/结束；同一次重复观察归一；同一 tick 多次有效完成不被错误合并；完成回调确实在工资所定义的劳动完成点。没有证明前只记观察日志，不发钱。

### 3.2 安全消费调度探针

同时测试空闲和正常忙碌 Pawn。PostMain 分支验证短 Job/预约/清理；再在目标游戏 Humanlike 主树中核对 priority sorter 与非紧急经济窗口。

原版参考位置：`Data/Core/Defs/ThinkTreeDefs/Humanlike.xml` 的 MainColonistBehaviorCore 与 PostMain；`SubTrees_Misc.xml` 的食物/休息/娱乐/工作 sorter；本地源码 `ThinkNode_SubtreesByTag.cs` 的插入优先级排序。正式 XPath 必须以实际文件和目标节点为准，记录命中数量并检查其他 Mod 的 Patch 结果，不能从本手册复制一个未运行的 XPath。

退出标准：①空闲可购物；②正常忙碌者在允许的时段自然获得执行机会；③紧急吃饭、睡眠、医疗、救援、灭火、征召、玩家强制命令保留；④没有高频全局抢占。做不到②时只能验收“空闲经济行为”，R3 不得宣称完成自主消费模型。

## 5. 自动验证矩阵

只为关键行为和不变量建立有效测试，不照抄每个 getter，也不为本次文档编辑扩建运行测试套件。

| 编号 | 测试输入/动作 | 必须验证 |
|---|---|---|
| A01 | 金额 0、负数、上界；重复转账；余额不足 | 非法金额拒绝、checked 溢出拒绝、总额精确守恒 |
| A02 | Prepare→Cancel、Prepare→Commit、Commit→Cancel | 冻结释放；终态单一；提交后取消不退款 |
| A03 | 同 commandId 同/不同负载；已关闭明细裁剪后重放 | 相同返回原结果；冲突拒绝；旧 epoch 不再执行 |
| A04 | 在订单各状态序列化/恢复，并打断每一修改步骤 | 无双扣/双付/丢物；确认位和 RecoveryRequired 可解释 |
| A05 | 同完成事件重复、下一迭代、多产物、无合同 | 只为合法一次迭代付款；多产物不倍增工资 |
| A06 | 缺 Need、无 Pawn 引用、缺 Def、高版本 schema | 有效缺失处理；不当空账本覆盖；无静默资金销毁 |
| A07 | 更便宜但非法商品、同分候选、已达储蓄目标 | 非法永不入选；排序稳定；财富欲望有上界 |
| A08 | gap 阈值附近波动、购买未穿戴、免费公共替代 | 不抖动；不提前完成；公共替代合法纳入 |
| A09 | 过期 UI 快照、双击、政策草稿包含一项非法值 | 服务重检；只提交一次；政策整体拒绝而非部分应用 |
| A10 | 商品被取走/柜台销毁/地图卸载、订单过期 | 挂牌失效；经济冻结/原版预约均清理 |

## 6. 游戏内验收矩阵

保存基线存档和逐场景复现说明；不要以单张 UI 截图代替行为证据。

| 编号 | 场景 | 预期/记录 |
|---|---|---|
| G-T01 | 1 个工人、工资 20、衣物 60、个人 0，连续完成 3 次 | 前两次 WaitingFunds；第三次在许可窗口付款；双方余额符合夹具 |
| G-T02 | 中断加工、缺原料、无可执行工单 | 没有完成则无计件；正常让出给原版选择，无空转发薪 |
| G-T03 | 公共工资预算不足、后续补充合法预算 | 应付清晰、不增发；补付一次，下一次工资 ID 独立 |
| G-T04 | 两人同时购买同件衣物 | 一个预订成功，另一个得到 Sold/Reserved；总钱/总物均不变 |
| G-T05 | 路上征召、吃饭、需要治疗或灭火 | 保护行为优先；提交前取消清理；不反复强拉回店 |
| G-T06 | 玩家强制做工/穿戴/拿走商品 | 不覆盖强制行为；挂牌及时失效，订单不扣错钱 |
| G-T07 | 买到后因 outfit 限制/身体条件变化不能穿 | 保留已购资产；显示 AcquiredPendingUse/具体原因；不再收费 |
| G-T08 | Prepared/InTransit/Committed 后分别存读档 | 没有重复付款；引用、产权、目标恢复一致 |
| G-T09 | 关闭经济模块，再开启；地图移除；Pawn 离队/死亡 | 无新自主执行；未结记录保留；没有默认继承/追溯发薪 |
| G-T10 | 普通自动换装、搬运在柜台旁持续运行 | 柜内商品没有免费被普通装备 AI 取得；上架保留品质耐久 |
| G-T11 | 持续忙碌一个游戏日、许可购物窗口存在 | 能取得实际购买机会；只通过空闲案例不能替代此项 |
| G-T12 | 五个页面、各种就绪态、窄窗/不同 UI 缩放、中英文长文本 | 无截断关键信息；按钮真实响应；只读状态不能写账 |

## 7. 性能与容量验收

先记录无经济 AI 的同档基线，再分别测 10/50/100 名合格 Pawn、少量/较多商品、页面关闭/打开。记录实际 TPS、硬件、Mod 列表、地图规模、持续时间、采样器设置；不能按游戏刻预算推断现实秒性能。

建议观测：每 tick 经济主线程平均/分位开销、单次决策候选数和寻路次数、每分钟 Job 重启数、UI 每次快照构建次数与 GC、活跃订单数、日志/存档增量、账本守恒异常。初始目标可以定为相同场景 TPS 下降不超过基线 5%，但这是待评估目标，不是已达标的承诺；接近饱和或 TPS 不稳定时直接比较耗时和采样轨迹。

对所有集合给出上界和清理策略。不能为了内存有界裁掉未结订单/欠薪；也不能永久保留所有已关闭决定的完整候选快照。100 Pawn、1,500 tick、16 候选只能估算吞吐量，不能证明寻路和第三方成本可接受。

## 8. 第三方兼容验收

逐项增加，先测单独本 Mod+RUIF+必要 Harmony，再测实际组合。候选包括 Free Will、Work Manager/Work Tab、Colony Coupons 2/Smart Pawns、Hospitality/Gastronomy、外部价格 Mod；具体工坊来源见[证据册](05-证据索引与验证记录.md)。

必须明确唯一职责：谁维护工作优先级、谁拥有钱包真值、谁收款、谁决定价格。首版不与另一工资/钱包 Mod 同时接管相同人群；可检测后提示“此人群经济接管未支持”，不得双重发薪/收费。可选适配器只提供机会/服务，未拿到稳定公开 API 前不反射写它的私有余额。

补丁执行关系依目标 Mod 的 Harmony ID 和实际 patch info 核验，不把 loadAfter 当 before/after。树节点插入后的最终 XML 和异常处理都要有证据；一个基类 Hook 通过不等于所有派生类型兼容。

## 9. 正式构建与发布门槛

本次只编译文档示例，**没有执行下列正式构建、测试、部署或发布**。未来实装在对应工作包完成后：

1. 重新采集 DLL/源文件证据；所有新增调用与目标版本匹配。
2. 构建主工程并执行变更相关领域/车间/账本测试；报告自动检查和游戏验证分别通过哪些项。
3. 检查 Def/XPath、语言键、程序集引用、Compile glob、依赖、保存迁移与补丁档案。
4. 在干净测试部署目标运行完整游戏矩阵；RUIF 版本身份、个人经济闭环与存档恢复必须有证据。
5. 使用项目既有部署脚本和发布检查流程，核对实际被游戏扫描的 `Mods/殖民地综合管理系统`；源码工作目录本身不是部署结果。
6. 发布说明如实写支持人群、首版计件口径、受控售货点、私物权限边界及未支持玩法。

不能把“文档示例编译成功”“结构检查通过”或“主工程构建绿色”替代 R3 的完整游戏闭环，也不能在预算/物理交付/调度入口尚未通过时宣称可发布。
