# 06 微观机构与场所工具

版本 0.2 补充 · 2026-10-08 · 设计状态：待实装。

本册补齐“需求在哪里被满足、合同在哪里形成、服务由谁实际完成”。[九个核心模块](02-业务模块实装细则.md)继续提供规则和账本，本册新增 F03 机构服务基础层，将它们落到地图上的场所、设备、人员、队列和实际结果。所有新 Def/类/事件名均是拟议名称，本次没有注册运行内容。

## 1. 机构的最低构成

每个机构都必须填写：**实际场所、控制者、设备、岗位、服务对象、服务清单、营业条件、容量、价格与付款方、执行流程、完成证据、失败处理**。只增加一个总控页签或一个岗位名称，不算机构完成。

机构与建筑不是一一对应：一个公共服务大厅可以共用公告板、签约桌、工资查询台；体检必须另外有实际检查位与医生；工坊管理台连接既有工坊。初期不要求每个机构都新建独立大型房间和整套美术。

现有 `medical_center/logistics_center` 是预留系统中心，见项目[既有变更记录](../../../../../../changelog/v1.4.x_2026-10-06_医疗与内务降级为预留中心.md)。本册的“体检中心”等指拟议地图服务机构，不等于恢复上述中心的 Provider/运行状态。先通过经济机构读模型展示；是否启用更大系统中心另随正式功能实装处理。

## 3. F03：共用机构服务底座

### 3.1 实体与字段

| 记录草案 | 必要字段 | 规则 |
|---|---|---|
| `InstitutionRecord` | institutionId、类型、mapKey、anchorThing、ownerKind/ownerId、controllerId、accountId、营业时段、状态、revision | 资产主人、经营管理者和收款账户分开；引用失效暂停营业 |
| `ServiceDefinition` | serviceKey、requiredCapabilities、requiresStaff、capacity、durationBudget、收费触发点、产出类型 | 静态 Def 配置；不保存 Pawn 钱包 |
| `StaffAssignment` | institutionId、pawnKey、roleKey、资格、班次、contractId、revision | 名册上的人不等于当前可服务；执行前检查到岗/健康/紧急任务 |
| `ServiceOffer` | offerId、institutionId、serviceKey、费用、payerPolicy、有效期、revision | 给 M01/M04 的可选择机会；不可用机会不能进入可执行候选 |
| `Appointment` | appointmentId、clientKey、providerKey/待分配、slotKey、预约刻、截止刻、状态、orderId | 一个客户端一次只有一个同类活动预约；容量锁与资金冻结分开 |
| `ServiceOrder` | orderId、机构、服务、付款方、收款方、金额、预约/目标、阶段、结果、revision | 继承 M05 的幂等、补偿和恢复；不能另建第二套钱 |
| `ServiceReceipt` | receiptId、orderId、client/provider、完成刻、有效结果、证据/报告 ID | 去重后触发反馈；柜台点击不能直接产生服务完成 |
| `PositionOffer` | positionId、雇主组织、真实工坊/岗位槽、名额、工资、班次、技能/能力要求、revision | 必须绑定真实缺岗和预算；公告板不是无限生成岗位的资源 |
| `EmploymentApplication` | applicationId、pawnKey、positionId、状态、有效期、候选版本 | 申请/保留名额/签约/报到分别记录 |
| `WorkFitnessReport` | reportId、pawnKey、服务单、检查刻、有效期、已公开状态摘要、能力数值、规则版本、适配建议 | 只记录检查时事实；上岗仍重新核对即时可工作状态 |

这些记录由 F01 单一保存根管理；地图索引只做派生缓存。建议新增保存集合 `peaInstitutions/peaAppointments/peaServiceOrders/peaServiceReceipts/peaPositions/peaApplications/peaFitnessReports`，正式发布前登记 schema 迁移；本次未改变实际存档。

### 3.2 营业条件和容量

可提供服务 = 机构启用 ∧ 锚点存在/可达 ∧ 设备有效 ∧ 营业窗口允许 ∧ 服务容量可用 ∧ 必要人员可服务。电力、物资、房间要求只有服务 Def 显式需要时才加入；不能将显示“营业中”当作执行许可。

自助模式必须明确 `requiresStaff=false`，只支持公告查询、电子签约、工资查询或已实现的自助售货。体检等需要提供者参与的服务不能靠自助模式跳过医生。医生和客户各有自己的有限 Job，通过同一 appointmentId 在检查位会合，不能让一个 Pawn 的 JobDriver 直接操纵另一个 Pawn 的 jobs。

等待采用有界队列和预约时间窗：客户没轮到就继续正常生活；临近服务时间才生成前往 Job。到场后只等有限时长，医生被征召/抢救优先时暂停或改期，解除短期预约；不能让客户等一整天而错过吃饭/睡眠。

### 3.3 服务收费协议

`Requested → SlotHeld → Arriving → InService → ResultReady → Settled → Closed`

选定付款方后预留费用，到实际服务结果可提交时结算。因机构无医生/关门/取消/未完成而终止，释放费用和容量；首版不扣取消费。结算失败时保存 ResultReady 与已有结果，恢复后提交同一 orderId，不重复检查或收费。报告生成与钱的修改走同一服务协调器，不能在 UI 中各自创建。

公共支付、雇主支付、个人自费三种 policy 可选；一个订单只选一个主要付款方，首版不做多方分摊。公共机构的付款账户和收款账户相同时，不制造虚假自转账流水；记录免费/内部供给结果及实际消耗。医生工资若另付，使用独立服务完成 ID 和合同，与客户服务费区分。

## 4. I01 劳务服务站：可见的找工作过程

### 4.1 最小场景

一块招聘板绑定两个真实工坊岗位：纺织工与搬运/维护岗位。A 阶段仅启用已接入制造计件的岗位；其他岗位公示为未开放，不能为了例子给尚未验证的劳动发薪。公告显示雇主、工坊、班次、计件价、技能门槛、缺岗数、预算状态和产品归属。

工具草案：`PEA_RecruitmentBoard`（自助公告锚点）、`PEA_ContractDesk`（签约交互点）、既有 workshop/岗位槽。拟议动作：`BrowsePositions/SubmitApplication/SignEmployment/ReportToWorkshop`；名称未注册。

### 4.2 业务流程

1. 雇主控制者发布岗位，校验实际岗位槽、工资合同规则和有限预算；没有空缺不能生成有效公告。
2. Pawn 因缺收入、原岗位失效或换岗收益足够而查询公告。技能、工作禁用、排班冲突、通勤和有效健康要求先过滤。
3. 对合法岗位比较同一时域的预计收入、通勤/培训时间、偏好和已记录欠薪情况；计件价不是保证每小时收入。公告明确固定计件口径，不伪造“精确时薪”。
4. 提交申请并短期保留一个真实名额；两个候选竞争时只有一个能保留最后一岗。
5. 到签约桌确认有效版本，产生劳动合同及拟分配岗位；由既有车间服务尝试分配。分配失败不生成“已就业”结果。
6. 合同与排班分配通过协调器一起确认；跨服务部分失败进入待恢复，保留/撤回原分配有记录。到工作地点报到后才显示已上岗。
7. 后续劳动完成事件按合同付款。退出/转岗只在安全边界处理，不从正在进行的医疗/灭火/玩家强制任务中抢人。

A 的基础签约可由玩家发起；“Pawn 自主换岗”是独立验收能力。开放它需要显式 `AllowEmploymentChange` 政策、原岗退出规则、收益滞回与冷却。不能将旧版“继续原排班工作”标为已经会找工作。

### 4.3 接受后的社会关系

关系记录至少可回答：谁雇用了谁、在哪个工坊、谁指派岗位、工资由谁支付、生产设备/原料/产品归谁、合同到期/欠薪怎样处理。默认公共雇主可以先落地；私人经营/合作社经营需要生产单位产权与分配规则另行实装，不由公告标签自动形成。

完成标准：至少一名 Pawn 经公告申请→签约→真实分配→报到→完成劳动→收到工资；岗位已满/预算撤销/读档/主动退出不会形成重复合同或幽灵员工。

## 5. I02 体检中心：把健康变成有时效的服务结果

### 5.1 工具、人员与边界

最小工具：挂号锚点 `PEA_ExamReception`、绑定实际位置的 `PEA_ExamStation`、报告查询台；初版检查位可复用原版床/检查座的交互能力，不能直接将占用急救床当商业检查槽。医生岗位读取原版 Medical 技能，受原有医生排班与重要医疗任务约束。

首版服务为“岗位能力检查”：完成一次真实到场交互后，生成已公开健康状态、行动/操作/意识等配置能力的快照与岗位适配建议。不是全套疾病诊断系统，不自动治疗、不自动增加健康值，也不承诺发现隐藏疾病。

### 5.2 数据依据

| 需要的数据 | 已核验的游戏入口 | 使用方式 |
|---|---|---|
| 当前能力 | `Verse.PawnCapacitiesHandler.GetLevel(PawnCapacityDef)`、`CapableOf` | 读取能力及对应 Def 规则；不将所有能力一律 clamp 到 1 |
| 已公开伤病 | `pawn.health.hediffSet`、`Verse.Hediff.Visible` | 只显示允许公开的当前伤病；不调用 SetVisible 揭露隐藏状态 |
| 倒地/死亡 | Pawn/HealthTracker 的 Dead、Downed | 不适合常规检查时取消/转原版医疗；原版急救优先 |
| 岗位可做性 | `Pawn.GetDisabledWorkTypes(bool)`、`WorkTypeIsDisabled(WorkTypeDef)` | 原版禁用工作是硬条件，不靠合格报告解除 |
| 医生/求职者技能 | `Pawn_SkillTracker.GetSkill(SkillDef)`、`SkillRecord.Level/GetLevel(bool)` | 医生资格、岗位技能门槛；无技能 tracker 标为不支持 |

这些入口已在本机 1.6 DLL 中取证，见[接口证据](evidence/本机接口证据.json)。公开组件与分段执行机制参考 [Custom Comp Classes](https://rimworldwiki.com/wiki/Modding_Tutorials/Custom_Comp_Classes) 和 [Job 教程](https://rimworldwiki.com/wiki/Modding_Tutorials/Code_MendingJob)。它们不提供“自动体检报告”API；报告、预约和收费是本 Mod 新业务。

### 5.3 一次体检如何发生

1. 个人健康目标，或启用体检要求的岗位，产生检查请求。岗位强制要求的检查默认由雇主/公共预算支付，避免未就业者因没钱无法入职。
2. 机构提供可预约的医生与检查位；预留容量和费用。缺医生显示暂无服务，不原地创建无限等待 Job。
3. 客户在许可时段前往检查位；医生通过服务工作入口取得同一预约的提供者 Job。分别完成原版预约，再在同一预约令牌下会合。
4. 完成配置的有限检查时长；中断、位置不符、医生离场或设备失效则不生成已完成报告，不收完成费。
5. 在完成时重采样公开状态、能力、技能/工作禁用情况，保存报告和规则版本；ResultReady 后交 M05 结算。
6. 求职服务读取报告的观测时刻、有效期及所适用岗位规则。报告过期或身体发生相关变化，标记需复核；实际上岗仍读即时原版保护。

报告结果采用 `适配/需调整/当前不适配/信息不足`，同时列出具体工作要求和依据，不使用一个健康分数永久禁止所有就业。检查可能带来的效用是“获得有效报告/减少岗位信息不足”，不能伪装成原版健康恢复。

### 5.4 可复现的结算例

雇主同意支付 10 内部单位的入职检查费；求职者钱包为 0。检查完成后雇主→诊所账户转 10，求职者余额仍为 0；诊所再依独立服务计件合同支付医生 6，机构留存 4。所有账户合计守恒。取消检查则两笔工资/服务成交都不应凭空产生。数值仅为测试夹具，医生工资扩展尚未实装。

完成标准：有实际客户/医生会合和有限检查动作；报告只在完成后生成；中断不收费；钱不足不会卡住原版急救；存读档不重复检查/付费；失效报告不解除实时禁用工作。

## 6. 其余机构的落地合同

每类机构都复用 F03，但有不同的权威完成证据：

| 机构 | 应使用的完成证据 | 不能作为完成依据 |
|---|---|---|
| 门诊/药房 | 原版治疗实际结果、真实药物交付；各适配独立验证 | 医生领取了 Job、客户付款 |
| 培训所 | 实际训练进度/配方实践、既有资格流程结果 | 交钱就生成资格或每帧涨技能 |
| 工坊管理处 | 实际岗位分配、完成迭代、原料和产品流向 | 岗位名字、在车间站着 |
| 工资结算处 | M05/M06 已有账目与应付 | 到柜台领取就再次发一遍 |
| 商店/食堂 | 真实商品/食物交付；可选服务真实使用 | 商品列表里有库存、扣了钱 |
| 住房管理 | 具体床位的有效入住/退租与占用适配 | 购买了一个“住房券”就认定搬家 |
| 维修所 | 同一真实物品的加工完成和耐久变化 | 等待了指定 ticks，未检查材料/物品 |
| 配送站 | 正确目标持有/位置的送达结果 | 接单或搬运 Job 任意结束 |
| 福利/争议处 | 有限公共款转账、争议已核对的处理记录 | 创建申请即增发补贴，或自动删除欠薪 |

## 7. RUIF 前端具体增加什么

在原五页中新增“机构”入口/详情，可用一个 RUIF LayerSwitch 子页承载，不为十二机构各造独立通用 UI 框架。

| 区域 | 玩家看到/操作的内容 | RUIF |
|---|---|---|
| 机构列表 | 名称、位置、经营者、营业状态、在岗人数、队列/容量 | SearchField、分页 StatTable、选择 PrimaryButton |

## 8. 分期与实装验收

原 R0–R3 仍是核心账本/执行技术阶段；本册增加机构交付批次，互相标明依赖，不能以后台模块通过替代地图机构验收。

| 批次 | 必须交付的地图机构/流程 | 前置与验收 |
|---|---|---|
| A 基础生产关系 | 劳务站、工坊管理台、工资查询、供销商店，可共用公共大厅 | F03+原 R1/R2；先支持玩家发起签约，再验证自动申请；完成岗位→劳动→工资→消费 |
| B 体检与就业选择 | 体检中心、报告、付款方、医生服务计件；启用合法自主应聘 | A、双角色服务 Job/预约、M06 服务完成适配；完成求职→预约→检查→签约→上岗 |
| C 生活与专业服务 | 门诊、培训、食堂、住房、维修、配送、福利/调解 | 每种逐项验证真实完成、物资/容量/成本、失败补偿；不一次性全开 |

新增必测：无接待员/医生；医生临时急救；岗位最后一个名额竞争；过期公告；客户爽约；检查半途征召；报告过期/身体改变；付款方预算变动；机构锚点销毁；读档后双角色预约恢复；相同服务 Receipt 重放；关闭机构页后仿真仍运行。

**这套机构层的结果**：玩家能看到 Pawn 去哪里找工作、由谁检查、与谁签约、为谁生产、钱由谁支付、产品归谁，以及服务不足和分配规则如何影响下一次选择。所有效果都需要上述实际流程与证据，不能只添加装饰建筑或名册标签。
