# 07 需求驾驶舱与政策反馈

2026-10-08。状态：RUIF 前端与读模型已落地为经济窗口「需求观察」页；2026-10-08 追加 Pawn 检视窗「个人需求」页签（同一内容层的第二宿主，CHG-20261008-ECON-NEEDS-TAB）。本册其余愿景项（生活目标、预算、订单、需求驱动劳动）仍未实现。规则见[经济学优化 v0.8](../01-方案主线/经济学优化与需求可视化_方案_v0.8.md)，组件约束沿用[03-RUIF 前端](03-RUIF前端实装.md)。

## 1. 入口与信息层级

在现有系统中心的经济入口增加“需求”页并作为生活经营的默认总览，不新增独立主控窗口。Mod 设置只保留 v0.7 指定的制度总开关；需求观察不以收费开关开启为前提。若现有宿主导航有不同结构，实施时集中映射到同一页面，不复制需求真值。

### 1.1 已落地的宿主与扩展点（2026-10-08）

需求观察是**一个内容层 + 两个宿主**，不新增独立主控窗口、不复制需求真值：

| 宿主 | 入口 | 形态 |
| --- | --- | --- |
| 经济窗口 | 总控中心 → 经济 → 需求观察；机构 gizmo | `Dialog_PawnEconomy` 第 7 页签：名册分页 + 选中者详情（表格卡） |
| Pawn 检视窗 | 选中殖民者 → 「个人需求」页签（与「档案」「职业档案」同级） | **玩家向需求循环**：左列原版需求条（1:1 复用 `NeedsCardUtility.DoNeeds`）+ 右栏 RUIF 需求循环面板 |

- 内容层：名册页由 `NeedDashboardPanel`（宿主无关）承载全部测量与绘制；单人页由 `NeedsCyclePanel`（同族宿主无关面板）承载，**二者都只消费 `NeedDashboardView`**，不查询数据、不持有宿引用。
- 取数走同一只读门面：名册 `QueryNeedDashboard`、单人 `QueryNeedDashboardSingle`（`NeedDashboardBuilder.BuildSingle`，只读 1 个 Pawn）。
- **口径对齐（2026-10-08 需求循环批次）**：两条路径都接通影子规划目标——名册传 `targets: null + targetProvider`，单人 `BuildSingle` 补同义可选形参后由 `QueryNeedDashboardSingle` 传入 `QueryShadowTargets`。此前单人路径缺该通道，导致「目标 / 缺口」恒显示"未配置"。
- 单人页的分区靠 `NeedDashboardView.Planning` **结构化字段**（影子仲裁/预算/政策/机会行），不按显示文本匹配（GOV-009）；名册路径沿用旧口径把影子行并入 `Facts`，不改其消费方。
- 页签注入：`ChronicleInspectTabInjector.InjectAll(类型集合)` 由组合根 `ChronicleMod` 传入三个 ITab 类型（顺序敏感）；注入器本身不引用任何业务域，避免 Archive↔Economy 循环。

页面分三层：

1. **殖民地总览**：紧急受阻、预算受阻、供给受阻的去重人数；各需求域的需要、购买力与可供情况。
2. **需求详情**：选中一个域，查看需要谁承担、免费覆盖、预算意向、确认订单、供给和原因；显示建议治理入口。
3. **个人/家庭/机构追溯**：真实缺口、当前行动、责任与付款方、等待原因、有效合同和生活结果。

避免把全部原因、全部账目和全部 Pawn 塞入一张表。宽屏左侧选择/列表、右侧详情；窄屏以列表 → 详情 → 返回切换，保留正常字体。初版统计、表格与独立条形指标即可，不依赖未核验的复杂图表 API。

## 2. 默认画面内容

| 区域 | 内容 | 交互 |
|---|---|---|
| 页头 | 地图、范围、事实更新时间、未来规划窗、过去统计窗、制度阶段 | RUIF 分段选择/导航；窗口改变重建查询 |
| 紧急提示 | “2 人紧急受阻：1 人缺可达食品，1 人待救治”等有来源文本 | 查看个体和原因；避免提示点击直接强制 Pawn |
| 摘要 | 预算受阻人数、供给受阻人数、生活缺口人数 | 明确人数类别可以重叠，不相加得总人数 |
| 需求域列表 | 域、方案量、预算意向、确认量、可供量、主要原因 | 显示同窗单位；独立 RUIF 选择按钮，不假装 StatTable 支持点击 |
| 详情 | 需要/公共覆盖/付费候选/预算意向/已确认/可供各自数值、未知原因 | 拆分条形指标，禁止把相互包含的量堆叠 |
| 受阻原因 | 需要者与人数、时限、缺多少钱/多少物资/哪个时段、证据 | 多原因全部可查，摘要只取当前可解释主因 |
| 治理入口 | 调整新报价、机构预算、岗位/班次、公共保障、供给计划 | 打开草稿/机构；提交前复核真实资金/容量/权限 |
| 生活结果 | 最近窗口实际进食、休息、治疗、照护、等待与失败 | 与预计、订单和付款分列；前后同口径比较 |

需求表默认按紧迫性与持续受阻排序，不按有钱者优先。选择“全部需求”时按 12 个生活域完整列出；简版筛选只显示受阻项。条件不适用的项明确显示原因，不虚构婚姻/生育需求百分比。

## 3. 数据来源与聚合

| 数据 | 原始真值 | Application 投影 |
|---|---|---|
| Food/Rest/Joy 等 | Pawn 当前实际存在的 Need 与原版类别 | 只读当前值、目标、缺口、可用性、来源 Tick |
| 健康/衣物/床位 | 可见健康状态、真实 apparel、实际床位/房间事实 | 原版状态和合法方案条件；不造第二套疾病值 |
| 关系/照护 | 原版关系、发展阶段与已定义 CareResponsibility | 受益者、责任人、执行者、付款方分开 |
| 预算与合同 | 现有/扩展的账户、预留、有效订单和历史权益 | 可用、已承诺、未来工资预测分列 |
| 产品/产能 | 真实库存、原版 Bill/Recipe、有效工人和时段 | 规划窗内可完成数量/范围与受阻原因 |
| 实际结果 | 原版行动与已验证完成/使用证据 | 当前事实、期间交付、使用后变化；不从支付日志推断吃过饭 |

去重键拟议为 `beneficiaryId + canonicalGoalId + requirementComponent + intervalId`。儿童饥饿和“家长需要喂孩子”指向同一受益需求；一份食品采购和其使用是同链不同阶段，不再各记一次最终需要。睡眠恢复与长期住房改善不同目标，但同一次收益不能重复算入相同生活覆盖。

食品需要量由目标营养、合法食品/份量和有限预测转换；床位按有效时段；托育/教学按有对象的有效服务时长；医疗按可执行服务评估，而非将每条 Hediff 都算一名独立患者。不同单位只在域内比较。

人群筛选、地图范围、时间窗、数据修订必须贯穿列表和详情。事实/预算/供给快照若跨版本无法对齐，显示“更新中”并保留最近一致版本；不能显示互相矛盾的“0 缺口、3 人受阻”。

## 4. 拟议读模型

以下是设计 DTO，不是已存在的原版或项目 API。

| DTO | 字段 |
|---|---|
| `DemandViewRequest` | mapKey、populationScope、factTick、forecastWindow、historyWindow、domainFilter、selectedId、pageIndex、languageRevision |
| `DemandDashboardSnapshot` | readiness、builtAtTick、sourceRevisions、scope、uniquePopulation、urgentBlocked、moneyBlocked、supplyBlocked、domainRows、selectedDetail、actionStates |
| `DemandDomainRow` | domainId、applicableCount、gapPersonCount、urgency、unit、planQuantity、paidCandidateQuantity、budgetIntentQuantity、confirmedOpenQuantity、forecastSupply、estimateRange、status、primaryReason |
| `DemandDetail` | canonicalRequirements、publicCoverage、currentRights、budgetAllocation、quoteRevision、confirmedOrders、supplyLimits、blockers、outcomeSummary |
| `BlockerRecord` | beneficiaryId、requirementId、reasonCode、secondaryReasons、missingMoney/quantity/time、deadlineOrUnknown、evidenceIds、nextRecheck |
| `PolicyScenario` | baselineRevision、draftRevision、fixedAssumptions、changedFields、budgetIntentRange、expectedCashFlowRange、publicCost、capacityLimits、unaffectedExistingOrders |

每个量有 Known/Estimated/Unknown/NotApplicable 状态、单位和来源。未知容量不能传 `0` 后画红条；真值不足时暂不算相除比例。展示“预计 18–22 份”允许区间，不显示小数点后多位制造确定感。

原版 Need 的当前值/目标条仅在个人详情展示，明确哪条是满足度、哪条是缺口；群体条使用相同单位的“预算意向 / 付费候选”，不混用 Need 满足度和人头占比。

## 5. 原因码与推荐规则

| 稳定原因码 | 用户文案 | 推荐前提 |
|---|---|---|
| `MoneyShortfall` | 有合适方案，当前生活预算不足 | 存在已知可接受报价；未把其他已承诺预算算重复 |
| `NoAcceptableQuote` | 尚无合适报价/服务方案 | 不能把待报价直接写成买不起 |
| `StockShortage` / `InputShortage` | 缺成品 / 缺原料 | 具体物资和真实窗口计划可追溯 |
| `LogisticsBlocked` | 物资存在但无法交付 | 区域/可达性/搬运岗位已核验 |
| `StaffShortage` / `Qualification` | 缺可用人员 / 缺资格 | 需要真实岗位、能力或资格事实 |
| `CapacityFull` / `ScheduleConflict` | 容量已满 / 时段冲突 | 人员、受益者、设施和已有预约同窗比较 |
| `ProtectedAction` | 当前紧急/玩家指令优先 | 原版控制权；不能推荐强制覆盖 |
| `AwaitingUse` | 已获得，尚未使用 | 对应交付/权益真实存在 |
| `PublicCoverUnavailable` | 公共保障暂不可用 | 预算、物资或授权不足具体可见 |
| `FactUnknown` / `NotApplicable` | 暂无可靠数据 / 不适用 | 不生成伪订单或假缺口 |

推荐按原因到政策入口映射，记录 supportingEvidence 和 disabledReason。多重原因共存时说明先后依赖：先有药和医生才能新增治疗时段；只有补贴没有可供食品不能承诺解决饥饿。

## 6. RUIF 组件映射与限制

| 内容 | 已有 RUIF 入口 | 约束 |
|---|---|---|
| 页签/范围 | `NavAtomsB.LayerSwitch`、`InputAtoms.Segmented` | 使用已验证重载；只变查询/选择意图 |
| 摘要、详情读数 | `PanelAtoms.StatRow` | 可选 bar01 自带明确标签，不新增通用自绘卡片 |
| 需求域表 | `DataAtoms.StatTable` | 先筛选/分页；没有行点击/排序能力，选择用独立按钮 |
| 单域预算/容量 | `ProgressAtoms.CapacityBar` | used/capacity 同单位；零分母单独显示“无容量/未知”，不画成健康 |
| 紧急/陈旧/受阻提示 | `FeedbackAtoms.AlertBanner`、`EmptyState` | 显式处理返回动作；颜色外同时提供文字 |
| 个人/机构选择与政策入口 | `ButtonAtoms.PrimaryButton`、`SearchField` | 不叠自制透明按钮假装表格可点击 |
| 政策草稿 | `Stepper`、`Checkbox`、`PrimaryButton` | int 输入校验后转整数最小货币单位；禁止截断 long |
| 长列表 | `RUIF.Layout.BeginScroll/EndScroll` | 成对调用；独立分页，窄屏切详情 |

已读取当前 RUIF 源码：CapacityBar 对 capacity≤0 返回比例 0，而且默认接近满载变警告色。因此预算覆盖条要显式使用适合的语义色，容量负载条才用其默认警告语义；零容量依赖旁边文字，不把空条当“压力很低”。组件签名仍以安装 DLL 为准，源码说明不替代游戏实际加载证据。

高清预览仅展示信息层级和中文排版，颜色/边距由正式 RUIF Tokens 决定，不新增皮肤接口，不将 PNG 用作游戏内按钮或整页背景。

## 7. 命令与政策情景

页面查询只读。政策命令携带 commandId、expectedRevision、policyRevision、目标机构与草稿字段；主线程重新核查，再应用。未应用的草稿只重算估计，不预留资金、不改变 Pawn 目标、不提交订单。

情景重算与正常决策共享相同的纯预算/供给规则，但使用隔离输入副本；不重复运行有副作用的运行器。输出注明“固定其他条件”“下一新报价周期”和未知项。个人偏好/其他开销重新变化的动态预测属于后续，不伪装成确定结果。

对 v0.8 食品例子，提供两种草稿：在下一同等需要窗口只比较新订单，单价 3→2，预算意向 18→19，当前确认单不重定价；或公共采购 6 份，公共真实成本 18，原付费候选范围覆盖 18+6=24。第二种不改写为个人预算意向 24；加上原有公共覆盖 6 份，总生活覆盖为 30/36。公共机构间转账不当新外贸收入。

提交后显示“已应用，等待实际行动”，用政策修订关联后续交付/使用记录。已有确认订单仍按原约定结算；观察人口/库存/灾害变化时不保证面板差异完全由这条政策造成。

## 8. 更新、历史与性能

Needs/供给/预算各在原有事实或事件更新入口标脏，Application 构建有版本的有限快照；UI 只读缓存。快速需求与慢速规划采用不同采样周期，具体 Tick 值通过目标人数剖析确定。显示数据年龄，重大伤病/资源失效触发必要刷新，不能因 UI 未打开就不产生生活决策。

历史存有界分桶聚合：每域需要人数、实际交付/使用、受阻时长与现金流；原始事务/权利仍按账本持久化，不为画趋势无限保存每 Tick 全体 Pawn 快照。趋势没有样本时显示“积累中”，暂停游戏不制造新的时间样本。

查询缓存键包含地图、范围、时窗、事实/账本/供给/政策修订、语言、筛选与选中 ID。OnGUI 不做寻路、扫描地图、家庭关系重建、预算优化或翻译全量市场。首版先展示短期趋势数值/表格，不为复杂折线额外自研图表控件。

## 9. 页面状态与验收

必须覆盖 Loading、Ready、Empty、Unavailable、Error，并提供实际原因。制度关闭时需求仍可 Ready，但付费预算/合同功能显示未启用；无地图显示可选范围入口；没有 Biotech 时照护/学习域按实际能力标记，不以 0% 画缺口。

| 场景 | 通过标准 |
|---|---|
| 原版有免费食物 | 生活需要可由免费行动覆盖，不生成强制购买 |
| 有货没钱 | 仍显示需要者、预算差额和受阻原因，不因零订单隐藏 |
| 有钱没货 | 预算意向存在，库存/原料/物流瓶颈可追溯 |
| 已付款但未使用 | 确认/交付推进，生活目标仍按真实 Need 判断 |
| 同一儿童多照护者 | 受益需求和预算不重复，责任方分别可查 |
| 10 银币、多项缺口 | 计划分配合计不超过实际可用/已授权预算 |
| 同物不同产权 | 公共覆盖、待售库存、个人物品分别计算 |
| 价格/窗口/范围变更 | 列表详情同一修订；旧订单不改价；窗外供给不算本窗可用 |
| 零容量/未知/DLC 不适用 | 显示明确文字与状态，不能全部显示为 0 或绿色 |
| 多原因、无资源可调 | 不提供虚假一键解决；动作禁用有原因 |
| 长中文/英文/窄屏 | 正常字号、分页可达、文案不截断关键数字；无需颜色也可读 |
| 关闭窗口/反复点击 | UI 不改变决策频率，不重复付款；草稿不产生副作用 |
