## 1. 决定性发现：三个原生能力直接复用

写规格前先核对了原版 Def，发现三个能力**原版已提供**，T1 不该自造：

### 1.1 pawn 站位 —— 用原版 `hasInteractionCell`

原版所有工作台（`TableSculpting` / `ElectricSmithy` / `TableButcher`）统一写法：

```xml
<hasInteractionCell>True</hasInteractionCell>
<interactionCellOffset>(0,0,-1)</interactionCellOffset>
```

**这正是 T1「台面前沿 pawn 站位缺口」在代码层的原生对应物**——美术上画缺口，逻辑上由原版交互格机制承载。pawn 会自动走到交互格操作，且原版有 `PlaceWorker_PreventInteractionSpotOverlap` 防止交互格重叠。

> **不需要**自造 `CompOperatorSlot` 之类的组件。这解决了上一版规格里悬空的设计空洞。

### 1.2 断电降速 —— 用原版 `unpoweredWorkTableWorkSpeedFactor`

原版 `ElectricTailoringBench` 的写法：

```xml
<building>
  <unpoweredWorkTableWorkSpeedFactor>0.5</unpoweredWorkTableWorkSpeedFactor>
</building>
```

**T1「智能化辅助、断电就退化成手动台」的语义，原版已有一等公民字段。** T1 建议取 `0.4`（比原版电动裁缝台的 0.5 更低——T1 更依赖智能辅助，断电损失更大，这是 T1/T2/T3 差异化的一个真实抓手）。

> **不需要** Harmony 去 patch 工作速度，也**不需要**自己写 stat 惩罚。

### 1.3 工作速度上报 —— 用原版 `CompProperties_ReportWorkSpeed`

原版 `BenchBase` 基类自带：

```xml
<li Class="CompProperties_ReportWorkSpeed">
  <workSpeedStat>WorkTableWorkSpeedFactor</workSpeedStat>
</li>
```

配合 `PlaceWorker_ReportWorkSpeedPenalties`，游戏会在放置时提示"此处工作速度受影响"。T1 继承 `BenchBase` 即自动获得。

## 2. 架构决策：继承原版 `BenchBase` 还是自建基类？

这是 T1 最关键的一个架构选择，两种方案各有代价：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 继承原版 `BenchBase`** | `<ThingDef ParentName="BenchBase">` | 自动获得工作台全部原生行为（交互格/工作速度/设施连接/Bills 页）；零重复定义 | 被原版 Def 结构绑死；原版改 `BenchBase` 会传导；**不能用 `IProducingDevice` 那类自定义 comp 自由扩展** |
| **B. 自建 `PC_WorkshopDeviceBase`** | 仿照项目已有 `PC_AutoFarmBase` 自建抽象基类 | 完全自主；与项目既有范式（`PC_AutoFarmBase`）一致；可自由挂自定义 comps | 需手工补齐 `selectable`/`altitudeLayer` 等关键字段（**项目已踩过此坑**，见 `Automation_AutoFarm.xml` 注释） |

### **决策：选 B（自建抽象基类），但抄原版 `BenchBase` 的关键字段**

**理由**：

1. **项目一致性优先**（rimworld-modder 原则 5「模块之间通过契约通信」）：项目已有 `PC_AutoFarmBase` 自建基类的成功范式，T1 若单独去继承原版 `BenchBase`，会形成两套并存的基类体系——未来维护者要记两套规则。
2. **依赖方向**：继承原版 `BenchBase` = 把原版 Def 的字段传染进本 mod 的 Def 树。原版 Def 是"外部契约"，一旦 Ludeon 在 1.7 调整 `BenchBase`，本 mod 的 T1 会静默变化。自建基类只有**字段抄一次**，之后完全自主。
3. **红线提示**：项目已在 `PC_AutoFarmBase` 注释里明确记录"本基类不继承原版 BuildingBase，必须显式补齐其关键字段：`selectable` 缺失（默认 false）= 建筑无法选中；`altitudeLayer` 缺失会掉到 Item 层"——**这是已知坑，抄原版字段即可规避**。

> ⚠️ **禁止**：`<ThingDef ParentName="BenchBase">` 与自建基类**不可混用**（一个 Def 只能有一个 ParentName）。

### 3.1 与 `PC_AutoFarmBase` 的关键差异（为什么不能复用同一个基类）

| 项 | `PC_AutoFarmBase` | `PC_WorkshopDeviceBase` |
|---|---|---|
| 定位 | 全自动农机（无人） | 半自动工作台（**需人**） |
| 交互格 | 无 | **有**（`hasInteractionCell`） |
| 燃料 | `CompProperties_Refuelable`（化燃料） | **无**（纯电网） |
| 电力 | 光伏自发电 + 本体功耗 | **纯耗电**（`CompProperties_PowerTrader`） |
| Bills 页 | 无（自己做状态机） | **有**（`ITab_Bills`） |
| 断电降速 | 不适用 | **`unpoweredWorkTableWorkSpeedFactor`** |
| `passability` | Impassable | Impassable（同） |

> **不可合并为一个基类的理由**：两者在「是否需人」「是否烧燃料」「是否有 Bills」三个轴上是正交的，强行抽象成公共基类会得到一个包含大量空实现的基类（anti-pattern：God Base Class，违反 rimworld-modder「组合优先于继承」）。

## 5. 建筑类规格

### 5.1 `Building_WorkshopDevice`（新建，唯一新增 C# 类）

12 台共用**一个**类（零注册纳管的意义就在于不给每台设备开类）。

```csharp
namespace PersonalChronicle.Automation
{
    /// <summary>
    /// T1/T2/T3 智能化生产设备的薄壳建筑类。
    ///
    /// 识别契约：走 <see cref="IWorkshopDevice"/> 接口，不走 defName 前缀匹配
    /// （后者会把设备清单写死在数据层，第三方 mod 无法扩展）。
    ///
    /// 设计取向：本类保持"薄壳"——电力/开关/故障/Bills/交互格全部由原版 comps 与
    /// 原生 Def 字段承载（见 Defs/WeaponWorkshop_Base.xml）。仅当出现"原版无对应
    /// 扩展点"的功能（如原地升级）时，才在此类或其 comp 上落地。
    /// </summary>
    public class Building_WorkshopDevice : Building, IWorkshopDevice
    {
        /// <summary>设备显示名（管理面板设备清单用）。</summary>
        public string DeviceLabel => def.label;
    }
}
```

**规格约束**：

| 项 | 要求 |
|---|---|
| 基类 | `Verse.Building`（同 `Building_AutoFarm`） |
| 实现接口 | `IWorkshopDevice`（**仅此一个**——见 5.2） |
| 成员 | **只有 `DeviceLabel`**，不新增任何字段 |
| 存档字段 | **零**（纯 def 读取，无状态） |
| 是否 Harmony | **否** |
| 文件位置 | `Source/PersonalChronicle/Automation/Building_WorkshopDevice.cs` |

### 5.2 修正：不实现蓝图里的 `IProducingDevice` / `IPowerAwareDevice`

上一版设计文档写了"实现 `IProducingDevice` + `IPowerAwareDevice`"——**核对源码后必须修正**：

| 接口 | 源码实际状态 | 决策 |
|---|---|---|
| `IWorkshopDevice` | **已存在**，仅 `DeviceLabel` 一个成员 | ✅ 实现 |
| `IProducingDevice` | **不存在**（仅在蓝图 §5.1 提案里） | ❌ **不实现**——接口不存在，凭空实现违反「接口优先」且无人消费 |
| `IPowerAwareDevice` | **不存在**；且功耗原版本就挂在 `CompPowerTrader` 上可读，另造接口是重复 | ❌ **不实现** |
| `IQualityAwareDevice` | **不存在** | ❌ 不实现（同上一版结论） |

> **这正是 rimworld-modder 原则「接口优先于具体实现」的实践**：接口的价值在于有消费者。没有消费者的接口是空合同，会变成未来维护负担。**待 T2/T3 或车间面板真正需要读取产出进度/功耗时，再由需要方提出契约**，而不是现在凭空造。

### 5.3 潜在缺口：`Building_AutoProcessor` 悬空引用

源码核查发现 `IWorkshopDevice.cs` 的注释里引用了 `Building_AutoProcessor`，但**该类实际不存在**（全项目仅此一处注释提及）。

**决策**：T1 不复用这个幽灵类名，直接新建 `Building_WorkshopDevice`。同时**建议顺手修正 `IWorkshopDevice.cs` 的注释**（把 `Building_AutoProcessor` 改为 `Building_WorkshopDevice` 或删除该引用），消除文档与代码的不一致——这是 P3 级维护问题，应在实现 T1 时一并清掉。

## 6. 贴图规格

| 项 | 值 |
|---|---|

| 文件 | `<defName>.png`（north）+ `_east` / `_south` / `_west` |

| 基准向 | **east**（进左出右） |

> **交互格与贴图的对应关系**：`interactionCellOffset (0,0,-1)` 表示交互格在建筑**南侧**（-Z 方向）。贴图 `_north`（默认向）时，pawn 站位缺口应画在**图片下沿**；旋转后由 `Graphic_Multi` 自动换图，四向贴图必须保证"缺口永远对着交互格"。**这是四向出图的硬约束**——若四向都画成同一朝向，pawn 会站在设备背面。
