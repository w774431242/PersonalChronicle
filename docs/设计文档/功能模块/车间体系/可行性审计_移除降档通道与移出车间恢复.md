# 可行性审计 · 移除降档通道 + 移出车间即恢复原版工作面板

- **日期**：2026-10-05
- **玩家诉求原文**：「能否移除这项设置（一键全解除）……我不需要这个，只需要人员被移除车间体系，
  然后恢复显示原版的工作面板，玩家可以手动进行调整，避免多余。」
- **结论**：**可行**（净简化），但**有一个必须处理的旧档迁移**与**一个必须先分账的设计难点**。

---

## 一、现状：PC 一共动了工作面板的哪些东西（三条链 + 一张名单）

| 链 | 做什么 | 写台账？ | 出口 |
|---|---|---|---|
| **A 降档通道**（`WorkDemote.cs`） | 车间相关 → 1；**其余已勾选 → 4（最低档）** | ✅ 写「降档台账」 | 「一键全解除」 |
| **B 提档/补勾选**（`WorkEnable.cs`） | 值勤 → 3；映射类型 → 1；0 档补勾选 | ❌ **不写台账** | 无（不可逆） |
| **C 接管通道**（`WorkTakeover.cs`） | 车间类原版工作 → **取消勾选（0）** | ✅ 写「接管台账」 | 「解除接管」 |
| **D 隐藏名单**（`ChronicleGameComponent`） | 把车间成员加入【工作】面板隐藏名单 | ✅ 持久化 | 仅 Mod 设置里的「一次性清空全部」 |

**关键事实**：
- 降档通道**只有一个调用方**：`SyncVanillaWorkSettings`（`WorkEnable.cs:112`）⇒ 删它即断链，无其它依赖。
- 「一键全解除」**是降档通道的唯一出口**，且被 `EXC-2026-015` 当作"自动行为须有出口"的执行点
  ⇒ **不能只删按钮、留着降档**（那会变成"改了却没出口"）。

---

## 二、逐项可行性

### ① 删除「一键全解除」按钮 —— ✅ 可行（零风险）

- 删 `DrawWorkStationStatusRow` 内的按钮块（`WorkshopManageView.WorkStation.cs:186-194`）；
- 状态行其余读数（已对齐 / 跳过 / 在册 / 在岗 / 应到岗 / 作息异常）**全部保留**；
- 去掉「台账 N 项」这一项（它读的正是降档台账，删链后无意义）。

### ② 删除降档通道 —— ✅ 可行，但**必须做旧档一次性迁移**

**依赖面**：`SyncWorkStationForZone` 内只有两件事 —— 补勾选（保留）+ 降档（删除）
⇒ 删掉降档后该方法只做"补勾选"（无破坏性）。

**行为变化（这是你要的，但要知道代价）**：

| | 删之前 | 删之后 |
|---|---|---|
| 车间相关工作 | 1（最高档） | **1（不变）** ← 提档通道独立，仍生效 |
| 其余工作 | 被压到 **4** | **保持你原来的档位**（1/2/3） |
| 净效果 | 除车间活外一切靠后 | 车间活仍是最高档，但**其它工作不再被压制** |

⚠ **代价照实说**：失去"降档"后，"人在非排班时间也更愿意干车间活"这种强约束会**变弱** ——
其它工作（建造 900 / 采矿 600 / 种植 700 的 naturalPriority）可能在某些情况下先于车间活被选中。
你要的正是"回到原版、我手动调"，所以这是**预期行为**，不是缺陷。

⚠⚠ **必须做的迁移（否则旧档会卡死）**：
删除功能时，**旧存档里已存在的降档台账**意味着有人的工作在 4 档。
若只是删代码，这些 `4` **永远不会被还原**（原出口已消失）⇒ 玩家看到"一堆工作被压在最低档、且无法恢复"。
⇒ **做法**：在读档/开面板时执行**一次** `RestoreAllDemotedWork()`（复用现有实现），随后清空台账。
⇒ 这是"只执行一次"的迁移（用加性标记守住，同 `autoTakeoverDone` 的先例）。

### ③ 人员被移出车间 ⇒ 自动恢复显示 —— ✅ 可行，**但必须先给隐藏名单分账**

**现成机制**：`SetHiddenFromWorkTab(pawn, false)`（单个移除）已存在（`ChronicleGameComponent.WorkTabHide.cs:90-117`）。

⚠ **设计难点（必须解决）**：隐藏名单**同时服务"PC 自动隐藏"与"玩家手动隐藏"**
（`AutoHide.cs:18-21` 明确记载"刻意不做离队自动取消隐藏"正因如此）。
若直接"离开车间就取消隐藏"，会**把玩家手动隐藏的人一起放出来**。

⇒ **解法：两个集合分账**

| 集合 | 含义 | 离开车间时 |
|---|---|---|
| `hiddenWorkTabColonists`（既有） | 保持原义，**旧档已有项全部视为"玩家手动"** | **不动** |
| `autoHiddenWorkTabColonists`（新增，加性字段） | 只记 PC 自动隐藏的 | **移除该成员** |

- 显示过滤 = 两集合**并集**（现有 `WorkTabHideFilter.ShouldHide` 的调用点改传并集）；
- 旧档：新字段为空 ⇒ 所有既隐藏项都算"玩家手动" ⇒ **不迁移、零风险**；
- 此后：加入车间 ⇒ 进自动集合；离开车间 ⇒ 从自动集合移除（且在并集里消失 ⇒ **面板恢复显示**）。

### ④ 移出车间是否连带「解除该成员的接管」？—— ⚠ 建议做，否则是半残

接管会把"车间类原版工作"取消勾选（0）。若只恢复显示、不还原勾选，那个人**看着面板却仍然做不了那些活**
⇒ "移出车间"变成半残。
⇒ **建议**：移出车间时对该成员**按人还原接管**（现在 `ReleaseVanillaWork` 是**全量**还原，
需新增一个按 pawnId 的还原方法，复用同一本接管台账与其两道闸门）。

## 三、建议实施顺序（每步独立可编译、可回滚）

| 步 | 内容 | 风险 | 存档影响 |
|---|---|---|---|
| **1** | 删「一键全解除」按钮 + 去掉状态行「台账 N 项」 | 低 | 无 |
| **2** | 删降档通道 + **旧档一次性还原迁移** | 中 | ⚠ 一次写入（还原 4 档），无 schema 变更 |
| **3** | 隐藏名单分账（新增 `autoHiddenWorkTabColonists`）+ 移出车间即从自动集合移除 | 中 | 加性字段，无迁移 |
| **4** | 移出车间按人解除接管（新增按 pawnId 还原） | 中 | 无（复用既有台账） |

**留存不删**：`DemotionLedger` 字段保留（仅停止写入并留空），避免 Scribe 键结构变更 ⇒ **不强制存档迁移**。

## 四、风险与边界（照实登记）

1. **`EXC-2026-015` 需修订**：该例外授权的是"降档通道 + 出口"，删链后必须同步登记该 EXC 的废止/替代说明
   （否则工程例外表与实际实现不一致 —— 项目历史上正因这类漂移踩过坑）；
2. **"车间优先"强度下降**（见 ② 的代价段）—— 预期行为，但值得在 Mod 设置或 tooltip 里一句话说明；
3. **接管通道保持不动**：本方案只删降档，接管（取消勾选）与「解除接管」**全部保留**；
4. **玩家的手动隐藏永不被自动放出来**（分账设计保证了这点）；
5. 若你将来想要"更弱的自动约束"，替代手段是**只保留提档（映射 → 1）**，这已经是删降档后的状态。

## 五、成本对比：出口自动化（靠移出车间）vs 保留手动出口

### 先说一个决定性事实：「移出车间」不是原子动作

取证结果（`OnRosterChanged()` 共 **8 个**调用点，另有独立入口）：

| 移出方式 | 代码路径 | 会触发统一事件吗 |
|---|---|---|
| 人员页「移除」 | `zone.RemoveMember` → `OnRosterChanged`（`WorkshopManageView.cs:1039`） | ✅ |
| 班组编辑器「移出」 | `crew.Remove` + `DedupeCrewMemberships`（`Dialog_WorkshopCrewEditor.cs:186-187`） | ⚠ 走其自身 onChanged 回调 |
| 删除班组 | `zone.RemoveCrew` → `OnRosterChanged`（`Schedule.cs:407`） | ✅ |
| 删除班次 | `RemoveShift` → `OnRosterChanged`（`Shifts.cs:286`） | ✅（间接影响） |

⚠ 且成员口径是 **`zone.Members` ∪ `crew.Members`**（`AllWorkshopMemberPawns`）——
**只从班组移出、但仍留在"车间人员名单"里 ⇒ 仍算在车间**，不会触发"离开"。

⇒ 所以"给每个移除入口挂钩"是**错的路线**（会漏、且与成员口径分叉）。
**正解是差集对账**：不挂钩子，而在既有对账时机（`Refresh` / 名册变更）比较
「上轮成员集合」与「本轮成员集合」，把**差集**当作"已离开者"处理。
（上轮快照放 Manager 运行态、**不入存档**，与 `idleSplitCapacityByZone` 同款先例；
读档后首次对账时快照为空 ⇒ 差集为空 ⇒ **不会误触发**。）

### 成本对比

| 维度 | **A · 出口自动化**（移出车间即还原） | **B · 保留手动出口**（现状 + 删降档） |
|---|---|---|
| 改动文件 | 5–6 个 | 1–2 个 |
| 新增持久字段 | `autoHiddenWorkTabColonists`（隐藏分账）+ 迁移标记 | 仅迁移标记 |
| 新增运行态 | 上轮成员快照（Manager 级，不入档） | 无 |
| 是否要改各移除入口 | **不需要**（差集对账覆盖全部） | 不需要 |
| 覆盖完整性 | ✅ 全部（含死亡 / 换图 / 读档 / 任一 UI 入口） | ⚠ 仅在玩家**手动点按钮**时生效 |
| 误伤玩家手动隐藏 | 需分账（已设计：旧档项全视为手动） | 不涉及 |
| 玩家操作成本 | **零操作**（移出即恢复） | 移出后还要点一次按钮 |
| 面板简洁度 | ✅ 少一个按钮 + 少一项状态读数 | 保留按钮 |
| 回归风险 | **中**：差集口径必须与成员口径**严格一致**（分叉即误判"离开"） | 低 |
| 存档兼容 | 加性字段，无迁移 | 同 |
| 可回滚性 | 字段留档无害 | 同 |

### 结论与推荐

- **成本差不大**（A 比 B 多约 3–4 个文件的改动，且都是既有模式的重用）；
- **能力差很大**：A 覆盖"所有离开方式且零玩家操作"，B 只能靠玩家记得点按钮；
- ⇒ **推荐 A + 保留一个逃生舱**：
  - 出口自动化（移出车间 ⇒ 取消自动隐藏 + 按人解除接管）；
  - **保留** Mod 设置里既有的「恢复显示全部殖民者」（一次性清空）作为兜底 —— 这个已有、不动；
  - **删除**「一键全解除」（降档链整个移除后它无物可解除）。
- ⚠ A 的唯一硬前提：**"离开车间"必须从两处名单都移除**（人员名单 + 所有班组）。
  只从班组移出但仍在人员名单 ⇒ 仍算在车间、不会触发恢复。
  ⇒ 这必须在 UI 上说清（或在"移出班组且不在任何班组"的提示行里点明），否则玩家会以为功能失灵。
