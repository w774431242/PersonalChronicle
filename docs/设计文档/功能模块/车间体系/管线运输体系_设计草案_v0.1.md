# 管线运输体系 设计草案 v0.2（v0.1 修订版）

> 文档定位：在现有拼图（`Building_ConveyorSegment` MVP + `IItemStorage` 预留接缝）之上，
> 定义完整的自动化「管线运输体系」—— 物品在设备之间的自动流动。
> 上游文档：`../自动化体系规范/00-通用规范/自动化设备_开发架构样例_生命周期管线_v1.0.md`（设备生命周期与铁律）。
> 状态：**草案**；v0.2 按 PM 预期定案核心架构（§0.8），v0.1 的独立泵/装载口方案降级为备选。

## 0. 现状盘点（草案的出发点）

| 已有 | 内容 | 缺口 |
|---|---|---|
| `Building_ConveyorSegment` | 1 格传送带段，`Building_Storage` 底座（pawn 可直接搬货上带）；90 tick/拍沿朝向前送 1 件；目标须为**同向**相邻段（防对头互推）；目标空则前送、同类可合堆；链位贴图 Start/Mid/End 自动切换 | 无自动上货/下货手段，只能靠小人搬运 |
| `IItemStorage`（农机内置仓已实现） | `Capacity/StoredTotal/Buffer/AcceptQuantity/Push/TakeOut/DropAll`——**管道运输唯一对接缝**，管道端只依赖接口 | 没有任何设备真正调用 TakeOut 做自动运输 |
| `CompItemStorage` | 农机 S/M/L 150/300/500 容量；收获先进仓满了才落地 | 仓满后只能玩家手动「取出全部」 |

**结论**：运输体系 = 在 `IItemStorage`（源/汇）与传送带链（传输）之间补齐「提取」与「装载」两个交接件，形成闭环。

## 0.5 落地前预研：原版有无管道 & 通用入仓接缝（2026-09-06 程序集字节检索核实）

**① 原版无物品管道，不存在可复用的原生管道资产。**
- `Assembly-CSharp.dll` 字节检索：`Conveyor` / `VacuumTube` / `ItemPipe` 全部 0 命中；
- Odyssey DLC 新建筑清单（wiki 核实）围绕重力船体系，无任何运输/仓储建筑；
- Biotech 的 Wastepipe 是污染管网（流体），非物品运输。
→ 贴图与交互沿用**自绘资产**（传送带已就位）；原版只借 gizmo 图标（FloorPaint/Drop/OpenStatsReport，既有做法）。
- 原版唯一的「机器自动进料」范型 = 营养膏机**进料斗**（`IsHopper`/`WorkGiver_CookFillHopper`/`HopperFillFoodJob`）：由小人搬运填料，**无自动输送**。

**② 1.6 仓储体系关键 API（字节核实存在，直接依赖即为零兼容）：**
`TryFindBestBetterStorageFor` / `TryFindBestBetterNonSlotGroupStorageFor` / `TryFindBestBetterStoreCellFor`、
`ISlotGroup` / `ISlotGroupParent`、**1.6 新增 StorageGroup 体系**（`IStorageGroupMember` / `StorageGroupManager` / `StorageGroupUtility`，跨建筑共享仓储组）、
`IsInValidStorage` / `IsValidStorageFor`、`HaulToStorageJob` / `HaulToCellStorageJob`。
⚠️ 1.6 **已无 `SlotGroupManager` 类**（旧名 0 命中，职责并入 StorageGroupManager）。

**③ 装载口交付管线修订为三层（§3.3 升级）——"不对非本 mod 做兼容处理"成立：**
```
① 自家设备：IItemStorage.AcceptQuantity 问余量 → Push（天然反压）
② 原版通用入仓：TryFindBestBetterStorageFor(item, …) 找全图最优合法存储格
   → teleport 放置（DeSpawn→改位→Spawn，通知对齐 MVP 纪律）
   → 物品处于 IsInValidStorage，小人不再重复搬运
③ 兜底：GenPlace.TryPlaceThing(Near) 落在旁边，交还原版搬运链，物品零丢失
```
原理：RimWorld 的物品**不装进建筑内部**，而是躺在存储建筑覆盖的格子上；建筑"持有"物品只是作为搬运目的地。
凡第三方存储想让小人能搬货，就**必然**注册进 SlotGroup / StorageGroup 接缝——因此走 `TryFindBestBetterStorageFor`
= 原生存货区/货架、LWM Deep Storage、RimFactory 等**零适配代码直接可用**（优先级 StoragePriority、跨建筑 StorageGroup、
过滤白名单全部由原版逻辑代管）。
不覆盖的边缘情况：完全自研、不注册任何接缝的"封闭容器"型存储（物品在其建筑内部列表）——这类本来小人也无法自动搬入，
走 ③ 兜底即可，无物品损失。

**④ M4 虚拟流管道**：同样只依赖上述接缝——管网内移 def+count，目的端 `ThingMaker.MakeThing` 物化后按 ②③ 落格，模型可互换。

## 0.8 PM 预期定案与架构修订（v0.2，2026-09-06）

**PM 预期（原文）**：自动化设备存储组件可以通过管道自用运输物资；可以**定向输出到某个指定的存储格子内**
（第三方和原生存储无需额外兼容就可以使用）；管道运输体系核心在于**不需要额外内容——只需要输出端 + 管道**
即可实现物资输出。

### 由此定案的四条架构决策（覆盖 v0.1 相应内容）

**D1 · 交接件取消，输出端内建**——不再需要独立的「提取泵」「装载口」两个建筑（v0.1 §3.2/§3.3 降级为备选方案）。
输出能力做成**端口 comp**（`CompItemPort`，占位名）：挂在任何实现了 `IItemStorage` 的自动化设备上
（农机三档直接生效），设备储物仓即被「泵」化。装上端口 = 装上输出端，系统里没有第三个必要角色。

**D2 · 管道 = 虚拟流（v0.1 的 M4 提升为核心传输模型）**——管道段内移动物品用 `ThingDef + count`
（不生成实体 Thing），`MapComponent_PipeNetwork` 管网图 + 各段微量缓冲；只有**出口端物化**
（`ThingMaker.MakeThing`）后落格。理由：只有「输出端 + 管道」两个角色时，实体传送带模型必须依赖货物
在带格间排队，出口无人接货就没有意义；虚拟流让「管道末端贴着目标格」本身即出口，天然满足最小闭环。
传送带 MVP 保留为**实体流备选路线**（大吞吐可视化场景），与虚拟流并存，均只依赖 `IItemStorage` 与仓储接缝。

**D3 · 定向输出（端口 ↔ 目标一对一绑定）**——玩家经 designator 给端口指定一个目标：
① 任意存储建筑的**某个具体格子**（原版存货区/货架/第三方存储，或空地备用格）；
② 自家设备（实现 `IItemStorage` 的建筑，走 `Push`）。
绑定持久化（目标格 Scribe Value / 目标建筑 ThingID）。一格一目标，明确可预期；多目标后续按需扩展。

**D4 · 定向格交付三层（API 全部经 2026-09-06 程序集字节核实存在）**：
```
预检  目标格归属查询：SlotGroupAt / SlotGroupParentAt（cell→组）
      接受判定：Settings.AllowedToAccept(item) / Accepts(item)（不通过 → 端口不取货，反压）
交付  MakeThing 物化 → teleport 落到指定格（DeSpawn→改位→Spawn，通知对齐 MVP 纪律）
校验  IsValidStorageFor(cell, item) / IsInValidStorage(item)；不合格 → GenPlace.TryPlaceThing(Near) 兜底
```
零兼容原理不变：物品躺在存储格上即入仓，凡第三方存储可被小人搬货就必在 SlotGroup/StorageGroup 接缝内；
预检不过 = 该格过滤不收这类物品 → 端口反压不取（语义诚实：定向格收什么由原版过滤器说了算）。
辅助查询 `StoragePriorityAtFor` / `TryGetValidStoragePriority` 可用于检视面板显示目标格优先级。

### v0.2 最小闭环

```
[自动化设备 + IItemStorage]──(端口 CompItemPort，玩家绑目标)──[管道网 虚拟流]──[末端出口格=定向目标]──>[指定存储格子]
```

搭建成本 = ① 设备挂端口 comp ② 铺管道 ③ 点击绑定目标。**没有任何"接收端建筑"需要玩家额外建造**——
接收端就是玩家已有的任何存储（或我们自家设备），这正是"不需要额外内容"的落地形态。

## 1. 设计原则（继承产线铁律）

1. **缓冲表示**：泵/口等新增设备的内部缓冲只存 `ThingDef + count`（铁律①）；传送带段是唯一例外——格上物品由 map 托管（`Building_Storage`），不自研容器。
2. **物品移动**：段间 teleport（DeSpawn → 改位 → Spawn）+ `Notify_LostThing`/`Notify_ReceivedThing` 对齐持有清单；跨交接件的移动优先复用同一套 teleport 纪律。
3. **节拍**：全部 `TickInterval(int)` 累加配额；新设备默认 90 tick/拍（与传送带同拍，吞吐可按拍内件数调）。
4. **反压优先于丢弃**：下游满了就停取/停送——物品滞留在原位（传送带格天然是缓冲格），**绝不凭空 Destroy**；`Destroy` 仅保留在 `GenPlace` 彻底失败的最后兜底（铁律④收窄）。
5. **识别走接口**：泵/口对源/汇只依赖 `IItemStorage`，对带只依赖 `Building_ConveyorSegment` 或未来 `ITransportPort`；零 defName 硬编码（铁律⑤）。
6. **运行门控**：接电设备（泵/口）一律 `IsRunning()` 三连门控，不满足零扫描。
7. **存档纪律**：链拓扑每帧由相邻查询导出（不持久化）；持久化只存 def+count 平行表（可写引用 + PostLoadInit 对齐）。

## 2. 体系分层总览

```
[源 Source]      农机内置仓（IItemStorage）/ 未来加工机产出 / 任意 Building_Storage
     │
[提取 Extract]   ★新增 提取泵 Pump：贴邻源 + 贴邻带首
     │             TakeOut(def, stackLimit) → 前送入带
     ▼
[传输 Transport] 传送带段链（现有 MVP）——物理运输、天然缓冲、玩家过滤即分流
     │
[交接 Insert]    ★新增 装载口 Loader：贴邻带尾 + 贴邻目标
     │             取带尾物品 → 目标 IItemStorage.Push / 落地
     ▼
[汇 Sink]        设备内置仓（IItemStorage）/ 仓库 / 掉落地
```

设计取向：**M1~M3 走「实体物品 + 传送带」路线**（复用原版搬运/仓储/HaulDestination 生态，兼容性最好）；
「虚拟流管道」（物品不落地、MapComponent 管网求解）只作为 M4 远期备选，接口层（`IItemStorage`）已保证两者可互换。

## 3. 组件规格草案

### 3.1 传送带段 `Building_ConveyorSegment`（已有，小增强）

- 维持：1 件/拍、同向链、合堆、Standable、链位贴图。
- 增强（M3）：
  - 过滤提示：带段继承 `Building_Storage` 后 `defaultStorageSettings.filter` 玩家本就可调——补一句 gizmo/检视文案指路「设置过滤 = 分流」即可，不做新 UI；
  - 分流语义确认：异类物品滞留本格 = 物理分流（下游带过滤不同时自然形成分拣），文档化为特性而非 bug；
  - 贴图：Graphic_Multi 四向箭头已有待办（资产层）。

### 3.2 提取泵 `Building_ConveyorPump`（v0.1 方案，v0.2 降级备选——输出端内建端口 comp 后无需独立泵）

| 项 | 规格 |
|---|---|
| 摆位 | 自身 1 格；**后方**贴邻源（实现 `IItemStorage` 的建筑），**前方**贴邻带段或留空 |
| 缓冲 | 内部缓冲 1 栈（ThingDef+count），持久化 |
| 节拍 | 90 tick/拍，两步走：① 从源 `TakeOut`（按源 Buffer 顺序取第一类有货的，量 ≤ def.stackLimit）；② 有内部缓冲则尝试入带 |
| 入带 | 前方相邻格存在同向 `Building_ConveyorSegment` 且目标格无异类占用 → teleport 放置 + SlotGroup 通知；失败则缓冲滞留（反压传导到源） |
| 反压 | 前方不可入 → 不再向源 TakeOut（缓冲为空才继续取） |
| UI | 检视显示「源：xx / 输出：xx」；gizmo：切换取货过滤（复用 StorageFilter 简化版或全取） |
| 存档 | 仅内部缓冲平行表（Reference+Value） |

### 3.3 装载口 `Building_ConveyorLoader`（v0.1 方案，v0.2 降级备选——管道末端即出口，无需独立装载口）

| 项 | 规格 |
|---|---|
| 摆位 | 自身 1 格；**后方**贴邻带段（链尾），**前方/自身**贴邻目标 |
| 节拍 | 90 tick/拍：从后方带格取 1 件可搬物品 → 交付 |
| 交付优先级 | ① 前方相邻实现 `IItemStorage` 的建筑：`AcceptQuantity` 问余量 → `Push`（余 0 则不取，反压）；② 无接口目标 → `GenPlace.TryPlaceThing(Near)` 落地；失败滞留 |
| 反压链 | 汇满 → 口不取 → 带尾滞留 → 前段合堆失败 → 全链停 → 泵停取 → 源仓继续攒。**全链天然反压，无中心调度** |
| UI | 检视显示「目标：xx（余量 xx）」 |
| 存档 | 无状态（物品全在带格/目标上），最简 |

### 3.4 （M4 远期）虚拟流管道 `Pipe`

- 物品不生成实体：MapComponent 管网图（端口 = `IItemStorage`），按网络周期批量转移 def+count；
- 优点：无实体竞态、大吞吐；代价：绕开原版搬运/仓储生态，与传送带实体流并存时需明确分界；
- **本草案不展开**，仅锁定：任何端口实现 `IItemStorage`，切换成本为零。

## 4. 关键机制

### 4.1 反压（Backpressure）
全链无调度器：每段/每件设备只看「我能不能把下一件送出去」。任何一环满载即向上游传导滞留。
验证口径：汇仓塞满 → 整条线在 ≤2 个周期内静止，且无物品销毁。

### 4.2 分流与过滤
- 玩家在带段 `ITab_Storage` 调 filter → pawn 搬运与带内合堆共同决定物品走向；
- 异类滞留 = 分拣口语义（文档化）；
- 泵端过滤（M2 可选）：默认全取，若需要「只取某类」在泵 gizmo 给简化开关，复杂过滤交给带段 filter。

### 4.3 竞态与确定性
- 同拍多泵争同一带格：tick 顺序决定先后（原版同款行为），先到先得，不加锁；
- 泵/口 teleport 与 pawn 搬运竞争：SlotGroup 通知已对齐（MVP 已验证），持有清单不漂移；
- 传送带 `passability=Standable` 与 pawn 走位共存（MVP 已验证），泵/口建议 `Impassable`。

### 4.4 性能预算
- 单段 1 件/90t ≈ 400 件/千tick；长链吞吐 = min(单段速率)，瓶颈在交接件（泵/口同拍 1 件）；
- 节拍通道独立配额计数器（与农机三通道同款写法）；
- 全链静止时成本 = 每段一次 `GetThingList`（摊薄后可忽略）；百段级规模无需优化，千段级再考虑 MapComponent 分组扫描（列入 M4 观察项）。

- **`IItemStorage` 演进**：泵需要「按 Buffer 顺序取」→ 接口已够（`Buffer` 快照 + `TakeOut`）；若将来需要「按类过滤取」，加接口方法而非改语义（老实现靠显式接口实现/默认适配过渡）。
- **发布前恢复项**：传送带 0 成本（XML 注释：Steel 6 + ComponentIndustrial 1 + 研究 + 技能门槛）；泵/口沿用同款测试期注释纪律。
- **命名待评审**：`ConveyorPump`/`ConveyorLoader` 为占位名，落地前与现有 defName 前缀 `PC_` 对齐并过翻译键 grep。
