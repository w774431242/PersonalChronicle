## 0. 目标与范围

车间体系要解决的玩家闭环：

```
圈定区域 → 指派人员/归入设备 → 排班自动运转 → 产出归档到档案馆
```

**已明确的一期边界**（来自现有代码与设计注释）：
- 车间 = 玩家用设计器圈定的一片区域，作为**自动化设备的归属边界**与**人员调度单元**。
- 排班/轮岗已建模；人员`members`随存档持久化；管理面板 7 页壳已就位。
- 真实生产逻辑**不放在 `Zone_Workshop` 里**（第一版注释明确：不 tick、不存额外字段）。

**蓝图待定义**：车间与"生产"的关系、设备的统一行为契约、与物流（传送带/管道）的衔接、配方与设置页的范围。

### 1.2 调用链（现状）

```
圈地:   Designator_ZoneAdd_Workshop → Zone_Workshop 进 zoneManager
入口:   Zone gizmo → Dialog_WorkshopManage → WorkshopManageView(7页)
排班:   JobGiver_Work → WorkGiver_Workshop.NonScanJob
        → MapComponent_WorkshopManager.TryGetDutyJob → JobMaker(PC_WorkshopDuty)
        → JobDriver_WorkshopDuty
在岗:   NotifyDutyStarted → activeWorkers[pawn]=zone；FailOn(IsScheduledForDuty) 自动收工
轮岗:   MapComponentTick(60 tick) → ProcessRotations → RotationRule.Advance
设备:   WorkshopStats.ScanDevices 遍历 zone 格找 IWorkshopDevice（零 defName 硬编码）
```

### 1.3 已落实的契约 / 红线（不可在蓝图里推翻）

- **1.6 无 `ZoneDef` / `MapComponentDef`**：车间显式 `GetInspectTabs()=空` 防 NRE；MapComponent 须 `Get(map)` 惰性 `map.components.Add`。
- **`WorkGiver` 不继承 `WorkGiver_Scanner`**：无目标物可扫，走 `NonScanJob` + `scanThings/scanCells=false`（否则 `HasJobOnThing` 永不被调）。
- **绝不强制打断 pawn**：排班结束/车间删除/倒地靠 `FailOn` 自然收尾，`playerInterruptible=true` 仍可手动打断。
- **引用清理**：`PurgeDeadReferences` 剔除死亡 pawn / 被删车间 / 轮岗池悬空引用。
- **工时上报**走公开契约 `IWorkTimeCaptureService`。
- 颜色/字体走 `UITheme`+`UIComponents`；窗口只消费 Read Model 快照。

### 1.4 已知缺口与风险

1. **⚠️ 致命：`MapComponent_WorkshopManager` 从未注册。** 全代码无 `new MapComponent_WorkshopManager` 也无 `map.components.Add`（对照 `MapComponent_PipeNetwork.Get(map)` 有惰性注册）。后果：`map.GetComponent<...>()` 恒为 null → `WorkGiver` 返回 null（无人上岗）、`JobDriver` 的 `FailOn` 立即失败、管理面板排班/成员页 `Manager` 为 null。**排班/轮岗/在岗整套失效。** 修复见 §4。
2. **文档悬空引用**：`IWorkshopDevice` 注释写 `Building_AutoProcessor`（不存在）；`Dialog`/`WorkshopManageView` 注释写 `ITab_WorkshopManage`（不存在，仅有 Dialog 形态）。
3. **设计器图标**仍为原版 `ZoneCreate_Stockpile`，注释标 TODO 换自制图标。
4. **配方页 / 设置页**在 `WorkshopManageView.Page` 枚举中存在，但实现为空壳（蓝图 T5 要定义内容）。

## 2. 设计蓝图 · 待决议题

> 每个议题给出**已知约束（基于 RimWorld 1.6 API）**、**候选方案**、**开放问题**。
> 约束核验方法：知识库 `Thing_Job与工作环境.md`（Job/Bill/WorkGiver）、`组件化架构_Comp与Component.md`（Comp 不能按实例动态增删）、`Def系统与XML注入.md`。
>
> 📌 **具体设计提案已开列于 `车间体系_设计蓝图.md`**（车间类型/部门/人员/设备/政策/加成六维度）。下方各议题标注「已有提案」表示该维度已在蓝图给出推荐方案，待在决策记录表收敛。

### T1｜生产模型：车间是「容器」还是「生产单元」？

**已知约束**
- `Zone` 不是 `Thing`：无 `Comps`、无 `BillStack`、不能挂 `CompProperties`、不能复用原版 `Building_WorkTable` 的 Bill/Recipe 管线。
- 现有 `Building_AutoFarm` 已是**自驱设备**（自身 `TickInterval` 干活），不依赖车间排班驱动。
- 车间第一版注释明确"不含任何生产逻辑"。

**候选方案**
- **A. 纯容器（推荐基线）**：车间只做"区域归属 + 人员调度 + 设备纳管"。真实生产由各 `IWorkshopDevice` 设备各自承担。车间排班决定"谁在哪个时段在车间"，设备是否运转由自身逻辑决定。
- **B. 车间承载 Bill/Recipe**：在 `Zone` 上自建产线配置 + 自绘 UI，复用原版 `RecipeDef` 但不复用 `BillStack`。代价高（全部生产管线自研），且与原版 WorkTable 体验割裂。
- **C. 混合**：车间持有"产线配置"（选配方/优先级/启停），执行委托给区内 `IWorkshopDevice` 设备；车间相当于"控制器"，设备是"执行器"。

**开放问题**
- 玩家心智模型更靠近 A 还是 C？是否要"在车间里点配方→区内加工机自动按此配方生产"？
- 若选 A，车间与设备的"生产"关系如何可视化（设备状态汇总到车间概览页即可）？

### T2｜设备抽象 `IWorkshopDevice` 的演进

**现状**：接口只有 `string DeviceLabel`，仅用于统计与面板列表。

**候选方案**
- **T2-a 保持标记接口**：状态/产出/能耗由各设备自有 `Comp` 或类逻辑提供，面板通过 `as` 探测具体类型取字段（易碎，类型多了难维护）。
- **T2-b 上升为行为接口**：扩展 `IWorkshopDevice` 为 `DeviceLabel` + `DeviceStatus`(运行/待料/故障/停机) + `IsRunning` + 可选 `TickLight()`。设备统一向车间/面板暴露状态，零注册纳管不变。
- **T2-c 行为接口 + 可选能力**：基础 `IWorkshopDevice`（状态），另定义 `IProducingDevice`/`IPowerAwareDevice` 等可选能力接口，面板按需探测。

**开放问题**
- 蓝图里的"加工机"（`Building_AutoProcessor` 占位）需要哪些能力字段？是否要能耗、产出速率、品质？
- 设备状态是否要上报档案馆（与职业/生产统计打通）？

### T3｜物流衔接（传送带 / 管道）

**现状**
- `Building_ConveyorSegment` 实现 `IWorkshopDevice` 并被统计；管道走 `MapComponent_PipeNetwork` 距离表路由（段→出口段惰性 BFS）。
- 仓储对接缝已存在：`IItemStorage`/`CompItemPort`（设备 `Push` 进仓）、`CompItemStorage` 的 `cropOnly` 白名单。

**候选方案**
- 车间产出自动出仓：设备 → 相邻管道段（`CompItemPort`）→ 距离表路由到 `IItemStorage`/`cell` 目的地。
- 车间是否要"绑定默认出库点"（类似 `PipeDestination`）？还是完全靠管道网络自然汇聚？

**开放问题**
- 车间与管道网络的"归属"是否要强绑定（车间管理面板里配置出库点），还是纯几何相邻即可？
- 多车间共用一条主管道时的反压/优先级如何？

### T4｜排班与生产联动

**现状**：`duty` = 走到工位格 → 站岗（`ToilCompleteMode.Never`）→ 排班结束 `FailOn` 收工。当前**站岗没有任何生产行为**。

**候选方案**
- **T4-a 人员仅监察/维护/补料**：设备自驱（农机已如此），人员排班解决"谁来盯着/补料/应急"，不改变设备运转。
- **T4-b 在岗驱动设备**：人员到岗后 `NotifyDutyStarted` 触发区内设备启停/喂料（车间作为控制器 C 方案）。
- **T4-c 任务细分**：`WorkshopTaskType`(Production/Maintenance/QualityCheck/Standby) 已定义未使用——是否在岗期间按任务类型做不同行为（如质检员只巡检不操作）。

**开放问题**
- 农机全自动后，人员站岗的"价值"是什么？（补料？应对故障？战备？）
- 工时上报已按 `WorkTimeSample` 落地，是否要按 `WorkshopTaskType` 细分采样来源？

### T5｜管理 UI 范围

**现状**：7 页壳（Overview/Devices/Members/Schedule/Agriculture/Recipes/Settings），其中 Recipes/Settings 为空壳。

**候选方案**
- 配方页：若 T1 选 A，则配方页可省略或改为"设备配方总览"；若选 C，则配方页是"车间产线配置"入口。
- 设置页：车间级开关（如是否启用排班、默认出库点、配色）。
- `ITab_WorkshopManage`：注释悬空引用，当前仅 gizmo 弹窗。是否要"选中车间→右侧检视 Tab 打开管理面板"？

**开放问题**
- 蓝图要优先填哪个空壳页？
- 弹窗 vs 检视 Tab 的取舍（PM 此前拍板"只有 gizmo 弹窗"，是否维持）？

### T6｜多车间 / 跨图 / 性能

**现状**：`activeWorkers`/`dutySpots` 运行态、读档重建 OK；`ScanDevices` 仅在 `Refresh` 时全格遍历（非每帧）；`ProcessRotations` 每 60 tick。

**开放问题**
- 大型基地（几十个车间、单车间上千格）下 `AllWorkshops` 遍历 + `IsScheduledForDuty` 的频次是否够低（已在 WorkGiver 单次调用路径，非每帧，OK）？
- 跨图（多个 Map）MapComponent 各自独立，是否符合预期？

## 4. 下一步建议（与蓝图解耦的阻断项）

1. **先修 §1.4-1 的 `MapComponent_WorkshopManager` 注册**，否则排班/轮岗/在岗全部失效，无法实测任何蓝图假设。最小修复（照 `MapComponent_PipeNetwork.Get(map)` 模式）：
   ```csharp
   public static MapComponent_WorkshopManager Get(Map map)
   {
       var c = map.GetComponent<MapComponent_WorkshopManager>();
       if (c == null) { c = new MapComponent_WorkshopManager(map); map.components.Add(c); }
       return c;
   }
   ```
   并让 `WorkGiver_Workshop` / `JobDriver_WorkshopDuty` / `WorkshopManageView` 改用 `Get(map)`。
2. 清理 §1.4-2 悬空注释（`Building_AutoProcessor` / `ITab_WorkshopManage`）。
3. 逐议题（T1→T6）在本文档 §2 收敛结论，再进入实现文档阶段。
