## 0. 一句话结论

给「车间已追踪设备」增加重命名：入口在 车间管理 → 设备页 行内（形态见 O-3）；名字存进设备台账条目（加性字段，无 Migration）；经**单点 Harmony Postfix**（RimWorld.GenLabel.ThingLabel(Thing,int,bool,bool)）让**原版全局**显示新名；禁止同图重名（重命名提交时拒绝）；清空即恢复默认名。Harmony=Yes ⇒ **触发 Architecture Review + EXC（E2）**。

## 1. 背景与目标（含非目标）

### 1.1 背景

- 玩家痛点：车间内多台同类设备（如 4 台「炉灶（电力）」）在原版检查面板、设备卡等处全部同名，无法区分；现有 PC 别名（A/B/C…）只解决 PC 内界面区分，玩家要的是「自己起的名字在原版界面里也生效」。
- 玩家已裁决四项范围（不再变更）：① 生效范围＝原版全局显示新名；② 入口＝车间管理→设备页列表行内；③ 校验＝禁止重名 + 清空即恢复默认；④ 可改对象＝仅车间已追踪设备（WorkshopDeviceLedger 条目不存在的设备改不了）。
- 歧义句「允许车间体系设备页面自动重命名」列入开放决策 O-1（候选 A 批量自动命名 / 候选 B 仅指设备页手动重命名），本文档默认按候选 B 设计。

### 1.2 目标（做什么）

| 编号 | 目标 |
|---|---|
| G1 | 设备页行内提供重命名入口（逐行小按钮，或双击；见 O-3），对话框预填当前自定义名 |
| G2 | 新名在**原版全局**生效：原版检查面板标题、选中信息、堆叠名等一切经 Thing 标签的显示；PC 内设备页/设备卡/图例同步 |
| G3 | 重名拒绝（同一张地图内不允许两台同名设备）+ 清空恢复默认名；校验覆盖 读档 / 建造 / 重命名 三条路径（§4.3） |
| G4 | 仅车间已追踪设备可改（台账条目存在 = IsTracked） |
| G5 | 数据安全：存读档闭环、旧档无 Migration、补丁失败不破坏原版 UI（降级为默认名） |

### 1.3 非目标（明确不做）

- 不给原版检查面板注入改名按钮（入口固定为设备页；不实现 IRenameable、不改 thingClass）。
- 不给非车间设备改名（普通建筑 / 未追踪设备一律不可改）。
- 不做按规则批量自动命名（除 O-1 裁决为候选 A 另行立项外）。
- 不改任何第三方 Def；不引入硬依赖；不替换既有别名系统（A/B… 继续作为 PC 内稳定标识）。
- 不做「改名同步到蓝图/同类设备」等衍生扩散——名字是**单台设备**的实例属性。

## 2. 术语与约定

| 术语 | 定义 |
|---|---|
| 默认名 | 设备固有显示名：WorkshopStats.DeviceLabelOf(thing)（IWorkshopDevice.DeviceLabel 优先，否则 def.label） |
| 自定义名 | 玩家为重命名写入的名字；空 = 无（归一化：Trim 后为空视为清空） |
| 有效名 | 自定义名 ?? 默认名 —— 重名比较与显示的统一键 |
| 显示名（PC） | 别名 + " · " + 有效名（沿用 MapComponent_WorkshopManager.DisplayNameOf 现有语义） |
| 原版显示 | 只显示有效名本身（**不加别名前缀**——别名是 PC 内部标识，不注入原版） |
| 台账 | WorkshopDeviceLedger（按 thingIDNumber 索引，随存档） |
| 追踪 | 台账条目存在（IsTracked）；由设备扫描路径每 60 tick Touch 登记、PruneNotIn 淘汰 |
| 收口点 | RimWorld.GenLabel.ThingLabel(Thing t, Int32 stackCount, Boolean includeHp, Boolean includeQuality)：全部 Thing 标签变体的唯一收口（已核实，build 1.6.4871） |
| 比较集 | 重名校验的目标集合：同一地图内、全部车间当前扫描到的设备（排除自身）——见 §4.2 |

## 3. 需求条目（REQ-WORKSHOP-001 ~ 010）

> 条目 ID 按 REQ-004 格式（REQ-<功能域>-<三位序号>），本功能域首次登记为 WORKSHOP；条目废弃时保留 ID 并标状态，不复用。

### REQ-WORKSHOP-001 设备页行内重命名入口

- 描述：车间管理 → 设备页的每一行提供重命名动作（形态：逐行小按钮 或 双击行，见 O-3）；打开改名对话框并预填当前自定义名（无则空）。
- 验收（可观察）：
  - Given 某车间设备在设备页可见，When 触发该行重命名动作，Then 弹出改名对话框且输入框预填当前自定义名（无自定义名时为空）。
  - 单点行的既有语义（跳转镜头并选中设备）不被破坏（REQ-WORKSHOP-009）。

### REQ-WORKSHOP-002 生效范围＝原版全局

- 描述：重命名后，一切经 Thing 标签显示的位置都显示新名（原版检查面板标题、选中信息、堆叠名等；PC 内设备页/设备卡/概览图例/瓶颈图/设备库同步）。
- 验收：
  - Given 设备已改名，When 选中该设备看原版检查面板，Then 标题为自定义名（非 def 默认名）。
  - Given 设备已改名，When 查看 PC 设备页/设备卡标题，Then 显示自定义名（PC 显示名可带别名前缀，原版不带）。
  - 覆盖面论证：经单点收口 RimWorld.GenLabel.ThingLabel(Thing,int,bool,bool)（已核实：get_LabelNoCount / get_LabelNoParenthesis / GetCustomLabelNoCount 均汇入该重载）。

### REQ-WORKSHOP-003 仅车间已追踪设备可改

- 描述：可改对象＝设备扫描已登记、WorkshopDeviceLedger 条目存在的设备；条目不存在 ⇒ 拒绝并给出理由。
- 验收：
  - Given 设备未被台账追踪（无条目），When 提交改名，Then 拒绝 + 消息（Key：ErrNotTracked），不写入任何数据。
  - Given 设备已被追踪，When 提交合法改名，Then 写入成功。

### REQ-WORKSHOP-004 禁止重名（同一张地图）

- 描述：候选名不得与同图比较集中任一设备的有效名相同（归一化与比较规则见 §4.2）；违反 ⇒ 拒绝 + 消息（附冲突设备标识）。
- 验收：
  - Given 设备 B 有效名为「X」，When 对设备 A 提交「X」，Then 拒绝 + 消息（Key：ErrDuplicate，{0}=冲突设备显示名）。
  - 校验集合必须随 读档/建造/重命名 三路径保持正确（§4.3 矩阵；校验在提交时**实时计算**，无独立缓存）。

### REQ-WORKSHOP-005 清空即恢复默认

- 描述：输入清空（Trim 后为空）提交 ⇒ 移除自定义名 ⇒ 原版与 PC 均回落默认名；清空动作本身不受重名校验约束。
- 验收：
  - Given 设备有自定义名，When 清空提交，Then 自定义名被移除、原版恢复默认名、PC 恢复默认显示；重复清空幂等（无报错、无副作用）。
  - 归因边界：清空恢复出的默认名**可能**与某设备自定义名重复（后致同名，残余 R-2，§4.3）；不自动改名、不编造。

### REQ-WORKSHOP-006 存读档闭环（无 Migration）

- 描述：自定义名随设备台账条目存档；旧档无字段 ⇒ 照常加载（默认 null = 无自定义名）。
- 验收：
  - Given 改名后存档再读档，Then 名字保留且原版/PC 显示一致。
  - Given 旧版本存档（无 customName 字段），When 加载，Then 无报错、全部设备显示默认名。
  - 离线 Scribe 往返单测通过（沿 WorkshopWorkDemotionScribeTests 范式）。

### REQ-WORKSHOP-007 性能预算（GATE-PERF 对象）

- 描述：收口点位于 UI 每帧热读路径；无任何自定义名时，Postfix 必须两次判空即早退、零分配；有名字时仅增加一次 int 字典命中。
- 验收（预算见 §11）：
  - 静态审查：Postfix 无 LINQ、无字符串拼接、无装箱；try/catch 不引入稳态开销。
  - 离线微基准（Tier B，实现轮执行）：无名字场景相对原方法的开销可忽略（阈值与度量方法在实现轮登记）。
  - 未执行游戏内 PerfProbe（Tier C）时不得判定 PASS。

### REQ-WORKSHOP-008 降级与回滚

- 描述：补丁异常/签名漂移 ⇒ 原版显示不受影响（回落默认名）并有启动诊断；提供设置开关关闭「自定义名应用到原版 UI」。
- 验收：
  - Given 补丁未注册（模拟签名漂移），When 启动并进游戏，Then 无崩溃、原版显示默认名、日志有 Warning 诊断。
  - Given 设置开关关闭，Then 原版回落默认名（PC 自绘仍显示自定义名）；重开开关即时恢复。

### REQ-WORKSHOP-009 入口交互不破坏既有行为

- 描述：行内重命名动作与「单点行＝跳转镜头并选中」互不干扰；重命名动作具备悬停提示（LAND-008）。
- 验收：单点行仍跳转选中；触发重命名不触发跳转（或可容忍的既定实现语义，见 O-3）；悬停提示含「重命名」说明行。

### REQ-WORKSHOP-010（开放）设备页自动重命名

- 描述：玩家原话「允许车间体系设备页面自动重命名」存在歧义。候选 A：设备页提供按规则的批量自动命名；候选 B：仅指设备页内可直接执行手动重命名、不引入自动规则。
- 状态：待玩家裁决（§14 O-1）。本文档其余章节按**候选 B**（推荐）设计；若裁决为 A，需追加需求条目（批量规则定义/冲突策略/预览）后再进入实现。

## 4. 命名与校验规则（核心语义）

### 4.1 归一化规则

| 项 | 规则 | 理由 |
|---|---|---|
| 首尾空白 | Trim；Trim 后为空 = 清空（等价 null） | 与 Dialog_RenameWorkplace 现有 CommitAndClose 归一化一致（Archive/Dialog_RenameWorkplace.cs:135-150） |
| 内部空白 | 原样保留 | 不做隐式改写，玩家输入即所见 |
| 长度 | 不设硬上限（与原版改名对话框一致）；显示端截断兜底（设备页已有 TruncateToWidth） | 避免编造额外限制；超长风险记录为残余 R-3 |
| 相同名提交 | 归一化后等于当前自定义名 ⇒ 无操作（不写盘、不提示或轻提示，实现取无操作） | 幂等 |
| 大小写 | 比较用 OrdinalIgnoreCase（推荐，待 O-2 确认）；存储保留原样 | 防 Stove/stove 视觉重名 |

### 4.2 重名校验规则

- 校验时机：**重命名提交时**（对话框确定）实时计算；无独立校验缓存（保证读档/建造后始终正确）。
- 比较集：同一地图、全部 Zone_Workshop（AllWorkshopZones）**当次 fresh 扫描**到的设备（WorkshopStats.ScanDevices），排除自身。
  - 为什么 fresh 扫描：设备可建造/拆除，缓存可达 20 游戏秒滞后（deviceScanCache，20×60 tick）；重命名是低频玩家动作，允许同步扫描换取正确性（§11）。
  - 与「已追踪」口径的关系：目标设备**必须已追踪**（REQ-003）；比较集取扫描结果（含刚扫描到、尚未 Touch 的设备）——偏严一档，优先挡住重名。
- 比较键：有效名（自定义名 ?? 默认名），Trim + OrdinalIgnoreCase。
- 命中 ⇒ 拒绝：Messages.Message（Key：ErrDuplicate，参数 = 冲突设备的显示名（别名 · 有效名）/ 无别名则有效名）。

### 4.3 校验与不变式 · 三路径矩阵（玩家要求覆盖 读档/建造/重命名）

| 路径 | 事件 | 系统动作 | 结果与残余 |
|---|---|---|---|
| 重命名 | 提交候选名 | 追踪校验（REQ-003）→ 归一化 → 比较集实时重算 → 重名校验 | 通过 ⇒ 写条目；否则消息拒绝（不写） |
| 建造 | 新设备被扫描/登记（Touch） | 默认名合法即登记，**不拒绝建造**（无法也不应替设备改名）；登记后自动进入后续校验的比较集 | 新设备默认名可能与既有自定义名相同（后致同名）⇒ 残余 R-2：仅显示层可能同名，不自动改名、不编造；未来一切改名都会与它比对 |
| 读档 | Scribe 恢复条目（含 customName） | 名字随条目恢复；运行计数标志重算；比较集无缓存、实时重建 | 旧档无字段 ⇒ 默认名；理论遗留冲突（设计上不可达）仅日志，**绝不静默改名** |

> **不变式申明（诚实边界）**：本功能能主动保证的是「**任何一次重命名提交都不会引入与当前比较集的重名**」。无法在系统层面保证全局任意时刻零同名——因为 ① 清空恢复出的默认名（REQ-005）与 ② 后续建造的默认名（上表）都可能与既有名字相同，而这两路径都不允许被拒绝/自动改写。此为设计内残余（R-2），与玩家裁决「清空即恢复默认」一致。
>
> **为什么默认名之间本就允许重复**：车间内多台「炉灶（电力）」的现状即默认名重复，这是原版事实（别名系统的存在动因）。本规则不允许「重命名动作」制造重复，但不追溯清理既有默认名重复。

### 4.4 生命周期与淘汰

- 自定义名与台账条目**同生命周期**：设备拆除 / 长期收存（minify）后，扫描不再见它 ⇒ 下轮 PruneNotIn 淘汰条目 ⇒ 名字一并失效（与运行统计同规，不是新规则）。
- ≤20 游戏秒 的短暂窗口内装回，条目可能尚未被淘汰 ⇒ 名字可能保留（时序相关）；以「台账语义」为准，游戏内验证项见 §15 U-6。
- 重新建造 = 新登记（不继承任何旧名）。

### 5.2 扩展点选择（AI-003 风险升序）与被跳过方案

| 阶梯 | 方案 | 判定 | 理由 |
|---|---|---|---|
| 原生 Def/XML | Def patch 改标签行为 | ✕ | 运行期 Label 与 Def 无关 |
| DefModExtension | 挂扩展读工具 | ✕ | 只影响本系统消费方，触不到原版 |
| Comp/GameComponent | Comp 带名 + 原版按钮 | ✕ | Comp 改不了宿主 Label；按钮判 isinst(IRenameable)（IL_02B1→IL_02DF，已核实） |

| PatchOperations(XML) | 原版 PatchOperation | ✕ | 仅能改 Def XML，改不了运行期返回值 |
| **Harmony Postfix** | **单点收口替换** | **✔ 唯一可行** | 见 5.3；全链唯一收口 + 缓存之后拿到 Thing 引用 |
| Harmony Prefix | 前置拦截 | ✕ | 无必要性；风险高于 Postfix（COMP-005 风险序） |
| Harmony Transpiler | IL 级早退 | ✕ | 脆弱性最高（见 5.5） |

**被跳过方案记录**（AI-003：必须记录被跳过方案及原因；含对玩家既有判断的复核）：

1. **thingClass Def patch → PC 子类 override Label**：同意不可行。补强：① 任意/第三方工作台 Def 不可穷举，运行期改 Def = 改第三方 Def（AI-004 禁）；② 改 thingClass 即改 Scribe 节点类型名，旧档反序列化必须兼容；③ 存量已建实例不迁移；④ 等价收口需覆盖 Label / LabelNoCount / LabelNoParenthesis 多个成员，成本远超单点。

3. **零 Harmony 暗桩**：同意不存在（Cecil：fieldsearch customName / renamableName 均空）。

### 5.4 单点 Postfix 设计（实现轮规格）

- 目标：RimWorld.GenLabel.ThingLabel(Thing, Int32, Boolean, Boolean)（按重载精确定位：HarmonyPatch 传 new Type[]{ typeof(Thing), typeof(int), typeof(bool), typeof(bool) }）。
- 形态：public static class（新文件 Capture/Patch_WorkshopDeviceLabel.cs）；Postfix(Thing t, ref string __result)。
- 早退结构（零分配、无字符串操作、无 LINQ）：
  1) 外层 try/catch 包住全部逻辑（catch 静默——绝不打断原版调用点）。
  2) Map map = t.Map；map == null ⇒ 跳过车间名查询（未生成 / 非地图实体）。
  3) MapComponent_WorkshopManager mgr = TryGetExisting(map)（只读不创建）；mgr == null 或 !mgr.HasAnyDeviceCustomName ⇒ 快路径直跳 4。
  4) string name = mgr.CustomNameOf(t)；非空 ⇒ __result = name；return。
  5) （方案 A 合并后）遗留档案覆盖查询：Current.Game 组件计数为 0 即跳；命中 ⇒ 替换。
- 新增只读入口 **MapComponent_WorkshopManager.TryGetExisting(Map)**：Cache.TryGetValue 命中即返回；miss 时 map.GetComponent 只读探测（不创建、不 Add），命中则回填 Cache。理由：现有 Get() 内含创建（Cache.GetValue → Create → new + m.components.Add），热路径读标签不允许为只读查询创建组件。
- 实现纪律：patch 类 public；启动签名探测；EXC 登记（§12）；发布区 dll 同步（发布约定）。

### 5.6 与既有 Patch_BuildingLabel 的关系（必须处理，否则双源覆盖冲突）

- 现状：BuildingLabelOverrides（ChronicleGameComponent，key=thingIDNumber）由 v1.1.4 工坊别名链路写入；其 UI 写路径已休眠（Archive/Dialog_WorkplaceList.cs:248 注释「不再改设备名」），仅 DevTestButtons + 公共 API 可写；旧档可能残留条目。
- **对玩家的直接含义（2026-10-05 补，主 Agent 复核）**：玩家诉求的「原版全局显示新名」这一半，**既有链路若可写即已覆盖**（Postfix on `Thing.get_Label` 会让原版检查面板标题显示别名）。因此本功能的实质增量＝四件事：① 车间设备页行内入口（替代已休眠的 ITab 写路径）② 禁止重名校验 ③ 收口点从 `Thing.get_Label` 升级到 `GenLabel.ThingLabel` 全变体（补齐 `LabelNoCount` / 堆叠名等——既有补丁对堆叠物会把整个「原名 xN」替换成纯别名）④ 与车间台账合并为单一真相源。⇒ 实现轮应优先复用既有原语（`SetBuildingAlias` / 覆盖表语义），而非另起一套平行机制。
- 冲突场景：同一台设备既有档案覆盖、又有车间自定义名 ⇒ 两个 Postfix 在不同方法上（GenLabel 内层先执行、get_Label 外层后执行）⇒ **Thing.Label 读路径上旧覆盖盖掉新名，其他标签变体上新名生效 ⇒ 同机两名**（同屏两处不一致）。
- **方案 A（推荐 · 合并）**：档案覆盖查询并入新单点 Postfix（优先级：车间自定义名 > 档案覆盖 > 原版），退役 Thing.get_Label 挂点。收益：单点、无顺序歧义、全变体一致；对档案覆盖从「仅 Label 属性」扩展到全变体（行为改良，需 GATE-COMP 复核回归）。
- **方案 B（保守备选）**：保留旧补丁并在其查询前加「车间自定义名存在 ⇒ 让位」守卫。差异：档案覆盖仍只作用于 Label 属性；label 族补丁保持 2 个。
- 共同要求：EXC-2026-001 清单更新（#14 目标变更 或 新增条目 + 变更记录）。默认按方案 A 进入评审；若 GATE-COMP 判定扩大档案覆盖面风险不可接受 ⇒ 回落方案 B。

## 11. 性能预算（GATE-PERF 对象）

**热路径定位**：RimWorld.GenLabel.ThingLabel 是 UI 每帧热读路径（标签绘制 / 检查面板 / 堆叠名），玩家明确要求 Postfix 零分配、无名字时一次判空即返回。

| 场景 | Postfix 操作序列 | 分配 |
|---|---|---|
| 无名字（占绝大多数） | 1) t.Map 判空；2) TryGetExisting（CWT TryGetValue，miss 后 GetComponent 只读探测并可回填）；3) HasAnyDeviceCustomName == false ⇒ 返回 | 0 |
| 命中自定义名 | 上行 + 1 次 int 字典命中（CustomNameOf）+ 引用替换（__result = name） | 0 |
| 异常 | try/catch 静默 | 0（稳态） |

**关键规避点**：

- 替换必须做在**标签缓存之后**（2000 条 LabelRequest 缓存 key 不含 thingID；提前替换会跨设备互相污染——已核实）。
- 无字符串拼接 / 无截断 / 无 LINQ / 无装箱 / 无闭包捕获（全部引用类型直传）。
- 「一次判空即返回」= HasAnyDeviceCustomName 快标志（§6.1）：无任何自定义名时只多两次判空。
- 有名字时的字典 key = thing.thingIDNumber（int 哈希，无分配）。

**证据计划**（PERF-003）：

| 层级 | 内容 | 本轮状态 |
|---|---|---|
| Tier B（离线） | 微基准：有/无 manager、有/无名字三态下 Postfix 相对基线的增量耗时与分配（Stopwatch / GC.GetAllocatedBytesForCurrentThread，登记方法学与阈值） | 未执行（实现轮） |
| Tier C（游戏内） | PerfProbe 采样 + 帧时间对照（开/关设置开关、有/无名字） | 未执行（游戏内验证轮；未执行则 GATE-PERF 不得判 PASS） |

**存量对照**：现有 Patch_BuildingLabel 已在同类热路径（Thing.get_Label）执行同量级字典查询并稳定；本设计把查询**合并进更少的挂点**（2→1），且新增快标志把「无名字」场景压缩到两次判空。

### O-1 「允许车间体系设备页面自动重命名」语义歧义（玩家原句）

- **候选 A**：设备页提供按规则的**批量自动命名**（如按 def 生成「炉灶 1 / 2 / 3」或模板化命名）。需要：命名模板定义、批处理范围选择、与「禁止重名」「不编造（LAND-009）」的冲突消解、撤销/预览等 —— 体量与风险都够独立立项。
- **候选 B**：仅指「设备页内可直接执行（手动）重命名」，不额外引入自动规则 —— 本文档四范围的自然覆盖。
- **推荐：B**。理由：① 与四项范围裁决自洽（本轮是手动改名闭环）；② 既有别名系统（A/B/C…）已经提供「自动可区分标识」，自动命名的边际收益低；③ A 需要命名模板、冲突策略、批处理 UI 与撤销设计，属独立需求；④ 按 AI-001 最小安全假设，不凭「方便」扩大范围。

### O-2 「重名」比较语义确认

- 推荐语义（本文档默认）：比较集 = 同图全部车间 fresh 扫描设备（排除自身）；比较键 = 有效名；比较规则 = Trim + OrdinalIgnoreCase；清空不受限；残余 R-2 接受（§4.3）。

### O-3 设备页行内入口形态

- **推荐：行尾固定宽「改名」小按钮**（可发现性优先；成员页行尾按钮有直接先例；需过 GATE-UI 列宽复核）。

**③ 🔴 重大更正：§5.2 第 3 条「零 Harmony 暗桩不存在」被部分证伪。**
`Verse.ThingComp.TransformLabel(String label) -> String` 是**原版正式的 per-instance 标签变换钩子**（`public virtual`，默认 `return label`；`ThingWithComps.get_LabelNoCount` 与 `GetCustomLabelNoCount` 都逐 comp 调用它）。原版**已用它做同类事**，共 9 个覆写者：`CompArt`（艺术品标题）、`CompBiocodable`（生物编码武器）、`CompBladelinkWeapon`、`CompDestroyAfterDelay`、**`CompGeneratedNames`（生成名）**、`CompHasPawnSources`、`CompHasSources`、`CompStyleable`、`CompUniqueWeapon`。

- **为什么不改用它**：comp 只能经 **`ThingDef.comps`（Def 级静态）** 挂载 ⇒ 需逐 Def 做 XML Patch；而本功能的对象是「**任意**车间已追踪工作台」（含第三方与后续新增 Def），**不可穷举** ⇒ 不作为唯一路径（§5.2 的结论方向仍成立，但**理由须改为「原生钩子存在但受挂载面限制不可穷举」，不得再写「不存在」**）。
