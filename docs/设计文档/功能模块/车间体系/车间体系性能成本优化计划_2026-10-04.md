# 车间体系性能成本优化计划（2026-10-04）

**范围**：PersonalChronicle 车间管理体系（`Source/PersonalChronicle/Automation/` 车间域 + 其直接依赖的 Capture patch 与物流组件）
**宿主**：RimWorld 1.6.4871（rev591）
**取证方式**：只读代码审计（code-explorer，98 次工具调用）+ 既有 Player.log 实证
**约束**：玩家在同一台机器玩游戏（CPU/IO 敏感）；**任何优化不得改变玩法语义，不得要求玩家改玩法**

---

## 0. 现状量化（审计结论）

### 0.1 tick 路径（`MapComponentTick`，`CheckIntervalTicks = 60`）

| 项 | 复杂度 | 频率 | 分配 |
|---|---|---|---|
| `ReconcileDutyPlan` | 2 遍 `dutyPlan` | 每轮；重建受标脏 + 20 秒兜底 | 无 |
| `PurgeDeadReferences` | O((slots+rotations)×**Z**)（`IsAlive` 内含 `AllZones.Contains`） | 每轮 | 无 |
| `PruneScheduleHistory` | O(`AllZones`) + 每车间 prun | 每轮，**无天数门控** | 无 |
| `ProcessRotations` | O(rotations)，0 时早退 | 每轮 | 可能 |
| `AccumulateDeviceRuntime` | O(Z) + O(设备数)；每 20 轮全格扫描 | 每轮 | **每轮 1 个 `List<Zone_Workshop>`** |
| `DetectDeviceChannelChange` | O(Z) + **O(设备数 × defName 长度)**（逐字符 FNV 重算） | 每轮 | **第二个 `List<Zone_Workshop>`** |
| `ApplyOffShiftWorkTypes` | 门控命中时 O(Z×班组×班次)，最内层 **DefDatabase 查表** + 每(班组,班次) `new HashSet` | **每游戏小时 ≤1 次** | 命中时 1 List + N HashSet |
| `RestoreOnShiftWorkTypes`（本轮新增） | 门控命中时 O(Z) + O(scope×types)，每格过 `WorkTypeIsDisabled`（进 Harmony） | **每游戏小时 ≤1 次** | 命中时 1 List |

**稳态结论**：**每 60 tick 约 2 次 `List` 分配、无 LINQ/闭包**；`AllWorkshopZones()` **每轮被调 2 次**（重复分配 + 重复扫 `AllZones`），是可立刻消除的浪费。tick 路径本身**不重**。

### 0.2 UI 绘制路径（每帧）

`Refresh()` 只在开窗 / 刷新按钮 / 排班变更时调用，重活已正确下沉到 Refresh 期（`ScanDevices`、各 `Build*Cache`）。

**每帧真问题只有一个，但很大**：

* `UIComponents.TruncateToWidth` 在**绘制期无命中门控**（对比 `UIComponents.Label` 有鼠标命中短路）：
  设备页 **7 次/行**、成员页 **6+ 次/行**；每次 = 1 次 `Text.CalcSize` + 二分 ≤log₂(n) 次 `CalcSize`，**每次分配 2 个 `Substring`**。
  ⇒ 15 行设备 ≈ **100+ 次 `CalcSize` + 数百次小字符串分配/帧**。
* `T("Key")` 在绘制路径做 拼接 + `Translate` + `ToString`（每次 2 串分配）；项目已有零分配的 `UIComponents.Loc`（语言级缓存）但本文件未用。

**未发现**每帧 `ScanDevices` / `GetComponent` / Def 遍历 / `listerThings` 遍历 —— 这点是干净的。

### 0.3 日志与 IO（**玩家体感最明显**）

| 日志点 | 频率 | 门控 |
|---|---|---|
| 🔴 `ItemPort pushed <def> x<n> …`（`CompItemPort.cs:241`） | `pushIntervalTicks = 90` ⇒ **每端口每 90 tick 一行** | **无** |
| 🔴 `PipeSeg delivered <def> x<n> @<cell>`（`Building_PipeSegment.cs:330`） | **每批搬运一行** | **无** |

如实机日志所示：10 个端口的基地在 1 倍速下约 **6–7 行/秒**，3 倍速约 **20 行/秒**，每行一次同步 `Log.Message` 写入 `Player.log`。
⇒ **单位时间成本最高的一项**，且完全不影响玩法语义。

### 0.4 StatPart 热路径（此前被注释掩盖）

`WorkshopBonusResolver` 的取值源 `WorkingBonusOf` 注释自称"无遍历"，实际路径：

```
WorkingZoneOf → ActiveZoneOf(O(1)) 否则 → WorkshopZoneUtility.WorkshopAt = 遍历 AllZones
```

而它是 `StatPart_WorkshopWorkSpeed` / `StatPart_WorkshopResearchSpeed` / `WorkshopRatingShift` 的取值源
⇒ **未在岗者每次求工作速度/研究速度都要 O(Z) 遍历**。注释失真，需修。

### 0.5 可观测性缺口（决定"优化无法验证"）

车间体系（`MapComponent_WorkshopManager*` / `WorkshopManageView*` / `WorkshopStats`）**零 `PerfProbe` 调用**。
`PerfProbe` 已存在且零开销关闭（`EnablePerfProbe`，默认 false，唯一消费点在 `ChronicleGameComponent.GameComponentTick`），现有 7 个 key 全在档案/农业域。
⇒ **不补探针，本计划的收益无法 before/after 对比。**

## 2. 建议的执行顺序与预期

1. **第 0 批 + 第 1 批**（一批交付）：零行为变化，覆盖"最高成本项（日志 IO）+ 最高频项（每帧文本测量）+ tick 里的重复分配"。这是性价比最高的组合。
2. 用第 0 批探针做 before/after 对比（同一存档、同一倍速、同一时长）。
3. 视数据决定是否推进第 2 批。
4. **第 3 批暂不做**，等有明确数据或玩家反馈。

## 3. 不做的事（避免扩大范围）

* 不动任何玩法语义（值勤档位、接管红线、作息策略、摸鱼判定一律不变）。
* 不引入需要玩家改玩法才生效的"优化"。
* 不为省开销而牺牲已披露的可观测性（如"幽灵在岗"读数、作息异常读数）。
* 不重写 `WorkshopManageView` 的绘制架构（除非 1.4 收益被数据证明不足）。

## 4. 风险与回滚

* 第 0 批：只读插点 ⇒ 删除即回滚。
* 第 1 批：1.1 有开关兜底；1.2–1.3 纯内部；1.4–1.5 缓存失效逻辑需单测/实测；1.6 仅注释与 3 处日志键。
* 第 2 批：逐项独立，可单独回滚；2.1 / 2.3 需回归测试（pawn 移动、删车间）。

## 5. 执行记录（2026-10-04 首批）

### ✅ 已完成并部署（编译 0 错 0 警）

| 项 | 文件 | 说明 |
|---|---|---|
| **1.1 物流日志节流** | `CompItemPort.cs`（`pushed` 日志点）、`Building_PipeSegment.cs`（`delivered` 日志点） | 包 `ChronicleLog.Throttled("ItemPort.pushed" / "PipeSeg.delivered", 600)`（10 游戏秒最多一行）。**key 刻意用全局字面量** —— `Throttled` 的键表永不清理，传端口标识（动态键）会让键数随拆建端口无界增长；代价是日志不再逐端口区分，**逐端口排查时把该常量改为 0 即恢复原行为**。 |
| **1.2 `AllWorkshopZones()` 每轮复用** | `MapComponent_WorkshopManager.cs`（`MapComponentTick` + `AccumulateDeviceRuntime` 签名） | `MapComponentTick` 取一次 `zones`，`AccumulateDeviceRuntime(zones)` / `DetectDeviceChannelChange(zones)` 改接参 ⇒ 消除每 60 tick 一次的 `new List` + `AllZones` 全表扫描。 |

**验收**：`Player.log` 里 `ItemPort pushed` / `PipeSeg delivered` 行数应下降 ~90%；其他行为不变。

### ⏭️ 复核后**刻意不做**（附理由，避免被误认为遗漏）

| 项 | 决定 | 理由 |
|---|---|---|
| **1.3 `defName` 逐字符 FNV 缓存** | **不做** | 原实现对 `fingerprint` 是**累积式**（`fp = (fp ^ ch) * P`），与初始值耦合 ⇒ 无法"预计算独立哈希再合并"而保持指纹值不变。改成独立哈希会让指纹首轮变化（触发一次多余重算，无害但破坏"零行为变化"承诺），而收益仅 ~400 次乘异或/轮 ⇒ 不划算。 |
| **1.4 `TruncateToWidth` 结果缓存** | **缓做，等数据** | 缓存键含文本，而绘制期文本**高频变化**（数量/位置/进度）⇒ 命中率可能很低，反而新增字典查与存储开销。真正有效的解法是"把逐帧截断下沉到 Refresh 期"（与项目既有范式一致），但那需要重构文本缓存层 ⇒ 先补探针量化，再决定是否值得。 |
| **1.5 `T()` → `UIComponents.Loc`** | **缓做** | `Loc` 的公开签名未取证确认（`grep "public static string Loc("` 零命中，其定义为按语言缓存的逐行实现）；且 `T()` 同时被绘制路径与方法体调用，改动面大于预期 ⇒ 需先确认签名与语义等价性。 |
| **1.6 注释失真（3 处）** | **部分待做** | `dutyPlan`「兜底 1 秒」→ 实际 `DutyPlanFallbackIntervals = 20`（20 秒）；`WorkingBonusOf`「无遍历」→ 实际未在岗时遍历 `AllZones` 且落在 stat 热路径；`Throttled` 3 处动态键（`RuifBridge` 2 处、`BuiltinPopulationProvider.Overview` 1 处）。**这三处属"文档/注释级"，不影响运行**，列入下一批（其中 `WorkingBonusOf` 优先，因为它误导他人以为可安全放热路径）。 |
| **第 0 批探针** | **延后** | `PerfProbe` 数据只落 `Player.log`，玩家不会主动查看；其价值主要在**下一次由我排查**时提供依据 ⇒ 不阻塞本次优化，与 1.6 同批补。 |

### 结论

本批交付的两项都是**确定节省资源、零玩法语义变化**的改动：
日志 IO（单位时间最贵）与 tick 重复分配（频率最高）。
其余项经复核判定为"收益不抵风险/需先量化"，**不做不是遗漏，而是避免在无数据时引入复杂度**。
