## 1. 需求（用户原话）

> 「对于车间人员无法自动生效 work 的机制，我建议对齐车间类型。按车间类型自动分发原版的 work，也就是将车间工作优先度最高。」

拆解为 3 条可验收目标：

| # | 目标 |
|---|---|
| G1 | **对齐车间类型**：车间排班 → 该车间类型 Def 声明的原版工作类型（沿用 `WorkshopTypeDef.*WorkTypeDefNames` 映射，不另建一套对应关系） |
| G2 | **自动「分发」**：被排班的成员在原版「工作」面板中，这些工作类型被启用（勾选）——**已在 `CHG-SHOP-4FIX-001` 落地** |
| G3 | **优先度最高**：这些工作类型的优先级被提升到最高档，使原版排工优先派它们 |

本文只讨论 **G3**（G1/G2 已实现）。

---

## 2. 现象与根因

现状（`CHG-SHOP-4FIX-001` 后）：排班变更时把映射的原版工作类型由 `0` 档开为**默认档 3**，不改档位。

后果：即便工作被启用，它也只是「参与排队」，排在所有更高优先级工作之后。

---

## 3. 原版机制取证（反编译实证 · RimWorld 1.6.4871 rev590）

### F1 · 优先级如何决定排工顺序

`Pawn_WorkSettings.CacheWorkGiversInOrder`（:265-269）：

```csharp
float num2 = a.naturalPriority + (4 - this.GetPriority(a)) * 100000;
```

**每档优先级权重 = 100000，而 naturalPriority 最大约 1400。** ⇒ 优先级 **1** 的工作类型（权重 300000）**必定**排在所有 2/3/4 档（200000/100000/0）之前；同档内才比 naturalPriority。

### F2 · ⚠️ 简单模式下优先级完全无效

`Pawn_WorkSettings.GetPriority`（:190-198）：

```csharp
int num = this.priorities[w];
if (this.pawn.RaceProps.Humanlike && num > 0 && !Find.PlaySettings.useWorkPriorities)
    return 3;                      // ← 任何已启用工作一律视为 3
return num;
```

⇒ `useWorkPriorities == false` 时，**写入 1 与写入 3 完全等价**，排序退化为纯 naturalPriority。

### F3 · 该开关默认关闭

`PlaySettings.cs:34`：`useWorkPriorities` 默认 **false**（随存档）。原版开关位置：工作面板左上角「手动优先级」复选框（`MainTabWindow_Work.cs:67-90`，Key `ManualPriorities`）。

### F4 · 最高档就是 1

`Pawn_WorkSettings` **没有** `HighestPriority` 常量；合法档位 `0(关)/1/2/3(默认)/4`（:353-356）。原版工作面板用 `priority != 1` 判定「是否已是最高档」（`PawnColumnWorker_WorkPriority.cs:213`）。⇒ 实现里 **1 必须写成命名常量**（GOV-006）。

### F5 · 「班次时段写 Work」这条链已经有效

`JobGiver_Work.GetPriority`（:20-48）：think 优先级由时间管制表决定 —— `Work → 9`（最高）· `Anything → 5.5` · `Sleep → 3` · `Joy/Meditate → 2`。`SyncVanillaTimetables` 已把班次时段写成 `Work`，所以「时段内是否进入工作分支」不再是问题；问题在**进入工作分支后先做哪类工作**。

### F6 · 原版「强制优先」不适用

`mindState.priorityWork` 仅在 **emergency** 分支消费、需 `WorkGiver` + 目标 `Cell`，且把 job 标为 `playerForced`（`JobGiver_Work.cs:59-80`）。车间值勤是无目标的 `NonScanJob`，且语义是「玩家强制」——不采用。

### F7 · 值勤类型的 naturalPriority 是刻意压低的

`Defs/Automation_WorkType.xml:9-19` 记载：`PC_WorkshopOperation` 曾用 980，导致「被排班的成员**一直站着值勤、不去干活**，而产出类加成要求干活的那位在车间里 ⇒ 整条产出加成链在正常玩法下不可达」，故降到 **350**。

### 原版 naturalPriority 全表（1.6 Core，实测）

```
Firefighter 1400 · Patient 1350 · Doctor 1300 · BedRest 1200 · BasicWorker 1150 ·
Warden 1100 · Handling 1050 · Cooking 1000 · Hunting 950 · Construction 900 ·
Growing 700 · Mining 600 · PlantCutting 500 · Smithing 470 · Tailoring 450 ·
Art 430 · Crafting 400 · [PC_WorkshopOperation 350] · Hauling 300 · Cleaning 200 · Research 100
```

**简单模式下的实际后果**：车间生产类工作（Crafting 400 / Smithing 470 / Tailoring 450 / Art 430 / PlantCutting 500）排在建造 900 / 种植 700 / 采矿 600 **之后**；研究坊的 Research(100) 几乎垫底。这正是「车间人员看起来在闲置（其实在干别的活，或没别的活时站着）」的机制解释。

---

## 4. 由取证推出的硬结论

> **「把车间工作设为最高优先级」只在「手动优先级」模式下有效。**
> 在默认（简单）模式下，原版引擎根本不读优先级（F2）——写 1 与写 3 等价。

因此方案必须**同时**处理两件事：① 提升档位；② 处理简单模式。

---

## 5. 方案设计

### 5.1 核心改动（3 条）

**M1 · 提升映射工作类型到最高档**
在 `MapComponent_WorkshopManager.WorkEnable.cs` 的 `EnableWorkTypes` 中，对**车间类型 Def 映射的原版工作类型**：

```
if (GetPriority(wt) > 0 && GetPriority(wt) != MaxPriority)   // 已启用且不是最高档
    SetPriority(wt, MaxPriority);                            // MaxPriority = 1（命名常量）
```

**M2 · 值勤类型「不」提升（默认）**
`PC_WorkshopOperation` 保持现状（`0 → 默认档 3`），不参与提升。理由＝ F7：值勤是「没别的活干时的兜底/看护产线」，把它顶到最高会重现 Def 注释记载的 P0 反模式（站着不动、产出链断裂）。见决策点 D3。

**M3 · 简单模式守卫 + 可见提示**
`!Find.PlaySettings.useWorkPriorities` 时**跳过提升**（写了也无效），并给出可见提示。见决策点 D1。

### 5.2 待决策点

#### D1 · 简单模式怎么处理？

| 选项 | 行为 | 影响面 | 评价 |
|---|---|---|---|
| **D1-a** | 只在手动优先级模式下提升；UI 显示提示「当前为简单工作模式，优先级提升不生效（在工作面板左上角开启『手动优先级』）」 | 不改玩家设置 | 保守、零副作用；但用户要「自动生效」时还得自己点一下 |
| **D1-b** | 自动把 `Current.Game.playSettings.useWorkPriorities` 置 `true`，并按原版做法对全部玩家 pawn `Notify_UseWorkPrioritiesChanged()` | **改玩家游戏设置；全局所有 pawn 的工作面板都变成优先级模式** | 最"自动"，但属于替玩家改游戏规则，需单独 EXC 覆盖 |
| **D1-c** | D1-a + 在车间面板提供「一键开启手动优先级」按钮（玩家点击才改） | 同上，但由玩家触发 | 折中；推荐 |

> **推荐 D1-c**。理由：既给"一键"通路，又把「改游戏全局设置」的决定权留给玩家（符合 GOV-012「AI 不得绕过人工确认」的精神）。

#### D2 · 玩家控制权边界（最关键）

| 选项 | 行为 | 代价 |
|---|---|---|
| **D2-a（强）** | 无条件把映射工作设为 1：玩家手动设的 2/3/4 **被覆盖**；玩家关到 0 的工作**被重新打开**并设为 1 | 最强"自动生效"；但正是原 SDD 反对的「抢玩家控制权」 |
| **D2-b（中）** | 只提升**已启用**（`GetPriority > 0`）的工作；**不重新打开**玩家显式关闭（0）的工作 | 尊重"我不想让他干这个"的意图；若玩家没关，则一定生效 |
| **D2-c（弱）** | 仅在本 mod 首次为该 pawn 应用时提升一次，之后玩家怎么改都不再动（需持久化"已应用"标记） | 不打扰玩家；但**触碰 Save schema**（新增字段 + Migration），且"新排班后再不生效"不符合直觉 |

> **推荐 D2-b**：它在「自动生效」与「尊重玩家意志」之间取平衡，且不新增持久化字段（不触碰 SAVE-001/004）。
> 若你要最激进的效果（玩家关掉也强行打开），选 D2-a —— 需在 EXC 里额外声明「覆盖玩家关闭意图」。

#### D3 · 值勤类型（`PC_WorkshopOperation`）是否也提到最高？

| 选项 | 效果 |
|---|---|
| **D3-a（保持）** | 值勤维持默认档（3）。车间有活时干活，没活时可被派去看护产线 |
| **D3-b** | 值勤也设为 1 ⇒ **最高档 + naturalPriority 350**，在"没别的活"时会最先被派值勤。但若与映射工作同为 1，映射工作（naturalPriority 更高）仍优先，实际影响有限 |
| **D3-c** | 值勤设为 1 **且**把 `PC_WorkshopOperation.naturalPriority` 提到 1450 ⇒ 值勤压过一切 ⇒ **会复现 F7 记载的 P0 反模式**（站着不干活） |

> **推荐 D3-a**（保持现状）。若你希望「至少有人在产线上」，选 D3-b（风险低）。**D3-c 不建议**，除非同时把值勤 Job 改造成"在车间内找活干"。

### 5.3 被否方案（AI-003 要求记录）

| 被否方案 | 否决理由 |
|---|---|
| 修改原版 `WorkTypeDef.naturalPriority`（简单模式下唯一有效的途径） | 目标是**原版共享 Def**，一改全局所有 pawn 都受影响（非车间场景也变），且属"完整覆写第三方/原版 Def"（AI-004 禁止） |

| Harmony 补丁 `Pawn_WorkSettings.GetPriority` 绕过简单模式 | 引入 Harmony（Harmony=Yes，风险升级），且改原版核心取数语义，收益不抵风险 |

## 8. 验收标准（实机）

1. **手动优先级模式**下：排班变更后，映射的工作类型在原版工作面板显示为 **1**；该 pawn 优先去做它（对照改档前后行为）。
2. **简单模式**下：不报错、不写无效档位，UI 明确提示"优先级提升未生效 + 如何开启"。
3. 玩家手动设的档位：按 D2 选项表现符合预期（D2-b：已设 2/3/4 被提升为 1；已关 0 保持 0）。
4. 非排班人员的工作面板**零变化**；排班外的工作类型**零变化**。
5. 性能：无 tick / 绘制路径写入；`SetPriority` 调用次数与排班变更次数同阶。
6. 存读档：无 schema 变更；读档后不自动重写（或按 ARCH 裁定的对账点执行一次）。
