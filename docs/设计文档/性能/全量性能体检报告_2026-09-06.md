# PersonalChronicle 全量性能体检报告（2026-09-06）

> 方法：源码静态分析（约 59,000 行 / 254 个 .cs）+ 调用链审查 + 1.6 API 事实核对。

## 1. 结论速览

| 维度 | 现状 | 优化后预估（mod 自身） |
|---|---|---|
| **周期性尖峰**（每 600 tick 的世界级扫描） | 3 次全人口扫描 + 2 次世界对象遍历 + O(n²) 社交 | **−60% ~ −80%** |
| **档案/职业面板打开时的 UI 帧耗时** | 每帧重建视图（Translate ×34、排序 ×2、DefDatabase 查表） | **−35% ~ −55%** |
| **自动化设备 tick 成本** | L 档 441 格全量遍历（生长/改造两路无分片） | **−40% ~ −55%** |
| **mod 平均 CPU 占用（综合）** | — | **−35% ~ −55%**（保守 30%／乐观 65%） |

**换算到整体游戏帧率**（关键澄清）：
mod 只占帧时间的一部分。若 mod 占用帧时间的 10%，mod 自身降 50% ⇒ 整体帧时间仅降 5%。
实测口径建议：打开档案面板时整体约 **回升 8%~18%**；平时游戏（无面板）约 **1%~4%**；
**最可感知的收益是消除每 10 秒一次的顿挫**（尖峰 −60%~−80%）。

## 3. 已确认健康（勿重复排查）

## 5. 收益递减说明

- 剩下的成本主要是**必要工作**（数据采样、Stat 计算、绘制本身），无法再压。
- 60%~65% 是现实天花板；宣称更高通常意味着砍功能。
- P2 涉及 UI 数据流重构，收益虽高但回归风险大，**建议在 P0/P1 实测确认后再决定**。

## 6. 如何把"估算"变成"实测"

1. 在 Settings 加一个 `PerfProbe` 开关（默认关），打开后：
   - 在 `GameComponentTick` 的 600 tick 分支、`SampleWorkTimeAndPlaces`、`DriveGrowth`、`BuildCells` 入口各埋一个 `Stopwatch`；
   - 每 60 秒把「调用次数 / 总毫秒 / 最大单次毫秒」写入 Player.log。
2. 造档基准：20 人殖民地 + 3 台 L 档农机 + 1 条 20 段管道 + 世界 80 个对象，跑 5 分钟。
3. 记录 before/after 的**平均帧时间**与**最大单帧**（尖峰）两个指标，后者才是玩家能感知的顿挫。

### 重估后**不执行**的两项（附理由）

| 项 | 原判 | 重估结论 |
|---|---|---|
| P1-3 `DriveGrowth` 分片 | 高 | **不做**。分片会拉长每格更新间隔，必须同步放大 `scale` 才不破坏生长速率，属**功能性变更**；而绝对成本仅 ≈110 次 `GetPlant`/秒/台（441 格 ÷ 250 tick），收益远小于回归风险 |
| P1-2 合并两次 `AllWorldObjects` 遍历 | 高 | **不做**。`ArchiveLocationsByColonists` 开头有 `if (visitedTiles.Count == 0) return;` 早退（商队未停靠时不执行），实际每 600 tick 只有**一次**全量遍历；世界对象通常几十~几百个，收益不抵重构风险 |

> 教训：**"全量扫描"是模式判断，不等于高成本**——必须结合"循环体是否早退"与"实际频率"核算绝对量，否则会为了低收益改动引入高风险。
