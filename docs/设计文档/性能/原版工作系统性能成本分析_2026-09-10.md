# 原版工作系统性能成本分析（2026-09-10）

> **性质**：原版（Vanilla）机制的事实性分析，非本 Mod 的体检报告。姊妹文档见 [`全量性能体检报告_2026-09-06.md`](./全量性能体检报告_2026-09-06.md)（本 Mod 自身热点）。
> **方法**：`ilspycmd 8.2.0` 反编译 `RimWorld\RimWorldWin64_Data\Managed\Assembly-CSharp.dll`（1.6）+ 原版 `Data/**/*.xml` 元素计数。
> **证据等级**：本文所有代码引用均为**反编译原文摘录**（非推测）；所有数量为**脚本实测**。凡推测处均显式标注 `【推测】`。
> **回答的问题**：环世界原版「工作」相关开销在哪里，为什么 pawn 数量增加时性能大幅下降。

---

## 1. 结论速览

| # | 结论 | 依据 |
|---|---|---|
| C1 | 性能瓶颈的表现形式是**游戏时间变慢**，不是画面掉帧 | `TickManager` 每帧 45.45ms 硬刹车（=1000/22，`WorstAllowedFPS=22`） |
| C2 | **所有已生成 pawn 每 tick 全部被 tick，无错峰** | `Pawn.tickerType = Normal`，`TickList` 的 Normal 桶间隔 = 1 |
| C3 | 1.6 的"屏幕外降频"**只降 `TickInterval`，不降 `Tick()`** | `Thing.DoTick()` 对 Normal 无条件调 `Tick()` |
| C4 | 工作开销的主项不是"干活"，而是**「无工作时重新决策」** | `curJob == null` → `TryFindAndStartJob` → `JobGiver_Work.TryIssueJobPackage` 全表遍历 |
| C5 | **「这个工作没活干」比「有活干」贵得多** | `MaxRegionsToScanBeforeGlobalSearch` 默认 `-1` ⇒ 区域 BFS 无果后退化为遍历全地图 |
| C6 | 多 pawn 时成本**超线性**，主因是 Reachability 缓存失效 + 预约争抢抖动 | 缓存键为 `District`；抢不到目标会重新进入完整扫描 |
| C7 | 原版自身的 `WorkGiverDef` 规模已是乘法因子 | Core 97 / 含全部 DLC **143** 个；`WorkTypeDef` 22 个 |

**一句话**：成本 = `O(N_pawn)` 的每 tick 固定开销 + `O(N_pawn × N_workGiver × N_候选物)` 的工作扫描，其中 `N_候选物` 最坏退化为"全地图该类别物体总数"；再叠加 §5 的三个反馈环，最后被 §2 的刹车翻译成"慢放"。

## 2. 引擎的 tick 预算模型（为什么是"变慢"而非"掉帧"）

### 2.1 每帧 45.45ms 硬刹车

```csharp
// Verse.TickManager.TickManagerUpdate()
float tickRateMultiplier = TickRateMultiplier;
clock.Reset(); clock.Start();
while (realTimeToTickThrough > 0f && (float)ticksThisFrame < tickRateMultiplier * 2f)
{
    double t0 = clock.Elapsed.TotalMilliseconds;
    DoSingleTick();
    double t1 = clock.Elapsed.TotalMilliseconds;
    realTimeToTickThrough -= curTimePerTick;
    ticksThisFrame++;
    rawTickTimeAverage.AddValue((float)(t1 - t0));
    smoothedTickTimeAverage.AddValue(rawTickTimeAverage.GetAverage());
    if (Paused || (float)clock.ElapsedMilliseconds > 45.454544f)   // ← 45.454544 = 1000/22
        break;
}
if (realTimeToTickThrough > 0f) realTimeToTickThrough = 0f;        // ← 追不上就丢弃，不补帧
```

- 常量：`public const float WorstAllowedFPS = 22f;`
- `TickRateMultiplier`：暂停 0 / 1 速 1× / 2 速 3× / 3 速 6×（无事发生时 12×）/ 超速 15×；`TicksPerRealSecond = 60`（`Verse.GenTicks`）。
- 每帧 tick 上限是 `TickRateMultiplier × 2`（1 速最多 2 tick/帧）。
- **刹车语义**：单帧累计跑满 45.45ms 就立刻停止追加 tick，且 `realTimeToTickThrough` 被清零（**丢弃而非积欠**）。

> **结论**：pawn 变多 → 单 tick 变贵 → 每帧能跑的 tick 变少 → **真实 1 秒跑不到 60 tick**。玩家看到 3 倍速实际只有 1.x 倍速，但 FPS 计数可能仍是 60。这是最容易误判为"不卡"的地方。
> 附带：`smoothedTickTimeAverage` 暴露为 `TickManager.MeanTickTime`，是官方给 Mod 作者看的口径。

### 2.2 tick 分桶：Normal 类型无错峰

```csharp
// Verse.TickList
private int TickInterval => tickType switch {
    TickerType.Normal => 1, TickerType.Rare => 250, TickerType.Long => 2000, _ => -1 };
// BucketOf:  index = |thing.GetHashCode()| % TickInterval
List<Thing> list2 = thingLists[Find.TickManager.TicksGame % TickInterval];
for (int m = 0; m < list2.Count; m++) { ... thing.DoTick(); ... }
```

`Pawn` 的 `ThingDef` 实测为 `<tickerType>Normal</tickerType>`（`Data/Core/Defs/ThingDefs_Races/*.xml`）。Normal 桶的 `TickInterval = 1` ⇒ 分桶退化为单桶 ⇒ **全部 pawn 每 tick 都被 `DoTick()`**。

### 2.3 相机降频只作用于 `TickInterval`

```csharp
// Verse.Thing
protected virtual int MinTickIntervalRate => 1;
protected virtual int MaxTickIntervalRate => 15;
protected virtual int UpdateRateTickOffset => this.HashOffset();
public virtual int UpdateRateTicks => GenTicks.GetCameraUpdateRate(this);

public void DoTick()
{
    ...
    if (def.tickerType == TickerType.Normal)
    {
        Tick();                                    // ← 无条件，每 tick
        tickDelta++;
        int num = Mathf.Min(Mathf.Max(UpdateRateTicks, MinTickIntervalRate), MaxTickIntervalRate);
        if (tickDelta >= num || GenTicks.IsTickInterval(UpdateRateTickOffset, num))
        {
            TickInterval(tickDelta);               // ← 只有这一半降频
            tickDelta = 0;
        }
    }
}

// Verse.GenTicks
public static int GetCameraUpdateRate(Thing thing)
{
    if (!WorldRendererUtility.DrawingMap || Find.CurrentMap == null || thing.MapHeld != Find.CurrentMap)
        return 15;                                        // 非当前地图 → 15
    CameraDriver cameraDriver = Find.CameraDriver;
    if (!cameraDriver.InViewOf(thing)) return 15;         // 不在视口 → 15
    return (int)(cameraDriver.CurrentZoom + 1);           // 视口内：近景 1 … 远景 ~4
}
```

> **重要**：把镜头移开**不会**降低 `Tick()` 的一半开销（pather / verbs / stances / `JobTrackerTick` / `HealthTick`）。只有 pawn 不在当前地图时才拿满 15 倍。
> 这也解释了"分基地/远行队里的人不占性能"这个体感是对的，而"把镜头挪到空地"收益有限。

| 调用 | 每 tick 的开销性质 |
|---|---|
| `pather.PatherTick()` | 路径跟随：取下一步、检查停滞/门前/脏物、`Moving` 状态机 |
| `verbTracker.VerbsTick()` | 每个 Verb 的 warmup / burst 计时 |
| `stances.StanceTrackerTick()` | Cooldown / Warmup 等姿态的 tick |
| `jobs.JobTrackerTick()` → `curDriver.DriverTick()` | **toil 推进**；内含 `CheckCurrentToilEndOrFail()` 遍历 `globalFailConditions` + `curToil.endConditions` 的**委托列表** |
| `health.HealthTick()` | **把整个 hediff 列表 `AddRange` 到临时表，逐个 `Tick()` + `PostTick()`** |
| `equipment / abilities / inventory / genes / mutant` | 各 tracker 的 tick |
| `EffectersTick` / 音效 sustainer | 表现层 |

`JobDriver.DriverTick()` 骨架（`Verse.AI.JobDriver`）：

```csharp
public void DriverTick()

        if (wantBeginNextToil) { TryActuallyStartNextToil(); return; }

```

⇒ 单 pawn 每 tick = 几十次虚调用 + 若干委托调用。**这是 `O(N_pawn)` 的线性基线，常数不小但真正炸的不是它。**

## 4. 「工作」的核心成本：无工作时重新决策

### 4.1 触发路径

```
Verse.AI.Pawn_JobTracker.JobTrackerTickInterval(int delta)
├─ if (pawn.IsHashIntervalTick(30, delta))          // ← 只门控 Constant think tree
│     DetermineNextConstantThinkTreeJob()           //    （敌对检测一类）
├─ curDriver?.DriverTickInterval(delta)
│   └─ Job 过期检查：curJob.startTick + expiryInterval <= TicksGame
│        expiryInterval 由 DistanceIntervalCurve 按目标距离给出 (0→30, 50→120, 100→600)
└─ if (curJob == null && !pawn.Dead && pawn.mindState.Active)
      TryFindAndStartJob()                          // ← 主 think tree 重扫入口
```

```
TryFindAndStartJob() → DetermineNextJob(out thinkTree)
   → 先 DetermineNextConstantThinkTreeJob()
   → 再 pawn.thinker.MainThinkNodeRoot.TryIssueJobPackage(pawn, params)
        Humanlike 的 `ThinkTreeMain` = JobGiver_Work（经 ThinkNode_PrioritySorter 排优先级）
```

**触发频率 = 每干完一件活（或被打断）一次。** 另一个入口是 `CheckForJobOverride()`（`JobDriver` 的 toil `endConditions`/触发时调用）。

> 附带事实：`Pawn_JobTracker.FinalizeTick()` 内置看门狗 —— 若 10 tick 内起了 ≥10 个 job，会抛 `JobUtility.TryStartErrorRecoverJob`。原版自己在防"job 抖动"，说明这是已知病理。

### 4.2 被遍历的表

**原版规模实测**（脚本统计 `Data/**/*.xml`）：

| Def | Core | 含全部 DLC |
|---|---|---|
| `WorkGiverDef` | 97 | **143** |
| `WorkTypeDef` | 20 | **22** |
| `ThinkTreeDef` | 27 | — |

一个正常殖民者启用 6~12 个 `WorkTypeDef` ⇒ `WorkGiversInOrderNormal` 通常**几十条**。**每装一个 Mod 的 `WorkGiverDef`，就加进每个 pawn 的这张表**——这是乘法因子，不是加法。

`PawnCanUseWorkGiver`（每条都要过）：

```csharp
private bool PawnCanUseWorkGiver(Pawn pawn, WorkGiver giver)
{
    if (!giver.def.nonColonistsCanDo && !pawn.IsColonist && !pawn.IsColonyMech && !pawn.IsColonySubhuman) return false;
    if (pawn.WorkTagIsDisabled(giver.def.workTags)) return false;
    if (giver.def.workType != null && pawn.WorkTypeIsDisabled(giver.def.workType)) return false;
    if (giver.ShouldSkip(pawn)) return false;                    // ← 由 WorkGiver 实现，可能是重活
    if (giver.MissingRequiredCapacity(pawn) != null) return false;
    if (pawn.RaceProps.IsMechanoid && !giver.def.canBeDoneByMechs) return false;
    return true;
}
```

### 4.3 最贵分支：找不到活 → 全图兜底搜索

```csharp
// Verse.GenClosest.ClosestThingReachable
public static Thing ClosestThingReachable(IntVec3 root, Map map, ThingRequest thingReq, PathEndMode peMode,
    TraverseParms traverseParams, float maxDistance = 9999f, Predicate<Thing> validator = null,
    IEnumerable<Thing> customGlobalSearchSet = null, int searchRegionsMin = 0, int searchRegionsMax = -1,
    bool forceAllowGlobalSearch = false, ...)
{
    bool flag = searchRegionsMax < 0 || forceAllowGlobalSearch;              // ① 允许全图搜索？
    ...
    Thing thing = null; bool flag2 = false;
    if (!thingReq.IsUndefined && thingReq.CanBeFoundInRegion)
    {
        int num = (searchRegionsMax > 0) ? searchRegionsMax : 30;            // ② 先区域 BFS 30 个区域
        thing = RegionwiseBFSWorker(root, map, thingReq, peMode, traverseParams, validator, null,
                                    searchRegionsMin, num, maxDistance, out var regionsSeen, ...);
        flag2 = thing == null && regionsSeen < num;
    }
    if (thing == null && flag && !flag2)                                     // ③ 区域无果 → 全图
    {
        IEnumerable<Thing> searchSet = customGlobalSearchSet ?? map.listerThings.ThingsMatching(thingReq);
        thing = ClosestThing_Global(root, searchSet, maxDistance, GlobalValidator);   // 遍历全地图
    }
    return thing;
    bool GlobalValidator(Thing t)
    {
        if (!map.reachability.CanReach(root, t, peMode, traverseParams)) return false;   // ← 每候选一次
        if (validator != null && !validator(t)) return false;
        return true;
    }
}
```

`RimWorld.WorkGiver_Scanner` 的默认值：


而 `JobGiver_Work` 调用时**没有**传 `forceAllowGlobalSearch`：

```csharp
thing = GenClosest.ClosestThingReachable(pawn.Position, pawn.Map, scanner.PotentialWorkThingRequest,
```

⇒ `searchRegionsMax = -1` ⇒ `flag = true`。

> **C5 的核心**：**「这个工作没活干」比「有活干」贵得多。**
> 空闲 pawn（没东西搬、田里没熟的、所有工作台 `BillStack` 都排满、没东西可修）会**连续**触发多个 work giver 的全图兜底，每个都遍历全地图该 `ThingRequestGroup` 的物体并对每个候选做一次 `CanReach`。
> **原版自知这是热点**：`RimWorld.WorkGiver_CleanFilth` 显式写了 `public override int MaxRegionsToScanBeforeGlobalSearch => 4;`

另一处并行成本：`scanner.Prioritized == true` 时走 `GenClosest.ClosestThing_Global_Reachable(...)`，它对 **searchSet 全量** 逐个 `map.reachability.CanReach`（无区域剪枝）。

### 4.4 `scanCells` 分支：按"格"遍历

```csharp
// RimWorld.WorkGiver_Grower（WorkGiver_GrowerSow / WorkGiver_GrowerHarvest 的基类）
public override IEnumerable<IntVec3> PotentialWorkCellsGlobal(Pawn pawn)
{
    Danger maxDanger = pawn.NormalMaxDanger();
    List<Building> bList = pawn.Map.listerBuildings.allBuildingsColonist;
    for (int j = 0; j < bList.Count; j++)
    {
        if (!(bList[j] is Building_PlantGrower g) || !ExtraRequirements(g, pawn)
            || g.IsForbidden(pawn) || !pawn.CanReach(g, PathEndMode.OnCell, maxDanger) || g.IsBurning())
            continue;
        foreach (IntVec3 item in g.OccupiedRect()) yield return item;      // 每台 PlantGrower 一次 CanReach
        wantedPlantDef = null;
    }
    List<Zone> zonesList = pawn.Map.zoneManager.AllZones;
    for (int j = 0; j < zonesList.Count; j++)
    {
        if (!(zonesList[j] is Zone_Growing growZone)) continue;
        else if (ExtraRequirements(growZone, pawn) && !growZone.ContainsStaticFire
                 && pawn.CanReach(growZone.Cells[0], PathEndMode.OnCell, maxDanger))
        {
            for (int k = 0; k < growZone.cells.Count; k++) yield return growZone.cells[k];   // ← 全格枚举
        }
    }
}
```

- **一个 30×30 种植区 = 900 格**；`WorkGiver_GrowerSow` 与 `WorkGiver_GrowerHarvest` 都会枚举一遍 ⇒ 每个 pawn 每次决策 = 上千次枚举。
- 每格还要付 `WorkGiver_GrowerHarvest.HasJobOnCell`：

`HasJobOnThing` 的普遍内容（以 `WorkGiver_DoBill.JobOnThing` 为例）：

```csharp
if (!(thing is IBillGiver billGiver) || !ThingIsUsableBillGiver(thing) || !billGiver.BillStack.AnyShouldDoNow
    || !billGiver.UsableForBillsAfterFueling() || !pawn.CanReserve(thing, 1, -1, null, forced) || thing.IsBurning())
    return null;
if (thing.def.hasInteractionCell && !pawn.CanReserveSittableOrSpot(thing.InteractionCell, thing, forced)) return null;
CompRefuelable compRefuelable = thing.TryGetComp<CompRefuelable>();
if (compRefuelable != null && !compRefuelable.HasFuel) { if (!RefuelWorkGiverUtility.CanRefuel(pawn, thing, forced)) return null; ... }
```

每候选 = `IsForbidden` + `CanReserve`（预约查询）+ `BillStack` 遍历 + 组件查询 + 配方匹配。**全局兜底路径下这一步要被执行"全地图候选数"次。**

### 4.7 供给侧的缓存（正确范例，说明原版在哪些地方做了优化）

```csharp
// RimWorld.ListerHaulables —— 增量维护 + 每 tick 只重算 4 个格
public void ListerHaulablesTick()
{
    groupCycleIndex++;
    CellsCheckTick(map.haulDestinationManager.AllGroupsListForReading);      // 取 1 个 SlotGroup，重算其中 4 格
    HaulSourcesCheckTick(map.haulDestinationManager.AllHaulSourcesListForReading);
}

// RimWorld.WorkGiver_Haul
public override IEnumerable<Thing> PotentialWorkThingsGlobal(Pawn pawn) => pawn.Map.listerHaulables.ThingsPotentiallyNeedingHauling();
public override bool ShouldSkip(Pawn pawn, bool forced = false) => pawn.Map.listerHaulables.ThingsPotentiallyNeedingHauling().Count == 0;
```

`WorkGiver_Haul` / `WorkGiver_CleanFilth` 都是**正确范式**：`ShouldSkip` 只读一个缓存集合的 `Count`，`PotentialWorkThingsGlobal` 直接返回现成集合。
但注意 —— 这仍然**不能避免** §4.3 的全局兜底：只要这些集合非空，就会对集合内每个候选做 `CanReach`（`ClosestThing_Global_Reachable` 路径）或走区域 BFS（`ClosestThingReachable` 路径）。

## 5. 让"多 pawn"变成非线性的放大器

### 5.1 Reachability 缓存以 **District** 为键 ⇒ 一改布局就全废

```csharp
// Verse.Reachability.CanReach
if (ReachabilityImmediate.CanReachImmediate(start, dest, map, peMode, traverseParams.pawn)) return true;
...
if ((peMode == PathEndMode.OnCell || Touch || ClosestTouch)
    && traverseParams.mode != TraverseMode.NoPassClosedDoorsOrWater)
{
    District district = RegionAndRoomQuery.DistirctAtFast(start, map);
    if (district != null && district == RegionAndRoomQuery.DistirctAtFast(dest.Cell, map))
        return true;                                                    // ← 同 District 快路径
}
...
if (startingRegions.Any() && destRegions.Any() && CanUseCache(traverseParams.mode))
{
    switch (GetCachedResult(traverseParams)) { case BoolUnknown.True: return true; case BoolUnknown.False: return false; }
}
if (traverseParams.mode == TraverseMode.PassAllDestroyableThings || ... || NoPassClosedDoorsOrWater)
    return CheckCellBasedReachability(start, dest, peMode, traverseParams);   // ← floodFiller 格级洪泛
return CheckRegionBasedReachability(traverseParams);                          // ← 区域 BFS
```

`CheckRegionBasedReachability` 是区域图 BFS（沿 `region.links` 扩张），结果写回 `ReachabilityCache`（`cache.AddCachedResult(startingRegions[k].District, region2.District, traverseParams, reachable)`）。

> **关键**：缓存粒度是 **District**，不是"格子对"。开关门、建/拆墙、建家具、区域合并拆分都会让相关 District 重建 ⇒ **整片缓存失效**。
> **多 pawn 频繁开门/进出 ⇒ `RegionAndRoomUpdater` 反复重建 ⇒ 缓存全 miss ⇒ 下一轮所有 work giver 的 `CanReach` 全部变成真 BFS。这是"多 pawn 卡"最典型的正反馈。**

### 5.2 A\* 寻路叠加

真正接下工作后，`Toils_Goto` 类 toil 的 `initAction` 走 `PathFinder`（`Verse.PathFinder` / `PathFinderMapData`，1.6 为 A\* + Burst 辅助）。
多 pawn **同时重新寻路**（目标被抢、门被关、目的地不可达、被征召/取消）时成本叠加 —— 玩家体感是"一群人同时改主意"时一顿。

### 5.3 预约争抢 → 决策抖动（超线性的主因）

N 个 pawn 抢 M 个目标：

```
CanReserve 失败 → JobOnThing 返回 null → JobGiver_Work 继续下一条 workGiver
              → 整表扫完 → NoJob → 下一次 TickInterval 再重扫一遍
```

人多时"抢不到"的概率上升 ⇒ **决策频率不降反升**。这就是为什么 20 人常常不是 10 人的 2 倍。
信号：`WorkGiver_DoBill` 里有专门的 `DefCountList` / `TryFindBestBillIngredients` 用来在**同一件活上反复试配方**；`Pawn_JobTracker` 的 10-job/10-tick 看门狗也是为这种现象准备的。

### 5.4 基地规模放大扫描深度

所有全局兜底都遍历地图物品表（`map.listerThings.ThingsMatching(...)` / `ThingsInGroup(...)` / `listerHaulables` / `listerFilthInHomeArea`）。
⇒ **掉落物、蓝图、框架、脏物、作物、尸体越多，每次扫描越贵**。这是"老存档越玩越卡"的一部分原因（不只是 pawn 数）。

### 5.5 与本 Mod 共用同一 tick 预算的邻接系统

| 位置 | 节拍 | 内容 |
|---|---|---|
| `Pawn_MindState.MindStateTickInterval` | `IsHashIntervalTick(100, delta)` | `PawnUtility.EnemiesAreNearby(pawn, anyCloseHostilesRecently ? 24 : 18, passDoors: true)` — **区域遍历** |
| `SituationalThoughtHandler` | `RecalculateStateEveryTicks = 100`（`ExpireAfterTicks = 300`） | 重算全部情境思绪（`SituationThoughtsToAdd` 遍历思绪定义） |

## 6. 量级模型

设 `N_p` = 已生成 pawn 数，`N_w` = 该 pawn 启用工作类型下的 WorkGiver 数，`N_t` = 地图上相关类别物体数（含格子数），`f` = 决策频率（次/pawn/秒）。

| 成本项 | 量级 | 说明 |
|---|---|---|
| 每 tick 固定开销 | `O(N_p)` | `Pawn.Tick()` 全套（§3），常数大 |
| 决策开销 | `O(N_p × f × N_w × c_scan)` | `c_scan` 单条 WorkGiver 的扫描成本 |
| 全局兜底 | `c_scan` 最坏 = `O(N_t)` | 区域 BFS 无果 ⇒ 遍历全地图 + 每候选 `CanReach` |
| `scanCells` | `c_scan` = `O(Σ 相关区域格数)` | 种植区可达数百~数千格 |
| 缓存失效 | 使 `CanReach` 从 `O(1)` 退化到 `O(区域数)` | §5.1 |
| 预约争抢 | 使 `f` 随 `N_p` 上升 | §5.3 |

**整体最坏情况 `O(N_p² × N_w × N_t)` 的成分都存在**（争抢使 `f ∝ N_p`，兜底使 `c_scan ∝ N_t`）—— 这就是"非常多 pawn 时大幅降低"的机制解释。

**换算到体感**（`【推测】`，需 §7 实测校准）：若某存档 10 pawn 时 1 速刚好跑满 60 tick/s，则到 25~30 pawn 时很可能只能跑到 25~35 tick/s，且伴随 3 速完全追不上（3 速需要 180 tick/s，刹车在 45ms/帧下最多给 ~22 tick/帧 × 60 帧 = 但实际会先撞 `tickRateMultiplier × 2` 上限）。

## 7. 量测方法（怎么证伪/校准本文结论）

1. **`TickManager.MeanTickTime`**：官方口径的单 tick 平滑耗时。DevMode 的性能显示即读它。若它随 pawn 数线性/超线性上升 ⇒ 与本文一致。
2. **Dubs Performance Analyzer**（社区 Mod）：可直接看 `JobGiver_Work` / `GenClosest` / `RegionAndTraverser` 的占比。
3. **自研埋点**：本项目已有 `PerfProbe`（`Start/End("key", t0)`）。在自定义 `WorkGiver` 上包一层即可定位单条 work giver 的耗时。
4. **对照组**：
   - 把镜头移到没有 pawn 的地图 → 若性能几乎不变，即验证 C3（`Tick()` 不降频）。
   - 工作标签页里把所有人所有工作类型关掉 → 若尖峰消失，即验证 §4.2/§4.3。
   - 用一个"永远返回 null 的 `ShouldSkip` 全表扫描"测试 work giver 观察差异 → 量化 §4.5 量级。

## 8. 对本 Mod 的硬约束（写 `WorkGiver_Scanner` 的检查清单）

| # | 约束 | 理由 |
|---|---|---|
| W1 | **必须显式设 `MaxRegionsToScanBeforeGlobalSearch`（≥0）** | 默认 `-1` ⇒ 区域无果即全图遍历（§4.3）。这是收益最大的单点 |
| W2 | `ShouldSkip` 只读一个**缓存的计数/标志** | 它被 `PawnCanUseWorkGiver` 每条调用；见 `WorkGiver_DoBill` 反例（§4.5） |
| W3 | `PotentialWorkThingsGlobal` 复用现成 lister | 例：`listerHaulables.ThingsPotentiallyNeedingHauling()`、`listerFilthInHomeArea.FilthInHomeArea`（§4.7） |
| W4 | `PotentialWorkCellsGlobal` 返回**缓存的 `List<IntVec3>`**，不要 `yield` | 框架对 `IList` 走索引循环，`yield` 走 `foreach` 迭代器（§4.4） |
| W5 | `HasJobOnThing/Cell` 内禁 `new` / 禁 LINQ / 禁 `DefDatabase` 查询 | 该委托会被调用"候选数"次（§4.6） |
| W6 | 判据按**代价升序**：`IsForbidden` → `CanReserve` → `CanReach` → 业务判定 | 短路掉最贵的 `CanReach` |
| W7 | **少加 `WorkGiverDef`**；能并进已有 `WorkTypeDef` 就别新建 | 每个 def 都是每个 pawn 的乘法因子（§4.2） |
| W8 | 禁每 tick 调 `SetPriority` / `Disable` | 置 `workGiversDirty` ⇒ 全服重建表（§4.2）。**例外（EXC-2026-012 + EXC-2026-013）**：允许事件驱动低频 Enable（012）与**档位提升**（013）—— 每次排班 / 名册 / 班次变更 ≤ 每成员每类型 1 次 `SetPriority`（幂等：已是目标档不写）+ 打开管理面板对账 1 次；013 另规定：**简单模式下不写档位**（引擎不读，写了纯属浪费），面板「开启手动优先级」按钮触发时才对全部玩家 pawn `Notify_UseWorkPrioritiesChanged()`（镜像原版，≤1 轮）。**仍禁**每 tick / 绘制路径 / `Disable`（`SetPriority` 只置该 pawn 实例的 `workGiversDirty`） |
| W9 | 只读逻辑不要污染/清空 Reachability 缓存；不要高频改变墙体/门 | 缓存按 District 粒度，一处失效全片重算（§5.1） |
| W10 | 每帧入口（`GetGizmos` / `CompInspectStringExtra` / `Graphic` getter）禁 `new` / `GetComponent` / `Find.*` | 与 `全量性能体检报告` U1/U6/U7 同源 |

**玩家侧可操作项**（可写进面向玩家文档）：

1. **把用不到的工作类型关掉**（直接缩短 `WorkGiversInOrderNormal`）。
2. **给每个人留活干反而更省** —— 空闲 pawn 会持续触发全局兜底搜索。
3. 避免所有人优先级 1 抢同一件事（争抢 → 抖动 → 反复重扫，§5.3）。
4. 减少同时开关门的路径（减少 Region 重建，§5.1）。
