# 00 工程生命周期规范

**适用范围：** 需求、架构、实现、内容、本地化、兼容、测试、发布和迁移  
**关联总纲：** [GOV-001](00-规范体系总纲.md#4-全局不可违反规则)、[GOV-011](00-规范体系总纲.md#4-全局不可违反规则)

## 1. 生命周期总图

```text
需求 Intake
    ↓
架构与依赖评估
    ↓
数据/契约设计
    ↓
实现与内容制作
    ↓
Localization / Asset / UI
    ↓
Compatibility / Save / Migration
    ↓
Testing / Performance / Diagnostics
    ↓
Review / Gate
    ↓
Change Summary / Changelog
    ↓
Release / Rollback
    ↓
反馈 / 迁移 / 退役
```

任何阶段不得跳过“架构与依赖评估”直接写代码；任何 Release 不得跳过适用 Gate。

## 2. 阶段定义

### Stage 0：需求 Intake（`LIFE-001`）

需求必须写明：

```text
目标用户行为
不在范围内的内容
涉及层级
是否新增 Def / Runtime / Save / UI / Translation / Asset
是否涉及 Vanilla、DLC 或第三方 Mod
预期版本和兼容承诺
```

产物：`Change Intent`、影响范围表、初始规则 ID 清单。

### Stage 1：Architecture Review（`LIFE-002`）

在下列任一项为 Yes 时强制评审：

```text
新增公共 API / Contract
引入新模块或新依赖
Harmony = Yes
修改第三方 Def 或 UI = Yes
Save schema 改变
新增全局可变状态
新增硬编码例外
性能敏感路径改变
```

评审必须回答：

1. 目标属于哪一层？
2. 依赖是否落在 [00-规范关系矩阵.md](00-规范关系矩阵.md) 的允许单元？
3. 是否可以使用更低风险的原生扩展点？
4. 数据与表现边界在哪里？
5. 失败、缺失、旧 Save 和目标 Mod 不存在时如何降级？
6. 需要哪些 Gate 和 Evidence？

产物：架构决策记录（ADR）、依赖图、风险等级、测试矩阵。

### Stage 2：契约与数据设计（`LIFE-003`）

先定义稳定 ID、Contract、Def schema、Runtime State、Save schema、Translation Key 和 Asset ID，再设计实现。规则依据：

- [TERM-001](00-统一术语与定义.md#1-领域术语)–[TERM-022](00-统一术语与定义.md#1-领域术语)
- [DATA-001](03-架构层-数据与扩展规范.md#1-data-001-四类数据边界)
- [SAVE-001](03-架构层-数据与扩展规范.md#12-save-001-存档身份与版本)
- [LOC-001](05-表现层规范.md#loc-001-本地化命名空间)

产物：Def/DTO/Contract 草案、版本策略、迁移策略、Key 和 Asset 清单。

### Stage 3：实现与内容制作（`LIFE-004`）

实现顺序：

```text
Contract / Domain
    ↓
Application Service / Provider
    ↓
Def / Comp / Patch
    ↓
Presentation / Localization / Asset
    ↓
Compatibility Adapter / Harmony（如获批准）
```

代码、XML、本地化和资源必须按职责拆分；禁止为了省文件而形成全局大文件。

### Stage 4：本地化与表现验证（`LIFE-005`）

每个新增用户可见文本都必须完成：

```text
稳定 Key
默认语言
目标语言或明确 fallback
参数占位符核对
长文本/短文本布局验证
Translation Report / 等效扫描
```

Def 文本使用 DefInjected，代码文本使用 Keyed；禁止将任何翻译结果用于业务判断。

### Stage 5：兼容与数据安全验证（`LIFE-006`）

对第三方接入和 Save 变更必须执行：

- 目标 Mod 缺失时的启动与运行验证。
- 目标 Mod 存在时的条件 Patch/Adapter 验证。
- 旧 Save 加载、迁移、缺失字段、未知枚举和降级路径验证。
- Harmony 目标解析失败时的安全行为验证。
- 本 Mod 的 Key、DefInjected、Asset 路径不会修改其他 Mod。

### Stage 6：Testing 与 Gate（`LIFE-007`）

执行 [00-统一验收标准.md](00-统一验收标准.md) 中适用的 Gate，并保留 Evidence。没有 Evidence 的“看起来没问题”不算 PASS。

### Stage 7：Release 与变更记录（`LIFE-008`）

发布前必须生成：

```text
Change Summary
版本号和兼容范围
Changelog 条目
测试矩阵与 Gate 结果
Save/Migration 说明
已知问题与回滚方案
```

具体格式见 [06-变更日志与发布规范.md](06-变更日志与发布规范.md)。

### Stage 8：退役与清理（`LIFE-009`）

删除 DefName、Translation Key、公共 API 或 Save 字段前，必须：

1. 标记 Deprecated 或保留别名。
2. 提供至少一个兼容周期或 Migration。
3. 在 Changelog 标记 `Breaking` / `Removed`。
4. 更新规则索引、示例和接入文档。

## 3. 变更分类与生命周期要求

| 变更 | 最低评审 | 必需 Gate |
|---|---|---|
| 仅文档/注释 | 文档 Review | 文档一致性 |
| 新增 Def/Key/Asset | 数据与表现 Review | Data、Localization、Asset |
| 修改 UI | UI Review | UI、Localization、Performance |
| 修改核心规则 | Architecture Review | Architecture、Data、Test |
| 第三方 Mod 接入 | Compatibility Review | Compatibility、Startup、Localization |
| Save schema 改变 | Save Review | Save/Migration、Regression |
| Harmony | 强制 Architecture Review | Compatibility、Regression、Performance |
| 公共 API | Contract Review | API、Compatibility、Release |

## 4. Definition of Done（`LIFE-010`）

一个需求只有同时满足以下条件才算完成：

```text
[ ] 目标行为可描述且范围已冻结
[ ] 依赖方向通过矩阵检查
[ ] 稳定 ID / Contract / schema 已确定
[ ] 实现符合对应层规范
[ ] 适用本地化、资源、兼容、Save、性能项已处理
[ ] 测试和 Gate Evidence 已保存
[ ] Change Summary / Changelog 已更新
[ ] 无未登记 Exception
```
