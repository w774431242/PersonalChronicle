# 00 规范体系总纲

**体系名称：** RimWorld Mod Engineering Standard  
**版本：** v3.0  
**适用对象：** RimWorld 1.6 Mod 的设计、编码、内容制作、兼容、测试、发布与 AI 协作  
**规范地位：** 项目最高工程约束（平台事实除外）

## 1. 体系目标

本体系把 Mod 开发从“能运行的功能”提升为“可维护、可扩展、可兼容、可验证、可持续交付的工程产品”。核心闭环为：

```text
正确性 → 解耦 → 低耦合 → 可扩展 → 可兼容 → 可测试 → 可发布 → 可迁移
```

全局目标由 [GOV-001]–[GOV-012] 约束；术语以 [TERM-001]–[TERM-040] 为准；文件之间的允许/禁止依赖以 [MATRIX-001]–[MATRIX-010] 为准。

## 2. 规范层级与优先级

当规则发生冲突，按下列优先级处理。数字越小，优先级越高：

| 优先级 | 层级 | 典型内容 | 规则前缀 |
|---|---|---|---|
| P0 | 平台与安全 | 游戏/框架约束、数据安全、不可破坏行为 | `GOV`, `BASE` 中标为 P0 的条目 |
| P1 | 全局治理与架构 | 依赖方向、模块边界、标识唯一性、例外流程 | `GOV`, `MATRIX`, `ARC` |
| P2 | 数据、扩展与兼容 | Def、Comp、Save、Migration、第三方接入 | `DATA`, `COMP`, `SAVE` |
| P3 | 表现与体验 | UI、Theme、Asset、Localization、布局 | `UI`, `LOC`, `ASSET` |
| P4 | 工程质量与交付 | Testing、Performance、Changelog、Release | `TEST`, `PERF`, `REL`, `GATE` |
| P5 | 实现建议 | AI 执行策略、示例和风格建议 | `AI` |

同一优先级内按以下顺序裁决：

1. 更具体的规则优先于更抽象的规则。
2. 明确的“不得”优先于一般“建议”。
3. 平台事实优先于项目偏好。
4. 无法裁决时，停止实现并提交 Architecture Review；不得自行选择更方便的实现。

规则来源和冲突裁决由 [GOV-004](#2-规范层级与优先级) 固定；例外不得通过修改普通文档中的一句话来隐式产生，必须遵守 [EXC-001](00-规范例外与变更管理.md#exc-001-例外先登记)。

## 3. 总体分层

```text
Governance
├── 总纲 / 关系矩阵 / 术语 / 生命周期 / Gate / 例外 / 编号索引
│
Foundation
└── 01 基础层
│
Architecture
├── 02 Core 架构
├── 03 数据与扩展
└── 04 兼容与接入
│
Presentation
└── 05 UI / Theme / Skin / Asset / Localization / Performance
│
Delivery
├── 06 变更日志与发布
└── 统一验收 Gate
│
AI Protocol
└── 07 AI 开发
```

允许的主方向为：

```text
Foundation → Core/Data → Presentation
Foundation → Core/Data → Compatibility
Core/Data → Save/Testing/Release
```

禁止反向污染：

```text
Core  ✕→ UI / Theme / Asset / Compatibility
Domain ✕→ RimWorld UI 实现
Localization ✕→ 业务状态
Compatibility ✕→ 修改 Core 设计以迁就单一第三方 Mod
```

详细矩阵见 [00-规范关系矩阵.md](00-规范关系矩阵.md)。

## 4. 全局不可违反规则

| ID | 规则 |
|---|---|
| GOV-001 | 先架构后编码：新功能必须先标注所属层、依赖和数据边界。 |
| GOV-002 | 组合优先于继承：优先使用公开扩展点、服务和适配器。 |
| GOV-003 | 数据、运行时状态、持久状态与表现分离。 |
| GOV-004 | 依赖只能沿矩阵允许方向流动；冲突按本总纲裁决。 |
| GOV-005 | 所有跨模块通信通过契约，不得读取其他模块内部实现。 |
| GOV-006 | 所有硬编码必须有分类、来源和生命周期；魔法数字/字符串不得散落。 |
| GOV-007 | 先使用原生扩展点，再考虑 Harmony；Harmony 必须有理由、范围和回滚方案。 |
| GOV-008 | 第三方 Mod 行为必须位于 Compatibility 层，Core 不直接认识目标 Mod。 |
| GOV-009 | 程序逻辑依赖稳定 ID，不得依赖 label、description 或翻译文本。 |
| GOV-010 | 每个用户可见文本必须经过 Localization 管道并可审计。 |
| GOV-011 | Save schema、Migration、Testing、Performance 和 Release 是交付的一部分，不是事后补充。 |
| GOV-012 | AI 不能绕过 Gate、例外登记和人工确认要求。 |

## 5. 规则 ID 体系

规则格式为 `领域-三位序号`，例如 `ARC-006`。领域前缀及稳定范围以 [00-规则编号索引.md](00-规则编号索引.md) 为准。

```text
GOV    全局治理
MATRIX 依赖关系
TERM   术语
BASE   基础层
ARC    核心架构
DATA   数据与扩展
COMP   兼容与接入
UI     UI 架构与交互
LOC    本地化
ASSET  资产、Theme、Skin
SAVE   存档与迁移
TEST   测试
PERF   性能
REL    变更日志与发布
GATE   统一验收门槛
EXC    例外与规范变更
AI     AI 执行协议
```

规则 ID 不得重复、复用或因重构改号。废弃规则保留原 ID，并标记 `Deprecated` 与替代规则。

## 6. 变更与例外入口

- 需要临时偏离：登记 `EXC-*`，并按范围、理由、风险、替代方案、负责人、到期日执行。
- 需要永久调整：登记 `EXC-*` 的规范变更记录，更新版本和受影响文件。
- 需要新增功能：先走 [00-工程生命周期规范.md](00-工程生命周期规范.md) 的 Stage 0–2。
- 需要发布：所有适用 Gate 必须 PASS，发布材料必须符合 [06-变更日志与发布规范.md](06-变更日志与发布规范.md)。

## 7. 最小执行清单

```text
[ ] 已识别任务层级和规则 ID
[ ] 已核对允许/禁止依赖
[ ] 已区分 Def / Runtime / Save / UI 数据
[ ] 已处理 Localization 与 fallback
[ ] 已评估 Compatibility / Harmony / Hardcoding
[ ] 已补测试、性能证据和 Migration 结论
[ ] 已通过适用 Gate
[ ] 已生成 Change Summary 并更新 Release 文档
```
