# 00 需求与 SDD 规范

**体系名称：** RimWorld Mod Engineering Standard v3.0 — 需求与设计文档域  
**版本：** v1.0  
**适用范围：** 需求捕获与评审、SDD（Software Design Document，软件设计文档）编写与评审、需求 ↔ SDD 对齐追踪、设计变更  
**关联总纲：** [GOV-001](00-规范体系总纲.md#4-全局不可违反规则)、[GOV-011](00-规范体系总纲.md#4-全局不可违反规则)、[GOV-012](00-规范体系总纲.md#4-全局不可违反规则)  
**关联生命周期：** [LIFE-001](00-工程生命周期规范.md#stage-0需求-intakelife-001)（Stage 0）、[LIFE-002](00-工程生命周期规范.md#stage-1architecture-reviewlife-002)（Stage 1）、[LIFE-003](00-工程生命周期规范.md#stage-2契约与数据设计life-003)（Stage 2）  
**关联 AI 协议：** [AI-001](07-AI开发规范.md#1-ai-001-任务入口协议)、[AI-002](07-AI开发规范.md#2-ai-002-先架构后编码)、[AI-010](07-AI开发规范.md#10-ai-010-change-summary-协议)  
**关联 Gate：** [GATE-ARCH](00-统一验收标准.md#2-gate-arch架构-gate)、[GATE-REL](00-统一验收标准.md#10-gate-relrelease-gate)

## 1. 定位

需求端是工程生命周期的**输入闸门**，SDD 是需求到实现的**唯一桥梁**：

```text
需求成文（Change Intent）→ 需求评审（DoR）→ SDD 编写 → SDD 评审 → 编码 → 验收
```

三条硬约束：

1. **需求不 Ready，不得进入设计**（[REQ-003](#req-003-definition-of-ready)）。
2. **SDD 未 Approved，不得进入编码**（[SDD-004](#sdd-004-文档状态机)）；AI 同样受此约束（[GOV-012](00-规范体系总纲.md#4-全局不可违反规则)）。
3. **需求 ↔ SDD 通过追踪矩阵对齐**，任何一侧变更必须同步另一侧（[REQ-005](#req-005-需求变更) / [SDD-009](#sdd-009-sdd-变更)）。

本文件回答三个问题：**需求怎么写、SDD 怎么写、两者如何对齐**。

## 2. 需求端规范（REQ-*）

### REQ-001 需求必须成文

- 任何进入开发的需求必须以 Change Intent 形式落盘，**口头需求不直接进入编码**。
- 需求文档存放于 `docs/设计文档/` 下对应功能模块目录，或 `docs/设计文档/需求/` 集中目录（按模块归类优先，与 [SDD-003](#sdd-003-存放与命名) 同规则）。
- 需求文档是评审与追踪的原始依据，不是实现完成后补写的说明。

### REQ-002 需求文档必备要素

Change Intent 必须写明以下八项（模板见 [附录 A](#附录-a-change-intent-模板)）：

```text
1. 目标用户行为（玩家在什么场景下得到什么结果）
2. 非目标（明确不在范围内的内容，防止范围膨胀）
3. 涉及层级与模块（对应分层文件的哪一层）
4. 数据面：是否新增/修改 Def / Runtime / Save / UI / Translation / Asset
5. 兼容面：是否涉及 Vanilla、DLC、第三方 Mod
6. 验收标准：可观察、可测试的完成判据
7. 预期版本与兼容承诺
8. 风险与未知项（含需要人工确认的假设）
```

产物对齐 [LIFE-001](00-工程生命周期规范.md#stage-0需求-intakelife-001) 的 Stage 0：Change Intent、影响范围表、初始规则 ID 清单。

### REQ-003 Definition of Ready

需求满足以下**全部**条件才视为 Ready，可进入 SDD 编写：

```text
[ ] 目标与非目标可区分（知道做什么，也知道不做什么）
[ ] 验收标准可观察、可测试（检查清单或 Given/When/Then）
[ ] 涉及层级与初始规则 ID 已标注
[ ] 数据面、兼容面、依赖已识别
[ ] 无未决 P0/P1 歧义；存在歧义时已标记假设并等待确认
```

不满足 DoR 的需求不得进入设计；AI 信息不足时必须采用最小安全假设并标记（[AI-001](07-AI开发规范.md#1-ai-001-任务入口协议)），不得凭方便扩大范围。

### REQ-004 需求条目编号

- 需求条目 ID 格式：`REQ-<功能域>-<三位序号>`，例如 `REQ-Archive-012`。
- 需求条目 ID 是追踪矩阵的唯一键，**不得复用**；条目废弃时保留原 ID 并标记 `Deprecated` / `Replaced by <ID>` / `Removed`。
- 功能域用模块短名（如 Archive、Combat、Inherit），全项目统一；新增功能域先在需求文档中登记。

### REQ-005 需求变更

需求变更（新增、删除、修改条目或验收标准）必须：

1. 在需求文档中追加**变更记录**：变更理由、影响面（SDD / 实现 / 测试 / 发布）、受影响条目 ID。
2. 旧条目标记状态（`Deprecated` / `Replaced` / `Removed`），不直接改写历史条目正文。
3. 同步更新追踪矩阵与对应 SDD（见 [SDD-009](#sdd-009-sdd-变更)），并重新评审受影响章节。
4. 变更影响验收标准时，测试计划与 Gate 计划必须同步调整。

### REQ-006 需求评审

- 需求评审至少覆盖：完整性、可测试性、范围是否冻结、与既有规范/已实现模块的冲突、兼容与 Save 影响。
- 评审结论记录进 [统一 Gate Record 模板](00-统一验收标准.md#11-统一-gate-记录模板)，Gate 列填 `REQ`。
- 评审发现问题时返回修订，不得带病进入 SDD。

## 3. SDD 规范（SDD-*）

### SDD-001 定义与触发条件

SDD（Software Design Document）把 Ready 需求翻译为**可评审、可实现、可验收**的设计方案。

以下变更**必须**编写完整 SDD：

```text
新增功能模块 / 子系统
新增或修改公共 API / Contract
引入新模块或新依赖
Harmony = Yes
修改第三方 Def 或 UI
Save schema 改变
新增全局可变状态
新增硬编码例外
性能敏感路径改变
```

仅文档/注释、单个 Def/Key/Asset 新增且无架构影响时，可用轻量设计说明替代，但必须注明**为何不写完整 SDD**。

### SDD-002 SDD 文档结构

SDD 使用固定章节模板（[附录 B](#附录-b-sdd-模板)），**每节必须有结论**，禁止只写背景不写方案：

```text
0. 元信息：版本、状态、日期、作者（人或 AI）、关联需求 ID、规则 ID
1. 背景与目标（含非目标）
2. 术语与约定
3. 架构与依赖：层级归属、依赖图、扩展点选择与理由
4. 数据与契约设计：稳定 ID、Def schema、DTO/Contract、Save schema、Translation Key、Asset ID
5. 实现方案：模块划分、Provider / Service / Comp / Patch 分工
6. 表现层设计：UI 状态与 Read Model、Theme / Asset / Localization 清单
7. 兼容与降级：第三方 Mod / DLC / 失败路径 / 缺失资源
8. 存档与迁移：旧 schema → 新 schema、默认值、幂等性
9. 测试计划与 Gate 计划：测试矩阵、适用 Gate、Evidence 来源
10. 风险、回滚与已知问题
11. 追踪矩阵：需求条目 ↔ 设计章节 ↔ 规则 ID
12. Change Log：状态与版本变更记录
```

### SDD-003 存放与命名

- 存放：`docs/设计文档/功能模块/<模块名>/<模块名><主题>设计文档.md`，与现有模块文档（战斗履历、装备传承、地点地图志等）同规则。
- 命名：中文语义化文件名，**不加日期后缀**（遵循 [docs/README.md](../README.md) 命名规范）。
- 同一模块多次迭代时，用元信息版本与状态字段区分，不靠 `v1/v2` 文件名堆叠。

### SDD-004 文档状态机

```text
Draft（草稿）→ In Review（评审中）→ Approved（已批准）→ Implemented（已实现）→ Deprecated（已废弃）
```

- **只有 Approved 的 SDD 才能进入编码**；实现期间状态为 Implemented。
- 状态迁移必须记录在元信息 Change Log 中，含日期与原因。
- Deprecated 仅用于设计被整体替代的文档；替代文档在元信息中互相引用。

### SDD-005 SDD 必须回答架构评审问题

对应 [LIFE-002](00-工程生命周期规范.md#stage-1architecture-reviewlife-002) 的六问，SDD 中逐条给出结论：

```text
1. 目标属于哪一层？
2. 依赖是否落在关系矩阵的允许单元？
3. 是否可以使用更低风险的原生扩展点？（被跳过的方案要记录原因）
4. 数据与表现边界在哪里？
5. 失败、缺失、旧 Save 和目标 Mod 不存在时如何降级？
6. 需要哪些 Gate 和 Evidence？
```

### SDD-006 设计先行原则

- SDD 必须先定义稳定 ID、Contract、Def schema、Runtime State、Save schema、Translation Key 与 Asset ID，再谈实现细节（对齐 [LIFE-003](00-工程生命周期规范.md#stage-2契约与数据设计life-003)）。
- 实现不得发明 SDD 之外的公共契约；确有需要时先更新 SDD 再编码。
- 数据面必须按 [DATA-001](03-架构层-数据与扩展规范.md#1-data-001-四类数据边界) 四类边界（Def / Runtime / Save / UI）逐类声明。

### SDD-007 与 AI 协作

- AI 起草 SDD 时，必须先输出 [AI-001](07-AI开发规范.md#1-ai-001-任务入口协议) 的任务入口信息与 [AI-002](07-AI开发规范.md#2-ai-002-先架构后编码) 的架构评估，并在 SDD 元信息中标注作者为 AI 与使用的规则 ID。
- AI 必须显式标记假设；不得在 SDD 未 Approved 时写代码。
- AI 的最终交付模板（[AI-012](07-AI开发规范.md#12-ai-012-最终交付模板)）必须引用 SDD 路径与状态。

### SDD-008 SDD 评审（Gate）

SDD 评审检查清单（结论记入统一 Gate Record，Gate 列填 `SDD`）：

```text
[ ] 章节齐全，且每节有明确结论
[ ] 依赖方向通过关系矩阵检查
[ ] 扩展点选择有理由，被跳过方案有记录
[ ] 稳定 ID / Contract / schema / Key / Asset 已定义
[ ] 降级与失败路径已定义
[ ] 测试计划与 Gate 计划已列出
[ ] 追踪矩阵完整，无孤儿条目
[ ] 需求变更已同步，无过期内容
```

评审不通过时返回 Draft 修订；修订后重新评审，不得增量带病放行。

### SDD-009 SDD 变更

- 已批准 SDD 的任何修改：追加 Change Log 记录，重新评审受影响章节，并同步追踪矩阵。
- 实现中发现与 SDD 偏离：**先更新 SDD（或登记 [EXC-001](00-规范例外与变更管理.md#exc-001-例外先登记)）再继续**，禁止"实现优先、文档后补"。
- 需求变更（[REQ-005](#req-005-需求变更)）后，SDD 必须在进入实现前完成同步。

### SDD-010 SDD 的 Done

SDD 满足以下全部条件才算完成：

```text
[ ] 每节有明确结论，无待定占位
[ ] 无未决 P0/P1 风险，或已登记有效 Exception
[ ] 追踪矩阵无孤儿：每个需求条目映射 ≥1 个设计章节，每个设计章节映射 ≥1 个需求条目
[ ] 评审记录与结论已落盘
[ ] 已与关联需求、规则 ID、验收标准对齐
```

## 4. 需求 ↔ SDD 对齐（追踪矩阵）

### 对齐原则

1. **双向覆盖**：每个需求条目至少映射一个 SDD 章节；每个 SDD 章节至少回指一个需求条目。孤儿条目（需求无设计、设计无需求）视为未对齐，禁止进入实现。
2. **三线对齐**：需求验收标准 ↔ SDD 测试计划 ↔ 最终 Gate 结果，三者在交付时必须一致。
3. **随变更新**：任何一侧变更（[REQ-005](#req-005-需求变更) / [SDD-009](#sdd-009-sdd-变更)）同步更新矩阵。

### 追踪矩阵模板

```markdown
| 需求 ID | 需求条目摘要 | SDD 章节 | 规则 ID | 验收标准 | 状态 |
|---|---|---|---|---|---|
| REQ-Archive-012 | 档案 Tab 支持击杀图鉴 | §4, §9 | DATA-001, UI-007 | 见需求 §6 | Approved |
```

### 对齐检查表（SDD 评审与交付前各执行一次）

```text
[ ] 每个需求条目在矩阵中有对应设计章节
[ ] 每个设计章节回指至少一个需求条目
[ ] 验收标准可测试，且测试计划已映射到 Gate
[ ] 需求变更后矩阵已同步
[ ] 无孤儿条目，无未决歧义
```

## 5. 需求/SDD 评审记录模板

复用 [统一 Gate Record 模板](00-统一验收标准.md#11-统一-gate-记录模板)，Gate 列填 `REQ` 或 `SDD`：

```markdown
## Gate Record
- Change: <变更名称>
- Version: <版本>
- Date: YYYY-MM-DD
- Reviewer: <人或 AI>
- Scope: <模块/文件>

| Gate | Result | Rule IDs | Evidence | Risk |
|---|---|---|---|---|
| REQ | PASS/BLOCKED | REQ-xxx | <需求文档路径> | <风险> |
| SDD | PASS/BLOCKED | SDD-xxx | <SDD 路径 + 追踪矩阵> | <风险> |
```

## 附录 C：评审记录存放

- 需求评审与 SDD 评审记录存放在对应需求/SDD 文档所在目录的 `评审记录/` 子目录，或直接追加在文档末尾的评审节。
