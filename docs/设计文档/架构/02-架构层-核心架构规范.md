# 02 架构层：核心架构规范

**版本：** v3.0  
**定位：** 定义模块边界、依赖方向、Contract、Service、Provider 和可替换性  
**上位规范：** [00-规范体系总纲.md](00-规范体系总纲.md)、[00-规范关系矩阵.md](00-规范关系矩阵.md)

## 1. ARC-001 分层边界与单向依赖

推荐结构：

```text
Foundation
    ↓
Core
├── Domain
├── Application Services
├── Contracts / API
└── Ports
    ↓
Data / Infrastructure / Presentation / Compatibility
```

核心方向：

```text
UI → Core Contract              ✓
Compatibility → Core Contract   ✓
Save → Core Data Contract        ✓
Core → UI / Theme / Asset        ✕
Core → Target Mod               ✕
```

详细允许矩阵以 [00-规范关系矩阵.md](00-规范关系矩阵.md#2-依赖矩阵) 为准。

## 2. ARC-002 Core 纯净边界

Core 负责领域模型、业务规则、稳定服务、公开查询/写入契约和状态转换；不负责：

```text
UI 绘制、GUIStyle、颜色和 Texture
翻译文件和显示文本
第三方 Mod 类型与 Harmony Target
具体存档文件格式
特定窗口是否打开
```

Core 不得出现 `if (FamousModIsLoaded)`、`Widgets.Label` 或目标 Mod 的类型引用。

## 3. ARC-003 核心模块职责

| 模块 | 允许内容 | 禁止内容 |
|---|---|---|
| Domain | 稳定模型、不依赖 UI 的领域规则 | RimWorld UI 类型、第三方类型 |
| Application | 用例编排、事务边界、错误策略 | 直接绘制、散落翻译文本 |
| Contracts/API | 最小接口、DTO、版本、能力声明 | 内部对象泄漏、可变全局集合 |
| Data | Def/Comp/Save 数据装配 | Window、Theme、第三方 Patch |
| Presentation | ViewModel、Window、Panel、输入 | 直接决定核心业务规则 |
| Compatibility | 检测、Adapter、条件 Patch、Harmony | 反向修改 Core 语义 |

## 4. ARC-004 服务职责

一个 Service 必须有清晰的用例、输入、输出、错误和生命周期。禁止用 `Manager` 汇总无关的：

```text
采集 + 查询 + UI + Save + Localization + Harmony + 第三方适配
```

应拆为 `CaptureService`、`QueryService`、`MigrationService`、`CompatibilityAdapter` 等，并通过 Contract 组合。

## 5. ARC-005 Contract/API 边界

公共 API 必须：

```text
稳定、最小、可版本化、可测试、无 UI 依赖、无第三方具体类型
```

Provider 示例：

```csharp
public interface IArchiveUiDataProvider
{
    string SectionId { get; }
    ArchiveSectionSnapshot BuildSection(ArchiveUiContext context);
}
```

Provider 返回数据快照/DTO，不得返回 `Rect`、`GUIStyle`、Window 引用、Texture 实例或回调绘制权。这样 UI 仍由本 Mod 统一控制。

## 6. ARC-006 Provider、Adapter 与 Registry

需要允许未来模块接入时，优先提供：

```text
Contract → Provider → Registry → Read Model / UI Consumer
```

Registry 负责注册、优先级、能力过滤、异常隔离和生命周期；不得将 Provider 注册表直接写入 Save。Provider 失败时只影响自身能力，不得阻断 Core。

## 7. ARC-007 组合优先于继承

优先级：

```text
配置 / DefModExtension
→ Component / Comp
→ Service + Contract
→ Adapter / Provider
→ 继承
→ Harmony
```

继承只有在“is-a”关系稳定且替换不会破坏平台生命周期时使用；不能为了复用几个方法创建深层基类。

## 8. ARC-008 静态可变状态限制

静态状态仅允许用于不可变配置、只读 DefOf、短生命周期缓存或明确的 Registry；必须有初始化、清理、线程/生命周期说明。禁止把游戏状态、Save 数据或 UI 状态放入无界静态单例。

## 9. ARC-009 事件与回调边界

事件输入必须经过稳定 DTO、ID 校验、去重和容量限制。事件订阅者失败要隔离；事件不能成为绕过 Contract 的全局消息总线。跨存档生命周期的订阅必须在加载/卸载时重新建立。

## 10. ARC-010 初始化与关闭顺序

初始化顺序必须可描述：

```text
平台加载 → Def 加载 → Mod 初始化 → Registry 注册 → Save/World 加载 → UI 创建
```

不得在静态构造阶段访问尚未加载的 DefDatabase、World、UI 或可选 Mod。兼容检测应在可安全执行的初始化阶段完成并缓存。

## 11. ARC-011 架构评审触发

出现下列任一项即进入 Architecture Review：

```text
新增第三方类型引用
新增 Harmony
新增静态可变状态
Core 引入 Presentation/Compatibility
公共 API 改签名或语义
Save schema 改变
```

评审记录必须引用 [LIFE-002](00-工程生命周期规范.md#2-阶段定义) 与适用 Exception。

## 12. ARC-012 核心架构验收

```text
[ ] ARC-001–ARC-011 适用项通过
[ ] 依赖图无循环
[ ] Core 不引用 UI/Theme/Asset/Compatibility
[ ] Contract 不泄漏第三方类型和 UI 类型
[ ] Provider/Adapter 有异常隔离
[ ] 初始化顺序可解释
[ ] 高风险实现有 Architecture Review Evidence
```
