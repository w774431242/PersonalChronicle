# 07 AI 开发规范

**版本：** v3.0  
**定位：** 将本体系转化为 AI 可执行、可审查、可回滚的开发协议  
**最高约束：** AI 不得绕过总纲、依赖矩阵、例外登记和统一 Gate

## 1. AI-001 任务入口协议

AI 收到需求后，必须先输出或记录：

```text
需求目标与非目标
涉及文件/模块
任务层级
适用规则 ID
新增/修改的 Def、Runtime、Save、UI、Key、Asset
第三方 Mod/DLC/语言影响
是否触发 Architecture Review
计划使用的扩展点
验证和 Gate 计划
```

信息不足时，AI 必须采用最小安全假设，并标记假设；不得凭方便扩大范围。

## 2. AI-002 先架构后编码

AI 在写代码或大幅修改 XML 前，必须完成：

1. 读取总纲、关系矩阵、术语和对应专项规范。
2. 标出依赖方向和数据边界。
3. 说明为何选择 Def、DefModExtension、Comp、Service、Provider、Patch 或 Harmony。
4. 判断是否需要 Exception Record。

出现 `Harmony = Yes`、`Hardcoding = Yes`、`Cross-Mod Direct Reference = Yes`、`Static Mutable State = Yes` 任一项，必须进入 Architecture Review。

## 3. AI-003 扩展点选择协议

默认优先级：

```text
原生 Def / XML
→ DefModExtension
→ Comp / GameComponent
→ Service / Contract / Provider
→ PatchOperations
→ Harmony Postfix
→ Harmony Prefix
→ Harmony Transpiler
```

这不是“越后越强”，而是风险升级顺序。AI 必须记录被跳过方案及原因；不得因实现简单直接选 Harmony。

## 4. AI-004 依赖与硬编码禁止清单

AI 默认不得生成：

```text
Core 中的第三方 Mod 条件分支
显示文本/label 逻辑判断
完整覆写第三方 Def
裸 Translation Key / DefName / Asset Path
无界静态可变单例
Tick 中的全库扫描、反射和无界分配
空 catch、静默失败、无界重试
未登记的 Harmony
将 UI/翻译/Texture 写入 Save
```

如确实必要，必须使用 [00-规范例外与变更管理.md](00-规范例外与变更管理.md) 登记。

## 5. AI-005 实现协议

实现顺序：

```text
确认 Contract / 数据 schema
→ 写 Domain/Core
→ 写 Data / Def / Comp
→ 写 Read Model / Provider
→ 写 UI / Theme / Asset / Localization
→ 写 Compatibility Adapter / Patch
→ 补测试和诊断
```

AI 不得在同一类中混合“采集、聚合、存档、UI 绘制、兼容 Patch”。

## 6. AI-006 Localization 协议

新增任何用户可见文本时，AI 必须同时处理：

```text
Key 命名空间
默认语言
目标语言/fallback
参数一致性
长文本布局
Translation 扫描
```

AI 不得把中文默认值、英文覆盖值或某一语言的缺失状态当作业务条件。翻译结果永远不是稳定 ID。

## 7. AI-007 Save/Migration 协议

凡是改变持久化字段、DefName、事件 ID、枚举值、Provider schema 或缓存重建逻辑，AI 必须先写出：

```text
旧 schema → 当前 schema
缺失字段默认值
未知值降级
重命名映射
Migration 幂等性
失败隔离
旧 Save 测试
```

无法证明旧 Save 行为时，AI 必须暂停实现并报告风险，不得假定“字段会自动兼容”。

## 8. AI-008 Compatibility 协议

第三方 Mod 接入必须生成独立 Compatibility 文件/模块：

```text
检测 → 能力判断 → Adapter → 项目 Contract → 可选 UI/数据消费
```

目标 Mod 缺失时基础功能必须继续工作；目标 Mod 失败时必须降级并记录一次结构化诊断。AI 不得引用第三方内部类型扩散到 Core/API/Save。

## 9. AI-009 Testing 与 Gate 协议

AI 完成实现后必须执行适用 Gate，至少包括：

```text
Architecture / Data / Localization / Compatibility
Save / UI / Performance / Testing / Release
```

每项给出 PASS、BLOCKED 或 NOT APPLICABLE，并附 Evidence。没有可执行环境时，AI 必须诚实标记“未执行”，不得伪造通过。

## 10. AI-010 Change Summary 协议

每次交付必须生成 Change Summary，包含：变更范围、规则 ID、行为影响、兼容、本地化、Save/Migration、性能、测试、例外和剩余风险，并按 [REL-002](06-变更日志与发布规范.md#rel-002-change-summary) 更新 Changelog。

## 11. AI-011 审查优先级

违规等级：

| 等级 | 示例 | AI 行为 |
|---|---|---|
| P0 | 循环依赖、破坏存档、污染全局/第三方、绕过安全边界 | 禁止生成/必须立即修复 |
| P1 | 未登记 Harmony、完整覆盖 Def、第三方硬引用、UI 改领域状态 | 阻止交付，要求重构或 Exception |
| P2 | Service 依赖 UI、缓存无失效、性能证据缺失 | 必须修复或明确风险 |
| P3 | 命名、注释、文档互链不完整 | 交付前修正 |
| P4 | 纯风格问题 | 可后续优化 |

AI 不能用“代码能编译”覆盖 P0/P1 架构问题。

## 13. AI-013 变更标注协议

AI 在 Gate 定稿前必须生成**变更标注**（开发者向精确改动清单），解决“验收时无法精准定位已修改内容”。

> 规范性定义、Change ID 贯穿链路、改动类型与符号要求、范围约束、删除/重命名处置、GATE-DELTA 衔接，**全部以 [GOV-013](00-规范体系总纲.md#4-全局不可违反规则) 为唯一权威源**；本条目仅声明 AI 侧的强制动作。

**AI 侧强制动作：**
1. 交付前必生成变更标注（YAML front matter + 表格），覆盖全部 git 改动。
2. 用 `scripts/gate-runner.ps1 -Annotation <标注.md>` 自动校验：标注⊆diff、无超范围、无调试残留。
3. 缺失或不一致时 `GATE-DELTA = BLOCKED`，阻止 Release，不得绕过。

## 14. AI-014 交付粒度协议（禁止碎片化交付）

**目标**：防止 AI 将本属「一个可交付单元」的产品（如一个完整页面、一个端到端功能、一组强耦合模块）人为切分为无数小模块、逐一多轮交付，迫使使用者反复往返才能获得可用整体。

**定义——可交付单元**：在 AI-001 任务入口规划时，凡满足以下条件的集合视为一个可交付单元：
- 共享同一业务目标与同一组调用方；
- 内部模块间存在强依赖（后片依赖前片产物，且无独立验证价值）；
- 合并后单轮输出规模在模型可靠范围内（见下「允许拆分」第 3 条）。

**强制动作**：
1. **先整体规划，再整体产出**：AI 在 AI-001 必须一次性列出该单元的全部目标文件/模块与改动，并在同一轮回复中产出完整实现；不得自创「先给 A、下一轮给 B」的节奏。
2. **变更标注一次性覆盖单元全量**（承接 AI-013）：单元内所有文件写入同一份变更标注，禁止把单元切成多份标注、多轮 Gate。

**允许的拆分（不视为违规）**：
1. 跨 Gate 层级隔离所需（先架构后编码：先定 Contract/Def，但实现仍应在确认后一轮内完成）；
2. 存在**方向性阻塞**：架构选型 / 第三方 API 事实 / 预览目标形态未定，需用户拍板后才能继续；
3. 单元规模超过单轮可靠输出上限（经验阈值：单文件 > ~600 行或单元总量 > ~1500 行）——此时可物理分批，但**不得每片都等用户确认才继续**，应连续产出直到单元完成；
4. 用户在提示中**显式要求**分阶段 / 分批交付（用户意图优先于本规则）。

**禁止的「假拆分」**：
- 把可一次完成的单元按“我会分几步”表述为 N 轮，且每轮强制要求用户确认后才继续；
- 把同一页面的视觉 / 逻辑 / 数据层分别作为“独立交付”反复交回，无视它们构成一个整体；
- 以“先搭骨架”为名只给空壳 / 占位，把真实实现推到后续多轮。

**判定标准**：若拆分后任一片都**无法独立运行或被独立验证**，且整体合并后单轮可完成，则该拆分属过度拆分，AI 必须合并为单轮交付。

**Gate 关联**：用户主张“被碎片化交付”且违反本规则时，GATE-DELTA 视为交付粒度不达标，`BLOCKED` 直至单元合并交付。

## 15. AI-015 用户向开工准备报告协议（先报后做）

**目标**：补齐集群此前缺失的一环 —— 「开工时点上面向用户的准备报告」。`AI-001` 是工程向入口，`AI-012` 与变更标注都是**事后**产物；本协议要求在**写第一行代码之前**，把「怎么做 / 用什么做 / 前后区别」用用户能读懂的话讲清。

**触发时机**：

- 本轮涉及用户可见行为变化（新功能、多模块、UI、数值、流程）⇒ **必须输出七段完整版**；
- 单文件小修 / 纯内部整理 ⇒ 输出**三行简版**（改什么 / 前后区别 / 怎么验）；
- 纯问答、纯检索轮次不要求（但轮次内一旦开始动手，动手前必须补出）。

**七段（缺段视为未完成）+ 固定可视化排版**（照抄本骨架，只填内容；`<…>` 为占位）：

```text
━━ 开工准备 · <CHG-ID> ━━━━━━━━━━━━━━━━━━━━━━━━━━━━
① 结论  <一句话：这次要变成什么，可原样转述>
② 做法  <步骤1> → <步骤2> → <步骤3>
        影响 ▸ <模块> ×N 文件 · <Defs/X.xml> · <Languages/Y.xml>
③ 工具  编译 ⟶ compile_with_sdk.ps1 ｜ 部署 ⟶ deploy-to-game.ps1
        选型 ▸ UI=RUIF ｜ 扩展点=Def+Comp（写真实依据；无依据写「未见依据」）
④ 变化  1. 玩家 ▸ <现在> ⇒ <之后>
        2. 工程 ▸ <现在> ⇒ <之后>
        3. 不做 ▸ <后果>
⑤ 你要  1. ⚑拍板 <决策点>
        2. ⚑配合 <步骤>
        3. ⚑阻塞 <无｜项>
⑥ 风险  <最坏情况> ｜ ⟲ 回滚 <命令｜开关｜字段>
⑦ 验收  1. 代码 ▸ <可复现命令/断言>
        2. 游戏 ▸ <步骤｜无>
━━ AI <模型> · <日期> ━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**简版（三段以内的小修，一行）**：

```text
━━ <CHG-ID> ｜ 做 <…> ｜ 变 <旧>⇒<新> ｜ 验 <…> ━━
```

**排版硬规则**：

1. 首末为 `━━` 规则行；标签列固定 `①结论 ②做法 ③工具 ④变化 ⑤你要 ⑥风险 ⑦验收`（等宽对齐，不换标签名）。
2. **每段 ≤ 2 行**；超出 ⇒ 压成一句，细节下沉到变更标注 / `AI-012` Change Summary。
3. 箭头语义固定、不得混用：`→` 步骤 ｜ `⇒` 前后变化 ｜ `⟶` 命令或工具 ｜ `▸` 并列项（**仅 ≤2 项**）｜ `⟲` 回滚 ｜ `⚑` 需要用户动作。
4. **多项并列（≥3 项）必须编号** `1.` `2.` `3.`，且**每项独占一行**（2026-10-13 用户要求：禁止同行内联，
   内联会把行撑长又难扫）；编号**只用于清单**，不得替代 `→` 步骤与 `⇒` 前后变化（步骤用 `→` 串联、不用编号）。
5. ③ 只写**真实命令名 / 真实框架名**（取自 `.codebuddy/audit/toolchain-registry.md`）；禁止「用脚本跑一下」这类模糊表述。
6. ⑤ 无需用户动作写 `⚑无`；⑦ 未执行写 `未执行`（禁「应该可以」）。
7. 措辞直白、一句说完、说人话：仍禁规则 ID / Gate 名 / 分层术语，禁英文缩写堆叠；**整份报告 ≤ 18 行**
   （编号逐行后放宽 15 ⇒ 18；术语与证据细节留给 `AI-012` / 变更标注）。
8. **输出保真（硬性）**：报告必须以**代码块围栏**（围栏语言标 `text`）发出，不得裸行直发 ——
   聊天窗/预览器会把**单个换行合并成空格**，裸行输出会把整份报告压成一段（2026-10-12 实测：首末规则行与 `R1` 连成一行、`└` 明细全部消失）。
   围栏行**不计入**行数上限；不支持围栏的环境改用**行尾两空格**制造硬换行。
9. **行宽与折行（防横向滚动）**：代码块**不会自动折行**，长行会逼出左右滚动条（2026-10-12 用户实测截图）——
   故每行**视觉宽 ≤ 72**（中文 / 全角**按 2 计**）；超长内容**先砍措辞**，砍不动才**主动折行**：
   续行缩进 4 空格、视觉上仍属同一条；**折行不计入「每段 ≤ 2 行」的逻辑行数**（逻辑行 ≠ 物理行）。

**语言约束**：禁规则 ID、禁 Gate 名、禁「分层 / 契约 / Provider / Read Model」等内部术语。用户向 ≠ 术语减配版；技术细节留给 `AI-012` Change Summary 与变更标注。

**落盘**：默认**只在对话内输出**（避免每轮新增文档并触发 DOC 门禁）。用户明确要求归档时，按 `doc-standard` 先出「文档变更申请」（DOC-004）再定落点，**不得预设路径直接写盘**。

**与相邻产物分工（互不替代）**：`AI-015`（开工前·用户向）→ `AI-012`（完工后·工程向）→ `AI-013` 变更标注（完工后·开发者向）→ Changelog（发版·用户向版本级）。

## 16. AI-016 每轮必输出契约（Round Output Contract）与收尾校验

**目标**：把「每轮对话必须输出什么」敲成固定清单，消除「经常性缺漏」。**收尾回复缺任一项即视为未收尾**，不得声称完成（`GOV-012`）。

### 16.1 九项必输出（R1–R9）

```text
R1 开工准备报告   AI-015（七段 / 三行简版）
R2 做了什么       按实际 diff：文件 + 符号 + 为什么
R3 Gate 结论      四态表 Gate / Result / Evidence；N/A 必须带理由
R4 变更标注       + GATE-DELTA（有 git 改动时必出，含收尾校验结论行）
R5 现在能用吗     用户向一句结论 + 你要做什么（下一步）
R6 风险与遗留     未做项 / 未验证项 / 待裁决项；不得把「应该可以」写成「已验证」
R7 记忆与文档     记忆单状态（提案 / 批准 / 落库 / 无）；文档动作（申请 / 落点 / 索引 / 取代 / 无）
R8 AI 署名        每个交付物与收尾回复均署名
R9 台账收敛       AI-017：before → after + 本轮关闭项；非长项目轮次写 N/A 并给理由
```

### 16.1b 固定可视化骨架（排版是硬规则，不是建议）

**动机**（2026-10-12，`CHG-20261012-TOOLGOV-W1`）：用户反馈「R1–R9 报告的样式不够直观可视」——
原收尾是逐段散文，读者要通读才能判断「哪一门 BLOCKED / 遗留几项 / 台账降没降」。
故与 `AI-015` 同构地给收尾定一套**一眼可扫**的骨架（`AI-015` 管开工、本节管收尾，两者首末规则行同款）。

**固定骨架（照抄，只填内容）**：

```text
━━ 收尾 · <CHG-ID> ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
R1 开工报告  ✅ <一句话：本轮目标 / 已出 AI-015 报告>
R2 改了什么  ✅ <N 文件>（<分类计数>）｜符号级见变更标注
R3 Gate 结论  ⛔ <一句汇总：PASS a ｜N/A b ｜BLOCKED c>
             └ 1. <Gate>=<Result>
               2. <Gate>=<Result>
               3. <Gate>=<Result>
R4 标注+DELTA ✅ 标注 <CHG-ID> ｜GATE-DELTA <PASS|BLOCKED>（<n> 文件 · 提示 <n>）
             └ 收尾结论 <PASS|BLOCKED> ｜收尾链结论 <PASS|BLOCKED>
R5 能用吗     ✅|⛔ <一句用户向结论>
             └ 你要做
               1. <动作>
               2. <动作>
R6 风险遗留   ⚠ 未验证 <n> ｜未修 <n> ｜待裁决 <n>  → 去向 ▸ <台账 program / 无>
             └ 1. <最要紧的那一条>
               2. <次要的一条>
R7 记忆/文档  ✅ 记忆 <n 条已写｜无> ｜文档 <改 n / 新建 n 或「无新建」>
R8 署名       ✅ 由 AI 助手（<模型>）· <日期>
R9 台账收敛   ✅|⚠|⛔ <PROG> <before> → <after>（Δ<±n> · 关闭 <n> 项）<｜code=… 理由：…>
━━ AI <模型> · <日期> ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**排版硬规则（10 条）**：

1. 首末为 `━━` 规则行；`R<n>` 位于**行首**（`R<n>` 后紧跟一个空格与标签）。
   ⚠ **核验强度如实说明**：`round-closure.ps1 -Transcript` 实际用的是**词边界**正则 `(?m)(^|\W)R<n>(\W|$)`，
   连行内提及（`详见 R3 表`）与一行区间写法（`按 R1–R9 输出`）都会命中 ⇒ 机器**只能排除「完全缺项」**，
   **证伪力≈0**；骨架是否真按本节输出属**人工项**（已列入 `round-closure` 的人工项清单）。
2. 每条状态符固定、不得自造：`✅` 通过 ｜ `⚠` 警告/有遗留 ｜ `⛔` 阻断 ｜ `▸` 并列项（**仅 ≤2 项**）｜ `→` 变化 ｜ `└` 二级明细。
   符号按**语义**核对，**不逐字节比对**（编辑器可能自动补变体选择符 `FE0F`）。
3. **每条 ≤ 2 行**（`└` 明细算第二行）；**正文骨架 ≤ 26 行** —— 空行不计、**证据附录不计**（附录另行标注「附录」）。
   **行数已因「编号逐行」放宽 20 ⇒ 26**（`R3` 明细七门各占一行）；细节下沉到变更标注 / `AI-012`。
4. `R3` 必须**先给一行汇总**再给明细（这是「直观可视」的核心：一眼看到有几门不过）。
5. `R6` 必须给**数字**（未验证/未修/待裁决各几项）与**去向**（进了哪个台账 program），不得只写散文。
6. `R9` 非长项目轮次写 `N/A`（含理由），**不得省略该行**。
   **一致性已部分机器化**（`round-closure` 的 `M9b` 行）：传 `-Transcript` 时，脚本会从 `R9` 行抓 `before → after`
   与台账 `M9` 行的实际数字比对，**不一致即 BLOCKED**（伪造收敛）；`R9` 写 `N/A` 而本轮**已挂项目槽** ⇒ `WARN`（疑漏挂槽被伪装）。
   仍在人工侧的部分：`M9 = WARN`（waiver 轮）时须写 `⚠ 未收敛` 并复述 code，**不得写 ✅** —— 这一点机器不判。
   另外「真与长项目无关」的空槽轮次，机器另给一条软信号：台账中若仍有未清空的长项目即 `WARN`。
7. 语言约束同 `AI-015`：R1/R5/R6/R9 面向用户，禁规则 ID 与内部分层术语（术语留在 R2/R3/R4）；
   措辞直白、一句说完，禁英文缩写堆叠。
   冲突消解：`R9` 写 `N/A` 的理由若不可避免涉及内部概念（如「未挂项目槽」），允许写「本轮无长项目在推进（见台账）」，
   **以规则 7 为先**、规则 6 的「理由」允许多半句用户向表述。
8. **多项并列（≥3 项）必须编号** `1.` `2.` `3.`，且**每项独占一行**（2026-10-13 用户要求：禁止同行内联）；
   编号**只用于清单**，不得替代 `→` 变化与 `└` 明细行首；续行与首项对齐缩进（视觉上属同一条）。
9. **输出保真（硬性，同 `AI-015` 规则 8）**：收尾报告必须以**代码块围栏**（围栏语言标 `text`）发出 ——
   聊天窗把单个换行合并成空格，裸行输出会把整份骨架压成一段（2026-10-12 实测截图）；围栏不计入 20 行上限。
   若报告被压平，属**交付缺陷**：须重发，且不得声称已收尾（机器 `-Transcript` 核验仍按行首 `R<n>` 匹配）。
10. **行宽与折行（同 `AI-015` 规则 9）**：代码块**不自动折行** ⇒ 长行会逼出左右滚动条。每行**视觉宽 ≤ 72**
   （中文按 2 计）；超长**先砍措辞**，砍不动才主动折行（续行缩进 4 空格）；**折行不计入「每条 ≤2 行」**，
   也**不得把长行硬撑**成需要横向滚动的宽度。

## 17. AI-017 长项目台账与波次协议（跨轮续航）

**目标**：解决「无法进行长项目」——每轮都留下大批量小任务、下一轮重新发现同一批问题、永不收敛。

**问题根因**（2026-10-12 立项，`CHG-20261012-LONGPROJ-LEDGER`）：
`R6 风险与遗留` 只写在收尾回复正文，**无落点、无脚本读取** ⇒ 遗留项在上下文重置后蒸发；而交付原子被默认为「一轮对话」，使治理固定开销（十道 Gate + 变更标注 + 收尾契约）按轮次线性计价。实测代价：**131 份 gate-record / 66 个 ChangeID**（09 月 45 份、10 月 12 天 86 份），单日单项目派生 5+ 个 ChangeID。⇒ 单轮预算大部分被治理税吃掉，只剩做小问题的余量。

### 17.1 唯一台账

`program-ledger.json`（落点固定 `.codebuddy/audit/`；**数据文件，不受 DOC-001–010 文档门禁管辖**）。
**唯一写入入口** = `program-ledger.ps1`；**禁止手工编辑 JSON**（防双源漂移）。
结构：`programs[]`（`id / goal / nonGoals / wave / items[]`），`items[]` = `id / title / status / gate / wave / depends / assertion / evidence / note / source / updatedAt`。
状态枚举：`OPEN / IN_PROGRESS / BLOCKED / DONE / DROPPED`；**剩余项 = 前三者**（收敛计数的分母）。

### 17.2 硬不变量（GOV-012 同源，不得绕过）

```text
新增项必须带 -Assertion   （可证伪验收断言；无断言的任务不可收敛）
DONE   必须带 -Evidence   （无证据不得标完成；不得为让判据变绿而标 DONE）
DROPPED 必须带 -Note      （舍弃理由；禁止静默删除，同 DOC-007 口径）
```

### 17.3 轮次协议

```text
开工 → program-ledger.ps1 -List -Program <P>     （读台账；未挂 program 先 -Init 并把已知遗留 -Add）
     → 本轮未挂项目槽 ⇒ change-context.ps1 -Set -Program <P> -Wave <W>
干活 → 波次（Wave）内连续产出，只做增量检查
收尾 → program-ledger.ps1 -Set ... -Status DONE -Evidence <证据>   （写回台账）
     → close-round.ps1 -Program <P> -ChangeId <ID> -Annotation <标注> -Blocking
```

**收敛判据（M9，有牙齿）**：`剩余项 before → after` 必须下降或归零；不降且无 `-LedgerWaiver "<书面理由>"`
⇒ `round-closure` 的 `M9 = BLOCKED` ⇒ `收尾结论: BLOCKED`。**未收敛不得声称推进。**
基线由 `close-round.ps1` ④ 在 `② 非 BLOCKED` 时刷新（BLOCKED 时保留旧基线，避免「未收敛被静默原谅」）。

### 17.4 波次与反碎片化（AI-014 的长项目侧）

- **波次（Wave）**：一个 program 划分为若干可验收波次；**只有波次边界**做全量十道 Gate + 完整收尾 + 变更标注，波次内部连续产出。
- **一个 ChangeID 用于一个波次**：同一 program 同一波次内复用 `change-context.json` 的项目槽；
  **禁止**为同一 program 的同一波次另建 ChangeID 或另起一份变更标注（这是实测的碎片化来源）。
- **归属**：开工读 / 收尾写由 `pc-orchestrator` 执行；M9 收敛证据的核验由 `pc-release-clerk` 承载；不新建第 8 个 agent。

### 17.5 Gate 关联

`M9 = BLOCKED` ⇒ 本轮视为未收尾（同 `AI-016`）；为绕过 M9 而标 `DONE`（无 Evidence）或 `DROPPED`（无 Note）按 `AI-011` 的 `P0` 处理（伪造 PASS）。
