## 0. AI-001 任务入口（轻量化治理适用）

任何触发本规范的改动（新增模块、拆分大文件、归并散落文件），AI 必须先记录：

```text
目标：新模块组织 / 存量 god class 拆分 / 文件归并
涉及层与文件（按 TERM-011/012 标注 Domain/Application/Data/Presentation）
是否改动类名 / 公共签名 / Save schema / 翻译键（均应 = 否）
适用规则 ID：ARC-013, BASE-005, ARC-001, MATRIX-001
是否触发 Architecture Review（见 §6）
验证与 Gate：GATE-ARCH + 编译/单测
```

信息不足时采用最小安全假设并标记，不得凭方便扩大切片范围。

## 1. [ARC-013] 文件组织与类结构治理

### 1.1 规则原文

| ID | 规则 |
|---|---|
| ARC-013 | 文件与类必须保持单一职责与可维护规模；大文件通过 `partial` 物理切片或按层/职责归位治理，不得堆砌 god class。治理只允许物理组织变更，**不得**随之改动类名、公共签名、Save schema、翻译键或契约语义。 |

### 1.2 治理目标（锚定体系）

- **单一职责**：对齐 [BASE-005]（文件/类/模块单一职责）与 [ARC-004]（Service 不得用 Manager 汇总无关职责）。一个文件 / 一个 `partial` 只承载一类职责。
- **分层归位**：对齐 [ARC-001] 与 [MATRIX-001] 单向依赖。文件必须落在所属层目录（Domain/Application/Data/Capture/Archive/Api），禁止跨层混放（详见 [09-模块文件架构范式](09-模块文件架构范式.md) §1 分层契约表）。
- **零契约改动**：对齐 [GOV-005]（跨模块通信经契约）。切片只搬方法体，不改 `IArchiveService` 等公共接口、不改 Scribe 字段名、不改 `UI.*` 翻译键。
- **可维护规模**：目标单文件 ≤ 800 行（`PawnDetail` 等渲染密集型 ≤ 1200 行）；超出即触发本规范治理。

### 1.3 适用范围（全项目）

- **存量治理**：已存在的 god class（`ArchiveMainTabWindow`/`ArchiveService`/`ArchiveUiDataProvider`/`ChronicleGameComponent`/`SectionSnapshots`）按本规范 §3 方法继续切片。
- **新增模块**：任何新功能从第一天起按 [09-模块文件架构范式](09-模块文件架构范式.md) §4 SOP 挂在正确层，不得新建孤立大文件。
- **演进重构**：模块长大时主动切片，不等地狱式膨胀后再救火。

## 2. 治理原则（与体系一致）

1. **partial 切片为主**：不改类名、字段、方法签名、访问级别 → 零运行时风险、零契约变更（编译器合并）。同一 `partial` 类的成员天然互相可见，跨 partial 调用无需改访问级别。
2. **职责优先于行数平均**：按逻辑分组切，不按行数均分；一个功能单元 = 一个独立 partial 文件。
3. **不动契约**：接口、公共签名、Save schema、翻译键一律不动（对齐「关键实现契约勿改动」与 [SAVE-001]）。
4. **不引入新抽象**：单一实现的功能点不上路由/注册表（对齐 [ARC-006] 的"仅在确实需要未来接入时才提供 Provider"）；跨 partial 引用靠同类型成员可见性，不建硬引用链。
5. **编译 + 回归护栏**：每步编译 0 错 0 警 + NUnit 离线测试 + 游戏内抽查（对齐 [AI-009] Gate 协议）。
6. **发布同步**：每次落地立即同步发布区（dll 需重启游戏生效，对齐红线）。

## 3. 方法论：排序 → 识别 → 剥离（全项目通用）

对齐 [AI-002] 先架构后编码：拆分前先看清功能边界，不按行数硬切。

### Step 1：对象排序（按风险/体量/耦合度）

| 排序依据 | 示例 |
|---|---|
| Save 风险高（含 `ExposeData`/迁移） | `ChronicleGameComponent` → 需 [AI-007] 存档协议前置 |
| 跨接口强耦合 | `ArchiveService`（实现 `IArchiveService`/`IArchiveQueryService`） |
| 已部分 partial、耦合集中在 UI | `ArchiveMainTabWindow` |
| 纯聚合密度型 | `ArchiveUiDataProvider` |
| 零逻辑纯数据 | `SectionSnapshots` |

> 排序决定落地顺序（易→难 / 风险低→高），避免一开始动 Save 关键文件。

### Step 2：独立功能识别（每个文件的功能清单）

以职责为粒度列出功能单元（参考已落地映射）：

| 文件 | 识别出的独立功能单元 |
|---|---|
| `ArchiveService` | ① 基础读写 ② 工时强度 ③ 生产 ④ 损耗 ⑤ 战役 ⑥ 社交 ⑦ 地点/持有者 ⑧ Live 缓存与别名 |
| `ChronicleGameComponent` | ① 存档持久化 ② 采样 ③ 别名 ④ 查询 ⑤ 写入入口 ⑥ 迁移 ⑦ 索引/回填 |
| `ArchiveMainTabWindow`(主) | ① 缓存重建 ② 战斗扫描 ③ 派系图鉴 ④ 导航 ⑤ 头部/侧栏 ⑥ 绘制原语 ⑦ 标签解析 |
| `ArchiveUiDataProvider` | ① 主页/概览 ② 详情六宫格 ③ 事件 ④ 生产账本 ⑤ 传承/社交 ⑥ 通用辅助 |
| `SectionSnapshots` | ① Home ② Overview ③ Detail ④ Event 快照类 |

### Step 3：逐功能剥离（每个功能 → 一个独立文件）

- **原则**：一个功能单元 = 一个独立 partial 文件（或独立类文件），文件内自洽、不反向依赖兄弟文件。
- **剥离顺序**：先剥叶子功能（无下游依赖，如纯数据类、通用辅助），再剥主干功能。
- **跨功能依赖**：功能 A 调 B 时通过主文件字段 / 已注入依赖间接引用；同一 class 的 partial 成员天然可见。
- **验收**：剥离后每文件 ≤ 800 行；`git diff` 仅显示「删行 + 新增文件」，无逻辑行改动。

## 4. 分层文件归位（全项目结构基线）

此节给出各层文件组织基线；**具体模块挂接示例见 [09-模块文件架构范式](09-模块文件架构范式.md)（以劳动模块为样板）**。

| 层 | 目录 | partial 策略 | 命名 |
|---|---|---|---|
| Domain | `Domain/` | 否（小而专） | `<Concept>.cs` / `<Concept>Evaluator.cs` / `<Concept>Def.cs` |
| Application | `Application/` | 主类 `partial` | `<Service>.cs`（主）+ `<Service>.<Area>.cs` |
| Data | `Data/` | 主类 `partial` | `ChronicleGameComponent.cs`（主）+ `.Sampling/.Aliases/.Queries/.Migration` |
| Capture | `Capture/` | 否 | `Patch_<Target>.cs`（只转调 Service，不写业务） |
| Archive(UI) | `Archive/` + `Archive/ReadModels/` | 主类 `partial` | `ArchiveMainTabWindow.<Area>.cs` / `ITab_*.cs` / `Dialog_*.cs` / `SectionSnapshots.<Area>.cs` / `ArchiveUiDataProvider.<Area>.cs` |
| Api | `Api/` | 否 | `I*.cs` / `DomainProviders/**` |

**归位铁律**（对齐 [MATRIX-001/002/003]）：
- 纯逻辑（档位计算、series 归并、阈值评估）放 **Domain**，可离线 NUnit 覆盖。
- 跨字段聚合、写库入口放 **Application/Data**。
- 引擎事件入口放 **Capture**（只转调 Service）。
- 展示专用只读快照放 **Archive/ReadModels/SectionSnapshots.\<Area\>.cs**，与窗口绘制解耦。
- **UI 不直读 `ChronicleGameComponent`**；窗口只消费 `IArchiveUiDataProvider` 快照（对齐 [ARC-002]/[MATRIX-003]/[UI-003]）。

## 5. 单文件内部规范（轻量化编码约定）

| 项 | 要求 | 体系锚定 |
|---|---|---|
| partial 字段 | 字段集中留主文件；扩展方法留 `static` 类，勿误切进实例 partial | [ARC-013] |
| using/namespace | 与同模块一致；`ReadModels` 子命名空间不跨层引用 UI 绘制 | [MATRIX-001] |
| 注释分隔 | 大文件内 `// ---- <功能名> ----` 标注边界，便于未来再拆 | [BASE-011] |
| UI 配对恢复 | 禁 `new Color(...)`、禁裸 `GUI.color`；`Text.Font/Anchor/color` 改必须 `prev` 快照 + try/finally | [UI-006]/[ASSET-002] |
| 中文行高 | 大卡≥110f / StatCell≥64f / 小字≥18f / Medium≥28f | [UI-009] |
| null-guard | LINQ 前过滤 null；UI 不直读 GameComponent | [AI-004] |
| 防御 | 不依赖显示文本作为标识（[GOV-009]）；魔法值集中（[BASE-010]） | — |

## 6. Architecture Review 触发（[ARC-011]）

下列任一项出现，轻量化治理须进入 Architecture Review，不得自行继续：

- 切片涉及 `ExposeData` / `FinalizeInit` / Migration → 先执行 [AI-007] Save/Migration 协议（旧 schema→新 schema、默认值、幂等、旧档测试）。
- 切片误改了类名 / 公共签名 / Save 字段名 / 翻译键。
- 发现需引入 Provider/Registry/DI 才能解耦（超出纯物理切片范围）→ 回到 [ARC-006] 评估。
- Save 行为有变 → 暂停并报告（[AI-007]）。

## 7. Gate 联动（[00-统一验收标准](00-统一验收标准.md)）

轻量化治理的验收并入 **GATE-ARCH**：

```text
[ ] 文件/类单一职责（BASE-005 / ARC-004 / ARC-013）
[ ] 文件落在所属层目录，无跨层混放（ARC-001 / MATRIX-001）
[ ] partial 切片仅物理搬移，类名/签名/契约/Save schema/翻译键零改动
[ ] 单文件 ≤ 800 行（渲染密集 ≤ 1200）
[ ] 编译 0 错 0 警；NUnit 全绿
[ ] 发布区已同步（dll + 改动的 Def/语言文件）；重启游戏抽查通过（如涉及 Save）
```

对应 [AI-009] 各 Gate 至少 PASS/N/A 并附 Evidence；无执行环境时诚实标 N/A，不得伪造。

## 8. 反例与边界（明确不做）

- ❌ 不在主文件堆新业务方法（该切 partial 切 partial）。
- ❌ 为单一实现引入 Provider 路由 / DI 容器 / 反射注册（过度设计，违反 [ARC-006] 默认）。
- ❌ 改动类名、公共签名、Save schema、翻译键来"配合"切片（违反 [ARC-013] 零契约改动）。
- ❌ Capture 层写业务逻辑（只转调 Service）。
- ❌ Domain 层引用 `Verse`/`RimWorld`/`UnityEngine`（破坏离线可测性，违反 [ARC-002]）。
- ❌ UI 层直读 `ChronicleGameComponent` 或写 Save（违反 [MATRIX-003]/[SAVE-006]）。
- ❌ bump mod 版本（纯组织/功能变更，除非契约确需演进并经评审）。
