# EXC-2026-006 — 事件流采集 Harmony（E2）

- **Status:** **Obsolete（2026-09-20）** —— 对象随 `CHG-LCE-001` 删除：MVS 市场事件采集段已从 `Patch_IncidentWorker` 移除（战斗记录段保留），本例外失去对象。
- **Level:** E2
- **Rule IDs:** COMP-004, EXC-002, GOV-007
- **Scope:** 事件流采集补丁 **复用既有 `PersonalChronicle.Archive` HarmonyId 下的 `Capture/Patch_IncidentWorker`**（target = `RimWorld.IncidentWorker.TryExecute(IncidentParms)`），**不新增 patch 目标**。MVS 记录逻辑以**并列、不嵌套**的第二个 `try/catch` 追加在该 Postfix 体内。
- **Reason:** 原版**没有**任何派系级事件日志。Cecil 实证：
  - `list History` ⇒ 仅 `RimWorld.History` + `HistoryAutoRecorder*`（ColonistMood / FreeColonists / PopAdaptation / PopIntent / Prisoners / ThreatPoints / WealthBuildings/Items/Pawns）——**玩家殖民地的曲线记录器**，无派系标签、无事件语义；
  - `list Archive` ⇒ 仅 `RimWorld.Archive` / `ArchivedDialog`——**玩家信件归档**，只有发信事件才有记录，无派系标签；
  - `refs TryExecute` ⇒ 12 处调用点（`CompAbilityEffect_RaidEnemy` / `CompAbilityEffect_Infestation` / `Dialog_Trade` / `FactionDialogMaker.CallForAid` / `GameCondition_DroughtInitial` / `IncidentWorker_CaravanMeeting` / `Instruction_DownRaider` / `Planet.TimedDetectionRaids` / `QuestPart_Incident`×2 / `QuestPart_RandomRaid`）⇒ **一个 Postfix 收全部派发入口**。
  符合 COMP-004「原生机制无法完成」前提。
- **Alternatives rejected:**
  1. 补 `IncidentWorker.TryExecuteWorker` —— **否决**：`protected virtual`，子类（`IncidentWorker_RaidEnemy` 等）各自覆写，补基类会**漏掉绝大多数事件**（这是本项目最容易踩错的点）。
  2. 静态降级（v1 不采集事件流）—— **否决**：用户已明确拍板「走 Harmony」。
  3. 新建第二个 `[HarmonyPatch]` 类补同一方法 —— **否决**：`TryExecute` 是热路径，两个 Postfix 意味着门控开销翻倍（双次 `GetModExtension` + 双次 category 回退）。
- **Risk:** `TryExecute` 是热路径；白名单门控失效会误记事件。
  ⚠ **IL 取证推翻了原「宁漏勿误」假设**：`il RimWorld.IncidentWorker TryExecute` 显示存在提前返回路径——
  ```
  IL_0015: ldfld IncidentDef::requireColonistsPresent
  IL_0022: callvirt MapPawns.get_FreeColonistsSpawnedCount
  IL_0029: ldc.i4.1 ; ret     ← 未执行 worker，直接返回 true
  ```
  ⇒ `__result == true` **不保证事件真发生**，风险性质是「**可能误记**」而非「宁漏勿误」。
- **Mitigation:**
  1. **白名单（`MVSIncidentImpactDef`）是必需项**，不得放宽为「全记」；
  2. 独立 `try/catch` 失败隔离：MVS 侧异常**不拖垮**战斗记录（两块并列、不嵌套）；
  3. ~~只读 Postfix，**零 mutation**，故无需 `[HarmonyAfter]`/`[HarmonyBefore]`/`[HarmonyPriority]`；~~
     **⚠ 2026-09-19 修订（CHG-MVS-SETTLE-001，结算器落地）**：Postfix **本身仍不直接改任何状态**，
     但新增一处 **O(1) 入队** —— `MarketAccess.TryGetComponent()` → `WorldComponent_Market.EnqueueShock(impact, tick)`，
     其**后续效果会间接改写权威因子表**（`globalFactors`）。这正是"市场终于会响应事件"的必由之路，
     故不再适用"零 mutation"的原表述。风险面与缓解：
     - 入队位置**在去重门之后**（`MarketEventLog.HasRecent` 已过滤 `GameConditionTick` 类重复派发）
       ⇒ 不会把环形容器灌满触发假性溢出；
     - 入队契约为 **O(1) / 零品种展开 / 绝不抛**（`commodities` 展开推迟到结算步）
       ⇒ 补丁热路径增量 = 一次组件查找 + 一次数组写入，与"每秒多次 `TryExecute`"的实际频率同量级；
     - 组件侧自带「`stage == Ready` **且** 非只读降级」双闸门 ⇒ 未就绪 / 降级档**不入队、不改数据**，
       与"不迁移、不回写、不改数据"的存档安全边界一致；
     - 真正写 `globalFactors` / `shockOffsets` 的动作只发生在 `WorldComponentTick`
       （**原生虚方法覆盖，不是 Harmony**，不新增 patch 目标）。
     ⇒ **"无需 `[HarmonyAfter]`/`[HarmonyBefore]`/`[HarmonyPriority]`"的结论不变**：
       本补丁仍不与其他 Harmony 补丁产生顺序依赖（入队只依赖本 mod 自己的组件）。
     ⇒ **回滚说明**：删除 `MarketEventSink.RecordCore` 末尾的入队段即可退回"零 mutation"旧形态，
       此时结算器队列恒空 ⇒ 因子表恒空 ⇒ 价格通道恒等变换（等同结算器未上线，无存档副作用）。
  4. `parms.faction == null`（灾害/天象）⇒ 归 `EventScope.Global`，**不按 `parms.target` 归因**（target 是 Map/World 非派系）；
  5. 去重窗口 16 条（防 `GameConditionTick` 类重复派发）；
  6. 事件 ring（容量 200）**不落盘**，仅会话内。
