# EXC-2026-012 — 车间排班联动写入原版 Pawn 级状态（时间管制表 + 工作面板 Enable）（E2）

- **Status:** Approved
- **Level:** E2（跨模块边界写原版玩家级状态 + 以例外收窄既有 SDD 反向约束；可回滚、不改 Save schema）
- **Rule IDs:** GOV-005（跨模块通信/边界）· GOV-006（映射数据不得硬编码）· GOV-007（扩展点选型：不采用 Harmony/Patch）· PERF-001（事件驱动低频，W8 口径例外）· MATRIX-003（写入不得经 UI 层——限定条件）· AI-002/AI-003（先架构后编码、跳过方案记录）· EXC-001（例外管理）
- **Scope:** `Source/PersonalChronicle/Automation/`（`MapComponent_WorkshopManager.WorkEnable.cs` 新增 partial；`WorkshopManageView.OnRosterChanged` / `Refresh` 触发接线）+ Def 映射数据（`Defs/WorkshopTypes.xml` 的 `*WorkTypeDefNames`）+ 原版运行时状态写入（本 Mod 无新增 Save 字段）：

  1. **`Pawn_TimetableTracker`**：`timetable.SetAssignment(h, Work/Sleep)`，24 格/人 —— **补登记**（由 `CHG-20260925-TIMETABLE-DEVICES` 引入时未登记；本次行为不变，仅补办手续）。
  2. **`Pawn_WorkSettings`**：**仅 Enable** —— 当且仅当 `GetPriority(wt) <= 0` 时 `SetPriority(wt, Pawn_WorkSettings.DefaultPriority)`；`wt ∈ {PC_WorkshopOperation} ∪ 车间类型 Def 岗位映射声明的原版 WorkTypeDef`。**不含**档位变更 / 重排 / `Disable`。

  **触发时机（硬约束）**：排班/班次/班组/成员变更事件（`WorkshopManageView.OnRosterChanged`）+ 打开管理面板时对账一次（`Refresh`）。**禁**每 tick、**禁**绘制路径、**禁** JobGiver 内写。

- **Reason:**
  1. 需求 G3：车间值勤 Job 链的 `PC_WorkshopOperation` 在 Def 里是 `alwaysStartActive=false`，玩家不在原版工作面板手动勾选就永不被 `JobGiver_Work` 排到 ⇒ 实测现象「安排了班次和班组后 pawn 闲置」。
  2. 需求 G4：「班次设置 → 岗位 · 生产」应自动勾选原版对应工作类型，否则岗位语义只停留在展示层。
  3. 既有 SDD 反向约束（`Pawn自驱力框架_经济驱动的应用配置.md` §5.4 / §7 第 2 条；`原版工作系统性能成本分析_2026-09-10.md` W8）须以例外方式**收窄适用面**，而非静默违反。
  4. 既有未登记姊妹写入（`SyncVanillaTimetables`）借本批统一补登记。
- **Alternatives rejected:**
  1. **改 `alwaysStartActive=true`（XML）** —— 全局面（未参与排班者亦启用）+ 绕过原版「初始只开 6 项」上限；且 `alwaysStartActive` 的两个消费点（`Pawn_WorkSettings.EnableAndInitialize` / `GameInitData.PrepForMapGen`）**都只在初始化路径**，对既有存档零回补 ⇒ 运行时写无论如何都要做，改 XML 是纯增副作用的冗余项。否决。
  2. **Application Service + 新 Contract/Binder** —— 档案/经济应用域与车间自动化域不同域；为一个有界修复新建跨层管线会把「写原版玩家级状态」能力扩散到更多模块（与 EXC-2026-010 的收敛精神相反）。多子系统复用需求出现时重评。否决。
  3. **Pawn Comp** —— 无既有模式、生命周期/存档成本高、不解决触发与作用域。否决。
  4. **Harmony / Patch** —— `SetPriority` 为公开 API、WorkGiverDef 扩展点已用（`Defs/Automation_Jobs.xml`），不需要（GOV-007；Harmony=No）。否决。
  5. **UI 层直接写** —— 违反 MATRIX-003 / UI-004 与「绘制路径不写持久数据」纪律。否决。
- **Risk:**
  - 「抢玩家控制权」：Enable 改变工作面板勾选态；玩家手动关闭后若再遇排班结构变更事件可能被再次开启。
  - 工作链成本：`SetPriority` 置该 pawn 的 `workGiversDirty`，下次取工作链会重建其个人表（`Pawn_WorkSettings.SetPriority`）⇒ 禁高频调用。
  - 与「调优先级类 Mod」写同一字段的潜在交互。
  - 既有 timetable 24 格全量覆写会覆盖玩家手排（既有行为，纳入登记面）。
- **Mitigation:**
  - **硬性限定**：仅 `0 → DefaultPriority` 幂等写入；仅排班相关人员（班组成员 / 未编组时的车间名单 / 班次显式候选池）；仅事件 + 打开面板对账触发；禁 tick / 绘制路径 / `Disable` / 重排。
  - **守卫**：`workSettings != null` → `EnableAndInitializeIfNotAlreadyInitialized()` → 跳过 `pawn.WorkTypeIsDisabled(wt)`（原版对 disabled 类型写非 0 会 `Log.Error`）→ 仅 `GetPriority <= 0` 才写。
  - **映射为 Def 数据**（`Defs/WorkshopTypes.xml`），C# 侧零 defName 业务字面量（GOV-006）；解析用 `GetNamedSilentFail`。
  - **与「工作优先级类 Mod」共存**（COMP 复核补录）：本写入只把 `0` 档抬到默认档 `3`，**不重排、不改档**（1–4 一律不碰），因此与这类 Mod 的「排序」职责不重叠；冲突面仅限于「玩家把某工作显式关到 0 后被排班结构变更再次开启」，玩家可再次手动关闭。岗位菜单展示「原版工作：X」+ 编辑器提示行（`TaskSyncHint`）已把该联动对玩家可见，不属于静默改设置。
  - **可观测性（COMP-011）**：映射 defName 解析失败时按 defName **只告警一次**（`ResolveWorkType` 去重集合）；正常的 `0→3` 写入**不写日志** —— 它是本特性预期行为、且每次排班变更都会发生，记日志只会污染 Player.log 而不增加信息量。
  - **回滚**：撤销代码即止写；无 Save 变更；玩家可自行关闭。
  - **回归证据（批准条件之一）**：排班变更后勾选态正确 · 非排班人员零变化 · 已有优先级（1–4）零变化 · 无 tick / 绘制路径写入。
