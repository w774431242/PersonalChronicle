- **Reason（为什么默认方案不可行 / 为什么必须登记）:**
  1. **用户需求（2026-10-03，锁定决策）**：「还原真实车间分工」—— 排班/派工后把车间相关工作提到 1 档，**其余所有工作统一降到最低档 4**，玩家不设兜底，PC 只提供一键解除。这是**产品语义**，不是实现细节。
  2. **在字面上违反既有约束**：EXC-2026-013 明文承诺「不重排其它工作类型的相对次序」。「其余全部降到 4」必然重排（原来是 1..4 混杂）。**不能原地扩围**（EXC-2026-012 已确立此纪律：不得以"改一句话"隐式产生例外），故另立本记录。
  3. **静态取证（1.6，Cecil 核实）**：`Pawn_WorkSettings` 的工作链排序键 = `naturalPriority + (4 - GetPriority(wt)) * 100000`，每档权重 10 万。把其余工作压到 4 档（权重 +300000）**确实**能让车间工作稳定排到最前 —— 这是达成"专属工位"语义的唯一原版途径。
  4. **粒度天花板**：`RimWorld.Bill` 与 `RimWorld.Bill_Production` 在 1.6 **均无 `workType` 字段** ⇒ **不存在 per-bill 工作类型**。能控制的最小粒度只有 per-pawn + per-`WorkTypeDef`，"专属工位"只能是这个粒度。
  5. **不加台账就不可逆**：降档会覆盖玩家手排的档位。没有"PC 动过哪一项、原值多少"的记录，一键解除就无法只还原 PC 改过的项 ⇒ 会连带抹掉玩家自己的意图。台账是本记录可逆性的**唯一**凭据。

- **Alternatives rejected（含"不设兜底"的后果登记）:**
  1. **调 `WorkTypeDef.naturalPriority`** —— 简单模式下唯一有效的排序途径，但目标是**原版共享 Def**，一改则全局所有 pawn 在所有场景都受影响，且属"完整覆写原版 Def"（AI-004 明令禁止）。否决。
  2. **`Disable` / `SetPriority(0)` 取消勾选其余工作** —— 语义更彻底，但原版 `Pawn_WorkSettings.SetPriority` 对 disabled 类型写非 0 会 `Log.Error`；且"关掉玩家的工作"**不可逆且越权**（玩家无法从 PC 侧区分"PC 关的"与"自己关的"）。用户亦明确选择降档而非取消勾选。否决。
  3. **Harmony 补丁 `Pawn_WorkSettings.GetPriority` / `CacheWorkGiversInOrder`** —— 引入 Harmony（风险升级）、改原版核心取数语义；用户硬约束禁止引入 Harmony。否决。
  4. **per-bill 工作类型（`Bill_Production` 挂 workType）** —— **技术上不存在**（Cecil 核实 1.6 无该字段）。否决（记录在此以免后来者重试）。
  5. **给车间专属工作新建一套 `WorkTypeDef` + `WorkGiverDef`** —— 需重写原版 bill 扫描逻辑才能让工单走自定义类型，工程量与回归面远超收益。否决。
  6. **自动改写全局 `PlaySettings.useWorkPriorities`** —— 影响面为全存档全部玩家 pawn、随存档持久化、被本 Mod 反复重放（玩家无法持久否决）⇒ 命中 E3「不可回滚 + 全局性改写」。**沿用 EXC-2026-013 的拒绝结论**，改为面板状态行 + 玩家点击的"开启手动优先级"按钮。否决。
  7. **⚠ 不设兜底（用户裁决的后果登记）** —— 用户明确「**不设兜底**。全凭玩家决定，出 deadlock 玩家自负」。具体后果**如实登记**：
     - 若某殖民者被排到一个**车间里没有任何保留工作**的车间（未指定车间类型、或车间类型未声明任何 `processKeys` / `deviceWorkTypeDefNames` / 岗位映射），则其所有已勾选工作会被压到 4 档且**没有任何工作被提到 1 档** ⇒ 该 pawn 在该车间**无事可做**（表现为"在车间里闲着"）。
     - 该状态下**唯一**出口是：① 面板「一键全解除」；② 玩家在原版「工作」面板手动改档；③ 给车间指定类型 / 排一个有保留工作的班次。**PC 不做任何自动兜底、不自动解除、不打警告弹窗**（只在 L4 状态行如实显示"已对齐 0 人 / 保留工作 0 项"，由玩家自行判断）。
     - 依据：兜底逻辑会引入"PC 猜测玩家意图"，与本 Mod「玩家不设兜底」的产品语义直接冲突，且属 E3 级全局行为。
  8. **把值勤类型 `PC_WorkshopOperation` 也降到 4** —— 会让值勤排到所有原版工作之后，等于架空车间值勤 Job 链（`WorkGiver_Workshop` 仍会下发 Job，但排序上完全靠后）。**明确排除**：值勤类型保持默认档 3（`DutyWorkPriority`），既不参与最高档提升（EXC-013），也不被降到 4（本记录）。否决。

- **Risk:**
  - **覆盖玩家档位意图**（最高）：A2 会把玩家手排的 1/2/3 压成 4。缓解：范围严格限定在"车间相关"的补集 + 台账精确还原 + L4 状态行常驻披露 + 玩家随时可手动改回。
  - **台账被玩家手动改动"绕过"**：若玩家在 PC 降档后手动改了某项，还原会跳过它（F5）⇒ 那一项永远停留在玩家设的值（**符合预期**，不是 bug）。此时台账记录被丢弃，PC 不再声称拥有它。
  - **ID 复用**：新 pawn 可能复用已死 pawn 的 `thingIDNumber` ⇒ 闸门①（pawn 必须仍有效且为玩家 faction）+ `PruneDeadPawns` 双重挡住。
  - **多车间 / 多人竞争同一 pawn**：同一 pawn 被多车间排班时，降档与提档可能来自不同 zone 的并集。缓解：各车间各自计算保留集并写入，最终态取决于最后一次同步；**此为已知且可接受的语义**（EXC-013 已记载同类"多车间重复触发"，靠幂等吸收）。
  - **台账无界增长**：缓解：`MaxPawnRecords=256` / `MaxEntriesPerPawn=64` 双上限 + 死亡剪枝 + 条目清空即删记录。
  - **存档被非法 XML 字符污染导致保存失败**（ItemFlowLedger 曾发生 P0）：缓解：保存前 `Sanitize()` 就地清洗（`\x01` → `_`），并有单测守护。

  - **写入单点（MATRIX-003）**：全部 `SetPriority` 调用集中在 `MapComponent_WorkshopManager.WorkDemote.cs`；UI 只发命令（`RestoreAllDemotedWork`）与只读状态（`LastWorkStationStatus`）。
  - **守卫链（与既有 `EnableWorkTypes` 同规）**：`workSettings != null` → `EnableAndInitializeIfNotAlreadyInitialized()` → 跳过 `pawn.WorkTypeIsDisabled(type)` → 降档额外跳过 `GetPriority ≤ 0`。

  - **幂等**：已是目标档即跳过；台账 `Record` 首记优先、重复调用返回 false。
  - **事件驱动**：只在 `WorkshopManageView.OnRosterChanged`（排班/班次/班组/成员变更）与 `Refresh`（打开面板对账）触发，**沿用 EXC-012/013 的既有触发面，不新增 tick 钩子**。设备进出车间经 L1 设备通道在同一触发面被覆盖（工单/设备变更由面板刷新与排班事件对账）。
  - **档位常量**：`1` = `TopWorkPriority`、`4` = `Pawn_WorkSettings.LowestPriority`、值勤 `3` = `DutyWorkPriority`，**C# 侧零裸数字**（GOV-006）。
  - **简单模式降级**：`!Find.PlaySettings.useWorkPriorities` 时**降档通道整条跳过**（引擎不读档位，写了只是无意义扰动且白白置脏 `workGiversDirty`），保留集仍走 Enable；L4 状态行以警示色调显示"需开启手动优先级"。
