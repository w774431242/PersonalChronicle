# EXC-2026-025 · 车间在编员工忽略「无法从事」的 Harmony 例外

**类型**：Harmony 例外（Architecture Review 触发项）
**Change ID**：CHG-20261004-EMPLOYEE-ACCESS
**日期**：2026-10-04
**宿主**：RimWorld 1.6.4871（rev590）
**Patch**：`Capture/Patch_Pawn_GetDisabledWorkTypes.cs`（**Postfix on `Verse.Pawn.GetDisabledWorkTypes`**）
> 拦截点历经两次修正：`WorkTypeIsDisabled`（Prefix）→ **`GetDisabledWorkTypes`（Postfix）**，原因见 §3b / §3c。

---

## 1. 玩家诉求（原始口径）

> 「成为员工后，我需要忽略【无法从事】」

实机现象：角色卡显示"无法从事：艺术工作、烹饪工作"（背景故事 `DisallowedWorkTags`），
而玩家恰恰把该殖民者排进「操作员工」岗（映射 Crafting / Smithing / Cooking / Tailoring / Art）
⇒ 原版限制与玩家意图冲突。

## 2. 不加 patch 会怎样（为什么无原版扩展点）

`WorkEnable.EnableWorkTypes` 与 `WorkDemote` 均带 `pawn.WorkTypeIsDisabled(type)` 守卫
（该守卫本身是**必需**的：`Pawn_WorkSettings.SetPriority` 对被禁用类型写非 0 档会
`Log.Error` 并直接 return，见 IL 实证）⇒ 因背景故事被禁用的类型**永远勾不上**
⇒ 岗位映射形同虚设 ⇒ 员工在车间里没活干。

原版没有任何"允许某 pawn 从事其背景故事禁止的工作"的 API / Def 字段；
`Pawn_StoryTracker.DisabledWorkTagsFromBackground` 是只读计算属性，不可写。

## 3. 为什么是 `WorkTypeIsDisabled` 而不是只补 1–2 个调用点

原版实现只有一行（IL 实证，`Verse.Pawn::WorkTypeIsDisabled`）：

```csharp
public bool WorkTypeIsDisabled(WorkTypeDef w) => GetDisabledWorkTypes(false).Contains(w);
```

但它有 **62 个消费点**（Cecil `refs` 全量清单），其中三个必须**同时**放行，
否则会出现"界面允许但实际不干"或反之：

| 消费点 | 不放行的后果 |
|---|---|
| `JobGiver_Work.PawnCanUseWorkGiver` | 档位勾上了但不派 Job |
| `Pawn_WorkSettings.SetPriority` | 写非 0 档时 `Log.Error` 并 return |
| `WidgetsWork.DrawWorkBoxFor` | 工作面板仍画成"无法从事"，玩家以为没生效 |

## 3b. ⚠ 收窄修正（2026-10-04 同日晚，**推翻本记录初版的判定口径**）

初版按 `pawn.GetDisabledWorkTypes(false)` 的**并集**判断"是否被禁用" ⇒ 会放行 **9 类来源全部**。
后经 `Pawn.GetReasonsForDisabledWorkType` 的 IL 取证，原版"无法从事"的来源共有 9 类：

| 来源 | 提示键 | 是否应被车间身份覆盖 |
|---|---|---|
| 背景故事 | `WorkDisabledByBackstory` | ✅ 玩家诉求 |
| 特质 | `WorkDisabledByTrait` | ✅ 玩家诉求（同属"来历"） |
| 帝国爵位（conceited） | `WorkDisabledByRoyalTitle` | ❌ 设定 |
| 意识形态角色 | `WorkDisabledRole` | ❌ 设定 |
| 变异体 | （Def label） | ❌ |
| 任务限制 | `WorkDisabledByQuest` | ❌ 剧情强制 |
| 奴隶身份 | `WorkDisabledSlave` | ❌ 原版设定 |
| 健康 | `WorkDisabledHealth` | ❌ 伤员 |
| 年龄 | `WorkDisabledAge` | ❌ **儿童绝不该放行** |

⇒ 初版会把**儿童、伤员、奴隶、任务受限者**都放行，**超出玩家诉求且有害**。

**改为"正向确认"**：新增
`MapComponent_WorkshopManager.DisabledByStoryOrTrait(Pawn, WorkTypeDef)`
（口径与 IL 一致：背景遍历 `story.AllBackstories` 的 `DisabledWorkTypes`；
特质遍历 `story.traits.allTraits`，跳过 `Suppressed`），
Prefix 的短路① 改为 `!DisabledByStoryOrTrait(pawn, w) ⇒ 放行原方法`。

⇒ 其余 **7 类来源天然不会被放行**（正向检查返回 false），无需逐一枚举排除。
附带收益：该检查比原并集判断**更便宜**（不分配 List、不遍历全集），
而本方法处在 `WidgetsWork` 的**每帧绘制路径**上（62 个消费点）。

## 3c. ⚠ 目标下沉修正（2026-10-04 深夜，**再次推翻前一版的拦截点**）

**实机报错（玩家提供）**：

```
Attempted to calculate value for disabled stat FoodPoisonChance; this is meant as a consistency check,
either set the stat to neverDisabled or ensure this pawn cannot accidentally use this stat (thing=白班)
  at RimWorld.StatWorker.GetValueUnfinalized
  at RimWorld.CompFoodPoisonable.Notify_RecipeProduced (Verse.Pawn)
  at Verse.GenRecipe.MakeRecipeProducts
```

**因果链（IL 实证）**：

1. `SkillRecord.CalculateTotallyDisabled` / `CalculatePermanentlyDisabled` **直接调
   `Pawn.GetDisabledWorkTypes`**（Cecil `refs` 命中）——**绕过 `WorkTypeIsDisabled`**。
   ⇒ 只 patch `WorkTypeIsDisabled`（前一版做法）时：工人**被允许烹饪**，
   但其 `Cooking` 技能仍被判 `TotallyDisabled`。
2. `StatWorker.IsDisabledFor(Thing)`（IL 全文）：

   ```csharp
   if (stat.neverDisabled) return false;
   if (GenList.NullOrEmpty(stat.skillNeedFactors) && GenList.NullOrEmpty(stat.skillNeedOffsets)
       && stat.disableIfSkillDisabled == null) return false;
   if (!(thing is Pawn pawn) || pawn.story == null) return false;
   foreach (SkillNeed sn in stat.skillNeedFactors)
       if (sn.required && pawn.skills.GetSkill(sn.skill).TotallyDisabled) return true;   // ← 命中
   foreach (SkillNeed sn in stat.skillNeedOffsets) { …同上… }
   if (stat.disableIfSkillDisabled != null
       && pawn.skills.GetSkill(stat.disableIfSkillDisabled).TotallyDisabled) return true;
   return false;
   ```

   `FoodPoisonChance`（`Data/Core/Defs/Stats/Stats_Pawns_WorkRecipes.xml`）带
   `skillNeedFactors(Cooking)` ⇒ 对该 pawn 返回 **true**。
3. 他做完饭 ⇒ `CompFoodPoisonable.Notify_RecipeProduced` 求该 stat
   ⇒ `StatWorker.GetValueUnfinalized` 打一致性检查红字（`Log.ErrorOnce`）。

**修正**：拦截点从 `WorkTypeIsDisabled` **下沉到唯一上游 `Pawn.GetDisabledWorkTypes`**：

* 新 patch：`Capture/Patch_Pawn_GetDisabledWorkTypes.cs`（**Postfix**，改 `__result`）。
* 旧 patch `Patch_Pawn_WorkTypeIsDisabled.cs` **删除**（`WorkTypeIsDisabled` 只是上游的一个消费点，
  下沉后它自动生效 ⇒ 单一入口，不重复实现）。
* 第二参数用 `__0`（按位置）而非参数名 —— 原版参数名未取证，Harmony 按名注入、名字不符会静默失败。

**为什么 Postfix 比 Prefix 更优**：原版对该结果有缓存（`Pawn.cachedDisabledWorkTypes`，
由 `Notify_DisabledWorkTypesChanged` 失效重建）⇒ Postfix **只在缓存重建时运行**，
而不是每次调用（该判定有 62 个间接消费点，含 `WidgetsWork` 每帧绘制）。

**边界不变**：仍需同时满足「背景/特质禁用」（`DisabledByStoryOrTrait` 正向确认）
与「车间授权」（`EmployeeAccessAllows`）⇒ 年龄/健康/奴隶/变异/任务/爵位/意识形态角色
造成的禁用**天然不会被移除**。

## 4. 边界（影响面控制 —— 本记录的核心）

Prefix 有**两道短路**：

1. **先问原版**：`pawn.GetDisabledWorkTypes(false)` 里**没有**该类型 ⇒ 直接放行原方法。
   （绝大多数调用走这条 ⇒ 零额外开销。）
2. **确实被禁用时**才问 `MapComponent_WorkshopManager.EmployeeAccessAllows(pawn, w)`，
   其条件为三者**同时**成立：
   * 该 pawn 是某车间的**在编成员**（人员页名单 `zone.Members`）；
   * 该车间**已指定类型**（`zone.WorkshopType != null`；未指定 ⇒ 无映射 ⇒ 不构成授权）；
   * 该工作类型确实是该车间类型的**映射类型**（Production / Maintenance / QualityCheck /
     Standby 四类映射的并集）。

⇒ 其余 59 个消费点（抽血 / 仪式 / 商队医生 / 清洁房间 / 灭火 / 捕猎 / 灵感 等）
在语义上不受影响：这些类型要么不在任何车间类型的映射表里
（搬运 / 清洁 / 医疗 / 灭火本就是 `WorkshopTakeover.MandatoryKeep` 硬红线），
要么其使用者不在车间在编名单内。

## 5. 可逆性与降级

* **可逆**：无额外开关。判定每次现算、不缓存 ⇒ 把人移出车间人员名单，限制**立即**回原样。
* **降级**：任一前提不成立（无 Map / 无 Manager / 无车间 / 无类型 / 非在编）⇒ 返回原版结果。
* **fail-open**：`Prefix` 只在"确实被禁用 + 拿到车间授权"时才改写 `__result`；
  其余一律 `return true` 交还原方法。

## 6. 已知代价（如实声明）

* 该 pawn 在**其他原版系统**中也会被视作"能做该工作类型"。例如 bill 的
  「可执行该工作的殖民者」下拉里会包含他 —— 这与玩家意图一致（人已经是该岗员工），
  但确实放宽了原版对背景故事的约束。
* 若某车间类型的映射表被后续改成包含 `MandatoryKeep` 中的类型（当前 Def 未含），
  则该红线会被本 patch 绕过。**约束**：`Defs/WorkshopTypes.xml` 的映射表**不得**加入
  Hauling / Cleaning / Doctor / Firefighter（与 EXC-2026-016 同一条红线）。

## 7. 有效期

至 `Verse.Pawn.WorkTypeIsDisabled` 语义变更、或车间体系实现独立生产 Job
（届时可改为"仅对车间自己的 Job 放行"，进一步收窄）为止。启动探测已登记于
`CapturePatchDiagnostics`（目标消失会打 `capture target missing`）。
