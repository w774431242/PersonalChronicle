# 变更标注 · CHG-20261003-POSTS（车间岗位体系 Phase 1 + 2）

- **Version:** v1.1.6
- **Phase 1（岗位）:** 按**现实规模化工厂**划分的岗位标准表（9 岗）+ 岗位自动分配器
  （Domain 纯函数）+ **只读**岗位页。**不动任何原版工作状态。**
- **Phase 2（接管）:** 可切换「接管原版工作」—— **默认关闭、玩家逐次主动点击**，
  经**三道闸门 + 强制兜底**后取消勾选车间类原版工作；台账独立于降档台账，可一键解除。
- **例外:** `EXC-2026-016`（新增，E2 高风险）；`EXC-2026-015` 追加再补充说明。

## 关键设计

### 岗位 `deliversOwnService` = 能力对等闸门的唯一判据
9 岗中仅 4 个 `true`（已实现的值勤链），其余 5 个 `false` 且 `notes` 写明"未实现 ⇒ 不得据此禁用原版工作"。
**不得为好看虚填 true** —— 虚填会让接管后殖民地失去该服务且无人替代。

### 三道闸门 + 强制兜底（EXC-2026-016 授权面）
1. **fail-closed**：空 `defName` 直接拒（单测曾抓到 fail-open 漏洞并已修）
2. **硬红线**：`Hauling` / `Cleaning` / `Doctor` / `Firefighter` **永不接管**（闸门①优先于②）
3. **能力对等**：仅 `deliversOwnService = true` 的岗位所承接的工作可接管
4. **强制兜底**：接管后仍须留 ≥1 名自由工人，否则**整次拒绝**（不做部分接管）

### 接管台账必须与降档台账**分账**
降档写 4（还原闸门「当前=4」），接管写 0（会被降档闸门判为玩家改过而**永不还原**）。
独立段 `workshopWorkTakeover`（加性可选，**不需 Migration、不 bump SchemaVersion**），
还原闸门「当前仍为 0 且原值 ∈ 1..4」—— 玩家自己改过的档位一律不动。

### 实机验证反馈的 2 个问题（2026-10-03 14:5x）

**问题一：原版工作面板未隐藏** —— **不是缺陷，是 Phase 1/2 的既定边界**，但与用户预期有落差：
- Phase 1 是**只读**的，本来就不动任何原版工作；
- Phase 2 的接管**默认关闭**（EXC-2026-016 F4：只能由玩家点击触发，禁止自动生效）；
- 即便点了「接管原版工作」，**搬运 / 清洁 / 医疗 / 灭火永不被隐藏**（硬红线，见 `WorkshopTakeover.MandatoryKeep`），
  只有车间声明"可独立交付"的工作（建造 / 采矿 / 种植 / 烹饪 / 锻造 / 艺术 / 研究 / 手工）会被取消勾选。
- 截图佐证：车间列已按设计显示 **3**（值勤），建造/采矿已提升到 **1**（映射工作）⇒ 降档通道正常；
  其余列仍为 4 并保持勾选 ⇒ 接管未触发，符合设计。

**问题二：分配的岗位过多** —— **真实缺陷，已修**。
- 根因：`PostSpec.MaxHolders` 只限制「**每岗几人**」，**没有「每人几岗」上限**
  ⇒ 3 人抢 9 岗时，最会干活的候选人被**所有**岗位同时认领（实机：Sky 独拿 7 岗）。
  原注释写的是"一个工位一个人"，只实现了前半句。
- 修复：新增 `Candidate.AssignedPostCount` + `Assign(..., maxPostsPerCandidate, out result)` 4 参重载，
  **默认 `DefaultMaxPostsPerCandidate = 1`**（一岗一人，兼岗需显式传 > 1）。
  3 人 9 岗 ⇒ 只填满 3 岗，其余显示「暂无合适人选」。
- 测试：新增 2 例 —— `Assign_DefaultIsOnePostPerPerson_NoPersonHoardsEveryPost`（3 人 9 岗同分场景，
  断言每人 ≤1 岗、只填满 3 岗）、`Assign_ExplicitMaxPostsAllowsPartTimePosts`（显式传 2 允许兼岗）。
- 单测 474 → **476 通过 / 0 失败**。

### 第二轮实机反馈的 2 个问题（CHG-20261003-TAKEOVER-R2）

**问题一：原版工作面板仍未隐藏对应 pawn** ⇒ 改为**随排班/名册变更自动接管**。
- 根因：Phase 2 接管**默认关闭**（EXC-2026-016 F4 原文"只能玩家点击触发"），
  与玩家原始诉求「加入车间的 pawn 从原版工作面板中移除」有落差，实机连续两轮被判为缺陷。

  挂在**既有的** `WorkshopManageView.OnRosterChanged`（排班/名册变更 = "加入车间"）⇒ **不新增触发点**。

  **仍禁止** tick / 绘制路径 / 读档副作用触发，自动触发**幂等**（已为 0 的跳过 + 台账首记优先），
  拒绝原因静默（玩家要原因可手动点「接管」）。
- **EXC-2026-016 的 F4 已相应修订**（记录了修订理由与仍然禁止的边界），F1/F2/F3/F5/F6 不变。

**问题二：岗位自动分配应在「人员」tab，岗位 tab 作为岗位表** ⇒ 已按用户定责调整。

### 第三轮实机：接管 100% 未生效（CHG-20261003-TAKEOVER-R3）

**根因（确定性，非推测）**：`TakeOverVanillaWork` 开头的**自由人兜底**要求"接管后至少剩 1 名
非车间工人"。实机为 **3 人全部进车间** ⇒ `FreeWorkersAfter(3,3,1) = 0 < 1` ⇒ **每次整次拒绝**
⇒ 原版工作面板毫无变化。而"全员进车间"恰是本功能的**目标用法**，故该闸门在小殖民地
**必然 100% 误触发**。

**关键论证（决定它可以被降级）**：`MandatoryKeep`（搬运/清洁/医疗/灭火）**永不接管**，
所以任何殖民者永远还剩这 4 项工作 ⇒ **死锁在数学上不可能发生**。该闸门是**重复保护**，
用它拦截没有意义，只是把目标用法堵死。

**修复**：降级为**提示**（记录 `LastTakeoverShortfall` + UI 文案 `Takeover_no_free_worker_warn`），
**不阻塞接管**。EXC-2026-016 的 **F3 已相应修订**（记录修订理由），F1/F2/F5/F6 不变。

**测试**：新增 `FreeWorkerFloor_IsDiagnosticOnly_HardRedLinesMakeDeadlockImpossible` ——
断言「3 人全进车间时自由人确实为 0（读数本身没错）」**且**「硬红线覆盖这 4 项 ⇒ 该读数不构成死锁」。
单测 476 → **477 通过 / 0 失败**。
