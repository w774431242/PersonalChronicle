## 触发（玩家实机反馈，三条）

1. **无辜暴红字**：`Exception in Verse.AI.ThinkNode_PrioritySorter GetPriority: NotImplementedException`
   （Player.log 堆栈：`at RimWorld.JobGiver_GetRest.GetPriority [0x00147]`）。
2. **殖民者被自动编入其他班组**（待进一步取证，本轮未改动编组逻辑）。
3. **岗位不落地 / 殖民者闲逛 / 冗余员工发呆**，并要求「员工多于设备时用【娱乐】兜底并标注"摸鱼中…"」。

---

## 根因（全部 IL / 日志 / XML 实证）

### A. 红字：两个原版方法都硬编码时段，其余抛异常

- `RimWorld.JobGiver_Work.GetPriority`：Anything 5.5 / Work 9 / Sleep 3 / Joy 2 / Meditate 2，
  其余 `throw new NotImplementedException()`（IL_007C）。
- `RimWorld.JobGiver_GetRest.GetPriority`：Anything·Joy·Meditate 在 `rest < 0.3` 时 8、
  Work 0、Sleep 恒 8，其余 `throw`（IL_0147）。**实机红字出自这里。**
- ⇒ PC 的 `PC_Meal` 时段被涂到某小时后，这两个方法都会抛；
  `ThinkNode_PrioritySorter` 内部 try/catch 吞掉异常**并按优先级 0 处理**（只留一行红字）。

### B. 发呆：`Work` 时段 `allowJoy=false`，不是 Job 逻辑问题

- 原版 `Data/Core/Defs/Misc/TimeAssignmentDefs/TimeAssignments.xml`：
  `<defName>Work</defName><allowRest>false</allowRest><allowJoy>false</allowJoy>`。
- PC 写作息表时用的正是 Work（`WorkshopDutyCoordinator.ApplyWorkHoursToCrew`：
  `work[h] ? Work : Sleep`）⇒ 班次内**既不能娱乐也不能睡**。
- 叠加：值勤 Job 本身只是"走到车间格位站着"（`TryGetDutyJob` → `GetDutySpot` → `MakeJob`），
  且车间**只实现了值勤 Job、没有任何生产 Job**（`WorkshopPostDef.implementedWorkTypeDefNames`
  注释与岗位页「尚未实现」均为此设计状态）⇒ 站岗即当前全部能力。

### C. 岗位不落地：自动判定"开窗只试一次"

- `WorkshopManageView.Refresh` 原用会话级布尔 `autoTypeTried`：`
  if (!autoTypeTried && zone.WorkshopType == null) { autoTypeTried = true; … }`
  ⇒ 玩家在**设备为 0** 时开过一次面板，此后即便放满设备也不再判定
  ⇒ 岗位页永远「尚未实现」（与玩家现象一致：设备 3 台、岗位全未实现）。

## 实现

### 1. 红字：`Prefix` → `Finalizer`（关键修正）

原 patch 用 `Prefix` 直接给结果并 `return false`，**会绕过原方法的前置闸门**：

```
JobGiver_Work：if (workSettings == null || !EverWork) return 0f;
JobGiver_GetRest：rest==null / CurCategory<minCategory / CurLevelPercentage>maxLevelPercentage
                  / TicksGame<canSleepTick / Lord 不允许 / !CanFallAsleep  → 各 return 0f
```

⇒ 改为 `Finalizer`：原方法**完整跑完所有闸门**，只在它抛 `NotImplementedException` 的瞬间
接管并吞掉异常。兜底取值：

| 目标 | 取值 |
|---|---|
| `JobGiver_Work` | 「用餐」= 9（同 Work）；其他未知时段 = 5.5（同 Anything） |
| `JobGiver_GetRest` | 一律 `rest.CurLevel < 0.3f ? 8f : 0f`（逐字对齐原版 Anything 分支） |

### 2. 摸鱼兜底（新时段 `PC_Idle`）

- `Defs/Automation_TimeAssignment.xml`：新增 `PC_Idle`，`allowRest=true` / `allowJoy=true`，
  色 `(110,140,140)`。**允许休息是有意的**：`allowRest=false` 会让被判定冗余的人在极度疲劳时
  仍不能睡 ⇒ 精神崩溃不可逆，代价大于"上班睡了一觉"。
- `WorkshopDutyCoordinator.ApplyWorkHoursToCrew(zone, crew, work)`：按**设备容量**
  （`WorkshopStats.ScanDevices(zone).Count`，与概览页「设备 N」同源）切分 ——
  前 N 人写 `Work`，其余写 `PC_Idle` ⇒ 原版 `JobGiver_GetJoy` 自然接管，**零新增 Job**。
- `MapComponent_WorkshopManager.TryGetDutyJob`：摸鱼时段不下发值勤 Job（否则被立刻叫回车间站着）。
- `WorkshopManageView.ActivityText`：人员页「当前活动」列优先显示「摸鱼中…」，
  避免显示成 `--` 或原版娱乐报告而看不出是车间判定。
- 触发：`OnRosterChanged`（排班变更）+ 每日重放 + **设备数变化**（新增
  `SyncIdleSplitIfDeviceCountChanged`，复用 Refresh 期已扫的设备快照，不额外扫描）。

### 3. 自动类型判定：一次性 → 设备数变化可重试

- 新增 `lastAutoTypeCapacity`（设备数快照）+ `autoTypeSuppressedByPlayer`（显式表达"玩家清除过"）。
- `SetWorkshopType(null)`（= 玩家点「清除类型」）置抑制标志，保留原语义但不再靠副作用。

## 未做（如实声明）

1. **班组自动编入**：本轮只查到两个写入点 —— `EnsureCrewsForCycle`（仅"无班组"时、
   由玩家点「预设班次」触发）与 `DistributeUnassigned`（仅由「一键平均编入」按钮触发），
   二者都需要玩家操作，**未能复现"自动加入其他班组"**。需要更具体的复现步骤
   （哪个班组、什么时候、是否点过预设班次）才能定位。
2. **生产 Job**：车间仍然只有值勤 Job，`PC_Workshop*` 的 `implementedWorkTypeDefNames` 全空。
   「岗位彻底落地」= 逐个实现岗位对应的生产 Job，属独立大需求。
3. **员工数 > 设备数**的判定取"名单顺序前 N 人"，故冗余归属随名单顺序变化；
   无设备（capacity = 0）时全班组摸鱼（与"没工位"语义一致）。

## 验收步骤

1. **重启 RimWorld**（程序集不热重载）。
2. `Player.log` 搜 `NotImplementedException` ⇒ 应消失（原来每帧刷）。
3. 车间管理 → 面板右上应能看到类型；岗位页若仍「尚未实现」，去**「设置」页选车间类型**
   （设备风格判不出时必须手动选）。
4. 放 3 台设备 + 5 名员工 ⇒ 打开/刷新面板 ⇒ 前 3 人写 Work（去站岗），
   后 2 人作息表该班次应变成淡青色「摸鱼」块，人员页「当前活动」列显示「摸鱼中…（本班次无工位，已安排娱乐）」，
   且他们去做娱乐（下棋/聊天等）而不是站着。
5. 【管制】表里能直接看到「摸鱼」对应的淡青色格子。

## 审计修复（2026-10-04 · pc-orchestrator 只读审计后）

### ⚠ 披露口径更正（原披露与实现不符，DELTA 缺口）

本标注原先声明作息表重涂的触发条件是「**设备数变化**」。经审计（`Dialog_WorkshopManage.cs:43-44`：
每次开窗都 `new WorkshopManageView(...)` + `Refresh()`）确认：当时把快照存在 **View 实例字段**
（`lastIdleCapacity = -1`）⇒ **每次打开管理面板都会判定"设备数变化"并重涂全部在编班组的作息表**，
静默覆盖玩家手排。原披露漏掉了"每次开窗"这一实际触发面。

**修后口径（如实）**：快照移到 `MapComponent_WorkshopManager`（每图一个、跨开窗存活、按 `zone.ID` 记账）
⇒ 触发条件 = **同一次游戏会话内设备数首次/再次变化**（读档或重进游戏后首次开窗对账一次，与既有
「开窗即对账」口径一致）。
