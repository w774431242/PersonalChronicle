# 审计报告 · 设备页「列宽没变化」

> 玩家 2026-10-05：「**列宽没变化，针对这个问题发起审计**」（附设备页实机截图）

## 一、审计结论（先说结果）

**列宽改动在代码层确实生效了 —— 有 4 条独立证据；"看不出变化"来自两处真实原因，其中一处是硬缺陷，已修。**

| # | 命题 | 证据 | 判定 |
|---|---|---|---|
| 1 | 份额改动进了代码 | `DeviceColSharesFull` 8 项 = 0.23/0.10/0.075/0.21/0.11/0.105/0.11/0.06，与 COLTUNE3 标注逐项一致（Σ=1） | ✅ 生效 |
| 2 | 算法确实按份额切 | RUIF 源码 `TableAtoms.cs:106` `ColumnSplit`：前 n−1 列 = `shares[i] × 表宽` | ✅ 生效 |
| 3 | 已是新列结构 | 截图列头 8 项 = `DeviceHeaders(false)` 逐项一致（旧版本为 10/11 列）⇒ **游戏加载的就是最新 DLL** | ✅ 已加载 |
| 4 | 部署链新鲜 | 源码 03:47:23 → DLL 03:47:29；仅一份 Mod 副本；语言文件同步（截图文案「产出（每日/每周）」与仓库一致） | ✅ 无断点 |

⇒ **"没变化"不是"改动没生效"，而是下面两条：**

### 原因 A（硬缺陷 · 已修）：末列被 gap 吞掉，且**末列份额根本不被读取**

核实 RUIF `ColumnSplit` 的语义（`11\RUIF\Source\Components\TableAtoms.cs`）：

```csharp
for (int i = 0; i < n - 1; i++) {
    widths[i] = shares[i] * row.width;   // 前 n−1 列 = 份额 × 表宽（gap 不影响它们）
    used += widths[i] + gap;
}
widths[n - 1] = row.width - used;        // 末列 = 余宽（被扣掉 (n−1) 个 gap）
```

⇒ 两项后果（此前无人登记）：

1. **末列「建立时间」实际宽 = `0.06W − 28`**：960px 表宽下只有 **约 28px**，而份额本意是 58px
   ⇒ 该列被压到几乎不可读（"第 9 天"约需 56px）；
2. **`DeviceColSharesFull[7]` 是"名义值"** —— `ColumnSplit` 不读它
   ⇒ **任何一次"只动末列份额"的列宽调整，画面上永远零变化**（这正是"改了列宽却看不出"的一个真实来源）。

### 原因 B（幅度）：数值列只加宽 5~10px，增量都给了名称/制作

960px 表宽下的逐列宽度（COLTUNE 10 列 → 当前 8 列）：

| 列 | 旧（10 列） | 新（8 列） | 变化 |
|---|---|---|---|
| 名称 | 182 | 221 | **+39** |
| 操作员 | 77 | 96 | +19 |
| 状态 | 67 | 72 | +5 |
| 当前制作 | 163 | 202 | **+39** |
| 产出 | 96 | 106 | +10 |
| 累计运行 | 86 | 101 | +15 |
| 累计产值 | 96 | 106 | +10 |
| 建立时间 | 41（0.08W−36） | **28**（0.06W−28） | **−13** ⚠ |

⇒ **用户最可能盯着的数值列（产出/运行/产值）只动了 10~15px**（约 1 个汉字），而**末列反而更窄了 13px** ⇒ 观感上"列宽没变化"**完全合理**。

## 二、修复（本批已落地）

| # | 改动 | 效果 | 风险 |
|---|---|---|---|
| 1 | `DeviceColGap` **4 → 2** | 末列 `0.06W−28` → `0.06W−14`（960px 下 **28 → 44px**，约 1.5 倍）；**前 7 列宽度一字不变**（gap 与它们无关） | 零（列间距 2px 在 20 号字下仍清晰） |
| 2 | `DeviceCompactWidth` 注释修正 | 原文"全档 11 列 ⇒ 11×88=968"是 COLTUNE 之前的旧参数（现为 8×100=800）⇒ 改为只描述表达式，避免后人按 968 误判分档点 | 零（纯注释） |
| 3 | `DeviceColSharesFull` 末列注释 | 标明"末列份额是名义值、`ColumnSplit` 不读"⇒ 杜绝再次"改末列无效果" | 零（纯注释） |

## 三、顺带发现（已登记，**非**本次原因）

### D4：RUIF 存在两个不同版本，且游戏用的是较旧的那份

| 位置 | 时间戳 | MD5 |
|---|---|---|
| `Mods\RUIF\Assemblies\RUIF.dll`（**游戏加载 + PC 编译引用**） | 2026-09-20 23:32 | `AE7AD925…` |
| `RimWorld\11\RUIF\Assemblies\RUIF.dll`（RUIF 源码仓构建） | 2026-10-05 01:21 | `F2F7F464…` |

⇒ **两份内容不同**（哈希不一致）。**本次不是列宽问题的原因**：`TableAtoms.cs`（含 `ColumnSplit`）最后修改于 **09-16**，早于两份构建 ⇒ 两版里列宽算法相同。
⇒ **但这是隐患**：RUIF 侧任何"改了却没同步到 `Mods\RUIF`"的改动，PC 侧都会**永远看不到效果**，且编译引用与运行加载都指向那份旧 DLL —— 表现为"改了代码没反应"的经典陷阱。
