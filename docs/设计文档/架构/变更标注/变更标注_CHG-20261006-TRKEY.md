# 变更标注 · CHG-20261006-TRKEY

## 背景

玩家报「启用本 mod + RUIF 后其他 mod 翻译缺失」（截图：Vehicle Framework 设计器 `Road area` + 一个重音乱码串）。
GATE-LOC / GATE-COMP 双向取证结论：**本 mod 与 RUIF 不可能造成该现象**——两侧对翻译系统只读，
键/defName 空间与原版中英（各 4871）、`Vanilla-Expanded-ZH`（43856）、`!Translation_AI_Pack`（5411）、`PerspectiveShift_zh`（228）
**交集全为 0**；该 mod 显示英文的原因是 **VF 本体只带 `Languages/English/Keyed/*.xml`（无中文），全靠第三方汉化包**。
乱码串**产点未取证**（已排除 5 项：磁盘资产 / 本 mod+RUIF / 原版 `PseudoTranslated`（字符集判据，受截图转写精度限制，属存疑）/ 第三方 AI 引擎自带映射表 / 第三方 `LanguageWorker` 路径不可达）；
唯一保留能力面＝第三方运行时渲染期替换引擎 `Auto.AITranslation.Core`；下一步＝运行时对比实验（关 `EnableUIInterceptor` 或禁用该引擎后复现）。
该路径只在「回退 `defaultLanguage` 之后」执行 ⇒ **键的写入/覆盖永远不可能产出重音文本**，截图形态本身即可否证「被我们的键覆盖」类归因。
本变更为审计中发现的**本工程侧**问题的最小修复（不含任何行为逻辑改动）。

## 二、语言元数据死资产删除（定性经 GATE-LOC/COMP 复核修正）

删除 `Languages/ChineseSimplified/LanguageInfo.xml` 与 `Languages/English/LanguageInfo.xml`。

机制（盘上 `Assembly-CSharp.dll` IL + 反编译双证）：`LoadedLanguage.LoadMetadata()` 是**三层循环（RunningMods → foldersToLoadDescendingOrder → `Languages/*`）首命中即 leave 整个方法**，
只有它读 `LanguageInfo.xml`（全程序集唯一读取点）。Core 的中文 `.tar` 虚拟目录名恰等于 `folderName`（`ChineseSimplified (简体中文)`）、英文目录也在 Core，且 Core 恒在 `RunningMods` 首位
⇒ 本 mod 两份**永不生效**：影响他人 0、影响自己 0。**因此定性不是「越权声明」，而是「可清理的死资产」**（原口径经 GATE-LOC 复核降级）。
唯一条件性风险：`ModsConfig.ReorderConflict` 不拦「普通 mod 被手动排到 Core 之前」；若真发生，英文元数据将改由本 mod 提供 ⇒ `languageWorkerClass` 从 `LanguageWorker_English` 退化为缺省、`canBeTiny` 由 true 变 false。
删除即消除该条件性风险，且与 GATE-LOC 的建议①一致（Core 已是这两门语言的权威提供者，mod 无需声明）。
⚠️ 勿混：`LoadMetadata` 只管**元数据**；译文收集走 `LoadedLanguage.AllDirectories`（遍历全部 mod 的 `Languages/<folderName|legacyFolderName>`），是另一条路径 —— 删该文件**不影响任何译文加载**。

## 三、孤立 DefInjected 清理（LOC / 孤儿键纪律）

两侧「互相一致」⇒ 误判通过（教训：**校验必须以独立真值为基准，而不是双侧互比**）。
