## ECON-R01｜P1 工资证据没有绑定真实岗位 — **CodeVerified**

**复现（修复前）**：`ReportCraftIteration` 只取 `ActiveContractFor(PawnKey)`；有合同即生成应付 ⇒ 在 **B 工坊或普通工作台**完成任意账单，同样领取 A 合同的计件工资（单件上限只限制金额，不证明履约）。

**修改边界**：
- `EconomyEmployment.ReportCraftIteration`：发出证据前增加履约身份核对；
- 新增 `FulfilsContractedPosition`：合同 `PositionKey` 必须可解析 + 账单设备 `bill.billStack.billGiver` 必须**正落在合同绑定的车间**（`WorkshopZoneUtility.WorkshopAt(giver.Position, map)` 的 `Zone.ID == zoneId`）且该车间存活。
- **证据去重键保持不变**（`bill.GetUniqueLoadID() + "#" + PawnKey`）—— 它是持久化契约，改格式会让旧档已结算的完成事件被重新计薪。
- 不合格的完成**不发工资、也不记失败**（与本合同无关 ≠ 一次中断，不得污染 M9 退避/学习账）。

**针对性验证**：编译 0 错 0 警；全量 **1192 通过 / 0 失败 / 1 跳过**（`R01-R04-Final.trx`，零回归）。
**剩余限制**：`FulfilsContractedPosition` 需要真实 `Bill`/设备/地图 ⇒ **无离线测试面**；"区域外 / 错误任务 / 停业 / 无岗位授权均不记"须在**游戏内**逐场景验证（**GameVerified 未达**）。任务类型（`PositionKey` 第三段）已解析但当前**未参与**核对（缺设备↔任务类型的权威映射）—— 如实登记为待补。

## ECON-R02｜P1 实物回滚用原堆栈引用，且撤回不明仍取消款项 — **CodeVerified**

**复现（修复前）**：
1. `stock.Take(item, 1)` 返回的 `taken` **没有带出函数**，回滚却传原始 `item` ⇒ 堆栈 > 1 或背包合堆时 `inventory.Contains(item)` 恒 false；
2. 回滚熔断后**仍执行** `CancelPurchase`（原 `if (!returned)` 在取消之后）⇒ 物品在买方、钱没扣 = **白给**。

**修改边界**：
- `TryHandOver(..., out Thing moved)` 带出**实际被移动的那一件**（含"落不进背包"时也要报出身份）；
- `ReturnToStock(..., Thing moved)` 改按**持有者**判定（`moved.holdingOwner == stock` ⇒ 已回库；不在库存也不在买方背包 ⇒ 持有者不明，拒绝断言）；任何失败路径都保证该件仍有明确持有者（库存或买方背包）。
- 食品链与衣物链**同一纪律**：**先证明已完整撤回，才允许取消扣款**；撤回不明 ⇒ 保留 Prepared 悬挂交 M11 对账，如实上报 `TransactionUnknown`。
- 交割失败分支同样先追回再决定是否取消。

**针对性验证**：编译 0 错 0 警；全量测试零回归（同上）。
**剩余限制**：`TryHandOver`/`ReturnToStock` 为私有静态且需 `Pawn`/`ThingOwner` ⇒ **无离线测试面**；"源堆栈 1/10、目标已有同类堆栈、背包拒收、结算失败、回滚拒收、异常后读档"六种守恒场景须游戏内验证（**GameVerified 未达**）。**持久对账凭证**（把待对账笔落成可查询记录）未做 —— 当前仅保证"不再错误取消扣款 + 记录一次警告"，属 M11 对账批。

## ECON-R03｜P1 医疗交易重放重复消耗授权额度 — **CodeVerified**

**复现（修复前）**：`TrySettleCareAct` 在 `PreparePurchase` 返回 `Replay` 时**无条件**调用 `ChargeAndMarkFacts` ⇒ 同一医疗证据重复回调时钱包只扣一次、**授权额度被重复累加**（`Care.Charge` 每次 `WithCharged` 累加，不按 evidenceId 去重）。

**修改边界**：`Replay` 分支改为按**历史凭证的真实阶段**处置 ——
- `Finalized` ⇒ 钱确实只扣过一次 ⇒ 返回既有结果（`CareCode.Applied`），额度**不再累加**；
- `Prepared` / `Cancelled` / `Entry == null` ⇒ 钱未扣成 ⇒ 返回 `CareCode.SettlementUnavailable`，额度不消费，交重试走完整路径。

**针对性验证**：新增 `Tests/EconomyPurchaseTests.AReplayedChargeExposesItsRealPhaseSoCallersCanAvoidDoubleConsumingACap` —— 断言"进行中重放读作 `Prepared` 且不动钱""仅 `Finalized` 才允许调用方认定额度已消耗""重放后扣款恰好一次"。全量 **1192 通过 / 0 失败**。
**剩余限制**：`CancelPurchase` 在宿主持有者（`PawnSettlementSaveHost`）上 ⇒ 需游戏环境的"已取消"场景未离线覆盖；**"钱已结算而额度记账失败 ⇒ 保留可恢复状态"未实现**（需授权额度的**逐笔持久账**，属 Save 变更）—— 当前取**安全偏向**：宁可少扣、绝不多扣，并把该场景登记为待收口。

## ECON-R04｜P1 执行层绕过规划层的原版保护判决 — **CodeVerified**

**复现（修复前）**：`OnPlanPublished` 在制度允许后**直接**尝试食品/衣物交易并可能立即 `Wear` ⇒ 规划写着"让路原版"，执行层仍在花钱、仍即时改穿戴。

**修改边界**（`EconomyEmployment.OnPlanPublished`，位于 `NewCommitmentsAllowed()` 之后、购买尝试之前）：
- `plan.Decision == NativeYield || WaitingFacts` ⇒ **直接返回**，不产生任何经济副作用；
- 复核 Pawn 当前保护状态：`Downed || Drafted || InMentalState` ⇒ 返回（计划发布到执行之间状态可变）；
- **`NativeNeed` 刻意不挡**：原版需求更急时，买一份食物正是它的解法，挡掉反而违背规划。
- `MaintainContract`（M6 退出复查）与 `LedgerFor(...).BeginDay`（日额推进）仍**先于**闸门执行 —— 清理与日推进不是副作用。

**针对性验证**：编译 0 错 0 警；全量测试零回归（既有计划链测试未受影响）。
**剩余限制**：需真实 Pawn ⇒ 无离线测试面；"征召 / 玩家强制 / 倒地 / 精神状态 / 火灾 / 原版治疗 / 睡眠时段期间不发起交易与穿戴，状态恢复后重新规划"须游戏内验证（**GameVerified 未达**）。"穿戴改走受保护的原版任务请求 + 完成证据"未做（属 R04 的进阶部分）—— 当前只保证**不在保护状态下发起点穿戴**。
