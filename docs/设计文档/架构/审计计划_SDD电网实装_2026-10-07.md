### 2.4 反假通过设计（本工程已付代价的三种机制）

| 假通过机制 | 本工程实例 | 本批的反制 |
|---|---|---|
| **① 双侧同变换**（源与副本一起改错，互相对照仍然"一致"） | 预览 HTML 与实现同用一个错锚点 | 断言必须锚在**第三方权威**上：原版 IL / 原版 Defs XML / 存档文本，而非"我方两份互相自证" |
| **② 断言恒真**（无牙齿证据） | `Assert.Less(60, 100)` 两个常量；`Assert.AreEqual(0f, x)` 在 x 恒 0 时 | 每条断言写成「什么情况下失败」可回答；关键项**内建反向对照**（A8/A9/A11 均为翻转一个开关） |
| **③ 旧 DLL 假绿** | 只跑 `dotnet test` 用旧 DLL 报全绿 | 测试前**必须**先 `compile_with_sdk.ps1`；判据是「输出无 error」（退出码不可信） |

**额外反制（本批新增）**：
- **交付物存在性核实**：`write_to_file` 存在路径解析缺陷（会把 `11\殖` 写成 `11_殖`，且静默"成功"）⇒ 每次写入后**必须 `Test-Path` 验证**；本批已据此发现并回移 15 个文件。
- **Cecil 存在性核实**：编译 0 error **不证明类型存在**（空 `.cs` 合法）⇒ 每个新增类型都要 Cecil 确认入 DLL。

```text
1. PERF/TEST 席：编译 + 全量测试 + Cecil 存在性（**先做**，其它席都依赖"产物真的在"）
```
