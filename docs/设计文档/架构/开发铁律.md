# PersonalChronicle 开发铁律

> 本文件固化本模组开发中反复踩过的坑，作为不可违背的硬约束。
> 任何代码 / XML / 文档 / 发布改动都必须遵守。违反即视为 bug。
> 最后更新：2026-09-03

---

## 一、XML 编码与合法性（最高优先级）

### 铁律 1.1 · 所有 XML 必须 UTF-8 **无 BOM**
- RimWorld / Steam 创意工坊对带 BOM 的 UTF-8 内容会按**本地代码页（GBK/ANSI）** 误读，导致中文全乱码。
- **错误写法**：`Set-Content -Encoding UTF8`、`[System.IO.File]::WriteAllText($f, $txt)`（.NET Framework 默认带 BOM）。
- **正确写法**：
  ```powershell
  $enc = New-Object System.Text.UTF8Encoding($false)   # $false = 无 BOM
  [System.IO.File]::WriteAllText($f, $txt, $enc)
  ```
- 校验：文件前 3 字节应为 `60 63 120`（即 `<?x`）；若为 `239 187 191`（EF BB BF）即 BOM，必须清除。

### 铁律 1.2 · XML 文本中的 `&`、`<`、`>` 必须转义
- `&` → `&amp;`（最常见踩坑点，英文简介里 `A & B` 必须写 `A &amp; B`）。
- `<` → `&lt;`、`>` → `&gt;`（BBcode 标签如 `[img]` 本身是纯文本，但若文本里出现 `<` `>` 也要转义）。
- 未转义的 `&` 会触发 `XmlException: parsing EntityName`，**整个 About.xml 解析失败** → RimWorld 回退默认值、丢失 `packageId`、版本识别混乱。
- 批量修复可用正则（排除已有实体）：
  ```powershell
  $txt = [regex]::Replace($txt, '&(?!(amp|lt|gt|quot|apos|#\d+|#x[0-9a-fA-F]+);)', '&amp;')
  ```

### 铁律 1.3 · 写 XML 后必须校验 well-formedness 再发布
- 任何对 `About.xml` / `Defs/*.xml` / `Languages/**/*.xml` 的改动，发布前用以下命令验证：
  ```powershell
  $x = New-Object System.Xml.XmlDocument
  $x.Load('路径\文件.xml')   # 抛异常即不合法
  ```
- 不能只靠"看起来没问题"。解析失败会在游戏日志里表现为 `XmlException` + `missing packageId`。

### 铁律 1.4 · 怀疑编码损坏时直接整文件重建，不要试图转码
- 若文件出现中文乱码且字节里混有 `EE` 开头（UTF-8 代理区，合法文本绝不该有），说明文件已被 **GBK/UTF-8 混合双重编码损坏，不可逆**。
- **根因常见场景**：原始文件是 GBK，却用 UTF-8 工具/pwsh 写入中文段，新旧字节混排；后续 PowerShell `ReadAllText(UTF8)` + `WriteAllText(UTF8)` 反复读写，进一步破坏。
- **正确做法**：用 write_to_file 整文件重写正确内容（工具以纯 UTF-8 写出），再用 `UTF8Encoding($false)` 去 BOM 同步；不要做 GBK→UTF8 的"修复式转码"（会把已损坏字节固化）。
- 验证：UTF-8 读回第 21 行应为正常中文（如 `前置依赖`），而非 `閸撳秶`/`鍓嶇疆` 等乱码。

## 二、Mod 元数据（About.xml）

### 铁律 2.1 · `modVersion` 禁止用纯 `x.y.z` 数字格式
- 部分加载器 / 启动器会把 `modVersion` 当**兼容的游戏版本**解析。写 `<modVersion>1.2.0</modVersion>` 会被识别为"支持游戏 1.2.0"，在 1.6 下显示不兼容。
- **正确写法**：加 `v` 前缀或日期格式，如 `<modVersion>v1.2.0</modVersion>` 或 `<modVersion>2026.8.24</modVersion>`。
- 兼容性**唯一权威**来源是 `<supportedVersions>`（本模组固定 `<li>1.6</li>`），必须存在且正确。

### 铁律 2.2 · `packageId` 不可缺失
- `About.xml` 必须含 `<packageId>PersonalChronicle.Archive</packageId>`，否则 mod 无法被依赖系统识别。
- 一旦 About.xml 解析失败（违反 1.1/1.2），`packageId` 会丢失，连锁引发各种异常。

## 三、发布同步

### 铁律 3.1 · 开发 / 发布区必须 hash 一致
- 开发区：`...\PersonalChronicle\`（含 `About\`、`Assemblies\`、`Defs\`、`Languages\` 等）。
- 发布区：`E:\SteamLibrary\steamapps\common\RimWorld\Mods\PersonalChronicleVer0.1\`。
- 任何改动同步后，必须校验双方 SHA256 完全一致：
  ```powershell
  (Get-FileHash 开发区\文件 -Algorithm SHA256).Hash
  (Get-FileHash 发布区\文件 -Algorithm SHA256).Hash
  ```
- dll 发布还需同步 `.pdb`（调试符号），否则异常栈不可读。

### 铁律 3.2 · 改代码必须编译 + 同步 dll
- 用 `run_csc.ps1` 或 `compile_with_sdk.ps1` 编译，确认 `EXITCODE=0`（0 错 0 警）。
- 编译产物 `Assemblies\PersonalChronicle.dll` 同步到发布区后 hash 必须一致。
- 版本号（`modVersion`、`ApiVersion.Current`、`README` 徽章）需保持一致，改动时同步更新。

### 铁律 3.3 · 版本号仅经显式声明方可变更
- 版本号以 `ApiVersion.Current` 为权威源；`About.xml` 的 `modVersion`、`README` 徽章须与之保持一致。
- **AI / 自动化不得擅自 bump 版本号**：仅在 PM 主动声明「升级版本」时才允许修改版本号（含为修复漂移而顺手改写）。无显式声明时，即使发现三处不一致，也只允许记录待办、不得改动。
- 新增 changelog 条目的版本号必须与 `ApiVersion.Current` 对齐；本模组当前权威版本为 **v1.2.0**。

## 四、PowerShell 执行环境

### 铁律 4.1 · 含 `$` 变量的命令必须用脚本文件，禁止内联 `-Command`
- 在本环境的命令调用语境中，内联 PowerShell 的 `$var` 会被外层 shell 展开为空，导致脚本静默失效或语法错误。
- **正确做法**：一律先把命令写成 `.ps1` 文件（路径硬编码绝对路径），再用：
  ```powershell
  powershell -NoProfile -ExecutionPolicy Bypass -File "e:\...\脚本.ps1"
  ```
- 路径含空格 / 括号时必须用双引号包裹。

### 铁律 4.2 · 二进制 / dll 验证用字节扫描，不依赖运行时加载
- 在无 RimWorld 运行时下用 `Assembly.LoadFrom` 会报大量"类型找不到"（依赖缺失所致），属正常现象，**不代表代码有错**。
- 验证 dll 内容变更（如确认某字符串已移除）用 `wuxia` 字节扫描或 `Get-FileHash`，而非 LoadFrom。

## 五、文档与玩家向内容

### 铁律 5.1 · 创意工坊简介 = 玩家向、双语、无开发者术语
- 简介只讲"能干啥 / 新功能 / 修复"，不写 API 契约、Provider 注册表、Harmony 补丁细节等。
- 中英双语段都放；中文段保留 `[url][img]` 配图，英文段用 `[img]URL[/img]`。
- 配图走 GitHub raw URL（`raw.githubusercontent.com/...`）。

### 铁律 5.2 · 改动须留痕
- 实机测试问题统一记入 `docs\问题跟踪\实机测试问题记录.md`（含根因、修复、hash、进度表）。
- 当日工作追加到 `.codebuddy\memory\YYYY-MM-DD.md`，跨会话稳定事实写入 `MEMORY.md`。

## 六、模块化与分层（治本，优于事后拆分）

> 拆分是**补救措施**，代价高（改调用点、核对 git、重编译、重同步）。
> 真正的标准是"一个文件只说一件事"——从第一行代码起就分层 + partial + 数据驱动，让拆分变成"从不必要"的事。

### 铁律 6.1 · 依赖单向，禁止回环
```
UI  →  Application  →  Domain  ←  Data / Capture
```
- **Domain**：纯数据 + 纯逻辑，尽量不引用 RimWorld 引擎，可离线单测。
- **Application**：聚合 / 取数服务（`ArchiveService` 已按 Career/Consumption/Qualification/Live 拆 partial）。
- **Capture**：Harmony 补丁只做"钩子 → 调 Application"，**不放业务**。
- **UI**：只消费 Read Model 快照（`IArchiveUiDataProvider`），**不在窗口里排序 / null-guard / 算数**。
- 违反方向（如 UI 直读 `ChronicleGameComponent`、Data 引 Capture）即视为 bug。

### 铁律 6.2 · 文件体量红线
| 信号 | 动作 |
| --- | --- |
| 单文件 > 400~600 行 | 警觉，审视可独立的内聚区块 |
| 单文件 > 800 行 | **必须拆**（本项目 `ArchiveMainTabWindow` / `ChronicleGameComponent` 到该体量才拆，属被迫返工） |
| 单方法 > 60~80 行 | 拆私有 helper，或下沉到 Application/Domain |
| 一个类承担 ≥ 3 种不相干职责（绘制+聚合+持久化） | 按职责分层拆 |

### 铁律 6.3 · 预划分 partial，别等膨胀
- 预期会有多区块的窗口/组件，**一开始就建 `Xxx.Overview.cs` / `Xxx.Qualification.cs`**，每块自管 ~200 行，主文件只留壳。
- god-class 拆分时，**契约锚点必须留主文件**：`ExposeData` / `FinalizeInit` / `MigrateLegacyData` / 字段声明留在主文件；扩展方法必须留 static 类。
- 拆前先备份 `_backup/YYYYMMDD_HHMMSS/`，拆后编译 0 错 0 警再同步发布区。

### 铁律 6.4 · 每加一个子功能就新建文件，而非往现有文件追加
- 文件数多不可怕，**单文件过长才可怕**。
- 工具方法集中到 static 类（如本项目的 `ArchiveMainTabWindow` 扩展方法 static 类），避免散落复制。

### 铁律 6.5 · 规则数据驱动，不写进 .cs
- 能用 `DefDatabase` + XML 表达的规则（如本 mod `ProfessionalSkills.xml` 含 Direction/Skill/Effect/Mapping/XpPolicy/Rating 6 类 Def），**走 XML 而非硬编码逻辑**，避免代码膨胀且支持热改不重编。
- 禁止在 `.cs` 里写技能名/方向名/评级阈值等可变数据（"本 Mod Def 显示名机制"另见 MEMORY.md）。

### 铁律 6.6 · Read Model 快照隔离绘制与逻辑
- UI 拿到的对象应是已排序、已过滤、null-safe 的快照；排序 / null-guard / 评价计算归属 Provider / Application，窗口代码瘦到只剩绘制。

## 七、属性浮层（Tooltip）透明铁律

### 铁律 7.1 · 浮层必须展示完整结构
- 任何属性字段的悬停浮层，必须展示与原版属性面板 stat tooltip 等价的全部结构因子（文化 / 光照 / 年龄 / mod parts 等）。
- **禁止以"贡献为零"为由省略行**；零贡献行应显示为 ×1.00 / 0%，作为结构透明的一部分。
- 浮层顶部必须展示 `StatDef.description`，让玩家知道"这个字段是什么"。

### 铁律 7.2 · 数据来源
- 必须走原版 StatPart 管线（`StatDef.parts` / `statFactors` / `skillNeedFactors` / `capacityFactors`），禁止手写近似公式。
- 对 `ExplanationPart` 返回的文本做本地化清洗，但不得丢失关键结构信息（如光照百分比、技能等级、年龄值）。
- 清洗实现见 `StatBreakdownBuilder.CleanLabel`：保留第一个括号内的参数，剥离尾部的"乘数 / multiplier / factor"等无信息词，失败时回退到 part 类型名。

### 铁律 7.3 · 层级与缩进
- 原版 `ExplanationPart` 中存在缩进关系（如 `"  Isekai Level 4"` 是 `"Isekai INT"` 的子项），浮层必须通过 `BreakdownRow.IndentLevel` 保留层级缩进。
- 层级缩进只改变视觉层级，不改变数值链式计算。

### 铁律 7.4 · 零贡献与视觉降噪
- 零贡献行不显示比例条、不显示增益/减益色（保持 `Muted/Dim`）。
- 比例条与红绿色只用于显著偏离 1.0 的因子；阈值由绘制层统一控制，不在清洗层做截断。

### 铁律 7.5 · 代码落地
- 数据模型：`StatBreakdown.Description` + `BreakdownRow.IndentLevel`。
- 构建器：`StatBreakdownBuilder.Build` 设置描述；`ApplyParts` 不再因 `cur ≈ before` 跳过，而是为所有返回 `ExplanationPart` 的 part 生成行。
- 绘制：`ITab_Pawn_Career.Breakdown.DrawBreakdownTooltip` 在标题与基础值之间绘制描述；`DrawBreakdownPartRow` 按 `IndentLevel` 追加水平缩进。
