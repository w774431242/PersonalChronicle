## 0. 文档目的与定位

本规范书建立在《终局宝典》（以下简称"宝典"）确定的**玩法规则**之上，职责是建立一套**统一的"描述语言 + 接入契约 + 调度总线"**，使任意"系统中心"在注册后，都能被统一调度层以一致方式驱动、编排、观测与扩展。

- 宝典回答"**玩法是什么**"（数值、规则、平衡）。
- 本规范回答"**系统怎么被统一管理**"（接口、生命周期、通信、优先级、治理）。

二者解耦：宝典变更不应要求重写调度层；新增系统中心不应要求改造其他中心。

> 注意：当前《终局宝典 v1.0-fixed.html》链接预签名已失效（COS `SignatureDoesNotMatch`），本文档内容暂以通用框架起草，宝典专属数值/规则将在"附录 B 对齐清单"补齐。

## 1. 设计原则（铁律）

| 编号 | 原则 | 说明 |
|------|------|------|
| P1 | 单一职责 | 每个中心只对自己的领域状态负责，越界职责通过事件委托给其他中心。 |
| P2 | 接口统一 | 所有中心实现同一套 `ISystemCenter` 契约，调度层无需感知中心差异。 |
| P3 | 数据归中心所有 | 中心状态由所属中心独占读写；外部只读经快照，写入经命令/事件。 |
| P4 | 跨中心只经总线 | 中心之间**禁止**直接引用实例或调用方法，一律走事件总线 / 能力注册。 |
| P5 | 调度与玩法解耦 | 调度层只管"何时推进、谁先谁后、失败如何隔离"，不懂具体玩法。 |
| P6 | 可观测 | 每个中心必须暴露结构化快照与指标（KPI），可被面板/日志统一消费。 |
| P7 | 可扩展 | 新中心按模板注册即可接入，无需改动调度层与其他中心。 |
| P8 | 配置驱动 / 零硬编码 | 规则数值、阈值、优先级均来自配置，不写死在调度逻辑中。 |
| P9 | 向后兼容 | 状态 schema、事件、命令的变更遵循"只增不改、弃用期"策略。 |
| P10 | 失败隔离 | 单中心异常不得拖垮全局；支持熔断、降级、回滚快照。 |

## 2. 宏观蓝图：系统中心注册表

所有系统中心登记于**中心注册表（CenterRegistry）**。调度层只认注册表，不认具体实现。

### 2.1 初始中心清单（按领域划分）

| 中心 ID | 中文名 | 领域 | 典型职责（草案） |
|---------|--------|------|------------------|
| `manufacturing_center` | 制造系统中心 | 生产 | 配方、产线、产能、原料消耗与成品入库 |
| `logistics_center` | 内务系统中心 | 运转 | 仓储、搬运、分配、清洁、内部调度 |
| `economy_center` | 经济系统中心 | 经济 | 货币、贸易、定价、收支、市场 |
| `medical_center` | 医疗系统中心 | 健康 | 伤病、治疗、药品、防疫 |
| `policy_center` | 政策系统中心 | 治理 | 律令、分配政策、权限、激励 |
| `population_center` | 人口系统中心（预留） | 人口 | 个体档案、需求、情绪、成长 |
| `diplomacy_center` | 外交系统中心（预留） | 外部 | 派系、声望、条约 |
| `research_center` | 科研系统中心（预留） | 科技 | 项目、进度、解锁 |
| `defense_center` | 防御系统中心（预留） | 安全 | 威胁、布防、征召 |
| `environment_center` | 环境系统中心（预留） | 世界 | 气候、灾害、资源点 |

> 预留中心先占 ID 与档位，待宝典对应章节明确后再填充规范。

### 2.2 中心清单（CenterManifest）

每个中心必须提交一份清单，作为注册凭据：

```
CenterManifest {
  id              : string        // 全局唯一 snake_case，如 manufacturing_center
  name_zh         : string
  name_en         : string
  version         : semver        // 中心自身版本，独立于规范版本
  owner_module    : string        // 实现所属模块/仓库
  priority_tier   : int           // 调度优先级档位（数值小者先，见 §3.4）
  depends_on      : string[]      // 依赖的中心 id（启动拓扑序依据）
  provides        : Capability[]  // 对外提供的能力标识
  consumes        : EventType[]   // 订阅的事件类型
  lifecycle_hooks : HookId[]      // 接入的调度钩子
  config_schema   : URI           // 配置 JSON Schema 位置
}
```

## 3. 统一调度管理层（核心）

统一调度层是**唯一**的中枢，负责：时间推进、事件分发、指令路由、依赖排序、优先级仲裁、失败隔离。它**不**包含任何玩法逻辑。

### 3.1 三层时间模型

| 层级 | 名称 | 说明 | 粒度（由宝典定，此处留接口） |
|------|------|------|------------------------------|
| L1 | Tick | 最小推进单位 | 由宝典给定 |
| L2 | Phase | 一个周期内的阶段（如"生产→结算→治理"） | 由调度层编排 |
| L3 | Round / Cycle | 完整循环 | 由宝典给定 |

调度层暴露 `OnTick / OnPhase / OnRound` 三类钩子，中心按需订阅。

### 3.2 调度总线（ScheduleBus）

```
ScheduleBus
  ├─ Clock        推进时间，触发 tick / phase / round
  ├─ EventBus     中心间事件分发（§4 契约）
  ├─ CommandRouter 外部/中心指令路由到目标中心
  ├─ StateRegistry 全局只读快照 + 受控写入
  └─ Supervisor   依赖解析 / 优先级仲裁 / 熔断隔离
```

### 3.3 事件总线（EventBus）

- 唯一跨中心通信渠道（P4）。
- 事件为不可变结构体：`{ type, source, tick, payload }`。
- 支持同步 / 异步两种投递策略（由事件声明决定）。
- 订阅基于 `consumes` 清单，运行时校验一致性。

### 3.4 优先级仲裁

同 tick 内多中心争用共享资源（如仓储、劳动力）时：

1. 按 `priority_tier` 升序（小优先）；
2. 同档位按动态权重（中心自报的当前紧迫度）降序；
3. 仍冲突则进入仲裁队列，下一 tick 补偿。

> 权重与档位均配置化（P8），调度层不写死。

### 3.5 依赖解析与启动

启动时按 `depends_on` 做拓扑排序；若存在环则拒绝启动并报错。重启支持"快照恢复"（§3.6）。

### 3.6 失败隔离（Supervisor）

| 故障 | 处理 |
|------|------|
| 中心 `OnTick` 抛错 | 捕获、记录、该 tick 跳过该中心，不传播 |
| 连续 N 次失败 | 熔断该中心，进入降级（只读快照可用） |
| 状态写坏 | 回滚至上一轮快照 |
| 依赖中心缺失 | 启动期即拦截，禁止半启动 |

### 3.7 中心接入契约（ISystemCenter）

每个中心必须实现：

```
interface ISystemCenter {
  Manifest        : CenterManifest
  OnInit(ctx)     : void                 // 注册、读配置、建初始状态
  OnTick(tick, ctx): void                // 最小推进
  OnPhase(phase, ctx): void              // 阶段钩子
  HandleCommand(cmd): CommandResult      // 指令处理
  Snapshot(): CenterState               // 只读快照，供观测/存档
}
```

## 4. 单系统中心规范模板（强制章节）

**每个中心的设计文档必须包含以下章节**，便于统一评审与接入。模板如下（以 `{{center}}` 占位）：

```
# {{center}} 系统中心规范

## 4.{{n}}.1 中心标识
- id / 名称 / 版本 / owner / priority_tier

## 4.{{n}}.2 职责边界
- 负责：……
- 不负责（委托给）：……（列出目标中心 + 事件）

## 4.{{n}}.3 数据模型（State Schema）
- 字段表：名称 / 类型 / 归属 / 读写权限
- 配置项：键 / 类型 / 默认值 / 说明（引用 config_schema）

## 4.{{n}}.4 事件契约
- 发出（emit）：事件类型 / 触发时机 / payload 结构
- 订阅（consume）：事件类型 / 来源 / 处理逻辑

## 4.{{n}}.5 命令接口
- 命令类型 / 参数 / 返回 / 是否幂等

## 4.{{n}}.6 调度钩子
- 订阅的 tick/phase / 每轮动作 / 资源争用点

## 4.{{n}}.7 KPI 指标
- 指标名 / 定义 / 计算公式 / 单位 / 目标区间

## 4.{{n}}.8 依赖与耦合
- depends_on / provides / 禁止的直接依赖

## 4.{{n}}.9 异常与降级
- 可能故障 / 降级行为 / 恢复条件

## 4.{{n}}.10 版本演进
- 当前版本 / 已知 TODO / 破坏性变更计划
```

## 5. 公共契约标准

### 5.1 命名规范

| 类别 | 前缀/格式 | 示例 |
|------|-----------|------|
| 中心 ID | snake_case | `manufacturing_center` |
| 事件类型 | `evt.<center>.<name>` | `evt.economy.trade_settled` |
| 命令类型 | `cmd.<center>.<name>` | `cmd.policy.set_law` |
| 指标 | `kpi.<center>.<name>` | `kpi.medical.bed_occupancy` |
| 配置键 | `cfg.<center>.<name>` | `cfg.logistics.max_haul` |
| 能力 | `cap.<center>.<name>` | `cap.economy.pricing` |

### 5.2 全局 ID 方案

- 实体 ID：`{center}:{entity}:{seq}`（如 `medical:patient:1024`）。
- 事件 ID：由 EventBus 自增，无需手动。

### 5.3 枚举 / 常量

集中管理于 `Contracts/Enums`，禁止各中心私自定义重复语义枚举（P8）。

### 5.4 错误码体系

```
ERR.{center}.{code}   // 如 ERR.manufacturing.recipe_missing
```
错误必须结构化：`{ code, message, context, recoverable }`。

### 5.5 日志 / 埋点

- 统一结构化日志：`{ ts, center, level, event, kv }`。
- 关键动作埋点经 EventBus，可被观测中心消费。

### 5.6 配置 Schema

每个中心一份 JSON Schema（`config_schema`），启动时校验；缺失/非法配置拒绝启动。

## 6. 跨中心协作协议

### 6.1 通信三定律

1. **只走总线**：中心 A 想影响中心 B，发事件或命令，绝不直接调用 B 的方法（P4）。
2. **读走快照**：A 需要 B 的状态，订阅 `StateRegistry` 快照，不持有 B 引用。
3. **能力发现**：A 需要某能力，查 `Capability` 注册表，而非假定某中心存在。

### 6.2 协作示例（经济 ↔ 制造）

```
制造中心 产出成品
  → emit evt.manufacturing.product_ready { item, qty }
经济中心 订阅该事件
  → 更新库存估值 / 触发定价
  → 若需补货，emit evt.economy.reorder { item, qty }
内务中心 订阅 reorder
  → 调度搬运 / 入库
```

全程无直接引用，任一方缺失仅影响该链路（P10）。

## 7. 版本与演进治理

| 项 | 规则 |
|----|------|
| 规范版本 | 语义化；本文件变更需评审 |
| 中心版本 | 独立 semver，随 manifest 提交 |
| Schema 变更 | 只增不改；删除字段需 ≥1 个版本弃用期 |
| 事件/命令变更 | 兼容旧消费者；破坏性变更升主版本并公告 |
| 热插拔 | 中心支持在 round 边界启停，状态可快照恢复 |
| 一致性校验 | CI 校验 manifest 与实现接口、config_schema 合法性 |

## 11. 系统中心单页预览文件的建立规程（本目录已验证做法）

> 适用：为任一系统中心建立「`{中心名}预览_RUIF单页统一版.html`」。已按此规程产出三件：
> 人员（4 视图）、制造、经济（5 视图）。规程来自三次实践里踩过的坑，不是理论。

### 11.1 定位
预览是**设计真源**，用于「1:1 落地」到游戏内 RUIF 界面，**不是**可交互产品，也**不是**组件图鉴。

### 11.2 强制前置取证（缺一不得动笔）
| 项 | 来源 | 反例后果 |
|---|---|---|
| 色 / 间距 / 字号 | RUIF `Core/Tokens.cs`（固定只读）+ 消费方 `UITheme.Palette` | 自创色值与实机不符 ⇒ 落地必返工 |
| 组件真实契约 | `RUIF/Source/Components/*.cs` 逐件读签名 / 内部几何 / 返回值 / **自画内容** | 漏画自画内容 = C 类缺口（如 `WealthBreakdown` 自画总额、`Gauge` 自画中心 %） |
| 承载外壳度量 | `MasterControl/MasterControlTabWindow.Detail.cs` 等 | KPI 卡 34/11/10/8 这类参数猜不出来 |
| 文案 Key | `Languages/*/Keyed/*.xml` | 硬编码中文 = P1 |

### 11.3 页面骨架（三件同构）
单页 + 页头主标签（`NavCandAtoms.MainTabStrip` 语义）切 N 个视图 + 底部状态条 + 悬浮提示。
`.panel > .ptitle` 范式，**标题条右端必须标注该面板所用的 RUIF 组件全名**。
末视图统一为「分档与契约」：分档三态 + 状态完备性 + 关键度量表 + **面板→组件映射** + 翻译键清单 + **接入缺口如实登记**。

### 11.4 硬约束
1. **禁止扩展 RUIF、禁止自研组件**（`Source/PersonalChronicle.csproj:34-40`）；缺件以现有件组合覆盖，并在缺口表登记「有意偏离」。
2. **禁假演示**：无数据源的读数一律画「—」+ 原因（LAND-009），版式示意值须单列一行并注明「实机不画」。
3. 图表 `viewBox` **取元素像素尺寸**——`.chart` 是「宽 100% / 高定值」，固定 viewBox 会把刻度文字纵向压扁。
4. 差异逐处归 **A 我做错了 / B 引擎降级 / C 预览缺失**，不得把 A 混进 B。
5. 表格行高 ≥ `Measure.RowHeight(font)`（Tiny 18）；分组行用**普通数据行**实现（`StatTable` 无需扩展）。

### 11.5 交付前自检
结构：`<section>`/`<div>` 配对、脚本 `node --check`、元素 id 齐备；
内容：窄/宽两档各看一遍、组件自画内容全画出、缺口表无「已通过」而实际未做。
